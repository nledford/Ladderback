# The text field

- `FormField` (a `<label>`, a hint and an error wired through `aria-describedby`, `aria-invalid` on error), since replaced by `TextField` (the text field, below), which keeps its wiring and its multi-line field.

- **The text field** is `TextField` (`components/text_field.rs`), for what a reader types, and it replaces `FormField`: every page's field moved onto it. A native `<input>`, or a `<textarea>` for many lines, drawn from the tokens rather than in the browser's own look (decision 113). What each kind asks of the browser, the ids its parts are wired by and what it says of its state are `components/text_field/rules.rs`, decided on the host. Its `id` is a constant, or one built for a field of a list, as each reason field of a proposal's review is; `components/text_field/tests.rs` renders a list's fields and checks each is wired by its own.

  Its `Kind` is one line (`Line`, the default); many lines (`Lines { rows }`, a `<textarea>` where Enter starts a line); a password (`Password`); a number (`Number`); or a code typed or pasted back (`Code`), a snapshot's short ID or a token, never spell-checked or capitalized by a phone's keyboard. Focus brings a many-lines field whole into view (`block: nearest`): Chromium scrolls only far enough to show a textarea's caret, so one starting near the viewport's bottom edge stayed mostly below it, its centre off-screen (2.4.11; the change journey of `features/ui/plans.feature` caught it).

  - *The password's button.* An icon-only `Button` after the field, named **Show password** whatever its state, pressed (`aria-pressed`) while the password shows, its `Icon` an eye then and an eye crossed out while it is hidden. One name with its state in `aria-pressed` is the toggle rule the button already keeps: a name that flipped to "Hide password" would be said as another control after the press. Showing switches the input's `type` and nothing else, so the value, the caret and focus stay as they were and `autocomplete` never changes, which a password manager reads. An unavailable password has no button (`rules::shows_toggle`): under `aria-disabled` it would stay a Tab stop that does nothing beside a field that left the Tab order.
  - *A shown password hidden again.* A shown password is hidden again when the page sets what the field holds rather than the reader typing it (`rules::hides_again`), so the next password typed after a form is cleared once it is sent (the admin password's) stays hidden until asked for. A dialog's field is drawn afresh at each opening, empty and hidden: the restore and download dialogs and the gallery's step-up are keyed on the opening, never on the dialog's `open` turning false, which a dialog closed with Escape and opened again at once may never see, since Chromium can raise its `close` event late, when it is already open again (`ModalDialog`).
  - *A number takes what is typed.* `inputmode="numeric"` asks for the keyboard of digits on a phone; `type="number"` would draw a spin box whose value a turn of the mouse wheel changes. Keys are never filtered: a key that silently did nothing would say nothing of why (3.3.1), so the form refuses a value that isn't a number when it is checked, its error above the field.
  - *Required, in words.* `required` shows "(required)" after the label (`ui-text-field-required`), in a span a screen reader skips, and sets `aria-required="true"`, so a screen reader says it once and the field's name stays its label, which still begins with the words it shows (2.5.3). The space before it is the message's own (`{ " " }(required)`), so a language that writes none there, as Japanese writes `（必須）`, leaves it out. Never the `required` attribute: the forms check their own fields (`novalidate`), and the browser's own check would draw an invalid state of its own.
  - *Which fields are required.* A field is marked when its form is refused without it on every path: a repository's Location and Password, a plan's Name, Repository and Sources (`plans::Field::required`), an API token's Label, the admin password's three fields and sign-in's Password. A repository's Name isn't, since only connecting needs it; nor is the step-up field, the one field of its dialog, whose description already says what to type and which has no optional field to be told apart from.
  - *Read only and unavailable.* `Access::ReadOnly` is `readonly`: still in the Tab order, so its value can be read, selected and copied, its edge dashed. `Access::Disabled` is the native `disabled`, out of the Tab order as HTML makes it: unlike a button, which stays focusable under `aria-disabled` so a reader can find why it does nothing, a field that must still be reached is read only instead. Each says its state in words, a note under its description that describes the field ("Read only: you can select and copy it, but not change it.", "Unavailable: it can't be changed now."), and a disabled field takes the surface with muted text (6.87:1 light, 7.30:1 dark), never graying alone.
  - *The look.* A 1 px edge in `--field-edge` (4.83:1 on the page and 4.39:1 on a surface in light, 4.95:1 and 4.28:1 in dark, past 1.4.11's 3:1), the button's small corner (`--radius-small`), flat, no shadow. Its `size` is a button's height in `em` (Small 1.75em, Medium 2em, the default, Large 2.5em, XLarge 3em) with the same inline padding, from the one set of utilities both take (`Size::control`), so a field and a button of one size stand level in a row of actions. As wide as its line up to 32rem; `token` widens it to 40rem in monospace for an API token's whole text.
  - *Its styling.* Tailwind utilities (decision 117), logical ones only, with no rule of its own in `style.css` (#931): `rules::FIELD`, `ROW` and `ICON` draw the field, its row and its icon, `rules::box_class` its box (its size's control set, its width, a token's monospace), and `rules::input_class` the input: its edge (`border-field-edge`), its height for one line or many, its padding with an icon or without, and its read-only, invalid, disabled and forced-colors looks. A token's font goes on the box, which the input takes through the base rule's `font: inherit`, since that rule, outside Tailwind's layers, outranks any utility on the input. The `text-field` classes stay as names, `text-field-input`, `text-field-icon` and `text-field-with-icon` the scenarios' hooks.
  - *Its edge and icon.* Invalid is a 2 px edge in the Error tone, its padding a pixel less so the text doesn't move. An `icon` (decoration, `aria-hidden`) stands inside the edge at the inline start, on the right in a right-to-left page. Under forced colors it takes `Field` and `FieldText`, a disabled field `GrayText`; invalid keeps its thicker edge and read only its dashes.
  - *For the step-up field and the API token's box.* `StepUpField` is a `TextField`: the admin password is its password kind; with sign-in off the short ID is a `Code` field whose description ends on the ID as data (`description_code`, in a `<code>`), with the **Copy the ID** button between the description and the field (`children`), and its error an alert (`alert`, `role="alert"`) in a dialog, as the Dialog contract asks of an error inside one, and the field's plain error on a page (`on_page`), where the page tells the reader (§4.5, "Step-up field"). The new API token is a read-only `Code` field with `token`, its secret a signal the page clears when the dialog closes.
  - *Described by the caller's element too.* `also_described_by` names an element of the caller's that describes the field while the signal names it, after the field's own description, note and error (`rules::described_by`), so a screen reader says it on reaching the field. The Machines tab names the warning under its address field with it, an `Alert` of the Warning tone that has no role, as its contract says: the warning is read with the field rather than announced while the address is typed.

  The caller's duties under WCAG 2.2 AA, which the component can't meet for it:
  - **Announcing an error (4.1.3).** The field is no live region: the page says the error through the announcer, or moves focus to an error summary on a failed submit; in a dialog, `alert`.
  - **An error that says what is wrong and how to fix it** (3.3.1, 3.3.3), set only when the form is checked, never while typing.
  - **A description that says why** a field is read only or unavailable, where the note's words alone don't.

  Not taken from Flowbite, the reference: shadows, a success state, floating labels and helper text in color alone (#776 lists them as not planned), and placeholders: a hint is the description, which stays when the reader types. Search is #843's, around this one.

  The gallery's "Text field" demo, just before the Progress demo, shows each kind (one line and many lines with their errors, a password, a number), a time with an icon, a required field, an invalid one, a read-only code, an unavailable field and an unavailable password, and a field and a button of each size in one `.actions` row. Its scenarios reach its controls by Tab from the Button demo's last buttons.

  `features/ui/components/text_field.feature` checks axe and the ARIA snapshot, the error's wiring, place and edge, autocomplete, the multi-line field, the password's toggle, the number's keyboard, read only and unavailable in the Tab order (an unavailable password's toggle too) and in words, the required marker, the heights beside a button at each size, the icon's place in both directions, the edge's token in light and dark, and forced colors; `features/ui/components/step_up_field.feature` checks the step-up's password hidden again when its dialog opens again, and `features/security/admin_password.feature` a shown password hidden again once its form is sent and cleared.
