# The tabs

- **The tabs** are `Tabs` (`components/tabs.rs`), for switching between views within one page (#792): a list of native buttons in a `tablist`, then every panel, each drawn once when the tabs are, the unselected ones `hidden`, so what a reader typed or scrolled to in one is there when it shows again. What a key does in each layout, which tab a press or an arrival newly selects, which tab is the Tab stop, each tab's and panel's `id` and ARIA attributes, the list's name and orientation and whether a panel is a stop of its own are `tabs/rules.rs`'s, decided on the host. The direction the arrows follow in a row is read on each key from the focused tab's computed `direction` (`l10n::Direction::of_computed`, which the tooltip reads its control's with too), so a part of a page set right to left mirrors the keys; a column's keys don't mirror.

  Its `orientation` (#934) is `Orientation::Horizontal`, the default, `Vertical` or `Responsive`. A vertical list stands at the panels' start in a column at most half their width, on a Slate Note rule at its end, and the selected tab's bar lies on that rule. Each tab is as wide as the column, its words wrapping, every line at its start.

  Responsive tabs are their own inline-size container, and a container query (at least 42rem, in rem so larger text needs more room) draws them as a column, a row below that; the window's width would draw a column in a narrow part of a wide page. The tabs' container takes no width from its content, so a caller gives responsive tabs a width, as a block has. The query repeats the vertical rules, since the tabs' styles stay custom CSS until #931, and a container query can't style its own container, so a `.tabs-layout` box inside the tabs carries them.

  The layout is CSS's alone, so `Tabs` reads it back: a responsive list's computed `flex-direction` sets its `aria-orientation` and its arrow keys, read once it is drawn and whenever the tabs or their list change size (a `ResizeObserver`, let go with the tabs). The size watch reports in the rendering update that draws a new layout, before it is painted, so a key never meets a layout on the screen that the tabs haven't heard of. A change of layout redraws nothing: the selected tab, the focus and every panel stay. A vertical set is a column at every width, its list half of a narrow screen; tabs that must suit one too are `Responsive`.

  It takes its `id` (the start of every tab's and panel's), its name (`TabsName::Label` or `TabsName::LabelledBy`), the tabs and its activation. The tabs are a `TabSet`, a first tab and the rest, so a set without a tab, a `tablist` with nothing to select, can't be built; each tab is its words, what its panel holds (`Holds::Text`, a stop of its own, or `Holds::Controls`, whose first control is the stop) and the panel. Nothing is announced on a switch: the screen reader says the selected tab, and the announcer stays the page's.

  `Manual` is for a panel that costs something to show, such as a read from the daemon, so `Tabs` tells its caller which tab is selected through an optional `selected: RwSignal<usize>`, the tab's index in the set, set once for each change and never for a press on the tab already selected; the caller reads it and loads that panel. It is the tree's own way (`selected`, which follows what the tree selects), and the tabs stay the one owner of the selection, so a caller can't name a tab the set doesn't hold. Words that say how a `Manual` set is chosen go beside it, and `described_by` ties them to the list.

  A caller starts the set on another tab than the first by marking that tab (`Tab::selected_at_start`), as Settings does for the tab its address names; the first tab marked is selected, and with none marked the first tab is (`rules::selected_at_start`), so a start can't name a tab the set doesn't hold either. `selected` hears of a start on another tab once, as the tabs are drawn. A modal dialog that opens inside a hidden panel shows that panel first, as a press on its tab does (`show_panel_holding`, which `live::open_modal` calls), since a dialog under a hidden panel isn't drawn. `features/ui/settings.feature` drives both by keyboard alone.

  A caller chooses a tab by writing `selected`, as Settings does when its address's fragment changes: the tab is selected and its panel shown, as a press on it would, and focus stays where it is, since the reader didn't move it. A tab the set doesn't hold changes nothing (`rules::selection_on_choice`), so the tabs stay the one owner of the selection.

  The gallery's "Tabs starting on a marked tab" demo is a set its caller starts on its middle tab, after the "Progress" demo, so it lengthens no walk from the page's top; `features/ui/components/tabs.feature` drives it from its anchor by keyboard alone, in a page that runs left to right and in one that runs right to left (`ar-XB`).

  The selected tab is bold with a 3px Ladder Blue bar on the Slate Note rule, under it in a row and at its end in a column, told by weight and a shape, never color alone (1.4.1). Each tab draws its own stretch of the rule, edge to edge with the next, and the list's rule runs on under the last line, so when the row wraps at 320 px with 200 % text, every tab whole, a tab selected on an earlier line still has its bar over a rule and the tabs beside it their rule. Under forced colors the rule and the bar are `CanvasText`, as the focus ring is, since `Highlight` need not reach 3:1 on `Canvas`; the bar stands apart from the rule by its thickness and from the ring by its place, the weight kept.

  Left out: disabled tabs (a tab that can't open says why in its panel), icons in tabs, boxed, lifted and pill tabs (a fill or a lift says a depth DESIGN.md doesn't use), tabs as navigation between pages (that is the navigation's links and `aria-current`), the selected tab kept in the address by the tabs themselves (a caller that wants it follows `selected`, starts the set on the tab the address names and writes `selected` when the address changes, as Settings does), and a column at the panels' end or a row under them (WAI-ARIA asks only that the list's orientation be said, and no use has come for either).

  The gallery's "Tabs" demo has an automatic set named by its heading, its middle panel holding a field, a manual set described by the paragraph above it and followed by a line naming the chosen tab, and a set right to left; its "Vertical tabs" demo a vertical set and one right to left; its "Responsive tabs" demo a responsive set as wide as the page, its middle panel holding a field, and one in a narrow right-to-left column, a row at every window width. `features/ui/components/tabs.feature` drives each by keyboard alone, a change of layout too (the window narrowed and widened again, with the focus, the selection and the field's text kept), and checks the look in light, dark and forced colors, every set in a column included, and at 320 px with 200 % text, a tab on an earlier line selected, where the responsive sets are rows.
