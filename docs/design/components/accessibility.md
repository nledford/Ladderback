### 4.5 Accessibility

Accessibility is designed in from the first screen, not audited in at the end. The target is WCAG 2.2 AA (A1–A6, §0).

**Supported assistive technologies** follow the supported platforms:

- Orca with Firefox on Linux;
- VoiceOver with Safari on macOS;
- keyboard-only use in any current browser. Safari reaches links and buttons with Tab only when "Press Tab to highlight each item" is on, or with Option+Tab; the manual pass uses that setting.

**Structure.**

- **Native HTML first:** `<button>`, `<a>`, `<table>` with `<th scope>`, `<dialog>` opened with `showModal()`, `<details>`, `<time datetime>`. ARIA only where no native element exists, and then following the WAI-ARIA Authoring Practices pattern for that widget. The progress bar is the one exception: a `role="progressbar"`, because a native `<progress>` draws the value it exposes, which is throttled, and can hold neither the step nor the text the bar shows (§16, decision 83).
- **Page skeleton:** landmarks (`header`, `nav`, `main`), exactly one `<h1>`, descriptive headings and labels with no skipped levels (2.4.6), and a "Skip to content" link. Text in another language, such as rustic's verbatim English messages, carries its own `lang` (3.1.2).
- **Route changes** (path navigation): the router updates `document.title` (page, then machine, then "Ladderback") and moves focus to the new page's `<h1>` (`tabindex="-1"`). Screen readers read the focused heading, so the announcer stays silent. Changing filters, sorting or pages updates the URL query without moving focus.
- **Pointer targets:** at least 24 × 24 CSS px (2.5.8). Nothing needs dragging (2.5.7) or works only on hover.
- **Tooltips and popovers** can be dismissed with Escape, stay open while hovered, and stay until dismissed (1.4.13). The `title` attribute never carries information on its own.
- **Sessions** end after **12 hours unused** and after **30 days** however much they are used (§10.1). Only what the reader does counts as use: what the page reads on its own, and its events stream, never keep a session alive.

  **Two minutes before** a session would end unused, the page warns in a dialog that takes focus on its one button, "Stay signed in", which keeps the session; Escape keeps it too, and closing it returns focus to where it was (2.2.1 Timing Adjustable; two minutes leaves a screen reader or a switch user ample time over the 20 seconds 2.2.1 asks for).

  The 30-day end is not warned of: 2.2.1's 20-hour exception covers it, and the warning is skipped when the lifetime ends the session first.

  Expiry never discards unsaved form input: a "Sign in again" dialog opens over the page, which stays as it was, and the request the daemon refused is sent again once signed in. The sign-in form is one "Admin password" field with `autocomplete="current-password"` (paste and password managers work, A5, A6) and the form's error summary; while signed in, the header's line ends with "Sign out", after the navigation.

  Escape closes that dialog without signing in: the requests that waited end with their refusal, which their pages say (Operations where its table goes, never as a daemon it can't reach), and so does a request still on its way then, unless the dialog has opened again meanwhile, when it waits in it; so the dialog never opens again under the reader on its own (#903). The next request the reader asks for that is refused, such as following a link, opens it again; until the page signs in, the reads it sends on its own end with their refusal.

  With sign-in off, **Settings says an admin password set since Ladderback started**, below its heading, as the page opens: "Admin password set. Restart Ladderback to turn sign-in on. The Restart Ladderback tab does it where a service manager runs Ladderback.", or, for a file Ladderback couldn't read, that it is damaged and the password must be set again, in the Admin password tab or with `ladderback set-password` (§10.1, decision 70). It is a banner in the page's reading order, information, or a warning for the damaged file, not a live region: it comes from the read the page makes as it opens, or from the one it makes once the password is set in Settings, when a polite message says it too.

  **Settings' "Admin password" section** (#617, §10.1) sets the password with sign-in off and changes it in a session; with the daemon unread it is left out. Its form has "New password" and "New password again" (`autocomplete="new-password"`, the first's hint giving the 8-character minimum), and, in a session, "Current password" first (`autocomplete="current-password"`); every field is a password field, which accepts paste and password managers (3.3.8). Its button is "Set the admin password" or "Change the admin password". The page checks only that each field is typed and that the two new passwords agree; the daemon's refusal (too short, too long, a wrong current password, a wait) joins the same error summary, linked to its field.

  A password set in Settings clears the fields, and the section's "no admin password yet" gives way to the restart message above, which the page shows even when its read after the set fails, since the daemon has said the password is set. A changed one ends the page's session, so the sign-in page shows, saying "Admin password changed. Sign in with the new password." in an information alert under its heading, and signing in returns to Settings. A reader who leaves Settings before the change is answered still gets that sign-in page next: forgetting the session is the page's step, not the section's.

**The shared component set** in `web` is where widgets are built: a page uses the set's component wherever it has one, and native elements (above) where it has none. Each component has an accessibility contract and tests for it, and a new one meets WCAG 2.2 AA in full when it merges (§13.7.5):

|---|---|
| Dialog (confirmations, step-up confirmation) | Native modal `<dialog>`. Focus moves in, the background is inert, Escape cancels, and focus returns to the control that opened it. A destructive button is never the default. Errors inside the dialog, such as a wrong password, use a `role="alert"` inside it, around the page's Error alert where there is one |
| Review dialog (a run reviewed before it starts) | The Dialog contract, and more. It is named by its title and described by what the run would do, so a screen reader reads both on entry. While the run is being started its buttons say they are unavailable (`aria-disabled`, still reachable by Tab so focus never falls), Escape does not dismiss it, and a polite live region inside it says "Starting the forget…", because the announcer holds its messages while a modal is open. While the run can't be confirmed yet (`held`, such as a restore whose dry run hasn't answered), the buttons that go ahead say they are unavailable the same way and are described (`aria-describedby`) by the reason, shown beside them; pressing one does nothing but say the reason in that polite region, cleared first so a second press is heard. Dismissing still works |

A press sorts the column its first way (ascending, unless the column sorts descending first), a second the other way, ties keeping the order given, and the caller's sentence says the sort politely. Rows are keyed and updated in place, so a focused control in a row keeps its focus as the rows change or move (2.4.3). Columns keep fixed rem widths (#194). The frame is a region named as the table is and focusable (`tabindex="0"`) at every width, so where the columns are wider than the page a keyboard scrolls it inline, each row's header pinned at its start; a word breaks inside only where it is longer than its column (#524). A time in a cell is its words in a `<time datetime>`, never in a `title` (#851). Loading (beside a `Spinner`), empty and unreachable each show the caller's sentence in the table's place. The caller's duties: a row's actions named with their row ("Delete plan nightly"), complete sentences from the catalog, a sort key that orders as the reader expects, a loading wait it caused announced, a key for each row unlike every other row's, and focus moved on (to the next row or the page's heading) when the focused row goes. It takes no tone, since a table is not a status, and no size: its cells follow the reader's text, their inline padding `min(0.5rem, 1.25vw)` |

The entry it selects is told to its caller (`selected`), so the actions for it sit in a pane next to the tree, reached with Tab: Restore (built, decision 109) and Download (built, decision 114). If M3's VoiceOver pass shows the tree is unusable there, the fallback is a nested list of disclosures |
| Status badge | An icon with a distinct shape per state, visible text, and color. Never color alone (A2) |
| Badge (a count or a tag: "Pending changes 3") | Plain text on a pill of its tone's pair of tokens, 4.5:1 in both color schemes: no role, not a live region, nothing in it to focus, so a screen reader reads its words where they stand. Its words say what it counts or names, the count included; its tone and its optional icon only repeat them (1.4.1). The icon is decoration (`aria-hidden="true"`), in its words' color. Tones `Primary`, `Secondary` (the default), `Success`, `Warning` and `Error`: no `Inherit`, which would leave a pill with no fill. No size and no placement: it takes the text's size and stands in its line. Under forced colors, its words and icon in the system's text color, edged 1px in it. The caller's duties: words that say it all, and a change the reader needs to hear said through the announcer (4.1.3) |
| Progress | A focusable `role="progressbar"` (`tabindex="0"`) named for what it measures and for its run, as its row and its Cancel button are, so two running backups' bars are told apart (WCAG 2.4.6): "Backup progress of home" by its plan (`ui-plan-progress`), "Check progress of demo" by what runs and its repository's alias (`ui-operation-progress-of`), and "Check progress" alone for a run the log names neither for (`ui-operation-progress`; "Operation progress" for a kind the page doesn't know), which holds everything it draws, so its focus ring surrounds what a sighted reader sees and a screen reader hears its value text alone. The fill and the visible text follow every report, and the fill moves smoothly. The value it tells, `aria-valuenow` and `aria-valuetext` (`ui-progress-value`: the step, the percentage, the amounts as sizes when the bar counts bytes, and the time left, as in "Backing up… 42%, 3.1 GiB of 7.4 GiB, about 6 minutes left"), changes at once for the first report, a new step, a total learnt or lost and the total reached, and otherwise at most every 30 s, the latest report told when the 30 s are over: screen readers speak value changes themselves, so the exposed value is throttled. The time left is measured from the first report of the step and total, and told once that measure has run 30 s and done 1 % of the total. A total not known yet (a backup before rustic has walked its whole source) or of zero is indeterminate: no `aria-valuenow` and no track, and in place of the percentage the text says the operation is working, never 0 % (#422). On the Operations page that text is the step the run is in (`ui-step-<code>`), or `ui-progress-working` for none; while the bar shows a percentage, the step's message stands above it. A bar that goes while it holds focus, as it does when its run ends, hands focus to the element its `then_focus` names, on the Operations page its row's header (`tabindex="-1"`: a script's target, no tab stop), so focus never falls to the page (WCAG 2.4.3) (§16, decisions 82, 83). Takes every tone of the shared vocabulary, `Primary` by default. The tone's own token fills the bar, not its status pair, which is for words on a tinted fill (decision 108). The track stays Ledger Gray and the words keep the text's color, so a `Success`, `Warning` or `Error` bar never tells how a run goes by its color alone (1.4.1). The contrast gate holds each tone's fill to 3:1 against the track and against the page (1.4.11). Its size is its track's thickness, half the shared scale's length: `Small` 0.5em (the default), `Medium` 0.75em, `Large` 1em, `XLarge` 1.5em. No placement: it fills the room its caller gives it, the track up to 16rem. Under forced colors the fill is `CanvasText` and the track `GrayText` |
| Text field (one line, many lines, a password, a number, a code) | Visible `<label>` above it; description, a note of its state and its error linked with `aria-describedby`; `aria-invalid` on error, with a thicker edge in the Error tone beside the words; `autocomplete` tokens where a field has a known purpose (1.3.5), and `off` where its caller names none. Required is said in words after the label, "(required)", which a screen reader skips, and once by `aria-required="true"`, never the `required` attribute (the forms check themselves). Read only (`readonly`, in the Tab order, a dashed edge) and unavailable (native `disabled`, out of the Tab order) are each said in words by a note. A password's **Show password** is a toggle (`aria-pressed`) that keeps the value, the caret, focus and `autocomplete`; an unavailable password has none, and a shown password is hidden again when the page sets what the field holds. A number is `inputmode="numeric"` text, never `type="number"`, and takes whatever is typed: the form refuses what isn't a number when it is checked. A list typed one entry a line, such as a plan's folders, is a native `<textarea>`, wired the same way; Enter there starts a line and never submits. On a failed submit, focus moves to an error summary (a heading with `tabindex="-1"`) that names each problem and links to its field. Errors say what is wrong and how to fix it (3.3.1, 3.3.3). Validation never interrupts typing. Sizes are heights, not the shared scale: a button's of the same size (`Small` 1.75em, `Medium` 2em, the default, `Large` 2.5em, `XLarge` 3em), so a field and a button stand level in a row of actions. No tone: the Error tone's edge marks an invalid field beside its words, and nothing else a caller picks |
| Checkbox (one choice, on or off) | A native `<input type="checkbox">`, named by its visible `<label>` beside it, which is also its click target. A description and its error under the label, linked with `aria-describedby`; `aria-invalid` on error, with a 2 px edge in the Error tone beside the words. Space turns it on and off, and the browser says its state, so nothing announces it. Its box is drawn from the tokens (decision 118): never under 24 px a side, 1.5 times its text; a 1 px Field Edge, filled in Ladder Blue under a check in the page's color once on, each 3:1 or more (1.4.11); under forced colors the reader's field colors, the check alone telling on from off. No tone or size of the shared vocabulary: its meaning is in its words (1.4.1), and its size is its text's. The caller says an error as a text field's caller does |
| Radio group (one choice of a few) | A `<fieldset role="radiogroup">` named by its `<legend>`; a description and its error under the legend, linked to the group with `aria-describedby`, so a screen reader reads them on entering it; on error the group is `aria-invalid` (ARIA 1.2 allows it on a `radiogroup`, not on a `radio`) and each choice is edged as an invalid checkbox is, drawn from the group's state. Each choice a native `<input type="radio">` sharing the group's `name`, named by its visible `<label>` beside it, its box the checkbox's but round, with a dot in the page's color once chosen. The browser makes the group one Tab stop, on the choice made or else the first, and the arrow keys move and choose within it, so it handles no keys. A label in another language declares its `lang` and `dir` (3.1.2). No tone or size, as the checkbox |
| Step-up field (restore and download; later approval, §10.4) | The one field a dialog confirms an action with, never a test of memory or transcription (3.3.8). With sign-in on, **Admin password**: a password field with `autocomplete="current-password"`, which a password manager fills. With sign-in off, a text field its caller labels (**Snapshot ID**), with `autocomplete="off"`, the short ID in its description as text that can be selected, and a **Copy the ID** button whose outcome ("Copied.", or to copy it by hand) a polite region beside it says, since the announcer waits while a modal is open. Nothing blocks a paste; spell checking and capitalizing are off. Hint and error are linked with `aria-describedby`; the error is a `role="alert"` inside the dialog (the Dialog contract) and sets `aria-invalid`, and is cleared before it is set again, so a second wrong try is heard. It takes no tone, size or placement of the shared vocabulary (decision 108): it draws nothing in a color of its own, its field is the text field's and its error the text field's error |
| Tabs (views within one page) | The WAI-ARIA tabs pattern: a `tablist` named by its caller's words (`aria-label`) or by an element on the page (`aria-labelledby`), its `aria-orientation` the layout shown; each tab a native `<button type="button">` with `aria-selected` and `aria-controls`, and one `tabpanel` per tab, named by its tab (`aria-labelledby`). Horizontal (the default), a row above the panel; Vertical, a column at its start; Responsive, a column while the tabs' own container has 42rem (a container query) and a row below that. The first tab is selected as the tabs are drawn, unless their caller marks another to start on. One Tab stop, the selected tab (`tabindex="0"`, the others `-1`); Tab from it goes into its panel, which is a stop of its own (`tabindex="0"`) only when its caller says nothing in it takes focus. Automatic (the default) selects a tab as focus arrives; Manual moves focus only, and Enter or Space selects, the words that say so tied to the list (`aria-describedby`). A caller may follow the selected tab. Every panel is drawn once and kept, the others `hidden`, through a change of layout too; nothing is announced on a switch. The selected tab is bold with a bar on the rule between the list and the panel, never color alone (1.4.1). No tone (the bar is the accent; tabs aren't a status) and no size (the tabs are the text's size, each at least 24 × 24 CSS px, 2.5.8) |
| Menus, disclosures | Their WAI-ARIA patterns, or native `<details>` where it suffices |
| Toast (the answer to what the reader did) | Spoken through the announcer, never a live region itself, and never steals focus: politely, and assertively only for a failure (`Error`). An icon and words, never color alone: the icon, the alert's shape for its tone, is an image named for the tone, so a screen reader hears the tone before the words. One at a time, a new one in the place of the one shown. `Primary` and `Success` go by themselves after 6 s, but never while the pointer rests on the toast or focus is in it, and they have their whole 6 s again once both have left (2.2.1); `Warning` and `Error` need the reader, so they stay until dismissed. | Banner (a page-wide notice above a page's content) | An icon and words, never color alone: the icon, one Lucide shape per tone, is an image (`role="img"`) named for its tone ("Information", "Warning"), so a screen reader hears the tone before the words. Never a live region of its own. The caller announces a wait the reader caused, and its end, through the announcer (4.1.3), marks the region it stands for `aria-busy`, and shows a progress bar or words instead where a spinner would start by itself beside usable content and might turn past 5 s (2.2.2; the spinner's notes below). The caller's duties: a label on every meaningful icon, and a labelled icon whose glyph changes built anew with the new glyph's label; never a tone as the only carrier of a meaning (1.4.1, A2), the glyph's shape or words saying it too; an icon-only control named on the control (`aria-label`), the icon inside staying decoration. Its caller gives where the process stands (`Reached`): the steps before it are done and those after it to do, so two current steps can't be shown; the step it stands at, under way or failed, carries `aria-current="step"`. Not interactive: no Tab stop and no keys. Not a live region: a change of where it stands is said politely through the announcer, as something that happened by itself ("Step 3 of 5: Commit", "Step 3 of 5 failed: Commit", "All 5 steps are done."), one message with its arguments, never on its first drawing, and focus never moves. A row while its own container has 42rem (a container query, in the reader's text size), a column below that, so 320 CSS px with 200 % text is always a column (1.4.10, 1.4.4); logical utilities only, so the row mirrors right to left; names wrap and are never cut. Connectors join the icons, Ladder Blue after a step that is done and `--muted` after the others, 3:1 or more on the page and a surface (1.4.11), as the icons are. No tone, size or placement of the shared vocabulary: each state picks its color, and the words carry it. The caller's duties: a name for the list, step names that say what each does, and a failure's reason shown beside the list. A list whose steps the reader can go back to would be a variant with a contract of its own |

**Print.** A surface that holds a secret has a print rule, and it is one of two, named by its page. A dialog that shows a secret once (a pairing token and its QR code, an API token) **hides** it: a printout of the dialog holds none of the secret, and no chrome. A page that is meant to be printed (the Recovery Kit, decision 121) is a **sheet**: a printout holds the sheet and nothing else, so its print rule hides the app's chrome, the Banner, every button and link, and every Alert that isn't part of the sheet, and keeps its own warnings. Either rule is a test, and a page says which it is in its decision.

**Exceptions.** A page that builds its own version of a widget the set has gives the reason in its pull request and lists it here, with where it lives. None is listed yet.

**The shared vocabulary** (§16, decision 108). A shared component takes its color, size, placement and side from one vocabulary, `crates/web/src/variants.rs`, each tone, size and placement a class of `style.css` (DESIGN.md, "Shared Vocabulary"), as each is built or reworked (#776); the spinner was the first to draw with it, the icon the second, the button the third, and the tooltip the first to take a side. As decision 108's amendments allow, it takes a tone and a size only where they mean something: the step-up field, the tooltip, the table, the tabs and the steps take neither, each its row saying why.

The badge, and the status badge built on it, draws `Success`, `Warning` and `Error` in their status tones' pairs and keeps its own pairs for `Primary` and `Secondary`, the Loading and Empty pairs (decision 103). A component's row above names any tone it leaves out because it makes no sense there, its default tone where it isn't `Primary`, and any size it draws at lengths other than the shared scale's, with the reason:

- **Tone:** `Primary` (Ladder Blue, `--accent`; the default, unless a component's row names its own, as the icon's does), `Secondary` (`--muted`), `Success`, `Warning` and `Error` (the status hues `--success`, `--warning` and `--error`), and `Inherit` (`currentColor`, for a part inside another component, such as a spinner in a button). A tone's class sets `--tone`, which the component draws with. A tone never carries the meaning alone (1.4.1, A2): the component says it in words or an icon too. Each tone's token is at 4.5:1 on `--bg` and `--surface` in both schemes (`just test-contrast`), and under forced colors every tone draws in the text's own color (`currentColor`, which the mode makes `CanvasText`), so the words tell them apart.
- **Status pair:** a pair of colors for a part tinted in a status tone, its words on its fill, for each of `Success`, `Warning` and `Error` (`StatusTone`, whose `pair()` gives its two utilities): `--success-fg` on `--success-bg`, `--warning-fg` on `--warning-bg` and `--error-fg` on `--error-bg`, a pale fill under dark words in light colors and a deep fill under pale words in dark ones. Every status-tinted part of a shared component draws from these, never a pair of its own. The words are at 4.5:1 on their fill in both schemes, and the Warning and Error fills at least 0.1 apart in OKLab lightness, Error's the further from the page, so the two neighboring hues never read as one. The Warning fill stands further from the page than the Success fill, so it never reads paler (decision 108). Under forced colors the system's colors replace both.
- **Size:** `Small`, `Medium`, `Large` and `XLarge`, one scale every component shares: a size's class sets `--size` to 1em, 1.5em, 2em or 3em, which the component draws its length with, so a size grows with the reader's text (1.4.4) and a spinner and an icon of one size line up. A component that needs other lengths may deviate, saying why in its row. No default in the vocabulary: each component picks its own.
- **Placement:** `Inline` (the default: in the line of text, as wide as what it holds), and `Start`, `Center` and `End`, a line of its own with the part at its start, middle or end, in logical properties, so `Start` is the right in a right-to-left page. The class goes on the line, an element of the component's own around its part, never on the part's root: it sets the line's `display`, which a root's own `display` would override (a badge) or which would stretch a boxed root across the line (a button).
- **Side:** where a part that floats beside a control stands (a tooltip, later a popover, #784): `Above` (the default: a note above a control leaves the lines below it, where the reader goes next, in view), `Below`, and `Start` and `End`, before and after the control in the page's direction, so `Start` is the right in a right-to-left page. A part with no room on its side flips to the opposite one, then to the other axis (`End` before `Start`, `Above` before `Below`), and with room on none stands where it overflows least. Not a `Placement`, which aligns a part in its own line. No class: the page measures the control and places the part (`components/tooltip/rules.rs`, `place`).

The gallery's "Shared vocabulary" demo shows every value named in words, each status pair as its name in its words on its fill, and `features/ui/components/vocabulary.feature` checks each tone's color and swatch, each tone but `Inherit` apart from the text around it, `Inherit` following that text inside an outer tone, every tone in the system's text color under forced colors, each status pair's words and fill in light and dark colors, and the placements in both directions.

**Live updates (A3).** `UiEvent`s update the page visually, but only the **announcer** talks to screen readers.

- **Two regions:** a polite `role="status"` and an assertive `role="alert"`. Both sit in the static `index.html`, outside the Leptos mount point, empty and never `display: none`, so they exist before anything is written to them.
- **Polite:** an operation finished, an agent came back. **Assertive:** only a failure that needs the user now, such as a failed restore.
- **Writing:** each message clears the region and sets the text on the next tick, so a repeated message is announced again.
- **Bursts are merged:** the same message within 2 s is said once, and ten agents changing at once become one summary ("3 backups finished, 1 failed").
- **Modal dialogs** make the rest of the page inert, including the regions. While one is open, announcements queue and are spoken when it closes.
- **Progress** is never written to a region. The start and the finish are announced.
- **Focus survives an update (2.4.3).** An update to a row changes text, values and the presence of what it is about; it never rebuilds a control the reader may be on. A control goes only when it stops being one, as a Cancel button does when its run ends. A row's Cancel button or progress bar that goes while it holds focus, its row staying, hands focus to the row's header, which names the run (`components::hand_focus_when_gone`; #438, and for the bar the Progress row above), and the run's end is announced as any other. A row that leaves the page, or a table built again (a change of what the page shows), takes the header with it, and focus then falls to the page.
- **Pause:** the Operations page, the one page that follows the daemon live, has a "Pause live updates" control (2.2.2). While paused, the page stops changing and a banner counts pending changes; the announcer holds what happens by itself and still answers what the reader does. Resuming shows every change at once and says once how many runs ended (decision 65).

**Settled in the first build** (`crates/web/src/announcer.rs` for the timing, `live.rs` for the regions):

- **Where it lives:** the timing is pure logic over an injected clock in a module of the `web` binary, so `cargo nextest run -p web` runs its tests on the host; the glue that writes the regions and owns the one timer is `live.rs`. The regions in `index.html` carry `role`, `aria-live` and `aria-atomic="true"`, are visually hidden with a class and never `display: none`, and the app mounts into `#app` beside them.
- **Merge window:** 2 s, from the first polite message, not the last, so a steady trickle cannot postpone the write for ever. The messages in it are joined with a space in arrival order (catalog messages are whole sentences) and a text already in the batch is said once. A page that wants a summary ("3 backups finished, 1 failed") builds it and sends it as one message; the announcer only merges. At most 16 messages are held for one write, so a modal left open cannot grow the queue without bound.
- **Write, clear, then set:** the region is cleared when the window closes and set 50 ms later. A message for a region that is still waiting to be set joins that set. Blank text and progress updates are ignored.
- **Modal dialogs:** opens are counted, so nested modals hold messages until the last one closes. Closing flushes everything held at once, without a new 2 s window, assertive first. A close with no modal open is ignored. A polite message sent inside an open window and held by a modal joins the same batch. A write already waiting for its tick when a modal opens is made after it closes. A page that unmounts a dialog while it is open (a route change) must tell the announcer it closed, because a removed `<dialog>` raises no `close` event.
- **Assertive messages wait for a modal too:** the design's "announcements queue" covers them, and it is the behaviour that works. A modal makes the rest of the page inert, and VoiceOver and JAWS say nothing for a live region in inert content (w3c/aria#1854), so an assertive message let through would be lost, and it is the urgent one.

  They skip the merge window; two for the same region that arrive within the 50 ms before the first is set, or while a modal is open, are joined into one set. The same limit of 16 holds per region.

  A failure that happens inside a dialog belongs in a `role="alert"` inside that dialog (the Dialog contract above), which needs no announcer. Moving the regions into the open dialog instead was left out: it needs a design change, and the real Dialog component is the place to revisit it.
- **Route changes:** `document.title` follows the path. An unknown path is the not-found page, with its own `<h1>`, and so is `/_gallery` in a build without the gallery. Each page's `<h1>` takes focus when it is shown after a navigation. The page load itself leaves focus at the top, where the skip link is, unless the address names a section by its fragment, as Settings' Language tab does when it loads the page again after a save (`/settings#language`): that section's `<h2>` (`tabindex="-1"`) then takes focus once, as it is shown, so a keyboard or screen reader user is not dropped at the top (`page::focus_when_named`). The gallery's demos are named the same way (`/_gallery#dialog-demo`, §13.7.5). Settings' other tabs' addresses start the page on their tab and leave focus at the top. A fragment changed while Settings is open moves no focus (§4.4, item 7).
- **The skip link handles its own activation:** its click handler moves focus to `<main>` and stops the click. Left alone, the router takes the click on `#main` and only scrolls to it, so focus stays where it was. The router ignores a click that something else has already stopped, so it needs no option, and the address and the history stay as they were (a `rel="external"` on the link, tried first, worked too, but called an in-page link external and left a `/#main` entry that Back had to step over).
- **The gallery** is the `gallery` feature of `web`: off by default and off in a release build, which `just architecture` checks. `just web-test` builds the UI with it, and `just test-ui` runs the scenarios against that build.

A change of layout redraws nothing: the selected tab, the focus and every panel stay. A vertical set is a column at every width, its list half of a narrow screen; tabs that must suit one too are `Responsive`.

  It takes its `id` (the start of every tab's and panel's), its name (`TabsName::Label` or `TabsName::LabelledBy`), the tabs and its activation. The tabs are a `TabSet`, a first tab and the rest, so a set without a tab, a `tablist` with nothing to select, can't be built; each tab is its words, what its panel holds (`Holds::Text`, a stop of its own, or `Holds::Controls`, whose first control is the stop) and the panel. Nothing is announced on a switch: the screen reader says the selected tab, and the announcer stays the page's.

  `Manual` is for a panel that costs something to show, such as a read from the daemon, so `Tabs` tells its caller which tab is selected through an optional `selected: RwSignal<usize>`, the tab's index in the set, set once for each change and never for a press on the tab already selected; the caller reads it and loads that panel. It is the tree's own way (`selected`, which follows what the tree selects), and the tabs stay the one owner of the selection, so a caller can't name a tab the set doesn't hold. A modal dialog that opens inside a hidden panel shows that panel first, as a press on its tab does (`show_panel_holding`, which `live::open_modal` calls), since a dialog under a hidden panel isn't drawn. `features/ui/settings.feature` drives both by keyboard alone.

  A caller chooses a tab by writing `selected`, as Settings does when its address's fragment changes: the tab is selected and its panel shown, as a press on it would, and focus stays where it is, since the reader didn't move it. A tab the set doesn't hold changes nothing (`rules::selection_on_choice`), so the tabs stay the one owner of the selection.

  The gallery's "Tabs starting on a marked tab" demo is a set its caller starts on its middle tab, after the "Progress" demo, so it lengthens no walk from the page's top; `features/ui/components/tabs.feature` drives it from its anchor by keyboard alone, in a page that runs left to right and in one that runs right to left (`ar-XB`).

  The selected tab is bold with a 3px Ladder Blue bar on the Slate Note rule, under it in a row and at its end in a column, told by weight and a shape, never color alone (1.4.1). Each tab draws its own stretch of the rule, edge to edge with the next, and the list's rule runs on under the last line, so when the row wraps at 320 px with 200 % text, every tab whole, a tab selected on an earlier line still has its bar over a rule and the tabs beside it their rule. Under forced colors the rule and the bar are `CanvasText`, as the focus ring is, since `Highlight` need not reach 3:1 on `Canvas`; the bar stands apart from the rule by its thickness and from the ring by its place, the weight kept.

- **The spinner** is `Spinner` (`components.rs`), a twelfth component, for a wait for something the page can't show yet: a track and a quarter arc of one SVG circle, stroked in the drawing's color, the arc turning once in 0.9 s, linear. Its `label` is a required prop, so a spinner without one doesn't compile, and it must say what the page waits for: an empty one leaves a spinner whose label is hidden an image without a name (1.1.1).

  It takes its `tone`, `size` and `placement` from the shared vocabulary. Every tone makes sense for it, so it leaves none out: `Primary` (the default), `Secondary`, `Success`, `Warning`, `Error`, and `Inherit` for a spinner inside a button or a toast. The tone's class sets `--tone` on the spinner, and the drawing alone is drawn in it (`color: var(--tone)`), the label keeping the text's color: a status tone may tint a wait, but the label says what the page waits for.

  The vocabulary has no default size, so the spinner picks `Small` (`spinner::rules::default_size`), as tall as the text, for a line of text or a button. Its sizes draw at the shared scale's lengths (`--size`: 1em, 1.5em, 2em and 3em), the drawing's own `width` and `height` of 1em keeping it the text's height without the stylesheet.

  The placement's class goes on the spinner's line, a `span` the component puts around it, never on the spinner: `Inline` (the default) keeps it in its line of text, the label on the line's baseline and the drawing centered on the text as an inline image is; `Start`, `Center` and `End` give it a line of its own, at its start, middle or end in the page's direction. There the spinner is a row of its own, so a long label wraps beside the drawing, never under it: every line of the label starts after the drawing, which stands centered on the first.

  What a screen reader meets is `spinner/rules.rs`, decided on the host, with the spinner's classes: with `LabelShown::Visible`, the default, the label is ordinary text beside the drawing and the drawing is `aria-hidden`, so the label is read once; with `LabelShown::Hidden` the drawing is `role="img"` named by the label. The track is the arc's color at a quarter of its strength. Each tone's token reaches 4.5:1 on the page and on a surface (the vocabulary's contrast pairs), more than the 3:1 the arc needs as a part (1.4.11). Under forced colors the arc follows the vocabulary's rule, the text's own color whatever the tone, and the track is `GrayText`. The reduced-motion rule stops the turning, leaving a still arc beside the label.

  The caller's duties under WCAG 2.2 AA, which the component can't meet for it:

  - **Announcing (4.1.3, Status Messages).** A spinner that appears because of something the reader did (a search, a save) has its wait, and the wait's end, said through the announcer, since the spinner is no live region.
  - **Busy.** The region it stands for carries `aria-busy="true"` until it is filled.
  - **Moving (2.2.2, Pause, Stop, Hide).** Moving content that starts by itself, runs longer than 5 seconds and is shown beside other content needs a way to pause, stop or hide it. A spinner has none, so where one would start by itself, not from the reader's press, beside content the reader can use, and might turn past 5 s, the page shows the progress bar or words instead, as a running status badge does. A spinner the reader started, one that is over within 5 s, or one that is all the page shows while nothing on it can be used yet (the preload animation W3C counts as essential, which holds only when no reader can do anything meanwhile) needs nothing.
  - **A busy button** keeps focus while the spinner stands in it: `aria-disabled="true"`, not `disabled`, which would drop focus to the page (A1). `aria-disabled` stops no press, so `Button` itself takes none while it is busy or unavailable; the page needs no guard of its own.

- **The tooltip** is `Tooltip` (`components/tooltip.rs`): a short note beside the one control it wraps, `<span class="tooltip-anchor">` holding the control and the note, a `popover="manual"` `<span class="tooltip">` in the top layer, so no container clips it; Chromium, Firefox and WebKit all have manual popovers. The page places it itself rather than through `popover="hint"` or CSS anchor positioning, so one host-tested rule decides where it stands in every engine: `position: fixed`, `left` and `top` from the viewport's top-left corner (the browser's own measures, physical in every direction of writing), set again as any scroller scrolls or the window changes size.

  What a screen reader meets, when it shows and where it stands are `components/tooltip/rules.rs`, decided on the host, so a popover (#784) places itself the same way. `Tip` keeps the two purposes apart: `Describes` is a description (`role="tooltip"`, the control's `aria-describedby`, added to any it has), `Names` an icon-only control's name (the control's `aria-label`, the tooltip `aria-hidden`).

  `Shown` takes focus, blur, the pointer's coming and going, Escape and its two waits (300 ms before a resting pointer shows it, 150 ms of grace after the pointer leaves) and answers whether it shows and what becomes of its one wait. Escape's dismissal lasts until focus and the pointer have both left, or the control gains focus anew.

  `place` tries the side asked for, its opposite, then the other axis, and takes the first with room for the note's depth from the control (its height above or below, its width at either end), keeping 0.5em of the control's text to the viewport's edge and 0.375em from the control; with room on none, the side it overflows least, the earlier side keeping a tie. Its length along the control isn't weighed: along its side it is centered on the control and moved inside the viewport. Across, it moves only away from the control, so it never covers it.

  Showing it: keyboard focus, as `:focus-visible` tells it, shows it at once. A mouse press's focus on a button doesn't: the pointer resting there has already shown it, and a note popping up on every click would cover what the press changed. A finger doesn't hover (`pointerType` `touch` is ignored), and a tap's focus on a button isn't `:focus-visible`, so touch shows nothing there: a tooltip is never the only way to learn something. A text field is the exception: every engine treats any focus on it as `:focus-visible`, a click's or a tap's too, as it shows its focus ring then, so a field's note shows on a press. It fades in and out over 100 ms (`opacity`, with `display` and `overlay` held until the fade ends), at once under reduced motion; hidden, it never takes the pointer.

  Its look is the page's colors swapped: the fill `--fg`, the words `--bg`, in light and dark, a pair the contrast gate checks; the small radius (`--radius-small`), no shadow, no arrow. Its text is 0.875em of its control's, so it grows with the reader's text (1.4.4), and it wraps at `min(20em, --room)`, `--room` being the viewport's width without its scroll bar less an edge at each end, which the page sets as it measures (`100vw` counts the scroll bar), no word cut (`overflow-wrap: anywhere`). Nothing limits its height: a note taller than the window runs past its edge, which the caller's short text prevents. Under forced colors it is `Canvas` and `CanvasText`, edged in 1px of `CanvasText`. It takes no tone, since it is a note, not a status, and no size, since its text follows its control's.

  The caller's duties under WCAG 2.2 AA: never a control's only name, outside `Names` on an icon-only control; short text, a sentence or two, so the note fits a small window at 200 % text; nothing the reader needs to finish the task, since a tooltip is found only by focusing or pointing at its control; no link, button or field inside (a popover's, #784); one control as its child, whose `aria-describedby`, if it has one, is set once and not reactive: the tooltip adds its id when it mounts, and a value the control set later would drop it. A table's time needs no tooltip: its words are the full time (#851).

  Taken from Flowbite's tooltip, the inspiration: the dark note over light text, the four sides, hover and focus. Not taken: its click trigger (a note opened by a click is a popover's), the arrow, colored shadows and the "light" style.

  The gallery's "Tooltip" demo is the gallery's last section, so a journey reaches its controls by Shift+Tab from the page's start: a button it describes, an icon-only button it names, each side, `Start` and `End` right to left, a long note, and a button at the foot of the page asking for `Below`, which has no room there. `features/ui/components/tooltip.feature` checks focus and Escape, the pointer's delay and hovering (through `ui-tests/support/pointer.ts`, which only moves the pointer), each side and the flips, 320 × 640 with 200 % text (a note beside a mid-screen control can't fit the 256 px height the other small-screen scenarios use), the colors in light, dark and forced colors, the fade and the scroll.

- **The text field** is `TextField` (`components/text_field.rs`), for what a reader types, and it replaces `FormField`: every page's field moved onto it. A native `<input>`, or a `<textarea>` for many lines, drawn from the tokens rather than in the browser's own look (decision 113). What each kind asks of the browser, the ids its parts are wired by and what it says of its state are `components/text_field/rules.rs`, decided on the host. - **The table** is `Table` (`components/table.rs`), which replaced `SortableTable`, and every table of the app is one (#876): Operations, Repositories, the plans, the start page's plans, API tokens, the Log, a repository's snapshots and its stats, the forget review's lists and a proposal's forget preview. It is a real `<table class="data-table">` inside a frame, `<div class="data-table-frame" role="region" tabindex="0">`, named as the table is (`Name::Caption` or `Name::Heading`).

  What it decides is `components/table/rules.rs`, on the host. `press` sorts a column the way it first sorts, ascending unless the column is `descending_first` (as Operations' Started is, its history arriving newest first), the same column again the other way, and another column its first way whichever way the last ran. `aria_sort` and `glyph` follow it (`arrow-up-down`, `arrow-up` and `arrow-down`, from Lucide's `arrows` category). `order` is a stable sort on each row's `SortKey`, a number or a text compared by its bytes and read once a row, so rows that tie keep the order given either way. `shown` says what takes the table's place: loading, unreachable, empty, or the table.

  Rows are keyed (`key`, the caller's) and drawn by a keyed `<For>` over the order, each built once as it first shows. Its cells bind to a memo of the row found by its key, so a change reaches only what a cell binds to, and only a change of `shown` builds the table again.

  A row that moves (a sort, or a change to the sorted column) is taken out and put back, and a moved node loses focus in every engine. So the table notes the element focused in its body before it applies a new order and gives focus back after the move: in the same turn, and again at the next frame.

  Each column has a fixed width in rem on its `<col>` (`table-layout: fixed`), and the table is `max(100cqi, the widths added up)`: the frame's width (`.data-table-frame` is an inline-size container, so `cqi` is the frame's), or the columns' where that is wider, and the frame scrolls. On a wide frame the columns share its spare width in proportion. No container query rule is needed: the unit alone measures the frame, and no column's width follows its content (#194).

  No word breaks inside unless it is longer than its whole column (#524): the body's `overflow-wrap: anywhere` stays, and in a fixed table no column narrows below its rem, so where the columns are wider than the page the frame scrolls and no word is broken to fit, while a word longer than its column (a 64-digit ID, a long log source) breaks rather than run over the next cell. An address breaks between its parts first, where `address_view` marks them. The pinned headers' column is at most 40 % of the frame, so there a word wider than that breaks, as a 40-letter repository name or *Operation* at 320 px with 200 % text does. A header whose words must read whole, a snapshot's short ID, keeps their room instead (`Column::kept_whole`, below).

  So no table has width rules of its own: the per-page rules of the Operations and Repositories tables, and their container queries, went with the move. A page's columns add up to no more than the room it has at 1280 px (58rem; 44rem for the API tokens beside the Settings tabs), so a wide screen never scrolls.

  A time in a cell is its words in a `<time datetime>` that gives the instant to a program (`time_view`): the full time is the cell's visible text, and no `title` or tooltip repeats or hides it (#851).

  Each row's header, and the corner header above them, is pinned at the frame's inline start (`position: sticky; inset-inline-start: 0`, the right in a right-to-left page) on the page's background (`Canvas` under forced colors). The row header column is at most 40 % of the frame (`min(<width>, 40cqi)`), and the frame's `scroll-padding-inline-start` is the room it covers. Browsers already scroll a control focused beneath a sticky header nearly clear of it, to within a pixel or two in Chromium, Firefox and WebKit; the padding scrolls it wholly clear, so it stays in view (2.4.11), at 320 px with 200 % text too, where the frame is 8rem wide.

  A row header kept whole (`Column::kept_whole`) keeps the room its words need however narrow its frame, up to three fifths of it, so the cells beside it keep two fifths to be read in (`min(<width>, max(40cqi, min(<room>, 60cqi)))`, and the padding likewise). A snapshot's short ID keeps 8rem: its eight hex digits in bold at their widest (DejaVu Sans Bold's "b" and "d", 0.72em each) with 1.4.12's letter spacing, and the cell's padding at its widest. At 320 px that is 52 % of the forget review's 244 px frame, and the ID reads whole (#1129); at 200 % text the frame is 180 px, and the ID breaks inside three fifths of it. Only a header beside cells that hold no control is kept whole, as a snapshot's time holds none, so the room it covers hides no focused control (2.4.11).

  Borders are kept separate with no spacing, which draws as collapsed borders do while each cell keeps its own rule, so a pinned header carries its rule with it (a collapsed border belongs to the table and stays behind). The header row isn't pinned: the frame doesn't scroll vertically. A column at `Align::End` puts its header, cells and footer at the end of the line in figures of one width (`tabular-nums`).

  Its look is the incumbent's, refined rather than redrawn: full width, cells at the start and top, one Slate Note rule under each row, the caption in Slate Note, header text bold, flat. Taken from daisyUI's table: the pinned row header. Not taken from daisyUI or Flowbite: zebra stripes (DESIGN.md forbids them), a hover highlight on rows (rows aren't clickable; it would promise an action), an active row, shadows, a header band, built-in search, filters or pagination (#795 sits beside the table), checkbox selection, and density sizes.

  The gallery's "Table" demo, before the Tooltip's, has a choice of what the table shows (its rows, loading, empty or unreachable), a sortable table of demo folders with a total in its footer and an "Add a file to …" action in each row, and the same table, unsorted, in a narrow frame and right to left.

  `features/ui/components/table.feature` checks sorting by Enter and Space, `aria-sort` and the sentence said, ties, and a row action keeping its focus as its row changes and moves. It checks the numbers' alignment, each state (the loading words just before the busy region and outside it), the frame scrolled by keyboard at 320 × 640 with 200 % text in both directions with each row header whole at its start, and the row headers' fill in light, dark and forced colors. `features/ui/tables.feature` checks each page's tables at 400 px: each sits in its own frame that Tab stops on, named as the table is, no word breaks inside unless it is longer than its cell's room, and no time hides in a `title`; the Operations and Repositories pages' own scenarios check 320 px with 200 % text.

That is 1.4.10's allowance for a data table, and text an inner box cuts off still fails.

- **The skeleton** is `Skeleton` (`components/skeleton.rs`), for the still shape of content on its way, standing where the content will. Its `shape` says what it stands for, from the reader's text: `Shape::Lines { count, last }`, lines of text, each 1em tall in the middle of a line of the text's height and the full width of the room it is given, but the last, which is `last` of it (a `Share`, a whole percent); or `Shape::Block { inline, block }`, a box in `Rem`, such as a field or a button's place, never wider than its room. So the room it takes is the content's, and the page keeps its layout when the content comes. It has no circle or avatar shape, since the app shows no pictures of people, and no image or video placeholder.

  What it draws is `skeleton/rules.rs`, decided on the host: its class, and the inline size of each bar, or the block's two lengths. Its types can't hold no lines, a last line longer than its room or a negative length: `count` is a `NonZeroU8`, so it draws one line at least; a `Share` above 100 % is the whole line, the one clamp, made once where the share is built; a `Rem` is a count of tenths (the shared length of `variants.rs`, which a table's columns take too). It is a `<span>` of bars laid out as a column, so it stands in a room of its own, as wide as the content it stands for, never inside a line of text or a row that sizes it by its content; its bars stand at the start of their room, in the page's direction.

  It is flat, Pencil Gray (`--skeleton`) with the small corner (`--radius-small`): 1.61:1 on the page and 1.47:1 on Ledger Gray, 1.69:1 and 1.46:1 in dark colors, so one gray shows on the page and on the header, a toast or the pause banner alike. A skeleton carries no information, so no WCAG minimum applies (1.4.11 is for what a reader needs to see to understand), but a skeleton no one can see says nothing of its wait: `just test-contrast` holds both pairs to 1.4:1, a floor for visibility. The existing grays fall short of it: Ledger Gray is 1.10:1 on the page, the empty badge's gray 1.24:1. Under forced colors the system drops the fill, so a 1px edge in `GrayText` keeps its shape in view.

  - *Still.* It never moves, in any motion setting: no shimmer, no pulse, no transition. A skeleton starts by itself beside content the reader can use and may stay past 5 s on a slow daemon, and nothing on the page could pause it, the spinner's reason (2.2.2, Pause, Stop, Hide; the spinner's notes above).

  The caller's duties, which the skeleton can't meet for it:

  - **Words.** It is never a stand-in for words: the page says the wait in words ("Loading…"), visible, as it does without one, on a line just before the region and outside it, since a screen reader may leave a busy region unread. Where the content's size is known before it comes, the region keeps its height, and the content may take the words' line when it comes (the gallery's plan name does). A page's first load can't know how many rows are coming, so there the content takes the place of the words and the region both, and what follows it may move.
  - **Busy.** The region it stands for carries `aria-busy="true"` until the content arrives.
  - **Arrival.** The content takes the skeleton's place without moving focus, and nothing announces it: the announcer stays the page's (4.1.3, A6).

  *A page's first load* meets these duties through `first_load` (`components.rs`), one helper for every page: while the daemon's first answer is on its way, it draws the words ("Loading…") on a line, then, just after them, the region the answer fills, a `<div aria-busy="true">` holding the still shape of what is coming, an `Awaited` (`skeleton/rules.rs`, decided on the host), both in one `<div>`, so the page's layout sees one element. A table is its header and three rows, a line per column; a form is each field's label above a 20 rem field, then its button; words, a list or a few buttons, whose shape is known only once they come, are two lines of text.

  The shape is the content's kind, not its exact layout: a table of row headers, the controls above a table, or a radio group standing as a form's field take the nearest of the three. The page draws it where its content will stand and drops it whole when the answer comes, or when the reading reaches no daemon. Once it is dropped, nothing stays busy or says the wait; focus stays where it was, and nothing is announced. "Still waiting…" stays words. `features/ui/first_load.feature` checks a table's and a form's, busy and then not, the words just before the busy region and outside it, axe-core clean, and that the Snapshots page stops waiting once its reading of the repositories reaches no daemon.

- **The toast** is `Toast` (`components/toast.rs`), the answer to what the reader just did, shown where its page puts it: an icon, the words, then a Dismiss button. A page keeps one `Toasts` handle, the first build's `show_toast` gone, passes it to the `Toast` it draws and calls `show(tone, words)` on it. Its tone is a `ToastTone` (`components/toast/rules.rs`, decided on the host), `Primary` (information, the default), `Success`, `Warning` or `Error`, whose icon and the word that names it are the alert's for that tone, so one tone has one shape across the set. `Secondary` and `Inherit` are left out, as for the alert.
  - *Said, not shown, to a screen reader.* `show` says the words through the announcer as a reply (decision 65), politely, and assertively for `Error`, a failure of what the reader asked for, which needs them now; the toast itself is no live region, so it is said once, and its going is not said. It never takes focus: focus stays on the control the reader pressed.
  - *How long it stays* (`Lifetime`, host-tested). `Primary` and `Success` go by themselves after 6 s (`TOAST_MS`; 3 s, the first build's, left a keyboard reader too little time to reach the toast and hold it). The pointer resting on the toast (`mouseenter`, `mouseleave`) or focus in it (`focusin`, `focusout`) holds it, and once both have let go it has its whole 6 s again, so nothing goes under the reader (2.2.1). `Warning` and `Error` need the reader, so they start no timer and stay until dismissed. Each arrival and each hold voids the wait started before it (a token the timer carries), so an older toast's time never takes away a newer one.
  - *One at a time.* A new toast takes the place of the one shown, in the same box, so a hold on it carries over and focus on its Dismiss button stays there. The failure a replaced `Error` toast told still stands on its page (the row above). As no two toasts stand side by side, a `Success` fill never sits beside a `Warning` one, and decision 108's question of their likeness stays with the first component that sets them so.
  - *Dismissal.* A Ghost Small icon-only `Button` in `Inherit` (Lucide's `x`), named "Dismiss" (the alert's word), its name shown by a `Tooltip` (`Tip::Names`). Enter, Space or a click takes the toast away; focus on the button then moves to the element with the ID the page names (`then_focus`, a signal read as the toast goes, `hand_focus_when_gone_to`), and nothing is said. Escape is left to the button's tooltip, which it hides (1.4.13), so one key never does two things.
  - *The look.* Tailwind utilities (decision 117), logical ones only, and no rule of its own in `style.css` (the first build's `.toast` rule goes): a status tone's toast lies on its tone's status pair (`StatusTone::pair`, decision 108), information on Ledger Gray in the text's color, edged 1px all round in its tone (`--tone`) with the small corner. The icon and the Dismiss button take the words' color, so the pair's contrast covers them; the contrast gate adds the focus ring on each status fill (3:1) and each status pair's words on the surface a hovered Ghost button takes (4.5:1). Under forced colors the fill goes and the edge is `CanvasText`.
  - *Where the pages use it* (#983). A page answers the reader's own press with a toast where nothing else on it shows the answer, in place of a `live::reply`, so the words are said once: the Log page's **Copy for a bug report** ("Copied the lines shown."), a plan saved or deleted, an API token revoked and a proposal applied or rejected, each `Success`; a download handed to the browser, a restore started, a **Check again** that finds Full Disk Access still missing and the Operations page's "Still waiting for Ladderback to say how the run ended.", each `Primary`.

    A reply whose answer already shows on the page (a sort, a status line, a form's result, a busy button's "Saving…", a check that takes the Full Disk Access warning away) stays spoken only. Each page draws its one `Toast` after the control or the introduction it answers, `then_focus` naming the control or the heading just before it.

    A failure stays where it happened, never only a toast, but for one that is the press's alone and leaves nothing else on the page wrong: a copy the browser refused is an `Error` toast beside **Copy for a bug report**, said assertively once, which stays until dismissed. The snapshot pane's toast answers both its dialogs, so its `then_focus` follows the one that started what it says, Restore or Download. The Operations page's toast, after the start buttons, hands focus to the page's heading, since a row's Cancel may have gone with its run.

**Settled in the pause build** (`crates/web/src/pause.rs` and `announcer.rs` for the decisions, `components.rs`, `live.rs` and `operations_page.rs` for the glue; decision 65):

- **The stream goes on; the page shows a copy.** `Pausable` holds the copy of the Operations page's state and connection phase taken at the press; every view of the page (the heading, which rows show and in what order, each row's cells) reads through it, so while paused no update reaches them. `ws::watch`, its reconnects, the settle-poll and the end announcements read the live state. The resume drops the copy, and the page shows the live state at once: nothing replayed, nothing lost, no row twice. A sort while paused orders the copy.
- **The banner** counts each row that will look different on the resume, one however many events changed it, plus one when the connection's phase changed (`OperationsState::changes_since`). It reads "Live updates are paused. 2 changes are waiting." and is a paragraph the button's `aria-describedby` points at, present only while paused. Its edge has the table rule's color (`--muted`), not the focus ring's, so beside the focused button it never reads as a second focus ring.
- **Two kinds of message.** `live::say` sends a `Kind::Event`, which waits while paused; `live::reply` sends a `Kind::Reply`, the page's answer to the reader's own press (a sort, a start, "Still waiting…" after a start or a cancel, a form's result, a toast), which is said as usual. The end of a run the reader cancelled is the answer to that press: the row's Cancel button marks the run, and its end is a reply, said while paused and not counted. The Snapshots page's maintenance panel still sends all it says as events: it has no pause, and it mixes answers with ends.
- **The announcer's pause and resume.** `pause` writes "Live updates are paused." at once, joined after anything still in its merge window, with no new window. `resume` writes the page's summary first, then the events that waited, then any reply still in its window, one write per region at once, assertive first, each region's queue deduplicated and bounded at 16. A pause sentence not yet written (a resume within its 50 ms, or behind a modal) is dropped, never said after the resume; joined after a write still to come, it alone leaves that write. Behind an open modal they wait for it to close, as every message does. A resume while not paused writes nothing.
- **The resume's sentence.** While paused, the page counts the runs whose status it sees go from queued or running to an end, and the failures among them (`Ends`), in place of announcing each (a run the reader cancelled is answered instead); the resume says them in one polite sentence ("… 3 runs ended while they were paused, and one of them failed."), "No run ended while they were paused." when none did.
- **The control** is `PauseUpdates` (`components.rs`), a ninth shared component: the button with its constant name and `aria-pressed`, and the banner. The page passes what pausing and resuming do to its own state; the component tells the announcer. Leaving the page ends the pause (`on_cleanup`), and nothing is stored, so a reload starts unpaused. It sits after the Operations page's opening paragraph, before the plans' Start buttons. The gallery's "Pause control" demo pauses a demo's own updates: "Finish a demo run" says "Backup finished." while it is not paused and counts the run while it is.

**Time, numbers and charts.**

- Relative times ("3 h ago") are always paired with the absolute time, both in `<time datetime>` and in the accessible name. Text inside a live region never ticks.
- Sizes and durations come from `l10n` (§8.4). Where an abbreviation reads badly aloud, the visible text is `aria-hidden` and a visually hidden spoken form, from the catalog's `.spoken` attribute, sits next to it. An accessible name always contains the visible label text (2.5.3).
- SVG charts (§8.1) have `role="img"`, a title and a one-sentence summary ("Snapshot size grew from 41 to 44 GiB over 30 days"). A "Show as table" toggle exposes the same numbers as a real table.

**Visual adaptation.**

- Light and dark themes follow `prefers-color-scheme`, with a manual override.
- `prefers-contrast: more` strengthens borders and focus rings, and `forced-colors: active` falls back to system colors without losing state.
- `prefers-reduced-motion` stops every animation and transition: the progress bar's fill then jumps to each value rather than moving to it. Nothing flashes.
- Text resizes to 200 % without loss, and pages reflow at 320 × 256 CSS px (A4).
- Color tokens live in one CSS file, and a test checks every foreground and background pair against A4's ratios. Once the visual `DESIGN.md` exists, `design.md lint` runs the same check on its tokens.

**Safe actions and authentication (A5).**

- Restore, in-place restore, adoption, forget and prune say what will happen before it happens and can be cancelled (3.3.4).
- Step-up confirmation (§10.4) allows paste and password managers (`autocomplete="current-password"`). The "type the snapshot short ID" check used when auth is off accepts paste, and the ID is shown as selectable text with a copy button, so it isn't a transcription test (3.3.8).
- A multi-step flow never asks again for something already entered (3.3.7).

**Beyond the web UI.**

- **Notifications:** every message has a plain-text form (email has a text part). Meaning never depends on color or emoji, and every message says what happened and what to do next.
- **CLI:** color is never the only signal, and `NO_COLOR` is honored. Spinners and redraws are off when output isn't a TTY, or with `--plain`. Every command that reports state has `--json`.
- **CLI output,** as built:
  - *Colour.* `--plain` is a global flag, taken before or after a command's name. It turns off the colour of the daemon's log and of `clap`'s help and usage errors. `clap` colours those while it parses, before the flag has a value, so the raw arguments are scanned for the exact token `--plain`, never after a bare `--`. Without it, `clap` and `env_logger` both ask `anstream`, which reads the environment: a non-empty `NO_COLOR` means none, whatever else is set; a non-empty `CLICOLOR_FORCE` forces colour even into a pipe; `CLICOLOR=0` means none; and otherwise colour needs a terminal. Ladderback's own sentences have none to turn off.
  - *`--json`.* A command that reports state prints one document, as compact JSON on one line of standard output, and nothing on standard error. Its keys are kebab-case and its text is codes and arguments, never a sentence (§8.4), so a script reads the same document in every language. `import-profile` is the only such command: `export-profile` prints a profile, `serve` is the daemon and `worker` speaks the worker protocol, so `clap` refuses `--json` on them with 2.

    An import that saved the profile prints `{"repository": …, "plans": […], "notices": […]}`, with `notices` always there and each notice `{"code": …, "args"?: …}`. Once the command line is understood, every failure is `{"error": {"code": …, "args"?: …, "detail"?: …}}`, the REST API's typed error (`api::ErrorDto`), except one that cannot be a document: the document itself cannot be written.
  - *Statuses,* the same with and without `--json`: 0 when the command did what it was asked, 1 when it refused or could not start, and 2 when the command line was not understood: by `clap`, in its own words before any command runs, leaving standard output empty, or by `serve`, which refuses an `--allowed-host` that no request could match, in the catalog's words (§10.1). The worker is not a command a person runs, and ends with the statuses of §4.1.
  - *Nobody reads.* A pipe has no reader once the program at its other end has ended (`ladderback import-profile nas.toml | head -1`), and `print!` and `eprint!` panic on it (§13.5).

    Commands print through `output::to_stdout` and `output::to_stderr`, which return the failure, and the binary denies `clippy::print_stdout` and `clippy::print_stderr` so that a later `println!` cannot bring the panic back.

    A write that fails because nobody reads ends the command, quietly, with 141: 128 and the number of SIGPIPE, the status a shell shows for a program that a closed pipe killed. That covers the import (its words and its document), the export, `clap`'s help, version and usage errors, and the daemon's startup lines.

    A write that fails for another reason, a full disk say, is said as `cannot write the result: <reason>` on standard error, and the status is 1; `clap`'s own messages are the exception, which say nothing and keep `clap`'s status, as they did when `clap` printed them itself.

    A standard output that is not open at all is no failure: the runtime reopens it as `/dev/null`, so the command prints into the void and ends as it would have. The worker is left as it was: its standard output is the protocol stream, and it already ends with 74 when that stream breaks (§4.1).
