### 4.1 Worker process (the engine boundary)

This section decides what runs in a worker process, how the daemon talks to it, and how a job is stopped, bounded and cleaned up after.

Each operation (backup, forget, prune, check, restore, ls, dump, stats) runs in a **child process**:

```
daemon ──stdin: JobSpec (one JSON line)──► ladderback worker
daemon ◄─stdout: NDJSON Event stream── (progress, log, warning, result)
daemon ──stdin: DeleteAnswer (a prune's one line)──► ladderback worker
daemon ──SIGTERM → (grace) → SIGKILL──► cancel
```

Why a subprocess instead of `spawn_blocking`:

1. **Cancellation.** `rustic_core` has none, but a process can be killed. The worker installs a SIGTERM handler that stops emitting events and exits; without it the grace period would be meaningless.

   A backup that is archiving winds down instead (decision 50): its source (`CancellableSource`) lists, opens and reads nothing more, so rustic ends the backup its own way, writing its last packs and saving the index of every pack the worker wrote, and the backend that takes a snapshot first (`refusing_snapshots_once_cancelled`: the hot half when there is one, rustic writes the cold half only after it) refuses the snapshot that comes next. A snapshot write that had begun before the cancel finishes, in both halves, and the snapshot stays. The worker then exits with 143 and writes no more events, so the operation ends `Cancelled`.

   A backup past its deadline winds down the same way (item 4). The daemon's SIGTERM reaches the worker alone, so the `rclone` or `ssh` its backend saves through runs on during the wind-down; a SIGTERM sent to the whole group from outside ends them too, and then the index may not be saved.

   A file the cancel cut mid-read is left out; the blobs it had chunked, like the trees of the partial backup, are indexed but no snapshot uses them, which a check doesn't warn about and a prune removes while their packs are unused, or repacks past its unused limit once a later backup reuses some of their data.

   The wind-down lasts until the daemon's SIGKILL at the end of its grace period, or 30 s when the daemon is gone.

   Killing is safe for data:
   - A backup killed before it saved its index (a SIGKILL, a crash, a wind-down past the grace period) leaves packs no index lists and no snapshot: a check warns about each, and the next prune cleans them up.

     On the local backend it also leaves `*-tmp-*` files, which nothing in rustic removes. Once a job has opened a repository, the worker deletes the ones older than 24 h from each half that is a local folder (the cold half, and the hot half of a hot/cold repository), but only where the backend writes them: `config-tmp-…` in the half's root and `<id>-tmp-…` in `keys`, `snapshots`, `index` and `data/<xx>`. A job that fails to open its repository (a mistyped path, a wrong password, a missing hot half) deletes nothing.
   - Prune writes new packs and index files, then deletes the old index files, then the packs. A kill at any point leaves extra data or duplicate index entries, not missing data; the next prune deduplicates and finishes the job. This only holds without `early-delete-index` (I2).
   - M1a proves this with a kill test against a scratch repo, for the local backend and for OpenDAL's `fs` service. It kills real workers right after a chosen progress event, of a backup and of a prune that has packs to repack, spreading the kills over the events of an uninterrupted run, and then checks that the repository is sound and still takes a backup. OpenDAL's `fs` service writes in place unless `atomic_write_dir` is set, which can leave half a file under its final name, so the guarantee above holds for an `opendal:fs` repository only with `atomic_write_dir` (a directory on the same filesystem).
2. **No runtime nesting.** The backends' internal Tokio runtimes never meet the daemon's runtime.
3. **Isolation.** Memory from large indexes is returned to the OS when the worker exits, and a panic or out-of-memory kill in the engine can't take down the daemon.
4. **Deadline enforcement** (I3, §7.3; decision 55). `rustic_core`'s `backup()` writes the snapshot itself and offers no hook before that write. Instead, once the worker has written `Started` for a job with a deadline budget, a watchdog thread compares wall-clock time against `index_read_at + budget` and, once it notices the deadline has passed, first asks for the cancel of item 1, so the backend refuses every snapshot write from then on, then writes `Failed { DeadlinePassed }` as the last line and ends the worker with 75.
   - The watchdog's first check runs before the job's work starts, so a zero budget stops the job before it writes anything. After that it waits for the time left to the deadline, but at most `watchdog_interval` (5 s by default) at a time, and these waits don't count the time a machine is suspended, so it notices the deadline when it comes, and one that passed during a suspend within one interval of waking. A snapshot write that starts in that gap after a wake is not refused, as it wasn't before decision 55; the prune margin covers it.
   - A writer stuck on a full pipe can't hold the exit back: the watchdog tries the stream once, and goes on whether or not it could write the failure.
   - A job that isn't archiving a backup ends at once (`process::exit(75)`).
   - A backup that is archiving winds down as a cancelled one does (item 1): it starts no snapshot write and saves the index of the packs it wrote, and the job ends the worker with 75 once rustic returns, so a check finds nothing to warn about and the next backup reuses the data; a failure the watchdog couldn't write, the job writes then, as the last line.
   - A snapshot write that had begun at the deadline finishes, in both halves of a hot/cold repository: that write is what the prune margin covers, and ending the worker during it could leave the snapshot in one half alone. The operation is still `deadline-passed`, and in that case its snapshot exists, as after a cancel that comes once the snapshot was written.
   - The watchdog waits for the wind-down 30 s at most, which bounds a worker whose daemon is gone, and then exits with 75.
   - The watchdog stops once the backup has returned: the snapshot is written, and the result goes out before the repository's index is dropped, so a deadline that passes meanwhile can't turn a finished backup into a failure.
   - The daemon also stops the worker at the deadline, with its grace period (below).
5. **Privilege separation (later).** On servers, the worker can run as root to read `/etc` while the daemon and web UI run unprivileged. This uses a small setuid-free helper started via a systemd unit, or `sudo` with a fixed command. Before building it, hooks and `password-command` must be restricted to root-owned config, or the unprivileged UI could escalate to root through them.

Each running worker of a repository whose ID is known gets its own `cache_dir`, a cache slot `<cache folder>/<repo-id>/<slot>`, because rustic's cache has no cross-process locking: the slot is the lowest number no other running worker of that repository uses, and it is free again when the worker exits.

- **Lock.** The worker also holds an exclusive `flock` on its slot directory for as long as it runs, and a daemon looking for a slot skips directories whose lock is held, so a worker that outlived a restarted daemon never shares its cache with a new one; a worker that finds its directory held runs with `no_cache`. A lock is only taken while the slot's path still names the folder locked, not a link, so a slot removed while its lock was held is never held through the folder that was removed.
- **Cache folder.** The daemon passes its cache folder (below, under **Config**) to the engine at start, made 0700 when it isn't there yet; every folder made under it (the repository's folder, the slot, and the cache folder again when it was removed meanwhile) is always 0700.
- **No cache folder.** With no cache folder (no home directory and no `LADDERBACK_CACHE_DIR`), or one that can't be made or written to (the daemon makes and removes a file of its own in it at start), the daemon says so once in its log and its workers run with `no_cache`, which costs each job a fresh read of the index and nothing else (§16, decision 59).
- **No known ID.** Without a known ID, the worker runs with `no_cache`; a daemon job of a saved entry that records none therefore runs after an identify, with the ID it found (§16, decision 81), so only an identify, an initialisation and a job of a repository a request gave run that way.
- **Why a job has no slot.** When the daemon has a cache folder and gives a job that opens a repository no slot, its log says why in one line at the info level, with the operation's ID and the job's kind: the job names no ID, or none of the repository's slots is free (a look at the slots that fails is logged the same way). A worker that finds the lock of the slot it was given held runs with `no_cache` without a line of its own: the daemon gave it a slot.
- **A cache rustic can't write.** rustic itself treats a cache it can't write (a full or read-only disk) as a warning and goes on.
- **Tidy at start.** Each time it starts, before it listens, the daemon tidies the cache folder: it removes every slot no worker holds of a repository no entry records (and that folder once empty), every other repository's slots above the highest one in use (slot 0, a slot another process's worker holds, or one whose lock can't be looked at), and rustic's unfinished `<id>-tmp-` files over a day old in the slots kept.

  While an entry records no ID, no repository counts as one no entry records, since the tidy can't tell which folder is that entry's: every repository keeps its folder until the entry's next job records the ID.

  It touches a slot only while it holds the slot's lock, only folders named as a repository ID and slots named by their number, and never follows a link; the log says what went and its size (§16, decision 61). It runs with `nice` (and `ionice` on Linux) as configured per agent.

**Event protocol** (module `engine::job`, §8.3):

```rust
enum WorkerEvent {
    Started { op_id: Uuid, pid: u32, index_read_at: Timestamp }, // taken just before the index is read
    ProgressStart { key: u32, kind: ProgressKind /* Spinner|Counter|Bytes */, prefix: String },
    ProgressLength { key: u32, len: u64 },
    ProgressInc { key: u32, inc: u64 },    // coalesced: at most ~4 msgs/s per key
    ProgressTitle { key: u32, title: String },
    ProgressFinish { key: u32 },
    Warning { item: Option<String>, during: String, code: WarningCode, detail: String }, // from Progress::error; detail = rustic's text
    Log { level: Level, message: String },   // logs are never localized (§8.4)
    Snapshots { snapshots: Vec<SnapshotResult> }, // a batch of a listing, before its Result (below)
    Result(OpResult), // BackupSummary | ForgetSummary | PruneStats | CheckReport | …
    Failed { code: ErrorCode, args: Vec<(String, MsgArg)>, detail: Option<String> }, // codes from `api` (§8.4)
}
```

`ProgressBars` is implemented by `EventProgressBars`, which writes these events. Per-file errors raised through `Progress::error` become **warnings**, so an operation can end as `Succeeded`, `SucceededWithWarnings` or `Failed` (§3.1). The worker builds a `Redactor` (§3.1) from its `JobSpec`'s repository and `repo_hot`, password, options, `options_hot`, `options_cold` and resolved secrets (`RepositorySpec.secrets`, copied from `RepositoryAccess.secrets`) and passes every `Log`, `Warning` and error through it (I4); §10.2 lists what it masks. A worker stopped by its watchdog emits nothing more; the daemon records the operation as `Failed { reason: DeadlinePassed }`.

**Message cap.** The daemon reads the worker's stdout one line at a time and the worker reads the `JobSpec` from its stdin as one line, and each side reads at most `MAX_MESSAGE_BYTES` (1 MiB, in `engine::job`) of a message plus one byte to tell it from a longer one (§13.5, rule 2). The daemon closes a worker's stdin after the spec, but a prune's: a prune that has worked out its plan asks with `ready_to_delete` and reads one answer line of at most 64 bytes, `delete` or `delete_nothing`, waiting at most 60 seconds; anything else deletes nothing (§7.3, decision 161).

An event line past the cap fails the operation as `EngineFailed` with the cap in its detail, and the daemon kills the worker; a worker answers a `JobSpec` past the cap with `InvalidJobSpec`; the daemon refuses to start a worker for a spec it would reject. A line that never ends therefore never grows a buffer past the cap.

The worker keeps its own lines under the cap: it cuts each text field (log messages, warning items and details, failure details) to 64 KiB, after redaction, so a cut can never keep the start of a secret.

**What does not fit the cap is split by its sender (decision 32).** The cap stays at 1 MiB, and no list in a message grows with a repository: whoever sends one splits it, with a bound on each piece.

- *A job names at most `MAX_JOB_IDS` snapshots* (5,000, in `app::ports`; an ID is about 70 bytes of the spec). `RunMaintenance::execute` splits a forget's or an adoption's list into jobs of at most that many and runs them one after another as one operation, with one summary: the IDs removed (or the copies made) of every job, in order.

  The first job to fail, or a cancel during a job or seen as one ends, ends the operation as it would a single job and starts no more. A cancel that fired before a job's engine was up ends the operation cancelled, even when the job's result is ready at once.

  Every job touches only snapshots the selection named, so what earlier jobs did stays done and is not the operation's to undo; the operation records a warning that says how many were done, and the next run selects what is left. The engine refuses a job that names more with `EngineError::Unavailable`, as it does a spec past the cap.
- *A listing is a series of `snapshots` events.* `Ls` emits `Started`, then `Snapshots { snapshots }` events, newest first, each serialized to at most 512 KiB (one snapshot alone in an event may be longer, up to about 800 KiB), then `Result(Snapshots { count })`, where `count` is what the events carried: the daemon hands the list on only when its own count agrees, and fails the job (`EngineFailed`) otherwise, so a listing that lost a batch is never taken for the whole. This replaces "`Ls` emits `Started` and one final result".

  A repository with more than `MAX_LISTED_SNAPSHOTS` (200,000) fails the listing with its count in the failure's detail rather than being listed in part, and the daemon refuses a listing whose texts weigh more than `MAX_LISTED_BYTES` (256 MiB): the list it holds is bounded in both, and a partial list would make forget decide on history it can't see.

  A listing's worker reads the repository's whole index too, so at most two listings run at once, of every repository together, taking turns from a `ReadTurns` of their own as folder reads do (below; #710): the wait counts against `READ_TIMEOUT`, and a listing whose turn comes after its time is up starts no worker. A proposal's forget preview takes the same turns (#967): it reads at most two repositories at once, and each one's listing holds a turn as the snapshot list's does, while its retention reads after it, in the daemon, take none. An approval's second read takes them too.
- *Stats is one result.* `Stats` opens the repository, emits `Started`, reads the snapshots and then every index file, and ends with `Result(Stats { snapshots, total_bytes, stored_bytes, raw_bytes })`: the snapshot count, the sum of their `total_bytes_processed`, and the sums of the indexed blobs' lengths in their packs and of their raw lengths, packs marked for deletion left out (§16, decision 104). A read, never written to the operation log.
- *A download is a series of pieces.* `Dump` names the snapshot, the entry (its keys from the snapshot's top; none is the top) and the archive format, and runs with a backup's deadline, as a restore does. It emits `Started`, then `Dumping { found, name, host }` (a file and its size, or an archive; the entry's shown name; the host the snapshot records, which names the top's archive), then `Piece { bytes }` events, each at most 64 KiB of the entry (`PIECE_BYTES`) written as base64, about 87 KiB of text, and `Result(Dump { bytes })`. The pieces are the entry's own bytes, never masked: a redactor could change a file's contents. A snapshot or an entry that isn't there ends it at once with `SnapshotUnknown` or `EntryUnknown`.

  A file is rustic's dump of it. A folder or the top is an archive written as it is read (`tar`, or `zip` with every entry stored): each entry reached through the trees as `ls` lists it, its contents dumped straight into the stream, so no file is held whole; a zip writer keeps each entry's name until it writes the central directory at the end. A zip entry's name separates folders by `/` only, each `\` in a name written as `_`, so no extractor takes it for a folder; a tar entry keeps its exact name. Devices, pipes and sockets are left out (§16, decision 114).
- *A snapshot is cut to a size one message holds.* A listed snapshot carries at most 64 paths (`api::MAX_SNAPSHOT_PATHS`) and 64 tags (`api::MAX_SNAPSHOT_TAGS`), and no text (a path, a tag, the host, the label) of more than 1 KiB, a cut text ending in `…`. That is under 800 KiB for any snapshot, even with every character escaped, so each fits a message alone.

  The worker sets `paths_truncated` or `tags_truncated` when it left something out or cut it, and the DTO carries both (the UI does not show them yet); a cut host or label ends in `…`. When tags are cut, the `ladderback-*` tags that say who owns a snapshot are kept first, so a forget never takes an owned snapshot for an unowned one. The DTO validates the 64 limits (it refuses a snapshot beyond them); the worker is who cuts, for transport.
- *A folder of a snapshot is read a page at a time.* `Browse` names the snapshot, the folder (the names that lead to it from the snapshot's top, each as rustic records it) and the position its page starts at. It emits `Started`, then one `Result(Folder)`: the page, or that the repository has no such snapshot (`SnapshotUnknown`) or the snapshot no such folder (`FolderUnknown`). Like a listing, it is a read: it waits at most `READ_TIMEOUT`, holds no slot and writes nothing (§16, decision 102).

  A page holds the folder's entries in the order its tree records them, at most 1,000 (`domain::browse::PAGE_ENTRIES`) and at most 512 KiB serialized, with the folder's total and where the next page starts, so it is one message whatever the folder holds. The folder is reached through the trees, one name at a time, and an entry whose name is longer than 4 KiB (no file system writes one) is left out but keeps its position.

  A worker may hold the folder's whole tree, 350 MiB for one of 300,000 entries, so at most two folders are read at once, by all browses of every repository together (`app::reads::READS_AT_ONCE`, one `ReadTurns` shared through the configuration catalog): two reads that hang hold up every other browse until the read timeout ends them. The rest wait for a turn, in no set order; the wait counts against `READ_TIMEOUT`, so a read that waits ends as `TimedOut` no later than one that started at once, and a browse dropped while it waits takes no turn.
- *A repository's reads wait a bounded time.* `RunMaintenance::assess` gives up an identify or a listing after `READ_TIMEOUT` (10 minutes) with `MaintenanceError::TimedOut`, which stops the worker, holds no slot and writes nothing.

**What is implemented of this protocol (M1a, plus the secrets work of M1b):**

- A job is `Fake | Identify | Backup | Prune | Check` (decision 80 adds `Probe`, which opens one location with its own credentials and reports the repository ID it holds, so a location that hangs is killed rather than the job). The repository password travels as a plain string on stdin only, and `JobSpec` also carries `cache_dir` and `watchdog_interval_ms`.
- A repository with a hot half (`repo_hot`) is opened through both halves. `options` apply to both, `options_hot` to the hot half only and `options_cold` to the cold half only (rustic's own rule), and the job's repository string is the cold half.

  rustic reads the hot half's config first and requires the keys of the halves to match, so a missing hot half fails the job at the open. It keeps keys, snapshots, index files and tree packs in the hot half and reads them from there, so a check fails when a snapshot is missing from it; file data is in the cold half only.

  A `RepositorySpec` that leaves the hot fields out, as an older daemon's would, is refused as `InvalidJobSpec` (`options_hot` and `options_cold` have no default) instead of being opened as a cold-only repository.
- The first line of a worker's stream, once its spec has parsed and the redactor is installed and before it opens anything, is a `Log` at the debug level reading `job accepted`, with nothing of the job in it: it is the proof of life the daemon's start timeout waits for (below). A spec that doesn't parse gets `Failed(InvalidJobSpec)` alone. `Started` is written when the job's clock starts: right before `to_indexed_ids()` for a backup, before `prune_plan` for a prune, before `check` for a check, and after opening the repository for `Identify`. Progress that rustic begins earlier (listing snapshots) never reports, and only `Log` and `Failed` can precede `Started`.
- `ProgressInc` is coalesced on the leading edge: the first goes out at once, the rest are added up and sent at most every 250 ms per key, and the remainder is flushed before `ProgressFinish`. A source rustic could not read (`scan`, `archival`) is a `SourceUnreadable` warning; any other `Progress::error` is `Unknown`.
- `Failed.code` is `deadline-passed` only when the deadline ended the job (the watchdog writes it, or the job as the worker ends when the watchdog couldn't); the codes the engine adapter reads from what rustic reports (`repository-not-found`, `repository-config-not-found`, `repository-replaced`, `credentials-refused` with its `half`, `password-not-accepted`: `translate` in `client/translate.rs`) aside, all else rustic reports is `operation-failed` with `detail` = rustic's one-line message, after redaction. Exit codes: 75 deadline (the watchdog's, or the job's once a backup has wound down at its deadline), 143 SIGTERM, 74 events could not be written. The client maps `Failed { DeadlinePassed }`, and EOF with exit code 75, to `DeadlinePassed`.
- Stopping a job sends SIGTERM, waits the grace period (`STOP_GRACE`, 35 s, past the worker's own 30 s limit on a wind-down, so a backup that archives saves its index before the SIGKILL could land; decision 50), then SIGKILL; `stop()` returns once the process has exited, and the job's events end without a result.

  While it waits, `stop()` reads and drops what the worker still writes: a backup winding down (item 1) whose events went unread until the pipe was full would otherwise stay blocked writing one, and the SIGKILL would leave its packs unindexed. Dropping a running job kills the worker at once, but after a result it has 10 s to finish.

  At the deadline the daemon stops the job, with the grace period, so a backup that archives can wind down (item 4), and so it does when the worker reports the deadline first; it checks the deadline on every event too, so a stream that never pauses can't hold it off. Once the worker has exited, the operation is recorded `deadline-passed`, whatever the exit code, so its end time can be up to the grace period past the deadline, as a cancelled one's is past the cancel. A result stands even when it arrives past the deadline: its snapshot is already written.
- Two timeouts keep a hung worker from holding the daemon.
  - A new worker has one deadline of 30 s (`WorkerEngine::with_start_timeout`), counted from the start of the write of the job to its stdin, to take the job: it ends with the worker's first complete line of any kind, which is normally the `job accepted` log line above. Opening the repository, which a slow backend can make take longer, comes after that line and is not bounded by this timeout.

    A worker that doesn't read a spec larger than the pipe's buffer (64 KiB on Linux) leaves the write blocked, so `run` kills it with its process group and fails with `EngineError::StartTimedOut`.

    A worker that took its job and then says nothing is killed with its group by the job's event stream, which ends with a single `Failed(EngineStartTimedOut)`; `run` doesn't wait for it, because that would delay a user's cancel until the first event. Either way the operation fails as `EngineStartTimedOut` without having started.

    After its first line a worker is not on this clock: how long it takes from there is for the job's deadline and for cancel.
  - Once a worker's event stream has ended, the process has 10 s to exit (`with_exit_timeout`): one that stays alive is killed, and the operation fails as `EngineExitTimedOut`.

  A timeout too long to represent, such as `Duration::MAX`, never passes. The wait inside `Control::stop()` after SIGKILL has no timeout of its own: its signature can't fail, and a SIGKILL can't be refused short of an uninterruptible sleep.
- Backup chooses the parent with `PlanTags::parent`: explicit `ParentOptions.parents`, or rustic's own match when it returns `None`. Extra tags are `UserTag`s, which never start with the reserved `ladderback-` prefix in any case, so they can't make a snapshot look like another plan's (I6); the worker refuses such a tag in a spec too.
- A backup's snapshot names the build that wrote it. `ladderback worker` is handed the program and its build as `ladderback --version` prints them (`ladderback 0.3.0+3f937cf`, §16, decision 90), and the backup sets the snapshot's `program_version` to that text, which rustic would otherwise fill with its own `rustic <version>`; `rustic snapshots --long` shows it as "Generated by". It is not a tag: retention groups and ownership (I6) never read it, and it holds nothing of the job's secrets (I4).
- Prune always runs with `instant_delete = false` and `early_delete_index = false`, and `keep_delete` is a `KeepDelete`, never under rustic's 23 h default, passed as rustic's `keep_marked`; the worker refuses a shorter one too. Its summary counts `packs_marked = unused + repack`, `packs_deleted = packs_to_delete.remove` and `packs_recovered = packs_to_delete.recover`: the marked packs a snapshot uses again that the run marks for recovery or brings back, so one pack counts in two runs (§2.2). A pack marked for recovery that nothing uses any more is marked for deletion again, and rustic's statistics count it in none of the three.
- Check sends each finding as a warning of its level (`check-warning` for rustic's `Warn`, `check-error` for anything else) in rustic's own words, masked and cut like every warning, the errors first so that the operation's cap on warnings never keeps a tidy-up in place of an error, then counts the findings by level; a check that ran to its end succeeds, with warnings when it found anything (§16, decision 51).
- A backup's spec carries its plan's snapshot host (§3.1) and its whole `SourceFilter` as `SourceFilterSpec`. The worker maps the filter's globs and glob files onto rustic's `Excludes` and the rest onto `LocalSourceFilterOptions`, and the host onto `SnapshotOptions::host`; with no host, rustic records the machine's own name.

  The worker parses the host again as a `Hostname` and refuses one that isn't (`InvalidJobSpec`), before it opens the repository. A spec without `filter`, as an older daemon's would be, is refused the same way; a spec without `host` means no host.

  The job spec's size cap bounds every pattern and path the filter lists, but rustic reads each glob file whole, so a very large glob file costs the worker's memory, never the daemon's. The worker runs in the daemon's working directory, and rustic reads a glob file from the working directory, so every `glob-files` and `iglob-files` path is a `GlobFile`, an absolute path: the configuration refuses a relative one at its key when it loads (`Value(GlobFile)`, §6.1), and an import refuses it as unsupported (§6.2). The worker doesn't check the paths again.
- The `Redactor` masks each secret raw, fully percent-encoded with either hex case, and as the url crate encodes a userinfo (rustic quotes URLs that way); a secret a URL parser splits (`@`, `#`, `?`, `/`, `:`) is also masked piece by piece from 8 bytes, and as it is printed across the host, path and query. A password in the repository URL is masked as written and decoded, and also when a raw `/` in it ends the authority early.
- **Worker environment.** A worker is started with `env_clear()` and only the variables of an allow-list from the daemon's environment (module `engine::environment`): `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `TZ`, `LANG`, `LC_ALL`, `SSH_AUTH_SOCK`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `RCLONE_CONFIG` and the proxy variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, each also in lowercase. Names are matched exactly.

  Everything else, such as `AWS_*`, `AZURE_*`, `GOOGLE_*`, `RUSTIC_*`, `RCLONE_CONFIG_*` and the variable a secret reference was read from, is not passed; a repository that needs a credential gets it through `${…}` in its options (§10.2).

  A proxy URL with credentials embedded passes as it is, so those credentials stay in the worker's environment (a residual risk the user takes by writing them there; no secret source is added for them), but they are masked wherever the worker's output shows them: the daemon adds the password and the whole userinfo of each of `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (either case, with or without the scheme; `NO_PROXY` lists hosts, not a URL) to the job's `Redactor`.

  The base is the daemon's own environment, read at each job, unless `WorkerEngine::with_environment` replaces it; tests and a composition root that has read its environment already use that.
- **Masking by the daemon.** The programs a worker starts (rclone, ssh) write to its stderr without going through its `Redactor`, so the daemon builds a `Redactor` from the job's repository and `repo_hot`, password, the three option sets and secrets, and the proxy credentials above, and masks each stderr line before logging it. A line cut at the cap is masked as a cut text (§10.2, "Where masking runs"), and so is a last line the stream ended without its newline, which a kill can leave partway through a write; both are logged ending in `…`.

  It masks every text a worker's events carry as well: failure details, warnings, progress text (which then only names a step, and goes no further: decision 82) and log lines, and the failure it reports for a line it can't read.

  The worker masks its own, but it rejects a job spec before it has the job's secrets, and a parse error can quote the value it choked on, and it knows nothing of the proxy credentials. The worker cuts a text after masking it and marks the cut with `…`, so the daemon masks a text that ends in the mark as a cut text too. A fake job has no secrets of its own and masks only the proxy credentials.
- OpenDAL's local file service is the repository string `opendal:fs` with the option `root`.
- A worker leads a process group of its own. A stop sends SIGTERM to the worker alone, so a backup winding down (item 1) keeps the programs it started, then SIGKILL to the group after the grace period; a kill is the group's. A worker that exits by itself, at its deadline (75), on a broken event stream (74), on a SIGTERM (143) or by crashing, gets the group a SIGKILL as well, so the `rclone` of an rclone backend, which `process::exit` doesn't stop, ends with the worker.

  On Linux the daemon sees the exit with `waitid(WNOWAIT)` and signals the group while the worker is an unreaped zombie, which still holds its process id. nix has no `waitid` on macOS, so there the worker is reaped first and the group is signaled by the id it had.

  POSIX keeps a process id from being reused while a process group of that id has a live member, so the window left is a group with no live member, whose id a new process takes and makes itself leader of between the reaping and the signal.

  The worker keeps the event pipe on a close-on-exec descriptor of its own and points descriptor 1 at `/dev/null`, so no program it starts inherits the pipe or can write into the stream. Once the worker has exited, the daemon reads what is left in the pipe for one more second at most, so a process the worker left behind that holds the pipe open can't keep the events from ending.

  On Linux the worker asks for SIGHUP when its parent dies (`PR_SET_PDEATHSIG`) and handles it as a SIGTERM once its parent is no longer the process that started it. The kernel sends that signal when the parent *thread* ends too, and the daemon starts workers on tokio's blocking pool, whose threads end after 10 s without work while the daemon lives on: a SIGTERM there stopped a backup that outlived its thread, which failed with 143 (#448). Elsewhere a worker whose daemon died ends at its next event, when the pipe is broken.
- A progress or log callback that finds the event stream unwritable (the daemon is gone) ends the worker at once with code 74, and so does the job's own write failing. A panic is written to stderr with the job's secrets redacted. The worker's stderr is a pipe the daemon reads on a task of its own, never the terminal: a worker in a process group of its own is a background job to a terminal with `stty tostop`, and a write to the terminal would suspend it. Each line, cut at the message cap, goes to the daemon's log as a warning (target `ladderback::worker`), without holding up the events, and the reading ends with the worker like the events' does.
- Integration tests run the worker through `engine-worker`, this crate's own binary, which does what `ladderback worker` does.
- Every child the daemon starts, a worker, a hook, a password command or the `rclone` that serves an `rclone:` repository it opens to evaluate retention, starts through the spawn gate (`spawn_gate::hold`, decision 58): one start at a time in the process, so none inherits another's pipes where the standard library makes a pipe in two steps (macOS).

  The gate is held for the start only, not while the child runs, nor while `rclone` comes up: the engine starts that server itself, as rustic's backend does, and waits for its address outside the gate. That wait, and the one for `rclone version`'s answer, end 2 minutes after the open began, well inside the use case's read timeout: an `rclone` that hasn't answered by then is killed and reaped, and the open fails (#326).

  Async code waits for the gate on tokio's blocking pool (`spawn_gate::hold_blocking`), so a start whose `exec` stalls never holds up the runtime's threads.
