### 4.4 Web UI (Leptos CSR)

This section decides which pages the web UI has, what each shows, and how the pages stay in step with the daemon.

Every page follows §4.5. Pages:

1. **Dashboard.** A card per machine: online status, last backup per plan (time, result, size added), next run, overdue plans and any running operation with live progress. A list of recent failures and warnings.
2. **Machine detail.** Plans, history timeline, logs and an agent settings summary.
3. **Plans.** The configuration's plans, created, changed and deleted (decision 96). Tags, label, the retry policy, an interval schedule (`every`), and "Import rustic profile…" and "Export as rustic profile" are **not yet built**.
   - **The list.** A table named by the page's heading: each plan's ID as the row's header, its repository, its next run (its words in a `<time datetime>` that carries the instant, as on the start page) and its **Change** and **Delete** buttons, named for it. A read again changes a row in place, so a focused button stays. **Add a plan** follows the table. A Columns button before it lets the reader hide and reorder its columns (§4.5, "The table"; decision 140).
   - **The form.** Its heading takes focus as it opens. The name comes first, for a new plan only, since it is the plan's ID; then the repository (a new plan starts with the first one listed); then four groups: what to back up (sources, globs, iglobs and exclude-if-present, each a multi-line field of one entry a line, and git-ignore, a checkbox), the cron schedule, the retention counts and the hooks, one command line a line. A setting with no field, such as a host, a time zone or a hook written as a table, is sent back as it came.
   - **No schedule.** An emptied cron field removes the whole schedule, and the plan then runs only when it is started. The field's hint says so, and the save's announcement says it again when a plan that had a schedule is saved without one.
   - **Saving.** A save closes the form, reads the list again and returns focus to the button that opened the form when focus has fallen to the page as the form closed, as it does from anywhere in the form (`components::recover_focus`); to the page's heading when that button went with a list that couldn't be read again (#869). A reader who moved focus out of the form while the plan was saved, to the navigation say, keeps it where they put it, and a form they opened meanwhile for another plan stays open (A1, #850). A scheduled plan's row then shows its next run once the scheduler has planned it (read again every 0.5 s, at most ten times). A refusal moves focus to the error summary, at its field, in the form's own words where it has them and in the daemon's otherwise.
   - **Closing without saving** returns focus to the button that opened the form, or to the page's heading when that button went with a list that couldn't be read again (#869).
   - **Deleting** asks first, in a review dialog that says the plan's snapshots stay in the repository, that nothing forgets them on its own any more (I6), and that a new plan with its ID would take them over.
   - **Answers.** A plan saved or deleted is answered in a `Success` toast after the page's introduction ("The plan demo-home is saved.", "The plan demo-home is deleted. Its snapshots stay in the repository."), said politely once, since once the form or the row has gone nothing else on the page says it happened (§4.5, "The toast"). A refused save or delete stays an alert, never only a toast.
   - **Refusals** are Error alerts in the daemon's words (§4.5, "The alert"): a list the daemon refuses in the table's place, a plan whose form it can't read after **Add a plan**, focus staying on the button pressed, each said assertively once; a refused delete inside the dialog, which stays open.
4. **Repositories.** Add or connect (local, SFTP, REST, S3, B2, rclone…), test the connection, init, and request a maintenance owner and set the maintenance schedule. Shows the repository ID, the granted owner and any rejected claim. Testing opens the repository and reports its ID; a write-permission check is **not yet built** (it belongs with the maintenance-owner work). A repository's stats are on the Snapshots page, with the rest of what is known of it (below, and decision 104).
5. **Snapshots.** Pick a repository, and its history is grouped by owner:
   1. A section for each plan of this agent (a table of its snapshots, newest first: the newest are listed and the rest counted; each time is the one the clock that took it read, with that clock's offset after it when the viewer's was at another then, §16 decision 56).
   2. **Orphaned history** (snapshots tagged for an agent or a plan this configuration does not have).
   3. **Unmanaged history** (snapshots no agent tagged).

   A group that a plan of this agent could take over has an **Adopt** button (§7.3); a group that none could take over says why: an orphaned group lacks the tag of an agent or a plan, or no plan of this agent could take it, and an unmanaged group has no plan that backs up the same host, label and paths. A repository no plan backs up to that holds nothing says that too.

   Above the history sit **Forget snapshots**, **Prune unused data** and **Check the repository**. Each of them, and each adoption, is first *reviewed* in a dialog that says what the run would do and names the snapshots it touches, and nothing changes until the review is confirmed.

   A repository this agent maintains that holds snapshots from other hosts (§3.1) says so before those buttons and in the review of a forget, an adoption or a prune, since another machine may maintain it too (§7.3).

   After those buttons, **Maintain from this agent** (or **Stop maintaining from this agent** when this agent maintains it) turns maintenance of the repository from this agent on or off, after a dialog that says what that means (decision 48). A repository this agent doesn't maintain shows its history without those buttons and says why.

   **Refusals** are Error alerts in the sender's words (§4.5, "The alert"): a list of repositories the daemon refuses where the repositories to pick from would be, a refused read of the history, a refused maintenance request or a refused cancel after the maintenance buttons, and a refused read of the stats in their section, each said assertively once; a refused change of who maintains the repository inside its dialog, which stays open.

   A snapshot's ID in its row is a link to the snapshot's own page, `/snapshots/{alias}/{snapshot}` (built; §16, decision 102; `crates/web/src/components/tree/rules.rs` decides, `snapshot_page.rs` is the glue). Its heading names the snapshot by its short ID and the repository by its alias, and below it the snapshot tree (§3.1) is a tree (§4.5) named "Folders and files": each row is an entry's shown name, then what it is (a folder, and whether it is being read, empty or could not be read; a file and its size; a link; a device, pipe or socket) and when it was modified, as its description.

   The shown name is the name as the file system wrote it, as `rustic ls` prints it, with a control as its Control Picture (`new␊line.txt`) and a bidirectional control or a line separator as its code point (`abc[U+202E]txt.exe`); type-ahead searches it. Each page entry carries it as `display` beside `name`, rustic's escaped form, the key a folder's `path` joins.

   Each folder is read from the repository (`GET /api/v1/repositories/{alias}/snapshots/{snapshot}/folder?path=…&from=…&limit=…`, which an API token reads with the permission Snapshot contents, decisions 93 and 127; `limit`, clamped to 1..1,000 and a full page when not given, is for a program such as the MCP server, and the page never sends it) the first time it is opened, a page of up to 1,000 entries at a time; a folder with more ends in a **Show more: 1,000 of 4,210 shown** row that reads the next page and moves focus to its first entry. A refusal (the snapshot forgotten since the list was read, the repository out of reach) is an alert under the tree; a refused first page leaves the folder closed, to be asked again when it is next opened. A snapshot that is gone shows its alert in place of the tree.

   Filtering by host, label, tag, plan or path is **not yet built**. A pane beside the tree follows the entry it selects (`Tree selected=`, `tree::Selection`) and holds the actions for it in one action row, **Restore** (its Filled Primary, with the RotateCcw icon) then **Download** (Outlined), each named for the entry.
   - **Download** (built; §10.4, decision 114; `crates/web/src/download.rs` decides, `snapshot_page.rs` is the glue). The pane's **Download demo-1.txt** button opens a review dialog titled the same: for a folder a radio group **Archive format**, **Tar (.tar)** (checked) or **Zip (.zip)**, which says neither compresses; then the step-up field (§4.5) and a **Download** button, the dialog's Filled Primary confirm. On the hub this will use the hub's own repo access and work only for hub-managed repos.

     **Download** posts `POST /api/v1/repositories/{alias}/snapshots/{snapshot}/download` with `{path, format: "tar" | "zip", confirmation}`, which answers `201 {ticket}` once the worker has found the entry. The dialog then closes, a `Primary` toast after the pane's buttons says "Download of demo-1.txt started. The browser saves it with its other downloads.", said politely once, and the page sends the browser to `GET /api/v1/downloads/{ticket}` (`location.assign`), whose attachment the browser saves as any download, under the name `Content-Disposition` gives (a file's own, a folder's with the archive's extension, the top's `<host>-<short ID>`); the page itself stays. Both routes take a browser session only.

     A wrong confirmation is the field's error, as a restore's; any other refusal is an Error alert in the dialog (§4.5, "The alert"): `downloads-busy` (409), `downloads-unavailable` and `restart-pending` (503), `snapshot-unknown` and `entry-unknown` (404), and those of a read of the repository. A ticket fetched twice, or after its minute, is `download-unknown` (404). That refusal is no attachment, so a browser sent to it shows its JSON in place of the page; the page sends the browser to its ticket at once, so only a ticket opened again, by hand or from the browser's history, comes to it.
   - **Restore** (built; §10.4, decision 109; `crates/web/src/restore.rs` decides, `snapshot_page.rs` is the glue). The pane's **Restore demo-1.txt** button, named for the selected entry, opens a review dialog titled the same: a radio group **Where to restore**, **Into a new folder** (checked; under the agent's restore folder, `<host>-<snapshot-short-id>-<timestamp>/`) or **Over the original files**, the step-up field (§4.5) and a **Restore** button.

     Choosing the original files asks for a dry run (`POST /api/v1/repositories/{alias}/snapshots/{snapshot}/restore/preview` with `{path}`, answering `{added, overwritten, unchanged, kept, bytes}`), whose counts the dialog says in a polite region of its own ("0 files added, 0 overwritten, 1 left as it is. Files the snapshot doesn't hold stay."). Until it has answered with them, **Restore** is held (the review dialog's `held`, §4.5) by "Restoring over the original files waits until the dry run says what it would change.", or, when it couldn't be read, beside the refusal's Error alert, by "The dry run couldn't be read, so nothing is restored over the original files. Read it again, or restore into a new folder." A **Read the dry run again** button, there while the original files are chosen and unavailable while the dry run reads, asks again and clears that alert.

     **Restore** posts `POST /api/v1/repositories/{alias}/snapshots/{snapshot}/restore` with `{path, destination: "new-folder" | "in-place", confirmation}` and answers `202 {operation, folder?}`: `folder` is the full path of the folder made for a restore into a new folder, absent in place. Both routes take a browser session only: no API token scope reaches them (decision 93). A wrong confirmation (`step-up-failed`) is the field's error inside the dialog, which stays open with the field marked invalid; any other refusal, a sign-in wait included, is an Error alert there (§4.5, "The alert"), from its code's message. The refusals are §10.4's: `restore-folder-unset` and `restore-running` (409), `restore-in-place-not-here` and `restore-hub-not-allowed` (403), and those of a read of the repository.

     Once started, the dialog closes, a `Primary` toast after the pane's buttons says "Restore of demo-1.txt started.", said politely once, and the page watches the operation to its end, on whatever page is then shown: assertively when it failed, politely otherwise, and when the daemon stops answering it says the Operations page will show the end. A restore into a new folder that finished or was cancelled names that folder ("Restore of demo-1.txt finished. Its files are in …"), so the person knows where its files went; a failure sends them to the Operations page. Dismissed, the toast hands focus back to **Restore demo-1.txt**, and a download's to **Download demo-1.txt**.
6. **Operations.** A searchable history with full logs, warnings and a cancel button.
7. **Settings.** Auth, hub pairing, notifications, what AI agents may do without a token (decision 127), the allowlist of folders a dry run may read (§16, decision 89), the language of the web UI (decision 101), the width of its pages and a restart of Ladderback (decision 94).
   - **Tabs** (built; #935; `crates/web/src/settings_tabs.rs` decides, `settings.rs` and `page.rs` are the glue). Each section below is a tab of its own, in that order, on the shared `Tabs` (§4.5), named by the page's `<h1>`, `Responsive`: a column beside the section where the page has room (the Narrow page width at 1280 px), a row above it where it hasn't (320 px). Each tab's words are its section's heading, which the panel keeps. The admin password's and the signing-in tabs show only where their sections do. The first tab is selected as the page opens, unless the address names another.

     Each tab has an address, `/settings#` and its section's name: `language`, `page-width`, `admin-password`, `signing-in`, `api-tokens`, `ai-agents`, `dry-run-allowlist` or `restart`. Opening it starts the page on that tab; any other fragment starts it on the first. Choosing a tab replaces the address's fragment with its name (`history.replaceState`), so loading the page again, as saving the language does, comes back to the same tab, and Back doesn't stop at each tab shown.

     While Settings is open, a change of the fragment alone (a `hashchange`: one typed in the address bar, a bookmark to another tab opened from Settings, or Back to the address before) chooses the tab it names, and no fragment the first, as the page opens; a fragment that names no tab shown leaves the tab as it is (`settings_tabs::tab_named`), so a tab's address always shows that tab (#1030). Focus stays where it was; focus inside the panel hidden goes where the browser puts it, as for any element hidden. No element of the page has a tab's name as its `id`: Chromium takes focus from where it was when the fragment changes to an element's `id`.

     A panel with a control is no Tab stop of its own; the restart's, whose button shows only where a service manager runs Ladderback, the dry-run allowlist's, whose controls show only once the daemon has read the list, and the signing-in and API tokens' with sign-in off, which hold only words then, are (`Holds::Text`). A dialog that opens once the daemon answers, as a new token's does, shows its own tab first if the reader has chosen another meanwhile. Only how a section is reached changed: each one's journeys, words and announcements are as before.

   - **Language** (built; §8.4, decision 101; `crates/web/src/language_choice.rs` decides, `settings/language.rs` and `page.rs` are the glue). The first tab, its section's `<h2>` "Language": a radio group **Show Ladderback in** offers **The browser's languages**, chosen until another choice is, then each language the build offers, named in itself and marked with that language and its direction (`RadioGroup`'s `label_languages`); a development build adds both pseudolocales. Its hint says the choice is kept in this browser.

     **Save the language** keeps the choice in the browser's local storage (the browser's languages forget it), then loads the page again at `/settings#language`, so the whole page is shown in the language from its start, on the Language tab, and focus comes back to the section's heading (§4.5, "Route changes"). A browser that refuses to keep it says so in an Error alert under the button ("This browser didn't keep the language."), said assertively too, and the page stays as it was.
   - **Page width** (built; #933; `crates/web/src/page_width.rs` decides, `settings/page_width.rs` and `page.rs` are the glue). The section after Language, its `<h2>` "Page width": a radio group **Width of each page** offers **Narrow**, chosen until another choice is, and **Full width**. Narrow centers the page's content at up to 60rem, as every page was before the choice; Full width lets it use the window's width, tables included, while each paragraph and form in `<main>` stays at up to 70 characters (`70ch`), a readable line (DESIGN.md, "Layout"). At 320 px both fill the window.

     The choice is a viewing preference of one browser and its screen, so, like the language, it is kept in the browser's local storage (`ladderback-page-width`: `full`, or nothing for Narrow), never by the daemon, and anything else kept there is Narrow. It applies from the page's first render and as soon as a radio is chosen, with no button and no reload, which the hint says; moving between the radios with the arrow keys chooses as it goes (§4.5). A browser that refuses to keep it says so in an Error alert under the group ("This browser didn't keep the page width, so the page stays as it was."), said assertively too, and the page and the group keep the width in effect.
   - **API tokens** (built; §10.1, decisions 93 and 127; `crates/web/src/api_tokens.rs` decides, `settings.rs` is the glue). A section of its own, its `<h2>` naming the table: Label (the row's header), Permissions (each permission the token holds with its level, "Backups: Read", one said as it is, several as a list, #430), Created, Last used (in words counted back on the browser's clock: "Never", "Less than a minute ago", "3 hours ago", the instant in a `<time datetime>`), and a **Change permissions of token nightly-mcp** and a **Revoke token nightly-mcp** button per row. The table has the Columns panel (decision 140).

     Revoking is confirmed in a review dialog (Cancel first, **Revoke the token** to confirm, "Revoking the token…" while it goes); once revoked, the row goes, focus moves to the section's heading and a `Success` toast after the section's introduction says "Token nightly-mcp revoked.", said politely once.

     Changing a token's permissions opens a review dialog, "Permissions of token nightly-mcp", starting on Cancel: a group per permission, as the form below has, at the token's permissions, the **Admin password** field and **Save the permissions** ("Saving the permissions…" while it goes), through `PUT /api/v1/tokens/{id}/permissions`. Once saved, the dialog closes, focus goes back to the row's button, the row lists the new permissions and a `Success` toast says "Token nightly-mcp has its new permissions." A wrong password is the field's error and the dialog stays open; Cancel or Escape keeps the permissions as they were.

     The form under the list takes a label (spaces around it dropped; the daemon judges its 64 characters) and the token's permissions, in a `<fieldset>` "Permissions": a radio group per permission, named by it, offering No access and the permission's one level, its hint saying what it opens in plain words. Backups' hint says it opens neither the files inside a snapshot nor the daemon's log, each a permission of its own. The groups start at a new token's defaults: Backups, Backup runs, Previews and Configuration. A form without a label or with every permission at No access, and any refusal (`api-token-label`, `api-token-no-permission`, the 100 kept, `api-tokens-unavailable`), moves focus to the error summary.

     A created token opens a dialog that says it is shown this once, holds its whole text in a read-only field that can be selected by hand, and starts on **Copy the token**, which writes it to the clipboard and says so in the dialog's own polite region (or says to copy it by hand where the browser has no clipboard, as over plain HTTP to another machine); leaving the dialog, by Close or Escape, clears the text from the page's state and returns focus to **Create the token**.

     With sign-in off the daemon refuses the list (`409 sign-in-off`) and the section says why, with no form; a list it can't read (`503`) is said calmly in its place.
   - **AI agents** (built; §10.1, decision 127; `crates/web/src/api_tokens.rs` decides, `settings/ai_agents.rs` is the glue). A section after API tokens, its `<h2>` "What AI agents may do without a token", shown with sign-in on or off: the `[without-token]` table, through `GET` and `PUT /api/v1/settings/without-token`. It says what these permissions limit, `ladderback mcp` in a session of its own and connected while sign-in is off; with sign-in off, it adds that any other program may use Ladderback all the same, and recommends turning sign-in on.

     Once the daemon has read the table, the section holds a group per permission, as the token form does, then, with sign-in on, the **Admin password** field, and **Save what AI agents may do** ("Saving…" while it goes). A save kept is a `Success` toast, "AI agents without a token now have the permissions you chose." A wrong password is the field's error; a read or a save the daemon refuses, or doesn't answer, is an Error alert. Once the table is read the panel is `Holds::Controls`, so its first choice is the stop after its tab: the panel is taller than a window, so a Tab stop on it couldn't be in sight. Until then, and after a read refused or unanswered, it holds words alone and is `Holds::Text`, a Tab stop of its own.
   - **Dry-run allowlist** (built; decision 89, point 13; `crates/web/src/dry_run_allowlist.rs` decides, `settings/dry_run_allowlist.rs` is the glue). A section after AI agents, its `<h2>` "Dry-run allowlist", shown with sign-in on or off: the folders a plan dry run an AI agent asks for may read, which only a person sets, through `GET` and `PUT /api/v1/settings/dry-run-allowlist`. It says what a dry run tells the AI agent (counts and sizes, never a file's name), then lists the folders in the shared `Table`, named by that heading, each folder the row's header (isolated with `<bdi>`, so a path reads left to right in a right-to-left language) and a **Remove** button named for it.

     An empty list says a dry run the AI agent asks for refuses every source until a folder is added. A read the daemon refuses, or doesn't answer, is said calmly in the table's place, as the API tokens' is, with no button and no form.

     **Remove** asks first in a review dialog named for the folder (Cancel first, **Remove the folder** to confirm, "Removing the folder…" while it saves), saying the AI agent's dry run can no longer read it and that the folder, the plans and their backups don't change. Removed, the row goes, "Folder … removed from the dry-run allowlist." is said politely, and focus moves to the section's heading.

     The form under the list takes a folder's full path (spaces around it dropped) with **Add the folder**: nothing typed, or a folder the list holds already, is the field's error before anything is sent. The daemon judges the rest. Its refusal of a folder that isn't a full path (`dry-run-folder-invalid` of the folder typed) is the field's error too, said assertively: it names the folder as typed and suggests a full path, the home folder's Documents. Any other refusal is an Error alert after the form, said once, in words that name no control the page hasn't (`dry-run-allowlist-too-long` in the page's own). Focus stays where it was, and the field keeps what was typed until that folder is added.

     Each change saves the whole list, so one save goes at a time: while it does, **Add the folder**, **Add home folder** and each **Remove** are busy, still in the Tab order, and take no press. A dialog's confirm button stays busy until the dialog has closed.

     **Add home folder**, shown while the daemon names a home folder the list doesn't hold, opens a review dialog before it adds anything: it warns that an AI agent could then count the files under the whole home folder, `~/.ssh` and browser profiles included, learning only counts and sizes, never a name, and suggests a narrower folder, such as one a draft plan backs up. Cancel comes first and takes focus, so a stray Enter backs out; **Add the home folder** adds it, and focus moves to the section's heading, since the button has gone. A folder typed that is the home folder or holds it, compared as text (`/` holds every one), opens the same dialog; leaving it, or adding the folder, returns focus to the Folder field.
   - **Restart** (built; decision 94; `crates/web/src/restart.rs` decides, `settings.rs` is the glue). A section after the dry-run allowlist, its `<h2>` "Restart Ladderback". When a restart is offered it says what one is for, with a **Restart Ladderback** button; when none is, it says no service manager runs Ladderback and to install the service, with no button.

     The button reads the route, then opens a review dialog, "Restart Ladderback?", which says how many operations are running and that queued ones run once Ladderback is back. Cancel comes first; then **Restart** with none running, or **Restart once they finish** and **Restart now**, which stops them. "Asking Ladderback to restart…" while the request goes; a refusal is an alert in the dialog.

     A restart that waits leaves the section saying so in its status, with a **Cancel restart** button, and the section reads the route every second until the restart comes or is cancelled. Once the daemon begins to restart, the status says "Ladderback is restarting. This page reloads once it answers again." Each new status reaches screen readers through the page's polite region, not a status region of its own. The page asks every 250 ms, with 2 s of patience, whether the daemon answers, and reloads once it has seen it go down and answer again. Only Ladderback's own answer counts, the session's JSON or one of its refusals (`restart::is_ladderback`): a reverse proxy's 502, 503 or 504 for the daemon that is down doesn't. After a minute it says where to look and goes on asking.
8. **Pending changes.** Proposals waiting for a person, with a count in the navigation that is part of the link's accessible name and reaches screen readers through the announcer (A2, A3): the summary Ladderback writes from the changes, the exact `config.toml` diff, the forget preview, any maintenance claim and each command with its own tick; approve with step-up, or reject with a reason per change (§16, decision 89).
9. **Log** (built; #618, decision 111; `crates/web/src/daemon_log.rs` decides, `daemon_log_page.rs` is the glue). The **recent log** (§3.1) on a page of its own at `/log`, which a **Log** link in the navigation, before Settings, leads to.
   - It reads `GET /api/v1/log` once as it opens, saying "Loading…" until the answer comes, and lists the lines newest first in a table its heading names, with the columns Time (UTC) (the instant as the log writes it, in a `<time datetime>`), Level, Source and Message; the source and the message are marked `lang="en"`, the words the log wrote. A Columns button before the table lets the reader hide and reorder all but the time (decision 140).
   - A radio group **Show** narrows the table to **All levels**, **Warnings and errors** or **Errors only**, in the browser (the recent log holds at most 1 MiB of text): only the table follows the choice, so focus stays on the radio button moved to, and a choice that keeps no line says so in the table's place.
   - **Copy for a bug report** puts the lines shown on the clipboard, newest first and narrowed as shown: first `ladderback <build>` as `--version` prints it, from the build the daemon told the page (decision 90), left out while the page hasn't been told it, then each line as the log writes it, `[<time> <LEVEL> <source>] <message>`. Once copied, a `Success` toast after the button says "Copied the lines shown.", said politely once, and focus stays on the button; a copy the browser refused is an `Error` toast there instead ("The browser would not let the page copy the lines. Select them in the table and copy them yourself."), said assertively once, which stays until dismissed.
   - A read the daemon refuses (it couldn't read its sessions, say) is an Error alert in the lines' place, in the daemon's words, and said assertively (§4.5, "The alert"); one that doesn't answer is said as on every page, the heading saying Ladderback can't be reached.

Live updates come from one WebSocket per tab carrying `UiEvent` (operation started/progress/finished, agent online/offline). The page fetches initial state over REST. The daemon forwards an operation's warning events to subscribers unchanged, and its progress events as `LiveProgress` shows them (below): coalescing happens once, in the worker (§4.1), and the daemon never re-coalesces. A hook's warning is published by the daemon itself as the hook ends, in every phase, once the operation has kept it, with the phase and, for an exit, the exit status, never what the hook wrote (#369). A program whose API token lacks Snapshot contents is told the event without those arguments, as it is told every warning and failure (`event_shown`): it hears that a hook warned, and reads the phase from the operation's detail, where a warning's `during` is kept for it; it isn't told which before-hook stopped a run.

Progress bars are stateful per key on the way out (`app::progress::LiveProgress`): a page is told of the bar the engine began last that is still open, with its **step** (§3.1), as `operation-progress` with `step`, `current`, `total` and `unit`, what the bar counts: `bytes`, or `count` for a counter or a spinner, and `count` when a daemon older than the field leaves it out (§16, decision 83) (`Begin` publishes 0, `Advance` adds, `Length` sets the total, a title names the step; a change to an older open bar, or a finished bar, publishes nothing), so a page sees current-of-total numbers of one step, not deltas. Each carries `at`, the RFC 3339 instant the daemon heard the report, which the page shows of a bar without a percentage (decision 83, item 7).

The engine adapter maps rustic's text for a bar to the step; the text never leaves it, and a text it doesn't know is no step (§16, decision 82).

How an operation started and how it ended are not the worker's to announce but the run's that records them (decisions 41, 68).
- It publishes one `operation-started` once the log has the write that says the operation is running, with the log's start time, so a page that reads the history on hearing it finds the run there; a maintenance run, whose `start` already wrote it running, publishes it once as it begins its jobs, however many it takes.
- It publishes one `operation-succeeded` or `operation-failed` after its last write to the operation log, from the operation as it ended and after its ending hooks have run, so a page that reads the history on hearing it finds the end there.
- A write the log refused, or gave up on after `SAVE_BOUND` (§9), does not hold either announcement back: the history then shows the operation as the log last had it, and the run's `Finished::recording_errors` holds the write.
- A cancelled operation announces no end, and one cancelled before the log had it running announces no start either; a run of several engine jobs announces once.

A job that is no operation (the repository's ID, a snapshot list, the groups, a preview, initialising a repository) publishes nothing at all, no start, end, progress or warning (#308): the history has no row for it, and a run that reads first keeps none of what its read said.

The events WebSocket answers a client's ping with a pong, so a live page survives an idle network.

**Settled in the live-pages build** (`crates/web/src/backend.rs`, `ws.rs`, `operations_page.rs`):

- **State model.** Each live page holds its state in one `RwSignal`. The operations page's is `OperationsState`: the history rows (newest first) plus the live progress of a run still going. The initial REST fetch builds it; every `UiEvent` is applied to it by a pure function (`apply`) in the host-tested module, so a missed event cannot be represented wrongly; an event about an operation the state doesn't hold is ignored — the reconnect's re-fetch brings the whole story, never a half-invented row.

  Nor does an event take a row back, whatever order it and a read of the history arrive in: a start moves only a queued row, and progress and warnings reach only a row that has not ended.

  A run that warned on its way to the end becomes `succeeded-with-warnings`, not a plain success. A `failed` event keeps its typed code for rendering through the catalog.
- **Reconnect and merging.** The socket dropping is a failure like any other: after `reconnect_backoff(attempt)` (doubling from 1 s, capped at 30 s) the loop re-fetches the whole history and resumes the stream; a fetch that fails leaves the page in `Phase::Unreachable` and the loop keeps trying, so a daemon that comes back is a page that heals.

  Each stream that opens, the first and every reconnect's, reads the history once more (decision 68): the page hears nothing told before its stream opened, such as the start of a run its first read had queued (#305). The first read does not wait for the stream, and events heard while the later one is out are applied as they come.

  The re-fetched page is `merge`d: the store's page is the truth for what it holds, but a status an event advanced is never regressed (the store can answer with what it held before news the stream has told since, and an end event can beat it when the log lost its final write), and a live row the page doesn't hold yet stays, newest — dropping it would unshow a run the reader is watching.

  At the stage the page's row already has, a run still going keeps its status, start and progress as the events left them and gains the warning codes the store has and the row lacks: mid-run, that is a before-hook's warning told before the page's stream was open (#328, #369) or a secret file other users can read that the run's start met (#386), which no event tells and the run's start write puts in the store; a run's other warnings reach the store only with its end.

  A row the read moves on, from queued to running or from running to ended, takes the store's row and keeps each warning code the page heard that the store lacks. A row names each code once, as the history does (#508), so a code is added only when the row lacks it: the store's first, in the order the first warning of each was recorded, and those only the events told after them.

  A run that ended takes the store's end whole, which has every warning (so `succeeded-with-warnings` where the end event left `succeeded`) and the result an end event doesn't carry; the status's change is no second end, so nothing more is announced.
- **Settle-poll.** A start announces "Backup started." at once, then polls the history until the operation ends (120 s, every 250 ms), merging each page: the first `UiEvent` may lose the race with the announcement, and a cancelled run emits no `UiEvent` at all. A cancel does the same, without an announcement of its own. A poll that runs out of its budget without an end says so in a `Primary` toast after the start buttons, said politely once ("Still waiting for Ladderback to say how the run ended.", #983), so no reader, sighted or not, is left watching a row that quietly stopped moving; the connection's own loop keeps the page healing behind it.
- **Leaving the page (#300).** The connection, its reconnects and re-reads, and every settle-poll last as long as the reader's visit to the page and no longer: the page begins a `visit::Visit` as it is built and ends it as it goes (Leptos's `on_cleanup`), and each of those tasks runs through `Visit::during`, which ends it at its next await, whether it is waiting on the stream, on a read, or out a back-off or a poll's pause.

  The task is dropped there, and the events stream it holds closes with it; a task the end finds ready to go on goes no further, so nothing is applied to a page that is gone, and a settle-poll that ends this way says nothing. Coming back builds the page again, with one stream of its own. A pause is the page's too, and ends with it (§4.5, "Live updates").
- **Announcements.** The end of a run (finished, cancelled, failed — failed assertively) is announced from a status-transition effect over the state, not from the code path that happened to see it, so the events stream and the settle-poll both arrive at exactly one announcement. It names the kind of run that ended ("Check finished.", "Backup finished."), so a check's end is never told as a backup's.
- **Rows (#192).** The first column is Operation, and each of its cells is its row's header (`<th scope="row">`): a backup is named by its plan, a maintenance run, a restore or a download by what ran and the alias of the repository it ran on or read ("Check of demo", "Restore from demo", "Download from demo", #893), or by what ran alone when the log kept no alias ("Restore", for a restore an earlier version logged). Its Cancel button and its progress bar are named the same way ("Cancel the restore from demo", "Restore progress from demo"), and so is the announcement of its end ("Restore finished.").
  - A restore the log kept the entry and the target of (#813) is named by both instead, with its repository: "Restore of /home/docs from demo to /srv/restore/laptop-3f2a1b4c" for one into a new folder, "In-place restore of /home/docs from demo" for one over the original files. Its Cancel button, its progress bar and its end follow ("Cancel the in-place restore of /home/docs from demo", "Restore of /home/docs to /srv/restore/laptop-3f2a1b4c finished."), so two restores of one repository, or of one entry, read apart.

  The Result column, before Actions, lists what a succeeded run produced (a backup's short snapshot ID, its files, the source it went through, what it added and how long it took; a check's findings; the count a forget, a prune or an adoption reached) and, for a failed run, says first why it failed: its `failure` in the catalog's words, the engine's own marked as English (`lang="en"`, WCAG 3.1.2), as the alert of a refusal says them (#474). It is empty for any other row.

  One item alone, such as a failed run's reason with nothing after it, is said as a sentence, and two or more as a list, one an item (`Said` in `operations.rs`): a list of one is heard as a list and draws a marker that sets nothing apart (#430).

  A placeable in an item (a path, an address, a snapshot's ID: `runs` in `repositories.rs` finds each between the catalog's isolation marks) is a `.placeable`, an inline block that moves to the next line whole rather than breaking where a line runs out ("home-" / "laptop.password"), and breaks inside only when it is wider than the cell, then first after a separator (`address_parts`, a `<wbr>` after each part).

  The table takes its name from the page's heading (`aria-labelledby` the `<h1>`, whose `id` is `page-heading` on every page), not from a caption that said "Operations" again under the heading (#431).

  A run whose choice used one of several locations says so after that, whatever became of the run, a failed one included: "Used location 2 of 2: rest:https://backup.example.net/laptop", the address as the run recorded it with credentials masked (decision 80; the earlier locations and their outcomes are in the summary's `locations`, which no page shows until an operation detail view exists). Each Cancel button names the run it stops.

  A restore's or a download's Result names first the entry of the snapshot it read, whatever became of the run: "Entry /home/docs/notes.md", by its path from the snapshot's top (`/` is the top), as the log keeps it (`entry`, §9): each name as the snapshot's tree shows it (rustic's escaped form undone, its controls made visible), masked of the repository's secrets (I4), and, when longer, cut to at most 1,024 bytes, its end after "…", so the entry's own name stays (#847).

  A backup the schedule started that was refused before it ran (§5) is a failed row like any other: its Started cell is the moment it was refused, the time it was queued, as it never started, and its Result says why as the refusal of a run by hand does: the refusal's code, its arguments, and what a platform or a command said as the detail, masked of the repository's secrets (I4).
- **Re-read on an end.** An end event carries no result, and the run tells of its end only after its last write to the log, so the page reads the history again when an end arrives (`backend::asks_for_a_reread`) and merges it, and the row's Result shows without a reload; a run started elsewhere, which the page did not hold, comes in with it.

  One re-read is out at a time (`backend::Rereads`), across the stream's reconnects too, and the read a stream's opening asks for is one of them: ends and openings that arrive while one is out are owed one more after it, and only one, so no run of reconnects has more than two reads waiting.

  A re-read that gets no history (a refusal, no answer, or none within `backend::REREAD_PATIENCE`, 10 s, after which its fetch is aborted) is tried again after 1, 2 and 4 s, and then left to the next end or the next reconnect's re-fetch.

  Its `@ui` journeys play the daemon, so an end reaches the page after the page is listening, one holds a re-read's answer back while the stream drops and another run ends, and one holds the stream's opening back while a run starts.
- **Sort.** The history arrives newest first; that is the default. The sort button cycles newest → oldest → newest, and each press is announced politely. A first press announces *newest first*, because the page's default is the daemon's order, not the button's. The Started cell's words are the instant through the catalog (`DATETIME($when)`, `ui-instant`), in a `<time datetime>` that carries the raw RFC 3339 instant, so the order is testable without the locale's text and nothing about the time hides in a `title` (#851).
- **Starting a plan.** The page has a start button for each plan, named with its plan ("Start backup of demo-home", one message with the plan as its argument), as a row's Cancel is ("Cancel demo-home"). Each is an Outlined Primary `Button` with the Play icon, busy while its start's request runs; a row's Cancel is a Small `Button` of words alone, busy while its cancel's request runs.

  A row's Cancel shows "Cancel" alone (`ui-cancel`), the word its name begins with (2.5.3), so it takes one line in the 8rem Actions column at 1280 px (#430). A reader tabbing through the plans hears which one each button runs (2.4.6, 4.1.2), and the visible label is the name (2.5.3).

  The buttons are one row of actions (`.actions`, drawn only when there is a plan), so each stands apart from the next by the row's gap rather than touching it, and on a small screen with larger text they wrap one under the other (#284).
- **Stable table and rows (#124).** The history is the shared `Table` (below): built once, its rows keyed by their operation's id and following the state in place, so an update to a row never replaces a control a reader has focused (2.4.3), and a row that moves, as a sort or a run joining the history moves it, gets its focus back. A progress report, a start or an end changes what a row's cells bind to, never the table; the Cancel button and the progress bar are present or absent by a memo of a boolean, and an ended run loses its button because it is no longer a control. The decisions (`shown`, `progress::percent`, `badge_of`, `OperationsState::row`) are pure and host-tested.
- **Stable columns (#194).** Its columns have the shared table's fixed widths in rem (Operation 8, Status 9.5, Started 11, Result 20, Actions 8: 56.5rem, inside the page's 58rem at 1280 px, so nothing scrolls there), so a run that starts, shows its progress and ends changes what its row says, not where the columns are, and a wide page shares its spare width among them in proportion. Where they are wider than the page, as at 320 px or with 200 % text, the frame scrolls sideways and the operation's name stays pinned at its start, rather than words breaking to fit (#524). The progress bar fills its cell, up to 16rem, rather than setting the cell's width.
- **Columns the reader chooses (decision 140).** A Columns button, after Mark all as seen and before the table, opens the panel that hides, shows and reorders every column after the operation's. Hiding Status sees its change marks, and marks nothing while it is hidden: no mark stands for a column the reader can't see.
- **Unreachable and loading.** `Phase::Unreachable` replaces the page's `<h1>` with "Cannot reach Ladderback" (the page is already open in the browser the daemon served, so this is a state of the page, not a navigation). `Phase::Loading` shows "Loading…" until the first answer arrives, just before a busy region holding the still shape of what is coming (the skeleton's notes in §4.5, "A page's first load"); the `@ui` loading scenario covers it by delaying every `/api/v1/` answer (the world's `answerDelayMs`, set by a Given that names the seconds), and that scenario is the phase-2 guard-class addition §13 asks for.

Only the daemon's answers are played: the page is the real one, and a request the script doesn't answer (a start or a cancel, unless a step has the script queue the backup or accept the cancel itself) goes on to the real daemon.

- **Errors.** A form missing what its button needs, and any refusal, move focus to an error summary: an `<h2 tabindex="-1">` ("There is 1 problem with the form") over a list of the problems. A problem about a field links to it, the link moves focus itself (the router would take the click and only scroll), and the field shows the same text with `aria-invalid`; a refusal about the repository (it would not open, it exists already) has no field and is plain text, a refusal of the credentials that names the hot or the cold half included (decision 112). The engine's own words in a sentence are in a `<span lang="en">` (3.1.2), and a repository that would not open is followed by the page's own advice. The summary is not a live region: focus tells the reader.
- **Results.** A test, a connection and a creation say what happened in the page ("The repository opens. Its ID is …") and politely through the announcer, without the ID, a long run of digits a screen reader would spell out. A request that takes the engine a moment says so; meanwhile the pressed button is busy and the other two are unavailable, so no second request starts.
- **What stays in the fields.** A failure keeps everything typed, the password included, so nothing is typed twice (3.3.7). A test keeps it too, since the next step is to connect. A saved repository, connected or created under a name, clears the form, turns the checkbox off again and reads the list again. The password is never shown after it is typed (I4): the field is a password field, the value lives only in the page's signal, and nothing the page shows or announces is built from it.
- **Where a typed password goes.** A radio group under the password field (`RadioGroup`, legend "Where to keep the password") offers **In the configuration file**, chosen first, and **In the system keyring** (decision 110); its hint names the entry, `ladderback/` and the repository's name. The form reads the group's choice when it is sent. A saved repository sets the choice back to the configuration file.
- **What each choice keeps.** In the configuration file, the daemon saves the password inline in `config.toml`, written 0600, and so it is in the copies of earlier versions of the file that a save keeps in `history/` (ten at most, also 0600, §6.1). The config folder is 0700 when the daemon creates it and is left as it was when it exists. In the keyring, the request carries `keep-in-keyring` (only with a name: creating without one keeps the password nowhere), and `config.toml` holds only the reference. A keyring refusal is a problem about the password field.
- **Left out, on purpose.** The `command` password source (see the API above); editing a backend's options (the API accepts them, the form does not); offering Create for no repository at a REST, rclone or remote OpenDAL location, which can't be told there from one that is out of reach (decision 53: only an empty local or OpenDAL `fs` folder fails `repository-not-found`; any other place with no repository config fails `repository-config-not-found`, decision 112); marking the hot or the cold half's field when its server refuses the credentials (decision 112); the maintenance schedule, asking for the hub as maintenance owner, changing who maintains a saved repository, and the write-permission check (later milestones). A repository's stats are on the Snapshots page (M3, decision 104).
- **Contrast.** The form error's color on the page background (the Error pair's words, `--error-fg`), links on the surface and page backgrounds, and the table's rule are pair-checked by `just test-contrast` along with the badge and status pairs.

**Settled in the maintenance build** (`crates/web/src/maintenance.rs` and `wording.rs` for the decisions, `snapshots.rs`, `components.rs` and `ws.rs` for the glue):

- **Where it lives.** Every decision is in a host-tested module. `maintenance.rs` holds the requests, the review a preview becomes, the sizes of the lists (`Rows`), what the page shows of a history (`shown`), the panel of a run (`Panel`: what the page asks, shows, says and does next, as a state machine over what happens to it) and the wait for a run (`Watch`, `poll_delay`).

  `wording.rs` turns each into the catalog's messages: one message for each caption or label, with the names, counts and kinds passed as raw arguments and chosen by the catalog's selects and plurals, never joined or inflected in code. `snapshots.rs` only draws what they decide and sends what they ask; it is left out of mutation testing, and `.cargo/mutants.toml` says exactly what stays in it.
- **The history.** It shows "Loading…" until the first answer. A repository that holds nothing says so ("No snapshots yet."), and a forget of a repository no plan backs up to opens a review that says why it has nothing to do, with a Close button and nothing to confirm. Picking the repository that is already shown reads its history again without building the page anew, so a run on the page stays on it, and the page's heading recovers when a later answer succeeds after one that failed.
- **The review.** An adoption, a forget, a prune and a check each ask the daemon for a preview first. The review is its answer: what the run would do, the snapshots it names, what it leaves alone, what it warns of (the other hosts of §7.3) and the selection that confirming sends back. A warning is part of what the dialog is described by, after the facts, so a screen reader reads it on entry. A refusal of the preview is an alert in the page, in the page's language, with the engine's own words in a `<span lang="en">` (3.1.2). The run is started with the selection the preview named, so what was reviewed is what runs.
- **Every wait is told.** The request of a preview says "Preparing the review…" (polite). Starting a run says "Starting the forget…" in the page and in the dialog; the dialog holds still while it does (see the review dialog under the component build), and the announcer holds its messages while a modal is open, so a polite region inside the dialog says it too. A run that is going says "A forget is running." (polite), and its end says how it ended (a failure assertively) and has the page read the history again.

  The wait polls the run every 250 ms for twenty reads, every second up to the eightieth, then every five seconds, and gives up after seven failed reads in a row; it then says the page stopped watching, that the run goes on and that the Operations page shows how it ends, never "still waiting" and silence. The end of the last run is cleared once another review is asked for.
- **Focus.** Closing a review returns focus to the control that asked for it; when that control has gone with the run (an adopted group's button goes with the group), focus goes to the maintenance heading. It never falls to `<body>`.
- **Who maintains it.** After the maintenance buttons, the repository's page has one button whose words follow whether this agent maintains it, **Maintain from this agent** or **Stop maintaining from this agent** (decision 48). It opens a review dialog, Cancel first, that says what that means: only one place may maintain a repository, or backups go on while nothing removes old snapshots. Confirming holds the dialog still with "Saving the change…" until the daemon answers, and a refusal, such as `maintenance-busy`, is an alert inside it. Once saved, the dialog closes onto the same button, now worded the other way, the change is said politely, the history is read again (what it offers to adopt follows who maintains it) and the repository picker keeps the change. The dialog is drawn again only when what it offers changed; asked again unchanged, the same one opens.
- **Journeys.** The `@ui` scenarios use the keyboard alone. `the daemon's answers to the UI are delayed by N seconds` holds every `/api/v1/` answer, so the waits above are long enough to read and to act within; `the repository has been removed` makes the history's read refuse with the engine's words, and `the config names no plan` leaves a repository no plan backs up to. The count of rows reads the history again before it counts, so a table the page left stale cannot pass. Unmanaged groups and the cancelling of a running maintenance are covered by host tests only. Instants in the new tables go through `routes::instant`, which writes UTC as the Operations page does.
- **Small screens and other languages.** The tables of snapshots are the shared `Table` (below), the ID 10rem and the time 20rem, so at 320 px and at 200 % text the frame scrolls sideways. The ID column keeps 8rem however narrow its frame, up to three fifths of it, so at 320 px a short ID stays whole, in Linux's DejaVu Sans Bold and with wider text spacing too, while at 200 % text it breaks inside three fifths of the frame rather than cover the time (#1129).

  The journeys pin the page and the review of a forget at 320 × 256 (a table's words whole, nothing scrolls sideways or is clipped, no accessibility violations), at 200 % text with wider spacing, and under `en-XA` and `ar-XB`, where the IDs and instants in the tables, the paths of a list and the engine's own words (`lang="en"`) are data and stay as they are; the check that every visible text is transformed exempts nothing on the pages that show no data. At 320 px the page is given every snapshot ID in the widest hex digits, "b" and "d", rather than the random ones rustic picks, so each run measures the widest.

**Settled in the stats build** (`crates/web/src/stats.rs`, §16 decision 104):

- **Where it is.** On the Snapshots page, the repository picked ends with its stats, under the heading "Stats of demo", after its history, so the page's earlier stops and the navigation are as they were. It shows the last reading kept, as a table named by that heading, a row for each figure with its header (Snapshots, Total size, Stored size and Compression), then when it was read, in the viewer's zone. A repository never read says so ("No stats have been read yet."), and one that stores nothing has no compression to show ("None: the repository stores no data yet."). The stats are looked at again whenever the history is, so a check that ended shows the reading it took.
- **A look that fails.** A look the daemon refuses shows its refusal in an alert, which the next look answered takes away; one that gets no answer leaves the page's heading to say the daemon is out of reach. Either way the section says no more than it knows: what an earlier look told stays, and with none it shows no line rather than "No stats have been read yet." Each look is numbered when it is sent, so one sent before a read was answered never puts its older reading back over the read's.
- **Reading.** **Read the stats now** asks the daemon to read them; it says "Reading the stats…" (polite) while it waits, and then "Stats read." with the new figures, focus staying on the button. A refusal or failure is said assertively in an alert under the button, and the figures shown before stay; a later look leaves that alert until the next read is asked.
- **Figures per locale.** Counts and sizes go through the catalog's `NUMBER` and `size` (§8.4), and compression is a whole percent, so a locale writes each as it writes numbers. The figures are data under the pseudolocales.
- **The API.** `GET /api/v1/repositories/{alias}/stats` answers the last reading kept (`latest`, or none); `POST` reads them now and answers the reading, or refuses: `repository-unknown` (404), a secret's refusal, or `engine-unavailable` (503) for a repository that can't be opened, with nothing kept. Like the listing, a read is refused for nothing that runs on the repository. An API token reads the last reading with its `read` scope, and needs `run` to read them now, which opens the repository as testing it does and keeps a reading (§10.1).

**Settled in the proposals build** (`crates/web/src/proposals.rs` for the decisions, `proposals_page.rs` for the glue; §16 decision 89 and its 2026-11-16 amendment):

- **Where it is.** "Pending changes" (`/proposals`), linked after Plans. Its one heading names the list of the pending proposals, newest first, each a Review button named for the proposal and who proposed it (the API token's label, or no token). The list is keyed by the proposal's ID, so a read again never replaces a focused button; one whose proposal goes while it holds focus hands focus to the heading. With sign-in off the page says that approving there is a convenience, not a safety boundary (point 7).
- **A review.** Review opens the proposal in a section below the list, its heading ("Proposal …") taking focus: what it changes in Ladderback's words (a line per change, and for a changed plan the settings it changes), the AI agent's words apart from them under their own heading, whether the file changed since the proposal was drafted, how many of the proposer's proposals were rejected before, and the masked diff of `config.toml`.
- **Approve and Reject.** Approve takes the step-up field: the admin password with sign-in on, the proposal's short ID with it off. A wrong one is the field's own error, cleared first so a second wrong try is said again; focus moves to the field to read it once, or the announcer says it when focus is there already (§4.5, "Step-up field"); any other refusal is an Error alert in the open proposal. A proposal that could delete snapshots offers no Approve and says why (point 8). Reject has a reason field per change, counted from 1; the spaces around a reason are dropped, so a blank field gives that change none. Once applied or rejected, a `Success` toast after the page's introduction says so, the page reads the list again, closes the section and hands focus to the heading.
- **Their buttons.** Approve and Reject answer one decision, so only Approve, its main action, is the Filled Primary; Reject is Outlined, in a proposal that offers only Reject too, and not in the color of errors, since rejecting deletes nothing. While a request waits, its button is busy and the other, if offered, unavailable, and the page says so beside it.
- **The forget preview.** A proposal that could delete snapshots offers "Show what it would forget", Outlined, busy while the daemon reads the repositories, and unavailable while a rejection waits. Reject stays available while it reads: rejecting deletes nothing and the preview only reads, so a read that can take minutes doesn't hold the decision. Under "What it would forget", each repository's heading, then what retention forgets of each plan now and after the proposal (or why it forgets nothing there), whether the proposal changes nothing it forgets, and a table of the snapshots it would forget only after, then of those it would no longer forget, each plan's captioned. A repository that couldn't be read says why in an Error alert under its heading.
- **Refusals** are Error alerts in the daemon's words (§4.5, "The alert"), where the reader is looking: a list the daemon refuses in the list's place; a review it can't read after the list, focus staying on the Review button; a refused approval, rejection or forget preview in the open proposal, focus staying on the button pressed; and a repository the preview couldn't read under its heading. Each is said assertively once as the page's answer, a preview's repositories one after another. One failure is one alert: pressing Approve or Reject takes away the refusal of either before it.
- **Left out, on purpose.** Approving a proposal that could delete snapshots, the count in the navigation, a command's tick, secrets and maintenance claims, and retrying a failed apply: later steps of #518.
