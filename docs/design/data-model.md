## 9. Data model (SQLite)

```sql
-- runtime state; config lives in config.toml
CREATE TABLE operations (           -- also the job queue (status = 'queued')
  id TEXT PRIMARY KEY,            -- UUIDv7 (time-ordered)
  agent_id TEXT NOT NULL,         -- 'local' on agents; registry id on hub
  kind TEXT NOT NULL,             -- backup|forget|prune|check|restore|stats|...
  plan_id TEXT, repo_uuid TEXT,   -- repo_uuid = rustic repository ID
  trigger TEXT NOT NULL,          -- schedule|manual|catch-up|retry|hub|mcp
  status TEXT NOT NULL,           -- queued|running|succeeded|succeeded_with_warnings|failed|cancelled
  queued_at INTEGER, started_at INTEGER, finished_at INTEGER,
  index_read_at INTEGER, deadline INTEGER,     -- backups (§7.3)
  lease_epoch INTEGER,            -- maintenance ops: owner lease they ran under (§7.3)
  attempt INTEGER DEFAULT 1,
  requested_by TEXT,              -- restores: local UI or hub (§10.4)
  snapshot_id TEXT,               -- for backups
  summary_json TEXT,              -- OpResult (files new/changed, bytes added, duration, …)
  error_code TEXT, error_args TEXT, error_detail TEXT,   -- api::ErrorCode, JSON MsgArgs, rustic's verbatim text (§8.4)
  warning_count INTEGER DEFAULT 0
);
CREATE INDEX ops_by_plan ON operations(plan_id, started_at DESC);
CREATE INDEX ops_queue   ON operations(status, queued_at);
CREATE UNIQUE INDEX one_maintenance_per_repo ON operations(repo_uuid)
  WHERE status = 'running' AND kind IN ('forget', 'prune', 'check');   -- I7; OperationStore::try_start

CREATE TABLE op_warnings (op_id TEXT NOT NULL, item TEXT, during TEXT, code TEXT, detail TEXT);
CREATE INDEX op_warnings_by_op ON op_warnings(op_id);   -- capped at 10,000 rows per op; warning_count keeps the total
CREATE TABLE op_logs     (op_id TEXT, seq INTEGER, ts INTEGER, level TEXT, line TEXT,
                          PRIMARY KEY (op_id, seq));      -- redacted; retained N days

CREATE TABLE schedule_state (plan_id TEXT PRIMARY KEY, next_run INTEGER, last_success INTEGER);

CREATE TABLE snapshot_cache (     -- refreshed after backups/forget, and on demand
  repo_uuid TEXT, id TEXT, time INTEGER, hostname TEXT, label TEXT,
  steading_plan TEXT, steading_agent TEXT,                -- from tags; NULL if untagged
  paths_json TEXT, tags_json TEXT, summary_json TEXT,
  PRIMARY KEY (repo_uuid, id)
);

-- agents with a hub configured
CREATE TABLE sync_outbox (epoch TEXT NOT NULL, seq INTEGER NOT NULL, op_id TEXT, event_json TEXT,
                          created_at INTEGER, PRIMARY KEY (epoch, seq));
                          -- rows deleted once acknowledged; capped at 100,000 rows, dropping
                          -- log events first and never operation start/finish records
CREATE TABLE repo_grants (repo_uuid TEXT PRIMARY KEY, owner TEXT, epoch INTEGER, expires_at INTEGER,
                          keep_delete_secs INTEGER, prune_margin_secs INTEGER, updated_at INTEGER);

CREATE TABLE api_tokens (id TEXT PRIMARY KEY, label TEXT, hash TEXT NOT NULL,  -- argon2id of the secret part
                         scopes TEXT NOT NULL,      -- comma list of read|run|preview (§10.1)
                         created_at INTEGER, last_used_at INTEGER);

-- hub only
CREATE TABLE agents (id TEXT PRIMARY KEY,          -- generated by the agent (§7.1)
                     hostname TEXT NOT NULL UNIQUE, pubkey BLOB, version TEXT,
                     paired_at INTEGER, last_seen INTEGER, last_acked_epoch TEXT, last_acked_seq INTEGER,
                     clock_offset_ms INTEGER);
CREATE TABLE agent_plans (agent_id TEXT, plan_id TEXT, plan_json TEXT, updated_at INTEGER,
                          PRIMARY KEY (agent_id, plan_id));
CREATE TABLE repo_owners (repo_uuid TEXT PRIMARY KEY, owner TEXT NOT NULL,  -- 'hub' | 'agent:<id>' | 'none'
                          epoch INTEGER NOT NULL, expires_at INTEGER, granted_at INTEGER);
CREATE TABLE repo_claims (repo_uuid TEXT, agent_id TEXT, requested TEXT, status TEXT,  -- granted|rejected
                          PRIMARY KEY (repo_uuid, agent_id));
```

**The operation log (M1b).** `migrations/0001_operations.sql`, at the repository root and applied by `sqlx::migrate!` when the store opens (§8.3), creates the `operations` and `op_warnings` tables, and nothing else above: later tables, columns and indexes arrive as migrations of the features that need them, among them the queue index and `one_maintenance_per_repo` with `OperationStore::try_start`. At version 1:

- `operations` has the columns the log writes: `id`, `agent_id` (always `local` for now), `kind`, `plan_id`, `repo_uuid`, `trigger`, `status`, `queued_at`, `started_at`, `finished_at`, `snapshot_id` (a backup's), `summary_json` (what the engine reported), `error_code`, `error_args`, `error_detail`, `warning_count`. `queued_at` and `warning_count` are `NOT NULL`. `kind` is `fake|identify|backup|prune|check`: `fake` and `identify` are the diagnostic and repository-opening jobs. `trigger`, `status` and the other columns take the values listed above.
- Times are Unix **milliseconds**, UTC, cut to the millisecond and never rounded.
- `ops_by_plan` is `(plan_id, id DESC)`, not `started_at`: history pages by operation ID, which is time-ordered (UUIDv7), and a queued operation has no start yet.
- The cap on warnings is the `Operation` aggregate's: it keeps the first 10,000 and counts the rest, so `op_warnings` holds at most 10,000 rows per operation and `warning_count` the total. Warnings are read back in the order they were recorded.
- A failed operation stores its reason as `error_code` (the failure's kebab-case code: the store owns the literals, which match `api::ErrorCode`'s), `error_args` (a JSON array of `[name, MsgArg]` pairs) and `error_detail` (the platform's or engine's own text, verbatim; an empty text is `''`, not NULL). The three columns are NULL unless the operation failed. The codes are `engine-unavailable`, `invalid-job-spec`, `engine-exited` (argument `exit_code`, left out when a signal ended the worker), `operation-failed`, `protocol-violated` (argument `transition`), `deadline-passed`, `engine-start-timed-out` and `engine-exit-timed-out`.
- `OperationStore::save` writes one operation by ID in a single transaction and replaces its warnings. The job runner saves an operation when it is queued, when the engine reports it running and when it finishes, and never in between, so a busy backup doesn't write the database for every progress event. A write the store refuses never changes how the operation ends (backups never depend on the database); the run reports it and the next write is the whole operation again.
- History lists newest first (`id DESC`) with a keyset cursor: `after` is the `next` of the previous page and need not name an operation that still exists. A page holds 50 operations unless the caller asks for another size, always between 1 and 200. The only filter is the plan.
- Reads are strict: an unknown status, kind, trigger or error code, malformed JSON, or an ID or time that doesn't parse is `StoreError::Corrupt`, never a silent default (one bad row fails the page that contains it). A database that holds a migration this build doesn't ship, because a newer Steading wrote it, is refused with `OpenError::NewerSchema` and left as it was.
- The store opens the file in WAL mode with `synchronous = NORMAL`, a five-second busy timeout and a pool of four connections, and a save takes the write lock when it starts (`BEGIN IMMEDIATE`), so concurrent saves queue instead of failing half way. `op_warnings.op_id` references `operations(id)` and its rows go with their operation. Reads are lenient only about additions: fields and error arguments this build doesn't know are ignored, an unknown warning code reads as `other`, and an upper-case ID is normalised.

Retention: logs 30 days, operations 1 year (configurable), snapshot cache rebuilt as needed.

**Recovery.** Backups never depend on the database. It keeps a daily copy (`VACUUM INTO`). `steading db rebuild` recreates a corrupt database: schedule state from config, the snapshot cache from the repositories, and history from the latest daily copy. Backrest has open SQLite failures on btrfs and with corruption ([#978](https://github.com/garethgeorge/backrest/issues/978), [#1174](https://github.com/garethgeorge/backrest/issues/1174)), so CI runs the store tests on btrfs and a Docker volume, and NFS is documented as unsupported for the data dir.

**One process per data dir.** `serve`, `mcp --headless` and `db rebuild` take an exclusive `flock` on `<data>/steading.lock` before opening the database, and fail with `data-dir-in-use` (naming the holder's PID) when another process has it. SQLite's own locking allows several writers, so without this two schedulers could share one queue. The OS releases the lock when the process dies, so a crash never leaves it stale.
