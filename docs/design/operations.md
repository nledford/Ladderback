## 11. Notifications

Configured on the hub (or on a standalone agent). Each **notification rule** is **events → channel**:

- Events: `backup.started`, `backup.succeeded`, `backup.failed`, `backup.warning`, `backup.missed` (no success within N × interval), `backup.retrying`, `forget.failed`, `prune.failed`, `prune.refused` (`keep-delete` too small for the margin, §7.3), `check.failed`, `check.errors`, `restore.failed` (§10.4), `agent.offline` (> N min), `agent.pending` (a new agent has paired and waits for a person to approve it, or its replacement key does; it names the hostname, agent ID and key fingerprint, never a token, and fires once for each agent and again if the agent lapses and pairs again, decision 120), `hub.recovery_kit_viewed` (the hub's Recovery Kit was shown on its page, downloaded, or shown by `ladderback recovery-kit`; it names which, when, who (the signed-in user, or the operating-system user for the command) and the peer address, never the seed, and Settings shows the last view, decision 120), `repo.unmanaged_groups`, `repo.claim_rejected`, `repo.maintenance_paused` (lease not renewed, repo now shared, or not configured on the hub).
- **As built.** The agent emits `backup.retrying` when it plans a retry of a failed backup (§5): the operation that failed, its plan, which attempt of how many, and when it runs (`UiEvent::BackupRetrying`, decision 76). `backup.missed` isn't emitted yet.
- Channels: generic webhook (JSON), ntfy, Gotify, Discord/Slack webhook, SMTP.
- **Templates.** Default message text comes from the `notify.ftl` catalog in the configured locale (§8.4). Users may override it with their own templates, which are not localized. Webhook bodies are JSON with stable, unlocalized keys, event names and error codes, plus a localized `message` field. Templates never receive secrets (I4).
- **healthchecks.io-style pings per plan**: `start`, `success` and `fail` URLs. These are the most robust "it silently stopped" detector, because they work even when the whole Ladderback system is down.

**As built (M2, decision 74).** An agent sends the events it emits today: `backup.started`, `backup.succeeded`, `backup.warning` (a backup that succeeded with warnings, told instead of `backup.succeeded`), `backup.failed`, `backup.retrying` (a retry planned after a failed backup, with the failure's code, decision 76), `forget.failed`, `prune.failed`, `check.failed` and `restore.failed` (a restore of a snapshot's entry that failed, with the failure's code; a restore's start and success aren't told, §10.4). The others arrive with the parts of the agent that emit them (the scheduler, the hub).

An operation the daemon stopped during (a crash, a kill, a power cut), and a queued one it can't run again after a start, sends its kind's `.failed` event with `daemon-stopped` when the daemon starts again, at most once per start, with the time of that start (decision 91). One an orderly stop interrupted (a service stop or restart, the computer shutting down) sends nothing: the stop records it as `daemon-shut-down` and announces it to no rule, since whoever stopped the daemon knows why; a stop killed or cut off before it recorded them leaves them to the next start, which announces them as `daemon-stopped` (decision 92).

A queued backup that waited for its keyring and found a newer run of its plan going gives way to it, ends failed with `superseded` and sends nothing: it never ran, and the newer run sends its own end, so a rule or a healthchecks check hears one outcome per run that ran (decision 135, #1245).

Once that wait is over, a queued backup whose plan was deleted, or now backs up to another repository, ends failed with `plan-removed` or `plan-moved` and sends nothing either: it never ran, and the person made the change that stopped it. One whose configuration can't be read or used then ends failed with `config-unusable`, and one whose sources now take in the data folder's key files, which no glob can leave out, with `key-files-not-left-out`; each sends `backup.failed`, since the person has to act, though while the configuration can't be read no rule hears it (below). None ends as `daemon-stopped`, which would say the daemon stopped during it (decision 135, #1293).

A plan whose runs a stopped computer keeps missing is the overdue event's (#415). A run whose end was already sent though the log refused its last write (decision 41) still shows as running, so the next start sends it again as `daemon-stopped`; a start refused after recovery stops before the notifier can deliver; and while the configuration can't be read, no rule hears the end.

Channels are `webhook`, `ntfy` and `healthchecks`; Gotify, Discord/Slack and SMTP are not built.

```toml
[notifications.channels.ops]
kind = "ntfy"
url-env = "NTFY_TOPIC_URL"            # https://ntfy.example.com/backups
token-file = "/run/secrets/ntfy_token"

[notifications.channels.home-check]
kind = "healthchecks"
url-keyring = "ladderback/home-check"  # the check's ping URL

[notifications.rules.failures]
events = ["backup.failed", "prune.failed"]
channel = "ops"
template = "{event}: {plan} {repository} ({code})"

[notifications.rules.home-pings]
events = ["backup.started", "backup.succeeded", "backup.failed"]
channel = "home-check"
plans = ["home"]
```

- **A channel's URL is a secret**, as its token and password are: whoever knows a webhook's or a topic's URL can post to it. Each is given by exactly one of `-command`, `-keyring`, `-file` and `-env` (`url-…`, `token-…`, `password-…`), with the rules a repository's password follows (§10.2): a file by an absolute path, a command whose program is a name on `PATH` or an absolute path. Never as text in the file: `url`, `token` and `password` are not keys. Each is read when a notification is sent, never kept. `webhook` and `ntfy` may sign in with a bearer token (`token-…`) or with `username` and a password by HTTP Basic; `healthchecks` signs in with nothing and takes none of those keys.
- **A rule** names its `events`, its `channel` and, optionally, its `plans` (only those plans' events; an event without a plan, as a prune's, is sent only by a rule that names none) and a `template`. The configuration is refused when a rule names a channel or a plan it doesn't have. Rules are matched in name order, and each one an event matches sends it once.
- **A template** is text with the placeholders `{event}`, `{plan}`, `{repository}`, `{operation}`, `{code}`, `{time}`, and a retry's `{attempt}` and `{attempts}` (which retry of how many; `{time}` is when it runs); `{{` and `}}` write a brace. `{code}` is the failure's code (`operation-failed`) for a failure and for the retry planned after one, and for `backup.warning` the code of each kind of warning the backup kept (`hook-warning`), each once, in the order the first of each came, as the history names them, separated by `, ` (`source-unreadable, hook-warning`); the other events have none. A fact the event doesn't have is empty. It reads only these facts, so no secret, location or engine text can reach a message (I4). Without one, the message is the catalog's `notify-<event>` in the agent's locale (`[agent] locale`), or the system's when the agent names none or its locale has no catalog.
- **What is sent.**
  - A webhook is posted JSON: `event`, `plan`, `repository`, `operation`, `code` (what `{code}` says), `time`, `attempt`, `attempts` (`null` when the event lacks it) and `message`.
  - An ntfy topic is posted the message under a title in words, the catalog's `notify-title-<event>` ("Backup finished with warnings", "Backup failed") in the same locale as a default message, whether the rule has a template or not, and tagged with the event's name (`Tags: backup.warning`), so a filter on the event still works; a title with characters other than printable ASCII is sent as an RFC 2047 encoded word, which ntfy decodes. A title takes no fact of the event, so nothing a template can't say reaches it either.
  - A healthchecks check is pinged at its URL for a success, at `/start` of it when a backup starts and at `/fail` of it for a failure and for a retry planned after one.
  - A message is cut to 4 KiB, and a URL longer than 8 KiB, or not `http` or `https` with a host, is not sent to.
- **Delivery.**
  - Each request ends within 30 s, after the channel's secrets are read (a secret's command has 60 s of its own); only a 2xx answer delivers it, a redirect is never followed (so a channel can't move a notification and its credentials elsewhere), and the answer's body is never read.
  - A notification that isn't delivered is not tried again: the daemon logs `notification-undelivered` with the rule, the channel, the event and why (`secret-unavailable`, `invalid-address`, `unreachable`, `timed-out` or `rejected`), never the URL, the token or the library's text.
  - An event that comes while the configuration can't be read is logged once, with the configuration's error, and sent nowhere.
  - The notifier reads the configuration for each event, so a rule saved while the daemon runs applies to the next event, and it is subscribed to the events before any operation runs. It takes the starts and ends, and the retries planned, off the event bus as they come, while a slow channel is still being told, and tells them in the order they came: a subscriber's queue on the bus loses its oldest events once it is full (§4.4), and a run that warns often would otherwise push another run's end out of it.
  - An operation the daemon finds cut short when it starts is ended as failed before the notifier subscribes, and is not told.
- **Proxies.** Deliveries go through the proxy the standard variables name (`HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, in either case), as a worker's requests do (§4.1), read once when the daemon starts. A channel on loopback or the local network is sent through the proxy too, unless `NO_PROXY` names its host (`NO_PROXY=127.0.0.1,ntfy.example.com`). The macOS system proxy settings are not read.

## 12. Packaging and deployment

- **Linux:** an `x86_64`/`aarch64` binary that needs glibc 2.35 or newer (Debian 12, Ubuntu 22.04 and later) and no library outside glibc and `libgcc_s`: TLS is rustls and D-Bus is built in (decision 54). `ladderback install-service` writes a systemd **user** unit, `$XDG_CONFIG_HOME/systemd/user/ladderback.service` (`XDG_CONFIG_HOME` is `~/.config` when unset), that runs the installing binary's `serve --service-managed`, and has the user's manager enable and start it; `ladderback remove-service` stops and disables it and removes the file (decision 64).
  - The unit gives the agent 75 s to stop before systemd sends SIGKILL (`TimeoutStopSec=75`), past the agent's own 65 s limit on its stop, of which a backup that archives may take 35 s to wind down (decision 92); `install-service` and `remove-service` wait 85 s for the `systemctl restart` or `disable --now` that waits for that stop. Both are run as the user the service is for, never under `sudo`, and neither touches a unit of the same name it didn't write, nor a masked one. A system unit for servers (`--system`) is not built yet.
  - **Files the agent creates are the user's alone** (`UMask=0077`, #1139): the agent, its workers, rustic and the hooks it runs start with a umask that gives the group and others no access, whatever umask the user's service manager has. So do new packs, indexes and snapshots in a local or mounted repository, as restic's are; restores keep each file's mode from the snapshot. A hook that writes a file other users must read sets its mode itself, and a repository another account reads needs a drop-in, `~/.config/systemd/user/ladderback.service.d/umask.conf` with `UMask=0027`, which `install-service` leaves alone. It is the unit's only sandboxing line: `PrivateTmp` and `ProtectHome` would hide what a backup reads, `NoNewPrivileges` would stop a hook's `sudo`, and in a user unit they bound nothing the user can't undo. A unit written before this keeps the manager's umask until `install-service` runs again, which `just install-restart` does.
  - **Restarting from Settings** (decision 94): the agent makes its orderly stop and exits with status 75, which the unit starts it again on after `RestartSec=10`, without marking it failed (`SuccessExitStatus=75`). `--service-managed` is what tells the agent a manager will start it again, so a `serve` started by hand offers no restart. **A unit written before this has neither**, so Settings offers no restart until `install-service` runs again and replaces it.
  - **Any exit systemd didn't ask for is followed by a start** (`Restart=always`, decision 64 as amended for #1035): a crash, a refused start, a restart, and a SIGTERM another program sent, such as a `pkill -f` whose pattern matches the agent's command line, which the agent ends with status 0. Only systemd's own stop keeps it stopped: `systemctl --user stop ladderback` until the next login (or boot, for a user who lingers), `remove-service` for good. A unit written before, with `Restart=on-failure`, stays stopped after such a SIGTERM until `install-service` runs again.
  - On **Bazzite and other atomic Fedora** systems, put it in `~/.local/bin` (or `/usr/local/bin`, which is writable) with a user unit. No layering needed.
  - **A user's services stop when the user's last session ends**, unless the user lingers: `install-service` says to run `loginctl enable-linger` for a service that starts at boot and keeps running while the user is logged out, unless `loginctl show-user <uid> -p Linger` says the user lingers already. A check that can't say (no `loginctl`, a failure, no answer within the manager's limit) still prints it (#546).
  - **SELinux (Fedora, enforcing), not tested on Fedora:** under the targeted policy a user's services run in the user's own unconfined domain, as the user's shell does, so a user unit that runs a binary in `~/.local/bin` or `/usr/local/bin` should need no policy change, and the unit's `CacheDirectory=` is a folder systemd makes and labels. A confined SELinux user (`user_u`, `staff_u`) is not tested either. **firewalld:** the agent listens on loopback by default, which needs no rule.
  - **Keyring under a service:** a user unit shares the session's bus only while the user is logged in to a desktop session, whose login starts and unlocks the Secret Service. A service that lingers starts at boot, before anyone logs in, so a scheduled backup that runs then can't read a `password-keyring` password until someone logs in, and the read says so (the next item). A machine that backs up while its user is logged out keeps the password in a `password-file` that only the user can read (mode 600) instead. On Linux `install-service` says so when a repository's password is in the keyring (#479); a launchd agent runs only while its user is logged in, so on macOS it says nothing of it.
  - **The `keyring` secret source needs a Secret Service** (#259). On Linux a `password-keyring` entry is read from the Secret Service over the session's D-Bus. A headless machine has none by default: Fedora Server, Debian and Ubuntu servers, and a systemd **system** unit, which has no session bus at all. There every read is refused as `secret-keyring-unavailable`, which says what is missing and what to use instead, with the platform's words as its detail. So is a read the service refuses because it has no collection to look in.

    A read the service answers by saying its keyring is locked, one that finds no entry while the `default` collection is locked (oo7, Fedora's Secret Service, finds no items in a locked collection), and one whose unlock prompt was dismissed, which leaves the keyring locked, are `secret-keyring-locked`, which says how to unlock it (#993); a dismissed prompt is never asked again, and its run is never waited on. A locked keyring whose prompt nobody answers holds the read until the resolver's time runs out, and that is `secret-unreadable`.

    Either run a Secret Service in a session bus and unlock it, or keep the secret in a `password-file` (with a system unit, `LoadCredential=`), a `password-command` or a `password-env` instead (§10.2).

    **Which Secret Service:** anything that answers `org.freedesktop.secrets` on the session bus. Fedora 45 uses **oo7** (`oo7-daemon`) on every desktop, in place of **GNOME Keyring**; some images, COSMIC ones among them, ship none, and after installing it, `systemctl --user enable --now oo7-daemon.service` starts it. KDE Plasma's **KWallet** answers the same interface, untested here (#461). The install script's closing notes on Linux name these, or a `password-file`, when `busctl --user list` lists no `org.freedesktop.secrets`, running or one D-Bus starts when asked for, or can't reach the session bus. It asks as the user who runs it and installs none of them, as it never runs `sudo` (decision 79).
  - **When a keyring read fails on Linux:**
    - A locked keyring with no unlock prompt (seen on Fedora 45 with COSMIC after its compositor crashed and its portal didn't come back): `systemctl --user restart oo7-daemon` doesn't unlock it; logging out and in again does, as the login unlocks it. To lock it for a test, `secret-tool lock --collection=default` on oo7; GNOME Keyring's collection is `login`.
    - oo7's 0.7 beta, seen once: after a login, every keyring write failed with "The target file has changed" naming `login.keyring`, until `systemctl --user restart oo7-daemon`.
  - **An exported profile reads a keyring password with `secret-tool`** (§6.2), which ships apart from the Secret Service: in `libsecret` on Fedora (a Server or Minimal image may lack it) and in `libsecret-tools` on Debian and Ubuntu. `export-profile` warns (`profile-keyring-command-missing`, naming the package) when no folder of its `PATH` holds the command, and still writes the profile, which may run on another machine. With `PATH` unset it looks in `/usr/bin` and `/bin`, as `execvp` does, and it skips an empty or relative entry, which names a folder by the one rustic will run in.
- **macOS:** an `aarch64` binary until cargo-dist can build a universal one (axodotdev/cargo-dist#77; decision 54), with `install-service` writing a launchd agent, `~/Library/LaunchAgents/io.github.nledford.ladderback.plist`, that runs `serve --service-managed` and logs to `~/Library/Logs/ladderback.log` (decision 64). The plist gives the agent 75 s to stop before launchd sends SIGKILL (`ExitTimeOut`, 20 s when unset), past its own 65 s limit on a stop (decision 92), and `install-service` and `remove-service` wait 85 s for launchd to let it go. Without a Developer ID, a build from source carries the linker's ad-hoc signature, or a self-signed certificate's when the person names one; a published archive needs Developer ID signing and notarization first (decision 71). The worker needs **Full Disk Access** (TCC) to read `~/Documents`, `~/Desktop`, Mail and so on.
  - **Restarting from Settings** (decision 94): the agent's exit with status 75 is one launchd starts it again on, at least 10 s after its last start (launchd's throttle). An agent installed before this lacks `--service-managed`, so Settings offers no restart until `install-service` runs again.
  - **Any exit launchd didn't ask for is followed by a start** (`KeepAlive` true, decision 64 as amended for #1035), a SIGTERM another program sent among them. Only a `bootout` keeps it stopped, since it unloads the agent: `launchctl bootout gui/$(id -u)/io.github.nledford.ladderback` until the next login, `remove-service` for good. `launchctl kill` or `stop` don't: the agent comes back. An agent installed before, with `KeepAlive` `SuccessfulExit=false`, stays stopped after such a SIGTERM until `install-service` runs again.
  - TCC ties the grant to the code signature, so an ad-hoc-signed build loses it on every upgrade. A signature that stays the same across upgrades is required, not polish (decision 71).
  - **Signing a build from source** (decision 71, as amended): with `LADDERBACK_SIGN_IDENTITY` naming a code-signing identity, by its whole name or SHA-1 hash, `just install` signs the installed binary, `codesign --force --sign <hash> --identifier io.github.nledford.ladderback`, then checks it with `codesign --verify` (scripts/install-signing.ts). Without the variable, and on Linux, nothing is signed. Making the certificate: the [install guide](../guide/install.md#signing-your-build).
    - Before it builds, it refuses a name `security find-identity -v -p codesigning` doesn't list as valid, or lists more than once, so nothing is installed.
    - A signing that fails after `just install` has built, as over SSH where nobody can answer the keychain's prompt, leaves the new binary installed, ad hoc or with the signature that failed its check, says which, and fails the recipe; `node scripts/install-signing.ts sign` signs it again without a build. Under `install-restart`, which builds into a staging folder, it installs nothing, and the service runs on as it was.
    - After a restart, `install-restart` warns for an ad-hoc build that the keychain, Photos and Full Disk Access ask again, and says for a signed one that Full Disk Access and Photos carry over and the keychain asks once more.
    - **Tested on a Mac (macOS 27.3, 2026-11-16, #281):** a rebuild signed with the same certificate has a new code hash and the same designated requirement, and macOS asked for no privacy grant. The Full Disk Access grant given to the last signed build held: the next backup of the whole home folder ended `succeeded`, with no `source-unreadable`, so the launchd daemon's grant also reaches its `worker` child. Only the first signed build is new to Full Disk Access and Photos: grant them once.
  - **The keychain asks once per build, signed or not** (#892). A keychain item has a decrypt access list and, since macOS 10.12, a partition list. The certificate's signature is enough for the access list. The partition list lets a program in by its Team ID (`teamid:…`), which only an Apple-issued certificate carries; a self-signed one has none (`TeamIdentifier=not set`), so "Always Allow" adds that build's code hash (`cdhash:…`), and the next build, with a new hash, is asked again (`action:65538` in the keychain service's log). The #281 test read an item whose partition list already held that build's hash. **[Inference]** `security dump-keychain` doesn't show the partition list; the prompts' action and timing are the evidence. An unanswered prompt holds the read until it times out, so the first scheduled backup after an update fails (#891). The ways round it:
    - `just install-restart` reads each keyring entry once with the new program, `ladderback check-keyring`, in the terminal it runs in, from the staging folder after the build and before it waits and restarts, so the keychain asks while someone is there: a repository's `password-keyring`, and a notification channel's `url-keyring`, `token-keyring` and `password-keyring`. Answer "Always Allow": a single "Allow" lets the check read the entry, and the service is asked again. An entry it can't read stops it before the restart; `--ignore-keyring-failure` restarts all the same. By hand, run `ladderback check-keyring` after an update.
    - `password-command = "security find-generic-password -s <service> -a <name> -w"`: `security` is an Apple program, in the `apple-tool:` partition, so a new build of Ladderback doesn't change what the keychain asks. **[Inference]** An item Ladderback stored (`set-password`) lists only Ladderback in its access list, so the keychain should ask once for `security` itself: run the command once in a terminal and answer "Always Allow".
    - A `password-file` that only the user can read (mode 600), which no keychain guards.
  - **The running daemon's binary stays in place until its restart** (#1107). When `just install-restart` installed first and waited for the daemon to be idle afterwards, a scheduled backup that started during the wait failed to read its keyring password (`secret-unreadable`), and the next run, in the restarted process, read it. **[Inference]** The keychain checks a caller's code against its file on disk, which no longer matched. So it builds the new binary into a staging folder in the installed binary's folder, so on the same file system, checks it there, and once the daemon is idle moves it into place with one rename and restarts the service at once. What is left is the seconds between the last idle check and the restart (scripts/install-restart.ts).
  - **A reinstall asks again.** An ad-hoc-signed build is a new program to macOS on each reinstall, so a keychain "Always Allow" answer and the privacy grants (Full Disk Access, and per-category ones such as Photos) don't carry over. macOS asks again for the per-category ones on the next access, and a declined or unanswered prompt leaves the next backup reading less, with a `source-unreadable` warning. Seen on the maintainer's Mac in the 0.3.0 rollout ([#281](https://github.com/nledford/Ladderback/issues/281)).
  - **A missing Full Disk Access grant is detected** (decision 115, #558): nothing asks macOS for it, so the agent lists `~/Library/Safari` at start, before each backup and on the start page's **Check again**. A missing grant is one warning in the log at start, a warning banner on every page that links to the start page's steps and, for a browser on the same Mac, a button there that opens System Settings at Full Disk Access and shows the program in Finder; each backup item it explains is `full-disk-access-missing` rather than `source-unreadable`, so the notification says why. `install-service` says which program to grant, after it installs the launchd agent.
  - Some macOS versions refuse to add a bare CLI binary to Full Disk Access ([Backrest #986](https://github.com/garethgeorge/backrest/issues/986)); macOS 27.3 accepts `~/.cargo/bin/ladderback` (#281).
- **Docker** (#358, decision 126 as amended): `ghcr.io/nledford/ladderback` and `docker.io/nledford/ladderback`, for `linux/amd64` and `linux/arm64`, tagged with the version, and with `latest` only when the release is GitHub's latest one, published by each release after 0.5.0 (§12.1), for a machine's agent or, from M8, the hub; `just image` builds the same image from a release archive in a checkout. Until M8's release makes it the recommended channel for a machine whose only job is the hub (decision 136), it is a preview, not yet a supported way to install and run Ladderback.
  - **It copies the release binary:** the `Containerfile` takes `ladderback` from a Linux release archive, which `just image <version> <archive>...` unpacks into a build context under Docker's architecture names (`amd64`, `arm64`), so the image and the archive are one build. The base is `debian:13-slim` pinned by digest, with only `ca-certificates` added, for rustls's roots; jiff carries its own time zone data, so `TZ` sets the zone.
  - **It runs as 10001:10001**, with its config and data folders (`/var/lib/ladderback/config`, `/var/lib/ladderback/data`) as volumes and its cache at `/var/cache/ladderback`. Its command, `serve --listen 0.0.0.0:9898`, names no `--allowed-host`, so the daemon refuses to start until the person's run command names one (security §10.1). `set-password`, run in a container of its own on the data volume, turns sign-in on at the next start.
  - **An agent in a container** sees only the folders mounted into it, takes the container's hostname as its snapshots' host, records the paths inside the container, and is restarted by Docker's restart policy rather than by `install-service`. The [install guide](../guide/install.md#docker-image-not-supported-yet) says how to run it, with the same agent as a Compose file (`docs/guide/examples/compose.yaml`), and `just smoke-image <image>` checks an image the way the guide runs it, and that the Compose file parses.
- **Linux releases carry archives** from 0.3.1 (decision 54): one for `x86_64` and one for `aarch64`, with a `SHA256SUMS` file, which the [install guide](../guide/install.md#download-a-release-linux) checks with `sha256sum -c --ignore-missing` before it installs the binary.
  - **From 0.5.0 they also carry a `.deb` and an `.rpm` for each** (decision 123): `ladderback_<version>_<amd64|arm64>.deb` and `ladderback-<version>-1.<x86_64|aarch64>.rpm`, built by nfpm from the archive's own binary, listed in the same `SHA256SUMS`, and installed with `apt install ./ladderback_<version>_arm64.deb` or `dnf install ./ladderback-<version>-1.x86_64.rpm` ([install guide](../guide/install.md#install-a-package-debian-ubuntu-fedora)). A package holds `/usr/bin/ladderback` and the licences, has no maintainer scripts and starts no service: `ladderback install-service` does that, as a user service (decision 64). It is unsigned, and there is no apt or dnf repository yet, so an update is the next package installed. On Atomic Fedora (Bazzite) a package needs layering, so use the archive there. `scripts/install.sh`, one command piped into bash, `curl -fsSL https://raw.githubusercontent.com/nledford/Ladderback/main/scripts/install.sh | bash` (decision 79), installs the newest release's archive on Linux the same way, into the folder `cargo install` uses, and stops on a checksum that doesn't match.
- **macOS builds from source** until its archive can be signed (decision 71), and Linux can too, where the release has no archive for the system or with `--from-source`: the steps in the [install guide](../guide/install.md), or the same script, which then installs rustup, just and trunk after asking once (trunk from its release archive, checked against a SHA-256 the script pins, and built only where trunk publishes no archive), never a system package and never with `sudo`, keeps the source in `${XDG_DATA_HOME:-~/.local/share}/ladderback/source`, and builds the newest release tag that isn't a release candidate with `just install`; running it again updates.
- **Recommended channels** (decisions 126 and 136): an agent installs from the Linux packages on Debian, Ubuntu and Fedora, and from the install script on other Linux systems and on macOS. From M8, any installed machine can become the hub in place, and a machine whose only job is the hub runs from the Docker image, which an agent on Linux may use too, as an alternative. A Homebrew tap waits for a notarized macOS archive (#344), the AUR and Nix are left to the community, and Ladderback isn't published to crates.io (#207).

### 12.1 Versioning and releases

Ladderback follows [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). The **release unit is the product**: the `ladderback` binary, and its Docker image, which each release after 0.5.0 publishes. Every crate inherits one version from `[workspace.package]` and none is published, so crate APIs are not a public contract.

**The public contract**, which decides the bump:

| Surface | Breaking (major from 1.0) | Compatible (minor) |
|---|---|---|
| CLI: commands, flags, exit codes | Removing or renaming one, changing a default's meaning | New command or flag |
| CLI `--json` documents (§4.5): keys, error and warning codes | Removing or renaming one | New keys or codes |
| `config.toml` (§6.1) | Dropping the migration from an old `schema`, so a file stops loading | New keys; a new `schema` whose migration runs on load |
| REST and WebSocket API `/api/v1` | Anything that needs `/api/v2` | New endpoints and optional fields |
| Sync protocol `/sync/v1` (§7.2, decision 88) | Dropping a protocol the previous release spoke (a release adding protocol N+1 drops N−1) | New optional message fields; a new protocol in a release that still speaks every protocol the previous one did |
| Snapshot tags `ladderback-plan:` / `ladderback-agent:` (§7.3) | Any change: existing repositories would lose their plan links | — |
| Webhook JSON: keys, event names, error codes (§11) | Removing or renaming one | New events, keys or codes |
| Exported rustic profiles (§6.2) | A profile that the pinned rustic CLI reads differently | — |
| Database and data directory (§9) | A migration with no automatic path | Automatic migrations |
| MCP tools (§4.6): names, input schemas, result fields | Removing or renaming a tool, a new required argument, a result field whose meaning changes | New tools, optional arguments and result fields |

Not part of the contract: UI layout and wording, log text, the CLI's sentences (a script reads `--json`; the daemon's `listening on` line stays as §8.4 says), the worker protocol (both ends ship in one binary), and Rust APIs. Downgrades are unsupported; the config history and the daily database copy are the way back.

**Bump rules.** A release takes the highest bump among its changes, judged by the table, not by commit labels:

- before 1.0.0: a breaking change or a feature bumps the minor version, a fix bumps the patch;
- from 1.0.0: breaking bumps the major, a feature the minor, a fix the patch;
- every breaking change gets an entry under **Breaking** in `CHANGELOG.md`, with the upgrade step.

**Release line.** Nothing is released before M1b; the workspace version stays `0.0.0` until then. The end of M1b releases `0.1.0`, and each later milestone a minor version. M2 released `0.2.0` and `0.3.0` the fixes from running it on real machines (§14), M3 `0.4.0` and M3b `0.5.0`; each milestone after them takes the next minor version in the order it finishes. Since 2026-11-22 the MVP milestone, which starts real-world testing, comes first, then M4, M5 and M8 to M10 (§14). Between milestones a release is a patch, such as `0.3.1`, so it doesn't move that line. `1.0.0` follows once those are done and the contract above is declared stable. M6, M7 and M11 come after it, each a 1.x minor version; Japanese (M7) when its review is done. Release candidates (`X.Y.Z-rc.N`) are tagged before a release that bumps the config `schema` or the sync `protocol`, and run on real machines first.

The first release, release candidates, `1.0.0` and a patch between milestones whose commits include a feature are versions the commits can't imply, so the maintainer sets them on the release PR's branch with `release-plz set-version <version>`, which moves `[workspace.package] version`. The `ladderback@<version>` form would give that one package its own version and break the inheritance every crate shares.

**Tags.** `vX.Y.Z` on `main`, created only by the release workflow. A tag is never moved or deleted; a bad release is fixed by the next patch, and its GitHub release is marked as such. The "Protect release tags" ruleset enforces this for every `v*` tag, with no bypass: creating one stays open to the release workflow's `GITHUB_TOKEN`, and undoing a mistake means switching the ruleset off on purpose.

**Process.** [release-plz](https://release-plz.dev) in git-only mode (`release-plz.toml`, `.github/workflows/release.yml`):

1. Before `just release-pr`, a docs PR brings `README.md` up to date with what the release can do: the warning, the Backrest comparison and the roadmap, whose milestone is checked and linked to the coming tag. It merges first, so the tag includes it.
2. Running the Release workflow by hand opens or updates a draft **release PR**. It bumps `[workspace.package] version` from the Conventional Commits since the last tag (`feat` → minor; `fix` → patch; `!` or a `BREAKING CHANGE:` footer → breaking) and writes the `CHANGELOG.md` entry. `just release-preview` shows the same result locally, changing nothing. The workflow opens the PR with `RELEASE_PLZ_TOKEN`, a fine-grained token (contents and pull requests: write), because a pull request opened with the workflow's own `GITHUB_TOKEN` starts no CI; without the token the PR still opens, but with no checks. The token is a secret of the `release` environment, whose only deployment branch is `main`, and only the job that opens the PR names that environment, so a workflow edited on another branch can't read it.
3. The maintainer checks the bump against the contract table, since labels only navigate, and edits the notes. `just release-pr [version]` does steps 2 and 3: it runs the workflow, waits for the PR, sets the version if given, opens `CHANGELOG.md` in `$EDITOR`, then pushes to the PR's branch and retitles the PR. A later run of the workflow, the recipe's included, closes a release PR that carries such a commit and opens a new one from the commits alone, so a rerun needs the same version again and the notes redone.
4. Merging the PR to `main` triggers the tag and a GitHub release with that entry as its notes.

From 0.3.1, the same run builds the Linux archives of the tagged commit and attaches them to the release (§16, decision 54): `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, built and smoke-tested as the release builds below are, and a `SHA256SUMS` file. From 0.5.0 it attaches each target's `.deb` and `.rpm` too (decision 123), and `SHA256SUMS` lists all six files; the publishing job fails when one is missing or its checksum doesn't match. The release is created first and the archives follow when their builds pass, about an hour later; if one fails, the release stays without archives until the failed jobs are rerun. cargo-binstall already installs a Linux archive, without checking `SHA256SUMS`. M10 adds that check and the installers (#357); a macOS archive only once it can be signed and notarized (decision 71).

**The Docker image** (decision 126). From the release after 0.5.0, once the archives are attached, the run publishes the image of the two Linux archives, so a failed image never holds back the archives. Each platform's job (`release-image.yml`) runs on that platform's own runner, with no emulation: it downloads the release's archive and checks it against the `SHA256SUMS` that `publish` wrote, builds the image with `just image`, runs `just smoke-image` on it, and pushes it to GHCR by its digest alone, with no tag, after checking that the image pushed holds the layers of the one tested. It builds from the tag's `Containerfile` and recipes, so rerunning can't mend a fault in them: that release goes without an image until the next.

Only once both platforms have passed does a job of its own, the only one that reads the Docker Hub token, join the two digests into one image with `docker buildx imagetools create`. It tags it with the version in `ghcr.io/nledford/ladderback` and `docker.io/nledford/ladderback`, and with `latest` when the release is GitHub's latest one, so a pre-release or an older release's run run again leaves `latest` alone. Both registries hold the same digests, and the job checks, signed out, that anyone can pull each tag. Rerunning the failed jobs publishes the same tags again. A pull request that changes the `Containerfile`, the smoke test, the Compose example or these workflows builds and smoke-tests the image on both platforms from the latest release's archives, pushing nothing (`image.yml`).

It needs, once, the `release` environment's `DOCKERHUB_USERNAME` variable and `DOCKERHUB_TOKEN` secret, a Docker Hub access token that may read and write. GHCR makes the package private at its first push, so after the first release with the image the maintainer makes it public and reruns the failed job.

**Release builds.** The archives are built from M2 on, and the Linux ones published with each release from 0.3.1 (§16, decision 54). `just release-build <target>` builds the web UI with `release_flags` and then runs cargo-dist's `dist build` (`dist-workspace.toml`; `scripts/install-dist.sh` installs the pinned dist) for one target: `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu` or `aarch64-apple-darwin`. dist builds with `cargo auditable build`, so the binary embeds the daemon's dependency list for `cargo audit bin` (`just setup` installs cargo-auditable; the workflow pins its version and checks the list is there). The archive, its SHA-256 and dist's manifest land in `target/distrib`, dist's own folder, whatever `CARGO_TARGET_DIR` says.

`just smoke-release <binary>` checks the binary (`scripts/smoke-release.ts`):

- the build its `--version` names, which must be the checkout's (decision 90) unless the script's own `--version <x.y.z>` names another;
- no pseudolocales in the binary, asked for or looked for, and neither pseudolocales nor the gallery in the wasm it serves;
- its dynamic libraries, which must be the base system's;
- on Linux its glibc floor, at most 2.35;
- then `serve` in scratch folders answering with the UI, a scratch repository initialised and one backup that leaves one snapshot.

With `--container` it runs those in clean Debian 12, Debian 13, Ubuntu 22.04, Ubuntu 24.04 and Fedora containers (Docker, no network, images pinned by digest). With `--package <file>` (a `.deb`, an `.rpm` or both) each container also installs the package of its system's format, in a container of its own with the person's configuration, data and cache folders seeded first: `--version` must say the release's version, `/usr/bin/ladderback` must be the archive's binary byte for byte, the package must hold that and its licences only and have no maintainer scripts, and after the removal those folders must be as they were.

**The packages.** `just package <target> <binary> <version>` builds the `.deb` and the `.rpm` of a Linux binary with nfpm (`packaging/nfpm.yaml`; `scripts/install-nfpm.sh` installs the pinned nfpm, as `scripts/install-dist.sh` does dist) into `target/distrib`, each with a `.sha256`. The workflow runs it on Linux after the archive is built, from the binary unpacked from that archive and given the tag's version (a build between releases gets the version its binary names), and uploads the packages with the archive. Nothing rebuilds the binary (§16, decision 123).

The `Release builds` workflow (`.github/workflows/release-builds.yml`) runs `just release-build` and `just smoke-release` for each target every night, by hand, on pull requests labelled `release`, and for each release, where only the Linux builds must pass; the Linux builds run on Ubuntu 22.04, so the binary needs no newer glibc than 2.35 and runs on Debian 12 and Ubuntu 22.04. Each archive and package is a run artifact for 7 days, and a failed nightly run opens an issue. It is not a required check.

**Release build flags.** A release is built with `--no-default-features`, which leaves out the development pseudolocales (§8.4); the component gallery (§4.5) is off unless asked for, so the same build has none. The flags are one definition, `release_flags` in the `Justfile`, and `just --evaluate release_flags` prints them. `just architecture` checks a build made with them: no `fluent-pseudo`, no gallery.

The release builds use them: `just web-release` passes them to `trunk build --release`, and cargo-dist, which can't read the `Justfile`, has the same in `dist-workspace.toml`, which `just architecture` checks against `release_flags`. `just install`, the install guide's way to install from a checkout and the one `scripts/install.sh` runs (decision 79), builds `web-release` and passes them to `cargo install --path . --profile dist`, so the installed binary is built as the archives are, with the `dist` profile (thin LTO).

**The hub until M8.** The same flags leave out the hub: its code merges to `main` behind the `hub` feature, on by default, so development and test builds have it and no release can pair, sync or serve as a hub. From the first of the hub's pull requests (#1040, slice 1), `just architecture` checks that a build with `release_flags` has no `hub` feature, and the smoke test that the binary refuses `serve --hub` and answers 404 on `/sync/v1`. A pull request merged just before M8's first release candidate deletes the feature, so the candidate is the build that ships (§16, decision 122).

The development recipes (`just web`, `just build`) don't use the flags. The Docker image builds nothing: it copies the release archive's binary, so the check and the artifact can't drift apart. A feature a release needs is added to `release_flags` and `dist-workspace.toml`, not to a workflow.
