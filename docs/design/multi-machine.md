## 7. Multiple computers

**Not in a release before M8.** The hub this section describes is built behind the `hub` Cargo feature, which development and test builds have and release builds leave out until M8's release candidate: `serve --hub`, pairing, the sync protocol, the `[hub]` table, and their pages and commands. A release refuses `serve --hub`, the pairing commands and a `[hub]` table, has the agent ID but makes no agent key, and its database holds the hub's tables empty. Without a hub, an agent maintains a repository as §7.3 says for that case, in every build. Decision 88 applies from M8's release, the first to ship protocol 1 ([decision 122](decisions/122-hub-out-of-releases-until-m8.md)).

**Becoming the hub** ([decision 136](decisions/136-an-installed-machine-becomes-the-hub.md)). Any installed machine becomes the hub in place, by the command line or, after M8, a form in Settings; a hub can also run beside a machine, as a second Ladderback it pairs with. From M8's first release, hub mode is `hub` in the `[serve]` table of `config.toml`, with the listening address (`listen`) and the allowed host names (`allowed-hosts`), read at start, and a command-line flag (`serve --hub`, `--hub=false`, `--listen`, `--allowed-host`) overrides its key ([decision 167](decisions/167-hub-mode-in-the-serve-table.md)): Settings then shows the value read-only and says the command line sets it. Hub mode turned off while any machine is paired, approved or waiting, stays on, and the daemon names those machines at start. Moving a machine's data into a container is not supported until #1050.

### 7.1 Pairing and identity

1. On the hub: **Settings → Agents → New pairing token**. The token is single-use, with a TTL of 15 min by default (5 min to 24 h). It holds the hub's key, whether the hub serves TLS itself and the certificate's fingerprint, and a one-time pairing key; the hub keeps only that key's public half, and shows the token once. An unused token can be revoked, and a rotation of the hub key voids it.
2. On the agent: `ladderback pair` (or the same in the agent's UI). The token carries the hub's address; the command reads the token at a prompt, from standard input or from `--token-file`, never as an argument, so it doesn't show in `ps` or the shell's history. The agent's UI takes the token pasted or scanned with a camera, and both ends show the hub key's fingerprint to compare. A phone, a headless machine over SSH and the share sheet are covered in [decision 121](decisions/121-pairing-a-machine-with-its-hub.md); the token, the step-up and the approval are [decision 120](decisions/120-agent-hub-connection-security.md).
3. The agent generates an **Ed25519 keypair** (its agent key) and an **agent ID** (UUIDv7) once, and keeps both in its data dir, never in the database, so `db rebuild` can't change them. A standalone agent has them too, because its backups are tagged with the ID (§7.3). The agent first checks that the hub proves the key in the token. Then it sends its agent ID, public key, hostname, machine zone (the IANA name of the time zone the machine runs in, absent when the zone has none) and a signature by the token's key and by its own, and the hub records the agent and spends the token.

   **A data folder copied from another computer stops maintaining** ([decision 144](decisions/144-a-copied-data-folder-stops-maintaining.md), #296). The ID lives in the data folder, so a restored home folder or a cloned disk brings it to another computer. Beside the ID, the agent records the machine identifier the operating system gives the computer (`/etc/machine-id` on Linux, `IOPlatformUUID` on macOS) and compares it at each start. A copy keeps backing up and refuses forget, prune and adoption (`maintenance-data-folder-copied`) until the person takes a new machine ID on the start page (`POST /api/v1/machine/new-id`), which first turns maintenance off on every repository it maintained; the new ID is used from the next start. An identifier that can't be read refuses nothing, and the log says so.

   **A new machine ID makes a new agent key** ([decision 154](decisions/154-removing-a-machine.md), #1489), whichever way it is taken: on a copy, on a machine its hub refused as a second computer, or on one its hub removed. A copy holds the original's key, and two computers must never prove themselves with one. The key is written before the ID, so a take cut short leaves the old ID with a new key, never the reverse.

   **The hub takes one computer under each machine ID** ([decision 150](decisions/150-the-hub-takes-one-computer-per-machine-id.md), #296). Each `Hello` carries the machine fingerprint, a digest of the machine ID and the machine identifier, never the identifier. The hub keeps the first fingerprint it hears under each ID and refuses another as `identity-conflict`: it takes none of that computer's reports, which wait in its outbox, lists when it last refused one, and logs it once. A `Hello` with none is taken. The way back is a new machine ID on the copy, which a machine holding that refusal, signed by its hub, may take from its start page (#1462), or, on the hub with its daemon stopped, `ladderback pairing-token --forget-computer <hostname>`, after which the next computer to connect is taken.

   **A new agent is held pending until a person approves it on the hub** (in its UI, or at its terminal with `ladderback pairing-token --approve`), which shows its hostname and key fingerprint, as the agent does; a pending agent has no grants, claims, leases or commands, and its reports are kept and not acted on (§7.3). Re-pairing the same identity (the same ID and key) reuses the existing record and keeps its approval; an ID that comes with another key is refused, unless the token is a replacement made for that ID. A hostname already registered to another agent is rejected, and the token stays good, because the UI, the `host` filter and the `machines` table all identify machines by hostname.

   **A person may reject a waiting agent or remove an approved one** on the hub's page, with no step-up, since either only takes authority away ([decision 154](decisions/154-removing-a-machine.md), #1439). The hub keeps a tombstone of its agent ID and key, and of its hostname as a record only, so another machine may take the name. The removed agent's next connection, and an ordinary token under its ID, are answered with a signed `machine-removed`, and a token under any ID that comes with its key is refused `machine-key-removed`. Its start page then offers a new machine ID, under which it pairs again with a new key and a new token and waits for approval (#1489). An agent nobody approves within 7 days lapses: the hub drops it and keeps no tombstone.
4. Every later connection is a WebSocket over TLS in which the hub and the agent prove themselves to each other: each signs a domain-separated message that holds the hub's key, the agent ID and both sides' nonces, and the agent checks the hub's signature against the key it pinned at pairing. After that every message in both directions is signed. To revoke an agent, remove it on the hub; to replace a leaked agent key, re-key it from its row. The exact messages, the pairing and the copy of a data folder (#296) are [decision 120](decisions/120-agent-hub-connection-security.md).

**The hub key.** The hub makes an Ed25519 key pair once and keeps it in its data dir, never in the database, as the agent does, with an offline recovery key pinned beside it. Each agent pins both public halves at pairing, whichever TLS mode the hub uses, so behind a reverse proxy the agent trusts the hub, not the proxy's certificate. The hub signs every message it sends (§7.2). It rotates the key with a handover the old key signs, and recovers a leaked key with one the recovery key signs. A hub that loses its key and its recovery key can't be recognized by any agent, and every agent pairs again; one hub moved or restored is not covered yet (decision 120). The key files stay out of Ladderback's own backup plans by default.

Hub TLS can be either of these:
- **Built-in.** A self-signed cert whose SHA-256 fingerprint is pinned during pairing (shown in the hub UI and included in the token string), served over TLS 1.3 only. The proofs and every later message also carry the session's `tls-exporter` value (RFC 9266), so they hold on that one session.
- **External.** A reverse proxy such as Caddy or Traefik, using normal CA validation. Forward the whole `/sync/` prefix to agents, not `/sync/v1` alone: an agent tries a newer hub's newer handshake path first, and a 404 there that the hub's signed list contradicts is refused as `handshake-hidden` (decision 120). Pass the WebSocket upgrade through and add no `Origin`: the hub's sync routes take only an agent's handshake (§10.1). Keep `/` and `/api` on a trusted network. The proxy ends TLS, so the proofs carry no session binding, and the hub key alone proves the hub. The agent names which kind it uses in `Connect`, and one hub serves both kinds, so agents on the LAN pinned to its certificate and the same agents through a proxy work side by side (decision 120).

Both modes serve UI, API and `/sync/v1` on one listener; the hub's default port is 9899. An agent refuses a plain `http://` hub address that isn't loopback.

### 7.2 Sync protocol (`/sync/v1`, WebSocket, JSON, versioned)

Agent → hub:
- `Hello { machine_version, hostname, protocols: [min, max], clock: Timestamp, zone?, machine? }`, signed by the agent. `machine_version` is the agent's build as `--version` names it (`BuildDto::display`, `0.3.0+3f937cf` between releases; decision 90). The hub records the clock offset and warns above 5 min. `protocols` is the range of sync protocols the agent speaks (no hub has shipped, so it replaces the single `protocol: 1`); the hub answers `Welcome`. `zone` is the machine zone, so a machine that moved tells its hub at its next connection (#114); how the hub reads and keeps it is [decision 120](decisions/120-agent-hub-connection-security.md) ("Signed messages after the handshake"). `machine` is the machine fingerprint (§7.1), absent when the computer's identifier can't be read; one other than the hub took under the ID is refused `identity-conflict` ([decision 150](decisions/150-the-hub-takes-one-computer-per-machine-id.md)).
- `PlansSnapshot { plans: [PlanPublic] }`, sent on connect and on change. Secrets are never included. As built (#1440), it is `{ plans: [{ plan, last?: { at, outcome }, next? }], left_out }`: at most 16 plans in the configuration's order, each with its last run's time and status and its next planned run, and how many more the agent has. The hub answers it with `PlansAck`.
- `Progress { op_id, step?, unit, current, total?, at }` (#1440): the latest progress of a running operation, as the local Operations page draws it (decision 83). The hub answers it with nothing.
- `ReposSnapshot { repos: [{ repo_id, alias, requested_maintenance, others_snapshots }] }`, sent on connect, on change and at least once a day, since each one renews the leases its sender holds (§7.3). `others_snapshots` says the repository holds another agent's tagged snapshots, which only the agent sees. As built (decision 151), it carries no `alias` and is sent in every session; `others_snapshots` is what the agent's last listing of the repository, at most a day old, showed (§7.3, decision 156).
- `OpEvent { epoch, seq, op_id, event }`. `epoch` is a random ID created with the agent's outbox; `seq` increases within an epoch and is assigned when the event enters the persistent outbox, so the agent replays from the hub's last acknowledged `(epoch, seq)` after a disconnect. A rebuilt database starts a new epoch, so its events are never mistaken for already-acknowledged ones. Progress events are sent live but never stored or replayed.
- `Heartbeat { running_ops: [{ op_id, repo_id, kind, index_read_at, deadline }], next_runs }`, every 30 s. As built (#1463, [decision 159](decisions/159-long-lived-hub-connections.md)), it is `{}`: `running_ops` and `next_runs` come with the owner prune guard (#573), their first reader. The hub answers each with `HeartbeatAck`.
- `RestoreResult { command_id, op_id | error }`
- `ReleaseAck { repo_id, epoch }`: the old owner's acknowledgement that it dropped a lease, which lets the hub grant the new owner (§7.3). The hub answers it with `Released`.
- `TransportAck { number }`: the agent holds the hub's list of addresses of that number.

Hub → agent:
- `Welcome { protocol, hub_protocols: [min, max], machine_protocols: [min, max], generation, hub_handshakes, hub_version, signed_at, status }`, signed (below): `protocol` is the highest both sides speak, or absent when they share none; `hub_protocols` lets the agent say which side is out of date; `machine_protocols` echoes the range the hub saw, so an agent notices a range lowered on the way; `generation` only rises, and an agent refuses a lower one than it holds (`generation-lower`); `hub_handshakes` names the handshakes the hub speaks, which the agent checks against a 404 on a newer path, so a hub reinstalled as an older release keeps its agents syncing and a hidden newer handshake is refused; `hub_version` is the hub's release; `signed_at` is the hub's clock; `status` is `pending` until a person approves the agent, then `approved` (decision 120). It answers `Hello`, the first message after both proofs (§7.1, step 4).
- `Ack { epoch, seq }`
- `HeartbeatAck {}`: the hub's answer to a `Heartbeat`, so an agent learns within the 15 seconds it gives each answer that its connection is gone. Signed (below).
- `PlansAck {}`: the hub kept the agent's `PlansSnapshot`.
- `RepoGrants { generation, grants: [{ repo_id, owner, epoch, expires_at, keep_delete, prune_margin }] }`: the owner lease and the deadline inputs for each repo (§7.3). Sent on connect and in reply to each `ReposSnapshot`, which renews them. The agent caches them. Signed (below). As built (decision 151), it answers each `ReposSnapshot` and carries `signed_at`, the hub's clock when it signed, and each grant only `repo_id`, `epoch` and `expires_at`: every grant is the receiving agent's own lease, and `keep_delete` and `prune_margin` come with the owner prune guard (#573).
- `Released { repo_id, epoch, signed_at }`: the hub's answer to a `ReleaseAck`, the same whether it ended the lease or the release named one the agent no longer held. Signed (below).
- `RunPlan { command_id, requested_at, plan_id }`, `CancelOp { command_id, requested_at, op_id }` (milestone 9). Signed (below).
- `RestoreRequest { command_id, requested_at, repo_id, snapshot_id, paths, requested_by }` (milestone 9). Always restores into a new folder. Refused unless the agent sets `allow-hub-restore = true` (§10.4). Signed (below).
- `FetchLog { op_id }` → agent replies `LogChunk`
- `UpdatePlan { plan }`: **reserved for post-v1.** Opt-in per agent ("allow hub to edit my plans"). The message type is reserved in protocol v1 so that adding it later isn't a breaking change. Signed when it ships.
- `TransportStatement { generation, number, addresses }`: the addresses agents may reach the hub at, each with its kind (decision 120). An agent replaces its list only when the statement's (generation, number) is higher.
- `Removed`: the hub removed this agent.

**Signed messages** ([decision 120](decisions/120-agent-hub-connection-security.md)). **Every message after the handshake, in both directions, carries the sender's signature** over its payload, the hub's key, the agent's ID and the connection's two nonces and binding, with a sequence number; hub messages also carry an expiry. A receiver acts on, stores and answers none of them unsigned, replayed, out of sequence or expired. Nothing is encrypted a second time, and no secret crosses the link (I4). A command (`RunPlan`, `CancelOp`, `RestoreRequest`) also carries a command ID and the time it was requested, and an agent runs none older than 15 minutes or twice.

**The handshake on the wire.** Until the handshake ends, `/sync/v1` carries JSON text frames tagged by `type`, with bytes as unpadded base64url. The hub reads frames of at most 4 KiB, closes a connection that sends no first frame within 2 seconds or doesn't finish the handshake within 15, and holds at most 32 connections not yet proved, closing the oldest for a new one. A refusal before the hub's proof is the close frame's reason, the error code's wire name. The agent gives a connection 10 seconds to open and the hub 15 seconds for each answer. `ladderback serve --hub` serves `/sync/v1` on its one listener; until `serve` has the built-in TLS, its sessions carry no exporter, so a `Connect` that asks for a pinned binding is closed with `binding-unavailable` (#567).

**What is built so far (#567).** A paired agent connects and proves itself: after the hub's `Challenge` it sends `Proof` with a counter greater than any it used before. The hub refuses, with one signed `proof-refused` and a close, an agent ID it never registered and a proof that doesn't hold under the key it registered or for a binding kind it paired with. A proof under the key of an agent a person removed is refused with a signed `machine-removed` instead ([decision 154](decisions/154-removing-a-machine.md)). A good proof keeps the greater of its counter and the one the hub held, and records when the agent was last seen; telling a copy of the agent by its counter is #296's.

The agent then sends `Hello` as its first signed message (sequence number 1), and the hub answers with a signed `Welcome` whose `status` says whether it holds the agent pending or approved it. The agent acts on that `Welcome` only if its signature, sequence number and kind hold, its expiry is no more than 15 minutes past its `signed_at`, it echoes the agent's protocols and picks the highest shared one, and its generation is no lower than the one the agent pinned. After `Welcome` the hub closes a pending agent's connection; an approved agent's goes on with its reports (below). `ladderback hub-status` makes one such connection and says what the hub answered ([decision 121, "From a terminal"](decisions/121-pairing-a-machine-with-its-hub.md)).

**Reports (#568, [decision 145](decisions/145-the-agents-outbox-and-the-hubs-reports.md)).** A paired daemon keeps each operation's start and end in its outbox, in SQLite, as it publishes them; progress, warnings and the rest are no reports. An approved daemon keeps one signed sync connection while it runs, and sends reports in order, at most 32 places ahead of the hub's signed `Ack`s. The connection also carries plans, progress, leases and the `Heartbeat` defined by decision 159. A pending agent sends nothing, and its reports wait. None of this touches the agent's operations, so an agent that can't reach its hub backs up on schedule all the same.

**Retries.** A failed connection is tried again after 1 s, doubled each time up to 5 minutes; a connection on which the hub answered a heartbeat starts that over at 1 s, and its end is no failure. A hub that stops answering, mid-handshake or before an `Ack`, fails the connection after the 15 seconds the agent gives each answer, and the agent tries again as after any failure. A live connection is not replaced by a polling session; after a drop the reconnect carries the outbox from its last acknowledgement.

**Online (#1463, [decision 159](decisions/159-long-lived-hub-connections.md)).** An approved agent holds its connection while it runs and sends a `Heartbeat` as it connects and every 30 seconds after, even while it lists its repositories for a lease exchange. The hub shows a machine online from its connection's first message after the `Welcome` until the connection ends, so a check from the machine's terminal, which sends none, leaves the daemon's connection in place. It closes a connection that sent no message for 90 seconds, three heartbeats missed, on its monotonic clock. Its browsers hear `MachineOnline` and `MachineOffline` as that changes; the dashboard says "Online now." or else when the hub last heard from the machine, the end of its last connection. A newer connection closes the older, and removing the machine closes its connection. Who is online lives in the hub's memory.

**The bounds.** The outbox holds at most 10,000 reports: full, it gives up its oldest start for a new report, and refuses one only when it holds 10,000 ends; either is a warning in the agent's log.

The hub takes a report once: past the last place it took of that epoch, the next place, else it acknowledges and drops it. One 32 or more places behind that last is no report sent again: the agent's database was restored from an older copy, and its log says so once per agent while it runs (#1387). It keeps the last place of each agent's 8 newest epochs, the one it just took always among them, and at most 10,000 reports of each agent, letting go of the oldest past that; it counts them, for the dashboard (#569), and its log says so once per agent while it runs, with the count and nothing a report says (I4).

Those bounds cover what reaches the outbox. The event bus can drop a start or an end from the reporting task's queue when the task falls behind, and then neither side says so (#1437).

**What the hub's browsers hear (#569, [decision 149](decisions/149-the-hubs-dashboard.md)).** Each report the hub takes, start or end, is told to its browsers as `MachineReported` with the machine, the operation and its outcome so far; a report dropped as already taken, or as from an older database, tells nothing. The dashboard then reads the machine's 40 newest reports again and folds them into its 10 latest operations, so the browser never rebuilds them from events. A machine that starts waiting for approval, one approved, and one removed or rejected are told as `MachinePending`, `MachineApproved` and `MachineRemoved` ([decision 154](decisions/154-removing-a-machine.md)); a lapse is told by no event. These events reach only a session's stream, or the browser's with sign-in off, as the hub's routes do.

**Plans and progress, the agent's side (#1440).** A paired daemon reads its plans, each one's last run from its operation log and its next run from its scheduler, at each connection and every 60 seconds between them, and holds them in memory until the hub acknowledges them. It sends a running operation's progress when it is new and 5 seconds have passed since the last it sent. The long-lived connection makes both updates incremental rather than separate sessions.

**A cancel is an end.** A cancelled operation announces `operation-cancelled`, which the outbox keeps as a `cancelled` report, as it keeps a success or a failure, and on which the daemon lets go of that operation's progress. The hub then shows the operation cancelled, and its progress no more. Migration `0025_sync_plans_progress` builds the outbox's table again so that it takes the new report.

**Plans and progress, the hub's side.** The hub keeps each machine's latest snapshot of plans and latest progress, each in place of the one before (migration `0025_sync_plans_progress`), and tells its browsers `MachinePlans` and `MachineProgress`, each of which reads the machines again. It shows a progress only while the machine's reports say that operation runs. The dashboard shows each machine's plans in a table, with a warning when the machine has more than it sent, and the progress in the shared progress bar, which is never announced (decision 83).

**Leases (#1443, [decision 151](decisions/151-a-paired-machine-maintains-only-under-its-hubs-lease.md)).** A paired daemon asks for its leases when each long-lived connection starts and whenever 15 minutes have passed on its clock since the last; a clock set back counts as time passed. Reports no longer trigger an exchange: they cross the held connection as they come (decision 159). It first releases leases whose repositories no longer ask for `local`, except while maintenance runs there, then sends `ReposSnapshot` with up to 9 repositories and takes the hub's `RepoGrants`. A configuration it can't read skips the exchange, with a warning, and keeps the connection, trying again at its next look. A hub without an ownership registry answers neither message, so the session fails after the 15 seconds the agent gives each answer.

**Versions** ([decision 88](decisions/88-hub-and-agent-version-compatibility.md), which sets the window and how long it lasts). Compatibility is counted in protocols, not releases: new optional fields stay within a protocol, and a signature covers a payload's bytes, so an older reader verifies a payload that gained one. The handshake (`Connect`, `Challenge`, `Proof`, `Pair`, `Paired`, their signatures, `Hello`, `Welcome` and those messages' fields) is the same in every protocol, so any two releases can negotiate and pair. From M8's release, the first to ship it, its label and path never change in place; a change would be a new path and a decision (decision 122). The key exchange of a pinned connection, `X25519MLKEM768` alone, belongs to the path too, so an agent a release behind is never refused at the TLS layer before it can be told it is out of date.

With no protocol in common, the agent keeps running its plans locally and says whether the hub or the agent is out of date, naming both ranges; the hub lists the agent as needing an update, or itself, and does so only for an agent whose proof checked out. Until they share a protocol again the agent ignores its cached `RepoGrants` and computes deadlines as if it had never received them (§7.3, layer 1), and its lease lapses as with any lost connection, so once it expires the agent runs no scheduled maintenance. An agent on the oldest protocol the hub speaks, or a hub on the oldest its agent speaks, is told so, with the release that will drop it.

A hub reinstalled as an older release that speaks only a lower handshake than the one it proved is no mismatch: the agent falls back to the older handshake the hub proves in its signed list, keeps syncing with no click, and shows which hub release it now sees; no identity conflict or re-pairing follows (decision 120).

The browser never talks to agents directly. When looking at a remote machine, the hub UI calls hub APIs, and the hub forwards requests like "run now" or "fetch log" over the agent's socket.

### 7.3 Repository maintenance: exactly one owner

**Repository identity.** A repository is identified by its rustic repository ID (`repo.config().id`), read when the repo is connected. The `[repositories.<name>]` key is only a local alias, and different machines may reach the same repository through different `repository` strings (an SFTP URL on the laptop, a local path on the NAS).

**One alias per repository** (decision 49). An agent's configuration names a repository once, so its plans have one history and one maintenance request. Connecting or initialising records the ID Ladderback read as `repository-id` in the entry (§6.1); an entry written by hand or imported from a profile has none, since Ladderback never opened it, until the first job that opens the repository has the daemon record the ID it read, adding the one key to the entry as written (decision 57).

An entry's location is the whole of where it points: its `repository` string, `repo-hot` and its three option sets (`options`, `options-hot`, `options-cold`), where an `opendal:` backend keeps its bucket or root. The password and the options that hold a credential (those the `inline-secret` warning names) are how to open it, not where it is, so moving a credential from text to `${VAR}`, adding one or removing one leaves the same location.

A drive is the exception: on opendal's Dropbox, Google Drive, OneDrive and Yandex Disk only a credential names the account, so two accounts can share one `root`, and there the credentials count, lest one account's plans back up into the other's. The cost: on a drive, a token moved from text to `${VAR}` is another location, so a profile that writes it the other way is refused under the alias that holds it, and two entries for one account with the token written two ways are caught as one repository only when both know their ID.

Two entries are one repository when both know their ID and the IDs are equal, or, when either knows none, when they are at one location, so two buckets of one backend are two repositories:

- `AgentConfig::new` refuses a configuration that names one repository twice (`SameRepository`, at the second entry's key).
- Connecting or initialising under a new alias a repository the configuration already holds, at the same location or with the same ID, is refused with `repository-already-configured` (HTTP 409, naming the alias it has); an alias already taken is refused first, with `repository-alias-taken`.
- A local path is compared without `local:` and without trailing `/`s; any other location written another way (an SFTP URL beside a mounted path) is caught only when both entries know their ID (decision 49, point 2).

A job opens the repository and, when the entry has an ID, compares it before it reads or writes anything: a location that now holds another repository fails the operation with `repository-replaced`. The forget preview's own read of the retention (`adapters/engine/src/retention.rs`) opens the repository again in process without comparing; it runs only after the preview's listing job, which compared it.

**Locations.** A repository may be reached at several locations (§6.1, decision 80). They are each machine's own configuration and stay on it: the sync protocol carries the repository ID and an alias, and the operation records it sends carry no location, position or outcome, so the hub learns nothing of where a machine was from them. A log the hub fetches holds what logs hold (rustic names the repository's address in its own lines, §10.2), with a position and an outcome code and never a network name. Ownership, claims and leases are keyed by the repository ID, so every location is one repository to them; the hub has its own entry, with its own locations, for a repository it maintains, and two agents may reach one repository by different locations.

**Meaning changes take a new protocol.** A change to what `RepoGrants`, `ReposSnapshot.requested_maintenance` or `Heartbeat.running_ops` mean (leases, grants, deadlines, ownership) takes a new sync protocol number (§7.2), never an optional field an older peer could ignore (decision 88).

**Owner.** Each repository has one maintenance owner (I1):

- `hub`: the hub runs forget, prune and check. Required for repos several agents use.
- `agent:<id>`: one specific agent runs them. Only for repos no other agent uses.
- `none`: nothing in Ladderback prunes. Use this if an existing cron job keeps doing it during migration. Set explicitly on the hub's repo page, or by a standalone agent's config.

**Requests and grants.** An agent's `maintenance` setting is a **request**: `local` asks for `agent:<self>`, `hub` asks for `hub`, and `none` makes no claim; a repository with no `maintenance` asks for `none`. Which request a saved repository gets (decision 48): one created under a name asks for `local`, since nothing else can know it yet; one connected asks for `local` only when the person turns on **Maintain this repository from this agent**, and for nothing otherwise, since another agent or the hub may already maintain it; an imported profile asks for `local` only when its `[forget]` has `prune = true` (§6.2). The Snapshots page turns maintenance from this agent on (`local`, replacing `hub`) or off (`none`, leaving `hub`), refused with `maintenance-busy` while a maintenance run of it is running here. With a hub configured, the agent reports it in `ReposSnapshot`, and the hub decides:

- The first claim for a repository ID is granted; conflicting claims are rejected and shown on both machines (`repo.claim_rejected`, §11). Only an approved agent claims: a pending agent (§7.1) has no claims, grants or leases, its reports don't make another agent's claim refused and its running operations don't delay a prune, and an approved agent's reports are acted on only when they are signed (decision 120).
- `agent:<id>` is granted only while no other agent reports the repo and the repo holds no other agent's tagged snapshots. When a second agent later reports it, the hub stops renewing that lease and raises an alert asking the user to configure the repo on the hub. Until then nobody prunes, which is the safe direction.
- `hub` is granted only once the hub has its own repository entry and secret for that repository ID. Until then the claim shows "pending: not configured on hub", with an alert, and nobody prunes.

**What an agent knows of other agents' snapshots** ([decision 156](decisions/156-an-agent-knows-others-snapshots-from-its-last-listing.md)). Every listing the daemon runs notes, for the repository it opened, when it started and the newest snapshot whose `ladderback-machine:` tags name another agent or disagree; the agent's own tag, the history of an earlier installation once adopted under it (decision 62), and an untagged snapshot don't count. Each report judges that snapshot on the agent's clock: recent within decision 62's 30 days, or ahead, it sets `others_snapshots`.

A listing stands for a day on the agent's clock, either way. Before each sync, the agent lists once each repository it asks to maintain (`local`) whose ID it records and that has no listing standing, unless an operation holds that repository here; a listing that fails is warned of once and tried again at the next sync. A repository with no listing standing, or listed under another machine ID, is reported with `others_snapshots`, since a lease on it can't be shown safe; the agent gets the lease at the sync whose listing shows none.

A grant is a **lease** with an `epoch` and an `expires_at`: 7 days from its grant or its last renewal, which is its holder's report of the repository with `local` again. An agent runs scheduled maintenance only while it holds an unexpired lease, and records the epoch on each maintenance operation. To move ownership, the hub stops renewing the old lease and grants the new owner only after the old owner's signed `ReleaseAck` for the epoch it held (sent once it has dropped the lease and has no maintenance running on the repository) or the lease expires, so two owners never overlap even when the old owner is offline or deleted. A hostile hub can still break this (decision 120, "What a hostile hub or agent can do"). A hub restored from a backup is held back from it by the start rule below (decision 137).

**When a lease and a report count** ([decision 147](decisions/147-the-hub-decides-leases-on-each-report.md)). A renewal never moves an expiry earlier, so a hub clock set back can't shorten a lease its holder was told of. The hub counts a lease until an hour past its expiry before granting the repository to another agent, so a holder whose view of the hub's time drifted by less than that has stopped first. Another agent's report counts as using the repository for 7 days after the hub took it, so a machine gone longer stops keeping others from it. The hub decides every repository of one report together, so of claims that race, exactly one is granted.

**On a paired machine** ([decision 151](decisions/151-a-paired-machine-maintains-only-under-its-hubs-lease.md)). From the moment it is paired, a machine runs a forget, a prune, a check or an adoption, scheduled or asked for, only while it holds a live lease on the repository the job opens, and otherwise refuses it with `maintenance-no-lease` (HTTP 409) before anything is stored, its log saying whether it holds none or the lease ran out. A preview asks for none. A repository whose ID it doesn't know yet holds none.

**A prune checks again at its first delete** ([decision 161](decisions/161-a-prune-asks-before-it-deletes.md)). A prune works out its plan, warms up and repacks, and at its first delete asks the daemon (`ready_to_delete` on its stdout) whether it may delete; the daemon checks again, as at the run's start, that this machine may maintain the repository, renewing nothing. The prune deletes, with the plan it worked out, only on `delete` on its stdin. On `delete_nothing` it deletes nothing and fails with `maintenance-lease-lapsed`; with no answer within 60 seconds, it deletes nothing and fails with `maintenance-deletion-unanswered`. What it repacked stays, as after a prune stopped there. A machine that isn't paired is always answered yes. A deletion already begun finishes, and I2's delayed deletion protects the packs it marked.

**Paused maintenance** ([decision 158](decisions/158-maintenance-paused.md)). While a paired machine holds no live lease on a repository it asks to maintain (`local`), its maintenance of it is paused: since its lease ran out, or since it first noticed it holds none. The repository list says since when (`maintenance-paused-since`, §4.2), and the Snapshots page warns of it before the maintenance buttons. Every 15 minutes, as often as it asks for grants, the daemon notes each pause in its database, keeping its date, and drops the pause of a repository it now holds a lease on or no longer asks to maintain; a grant clears the shown pause at once. A pause that has lasted 14 days is told once through the notification rules (`repo.maintenance_paused`, §11). Noting pauses never writes the leases or floors, so a grant taken meanwhile stands (I1).

Each `RepoGrants` replaces every lease the machine holds. A lease's end is kept on the machine's own clock, from the moment its request left plus the time from the hub's `signed_at` to `expires_at`, so it ends no later than the hub's, and time asleep counts. Leases and epoch floors are kept in its database. A grant below the floor is refused and only logged (`epoch-lower`, no error code), and the machine holds no lease on that repository until a grant at or above it. The hub's grants and the machine's leases and releases are each on the disk before either side acts on them, short of a power cut on macOS ([decision 164](decisions/164-the-store-commits-with-synchronous-full.md)): the floors catch a hub restored behind them, not one that lost a grant and gave its epoch again.

A machine that pairs with a hub it doesn't pin, as one that pins no hub does, forgets its leases and floors before it pins that hub: a new hub's epochs don't follow them, and a machine with no pin isn't paired and maintains under no lease, so they protected nothing meanwhile. The cost is that one that lost its pin and pairs with its own hub again no longer catches a rewound copy of it. One that pairs again with the hub it pins, or follows a handover or a recovery, keeps them (#1481).

**A rewound hub.** A machine refuses a grant below the highest lease it has seen for that repository, its epoch floor, ordered by recovery number, generation and epoch (`epoch-lower`). A hub that hears an epoch floor above its own counter, or is shown a grant it signed for a machine its registry doesn't know, grants nothing until it leaves recovery mode: a person's confirmation on the same machine, the recovery handover on another. A hub moves by handover, never by file copy, and a restore doesn't raise the generation (decision 137). Recovery mode is built; the machine identifier check still stops maintenance after a copied data folder, while hub recovery relies on the floor and its hub-signed proof carried in the heartbeat.

**The start window** ([decision 157](decisions/157-the-hubs-start-window-runs-on-its-monotonic-clock.md)). After any start, a restart or a restore, with or without recovery mode, no repository changes owner until every agent whose last report named it has reported since the start, or 7 days and an hour have passed since the start on the hub's monotonic clock. A repository no agent's last report named waits on every agent whose last report named any, since a restored hub can't tell which began using it after the backup. Until then a claim on it with no lease binding is refused, and its holder's lease is renewed as ever. The hub reads who used each repository at the first report after the start, however old each report is, and an agent's report counts as its heartbeat once it is stored. The hub runs no maintenance of its own yet; when it does, it waits the same.

Without a hub, `local` runs directly, and a second standalone owner can't be detected. The agent warns instead when a repository it maintains holds snapshots from **other hosts** (§3.1): the history's groups, the preview of a forget, an adoption or a prune, and the run of one carry the warning `maintenance-other-hosts`, which counts the other hosts and names the first five, sorted, each once; the run keeps no more of them than that. The Snapshots page says it before its buttons and in the review, and the daemon's log records it with the run, each host name escaped, since a repository's host names are anyone's to write. A check doesn't warn: it changes nothing.

Which host a snapshot is from:

- A snapshot is this host's when it carries this agent's own `ladderback-machine` tag, whatever host it records, as one made before the machine was renamed.
- A snapshot is another host's when it carries another agent's `ladderback-machine` tag and was taken in the 30 days up to the `Clock` port's now, or after it, whatever host it records: two machines with one hostname that both maintain a repository and back up to it see each other's agent ID (#214). A reinstalled machine's old agent ID stops warning once its newest snapshot is older than that; adopting its history quiets every view after the adoption, whose own preview and run still warn (§16, decision 62).
- Any other snapshot is this host's when its host is the machine's own name, the agent's `hostname` or any plan's `host`, compared exactly, so a machine that was renamed as well as reinstalled names its old host in its configuration to quiet it.

What this misses (a second maintainer that hasn't backed up to the repository in 30 days, clocks more than 30 days apart, a machine cloned with this one's data folder) is listed in decision 62. A data folder copied to another computer is told at start by its machine identifier and stops maintaining (§7.1, decision 144); a copy that keeps the identifier too, such as a cloned virtual machine, is still missed.

`hub` and `none` run nothing on this agent: a forget, prune, check or adoption of such a repository, and the preview of one, is refused with `maintenance-not-owner` before the repository is opened, and the Snapshots page shows its history with no maintenance buttons and a sentence that says why and how to ask for `local`; that history warns of no other host, since this agent maintains nothing there. The repository list's `maintained-here` tells the page which is which (§4.2).

**A write-only machine.** On a repository whose `protection` is `append-only`, a machine whose chosen location refuses deletes is refused forget, prune and adoption with `maintenance-write-only` before any delete call, after `maintenance-not-owner`; a check still runs. Under `object-lock` a delete only adds a marker, so no machine is write-only and the owner's maintenance runs as usual. The maintenance owner holds the unrestricted credentials, through the sources of §10.2, and the hub doesn't host that endpoint for a repository it doesn't own. A copy is counted as protected in the 3-2-1 view only if it is immutable and neither the hub nor any machine that backs up to the source or the copy has a route that can delete there (the file system, SFTP or an unrestricted endpoint), whatever its `protection`; the person confirms what Ladderback can't see (decision 138).

**Snapshot ownership.** Every Ladderback backup carries the tags `ladderback-plan:<plan-id>` and `ladderback-machine:<machine-id>` alongside the user's tags, label and host. The host is the plan's snapshot host (§3.1): the plan's `host`, else the agent's `hostname`, else the machine's own name, which rustic chooses (`Plan::snapshot_host`). Plan IDs must be unique within an agent's config; the importer adds a suffix on slug collisions. A backup's parent is the newest snapshot with the same two tags, passed explicitly in `ParentOptions`; when none exists yet (the first backup, or history imported from plain rustic), it falls back to rustic's default choice of the newest snapshot with the same host, label and paths, so a plan that names the host its imported history records continues that history. Changing a plan's sources, label or the machine's hostname therefore keeps its history attached to the plan.

**Forget algorithm (owner):**

1. Load all snapshots. Group tagged snapshots by `(ladderback-machine, ladderback-plan)`. A snapshot whose two `ladderback-machine:` tags or two `ladderback-plan:` tags carry different text, as a hand edit with `rustic tag` can leave them, names no owner of that kind, whichever tag comes first and even when one names this agent: no plan owns it, and it is listed as orphaned under the tags that agree (I6; `OwnerTag`, decided 2026-11-14, #286). Tags are compared exactly, case and spacing included; the same tag twice is no disagreement.
2. For each group, apply the matching published plan's `KeepOptions`, taken from a `PlansSnapshot` the agent signed. A tagged group whose plan or agent no longer exists is left alone and listed as "orphaned"; the user can attach a policy, delete it explicitly, or **Adopt** it into another plan (for example after a reinstall that created a new agent ID). A removed agent's ID can't be registered again with an ordinary token, so a rogue can't claim an orphaned group's plan IDs (decision 120).
3. **Untagged snapshots are never touched by default** (I6). They are grouped by the repo's `group-by` (default `host,label,paths`) and listed as "unmanaged groups". When a group's host, label and paths equal a plan's host, label and sources (after the same normalization rustic applies when it records paths), the UI offers **Adopt**: the owner rewrites those snapshot files with the plan's tags (new snapshot IDs, same trees). Examples of unmanaged groups are snapshots from an old cron job or a retired machine, and history imported from plain rustic.
4. **Preview first.** A forget and an adoption are previewed before they run: the owner evaluates the selection a run would make (steps 1 to 3) and says which snapshots of each plan the policy lets go, which it rewrites, and what is left alone (I6), without taking the maintenance slot or writing to the log. A person confirms from that review, and the start carries the preview's `selection`, a fingerprint of the exact snapshot IDs: a repository that changed in between (another backup, another machine's forget, an edited policy) refuses the run with `maintenance-selection-changed`, and the run is previewed again, rather than removing what nobody reviewed.

   A prune is previewed with the engine's own dry-run plan (the packs it would mark, delete, and mark for recovery or bring back, and the `keep-delete` wait before anything marked is deleted, I2), a check by whether it reads data. The optional approval threshold (more than N% of a group) is not built: every forget is confirmed by a person who saw its preview (§16, decision 44).

**Prune** runs after forget, on its own schedule (default weekly), with `keep-delete` ≥ 23 h (default **6 days**) and `max-unused` (default 5%). `instant-delete` and `early-delete-index` are never offered (I2). The default is just under the prune interval: a prune only deletes packs marked at least `keep-delete` earlier, so with a 7-day `keep-delete` a weekly prune that starts a few seconds early would skip last week's marks and reclaim space only after 14 days. The same wait applies to a marked pack a snapshot uses again: one prune marks it for recovery and a prune at least `keep-delete` later brings it back, so at the defaults that snapshot can't be restored until up to about 14 days after it was written (§2.2).

**Long-backup guard (I3).** Three layers:

1. **Worker deadline.** Every backup gets `deadline = index_read_at + keep_delete − prune_margin`, where `index_read_at` is taken just before the worker starts reading the index and `prune_margin` = 1 h + the longest prune duration recorded for that repo. The deadline is measured in wall-clock time, so time asleep counts. The worker's watchdog and the daemon enforce it (§4.1). An agent that has never received `RepoGrants` for a repo assumes rustic's 23 h `keep-delete`, which can only make the deadline earlier. An agent that owns its repository (`agent:<id>`) computes its deadlines from its own `keep-delete` and never from the grant's, so a hub can't stretch them; on a hub-owned repository the other agents take the grant's values (decision 120). The owner refuses to prune, and alerts, if `keep_delete` < `prune_margin` + 12 h, since backups would then get less than 12 h.
2. **Owner prune guard.** Before pruning, the owner waits for every unfinished backup on that repo that started reading the index before the previous prune **finished** (a backup that reads the index while a prune runs still sees the old index), as seen in heartbeats (online or offline agents) or, for an agent owner, its own running jobs. It waits until each one reports a result or passes its deadline. The hub caps any reported `deadline` at `index_read_at + keep_delete`, with `index_read_at` no later than the hub's clock, so a rogue agent can't hold the guard for ever. Only those backups can reference packs this prune may delete, so newer backups never delay it and frequent backups can't starve it. This layer is advisory; layer 1 is the guarantee.
3. **Duration warnings.** The owner warns when a plan's historical duration gets close to its deadline, and for a first backup that may take longer than `keep-delete` the UI suggests raising it until the backup finishes.

Backups made outside Ladderback (the rustic or restic CLI) are not covered by the guard.

**Check** runs weekly by default, with an optional `read-data-subset` such as `5%` for a rolling data check. Forget, prune and check on one repository are serialized (I7).

**Restic warning (I5).** If a restic client must still write to the repo, only its **backups** are safe: they take a non-exclusive lock, which rustic ignores, and restic simply doesn't see packs in `packs_to_delete`. **restic `prune`, `forget`, `rewrite` and `repair` must never run** on a repo Ladderback maintains. `restic prune` deletes every pack it doesn't index, including the ones rustic marked for delayed deletion, and leaves stale marks behind. `restic check` is safe but reports rustic's marked packs as "additional files" and suggests running `restic prune`; the repo page warns about exactly that suggestion.
