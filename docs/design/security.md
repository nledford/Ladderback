## 10. Security

This section decides how the web UI and the API are protected, how repository secrets are resolved and kept out of every output, what an agent, a restore, an MCP client and a repository location may do, and what the release check sends.

**Who is trusted** (§16, decision 99). Ladderback runs on a person's own computer, as a hub or an agent. The person, and every program running as their operating-system user, AI tools and development tools included, can already read and write the data folder: `config.toml`, the SQLite store, the admin password's hash, the logs. Ladderback doesn't rely on keeping its data from them, and a weakness that needs such a program first is not a security finding unless it reaches further than that user already could. Root and the machine's administrators are outside every boundary here.

What this section defends against instead:

- other machines that can reach the address the daemon listens on;
- other operating-system users of a shared machine, once an admin password is set ("Local users", §10.1);
- the storage a repository lives on, and the services in between;
- text from outside that a program acts on: an MCP client's calls, rustic's output.

I4 is unchanged, for reasons that reach beyond the person's own user: argv is visible to other users; environments are handed to hooks and the programs they start; logs, templates, sync messages and the UI leave the person's control. The rules that keep secrets out of the data folder stand too (repository passwords in the keyring, the generated password of decision 89 only in the daemon's memory), because the data folder can be copied, synced or backed up off the machine; they aren't a defense against the person's own programs. The Justfile's recipes are development tools for contributors who know the risks, so they may read the daemon's local state directly (#699).

### 10.1 Web UI

This section decides who may use the web UI and the API, what every request is checked for, and what the daemon says and refuses when it listens beyond the machine.

- Binds to `127.0.0.1` by default.
- **Sign-in is optional**, as in Backrest (§16, decisions 11 and 70). It is **on** while an admin password is set and **off** otherwise, and the daemon decides which when it starts: `ladderback set-password` turns it on at the next start, and a daemon started with it off stays off. With it on, every `/api/v1` request but the session route's own (`/api/v1/session`, which tells the page where it stands, signs in and signs out) carries a live session's cookie or an API token (below), and the events stream's handshake does too; without either it is refused with `401` and `sign-in-required` before any route runs. The web UI's files are served without a session, so the page can ask for the password.
  - **The admin password.** `ladderback set-password` asks for it twice at a terminal, without showing what is typed, or reads one line of standard input; it never takes the password as an argument, which other users of the machine could read. It takes 8 characters or more and at most 1024 bytes. Only an argon2id hash is kept (the `argon2` crate's defaults, a new salt each time), in `admin-password` in the data folder, created with mode `0600`, never in `config.toml`. A hash file the daemon can't read, one other users can read, one that isn't a regular file, or one that isn't an argon2id hash, refuses the start: it never means sign-in off. The daemon checks one attempt at a time (each hash takes about 19 MiB), and a password over 1024 bytes is refused unhashed.
  - **Reading the password and its file safely** (#399, #633, #1256). Ctrl-C, Ctrl-\ or `SIGTERM` at the prompt puts the terminal's echo back before the process ends, by the signal's own default action, so the shell sees the same end; Ctrl-\'s action would write a core dump, which `set-password` turned off before it prompted (decision 98). The hash file is opened without waiting (`O_NONBLOCK`), so a named pipe in its place holds up neither the start nor a request, and is refused as no regular file.
  - **A password set while sign-in is off waits for a restart, and Ladderback says so** (#612). With sign-in off, the session route looks for `admin-password` each time it is read and answers `"admin-password": "set"` when the daemon could check what it finds, so the next start should turn sign-in on, or `"unreadable"` when it couldn't, so `ladderback set-password` should write it anew; the field is left out while there is none, and the platform's words about the file never reach the answer. Its check is the start's own, and a file whose mode has changed since it was last read is read again, so the answer is the one the next start would give (#633). Sign-in itself stays off until the restart, whose own checks of the file decide. Settings says which (§4.5).
  - **Settings sets and changes the admin password too** (#617, decision 70), with `POST /api/v1/admin-password`, whose body holds `new-password` and, with sign-in on, `current-password`, by the rules `set-password` keeps and with its effects: the same lengths (`400 admin-password-too-short` or `admin-password-too-long`), the same hash file, and a new password ends every session and API token. With sign-in off it sets the password, which waits for a restart as above: whoever can reach the page can already run and change everything, so this opens nothing new. A file it can't write is `503 admin-password-unavailable`, and the log, never the answer, says why.
  - **Changing it takes a session and the current password.** With sign-in on, an API token is refused `403 api-token-permission` (permission `session`). The current password is checked as a sign-in from the connection's address is: a wrong one is `403 current-password-wrong` and counts in that address's waits, one sent during a wait is `429 sign-in-wait` unchecked, and only then is the new one checked. A missing or empty current password, or one over 1024 bytes, is refused `current-password-wrong` unhashed and uncounted, since it can't be the admin password. The answer to a change tells the browser to forget its cookie, whose session the change ended. Neither password reaches a log or an answer (I4). Turning sign-in off and recovering a forgotten password stay at the terminal (delete `admin-password` and restart): a web path to either would let whoever reaches the page downgrade it.
  - **Sessions.** Signing in with the admin password (`POST /api/v1/session`) starts a session: a random 32-byte token in the cookie `ladderback-session`, `HttpOnly; SameSite=Strict; Path=/`, so the page's scripts can't read it and no other site's request carries it.
    - The cookie is also `Secure` when the request's `Origin` is `https://` followed by the request's own `Host`, as from a page a TLS-terminating proxy serves; forwarded headers (`Forwarded`, `X-Forwarded-*`) are never read, since anyone can write them. The session remembers that choice, in the store too, and every renewal sets `Secure` as the sign-in did: a browser sends no `Origin` on a same-origin `GET`.
    - The daemon keeps each session by its token's SHA-256 and never compares tokens with plain `==` (the type has none), so how long a lookup takes says nothing about how much of a guessed token was right.
    - A session ends at **sign-out**, at **Sign out everywhere**, when the **admin password is set anew**, even to the same password (each session remembers the fingerprint of the hash it started under, and the daemon sees a new hash file at the next request, with no restart), at the end of the **session length** after it started, and **12 hours after its last use** while it has an idle limit.
    - **Stay signed in for** (`GET` and `PUT /api/v1/settings/sign-in`, `{"session-length": …}`) sets the session length: `until-browser-closes`, `7-days`, `30-days` (the default), `90-days`, `1-year` or `until-sign-out`. Only a session reads or sets it: an API token is refused `403 api-token-permission` (permission `session`), sign-in off `409 sign-in-off`. It applies to the sessions already open, measured from each one's sign-in, so a shorter one ends the older ones at once. Until I close the browser sets no end after sign-in, always keeps the idle limit and offers no Keep me signed in; Until I sign out sets no end after sign-in, and a session signed in without Keep me signed in still ends 12 hours unused.
    - **Keep me signed in on this device** (`keep-signed-in` in the sign-in's body) gives the session no idle limit. A signed-out session answer says whether the form offers it (`keep-signed-in-offered`). The "Sign in again" dialog asks the session route so without the session's cookie: it opens when the page's clock or a refusal has ended the session, and the page's clock ends it a moment before the daemon's does, so with the cookie that read would use the session and bring it back, and a page left open would never let its session end unused.
    - **The cookie** lasts as long as the session has left (`Max-Age`), at most the 400 days a browser keeps one; under Until I close the browser it has neither `Max-Age` nor `Expires`. A person's use renews it at most once a day, and at once after the session length changes or the daemon restarts; a background read never renews it, at any route, the session route's included.
    - **Sign out everywhere** (`DELETE /api/v1/sessions`, with the CSRF token) ends every session, the one that asked included; API tokens go on. A sign-in already starting its session finishes first, so the store never keeps a session Sign out everywhere ended; one still checking its password starts its session after.
    - **Sessions outlive a restart.** At most 16 are kept, and the one used longest ago makes room for a new one. The store keeps each one's token digest, never the token, with its password fingerprint, its sign-in, its last use (written at most once a minute), whether it was kept signed in and whether its cookie is `Secure` (§9 `sessions`); each gets a new CSRF token at start. At start the daemon forgets the rows it can't read (and logs how many), the sessions that ended while it was stopped and those of another password. A new password set in Settings, or by `set-password` with no daemon holding the data folder, has the store forget every session; with a daemon running, `set-password` leaves the store alone and the fingerprint ends them.
    - **At start**, the session length is the one kept as soon as it is read, even when bringing the sessions back then fails; one that can't be read is Until I close the browser, the shortest, until the next start. A session the store dates as started or last used after the daemon's clock is forgotten, so a clock set back never lengthens a session.
    - **When the database can't keep or forget sessions**, a sign-in, a sign-out, Sign out everywhere or a change of the session length is answered `503 sessions-unavailable`, and the log says why. A sign-in refused so counts as no failed guess. The session a sign-out refused so has ended, so the page's **Sign out** shows the sign-in page as for a sign-out done. A write no request answers for (a session's last use, or a forgetting left for a later write) is tried again at the next write; the log says so at WARN, by the error's code alone, at the first such failure since a write changed the sessions (a session kept, used or forgotten, or another session length kept), and not again until one has. A write that changed nothing (forgetting a session never kept, setting the same length) doesn't count: a full disk can let it succeed.
    - **An API token's last use the database can't keep** refuses nothing and is tried again at the token's next use; the log says so the same way, at WARN by the error's code alone, at the first such failure since a write changed the API tokens (a token created or revoked, its permissions changed, or a last use kept), and not again until one has. A write that changed nothing (such as setting the permissions a token holds already, or forgetting an earlier password's tokens when none are left) doesn't count: a full disk can let it succeed.
    - **Known limits:** a sign-out's sessions have ended all the same, with the cookie forgotten, but until a later write succeeds a restart would bring them back; a request dropped before the store answers leaves its sessions to the next write the same way. A `PUT /api/v1/settings/sign-in` dropped after the store keeps the length leaves the running daemon on the old one until it restarts. A cookie renewal lost when the client hangs up isn't sent again for up to a day, so after the length grows the browser may drop the cookie before the session ends.
    - The session answer names the build the daemon runs (its version, commit, whether it had changes and whether it is a release: decision 90) only with sign-in off, a live session or a `read` token (decision 95), never to a page that has yet to sign in, which needn't learn which fixes the daemon lacks.
    - An open events stream ends within 5 s of its session.
  - **CSRF.** Each session has its own random 32-byte CSRF token, which the session route gives the page and no cookie holds. A changed request (any method but `GET`, `HEAD` and `OPTIONS`) carries it in `X-CSRF-Token`, compared in constant time (`subtle`); without it, or with another session's, the request is refused with `403` and `csrf-token-invalid`. **Signing out needs it too** (`DELETE /api/v1/session`), so another site can't sign the admin out; a request whose session has already ended has nothing to end and is answered as signed out, with the cookie forgotten.
  - **Only what a person does uses a session.** A request the page sends on its own, not because its reader did something (a refresh of the history after an event, the re-reads that follow a run to its end), carries the header `x-ladderback-background`, whatever its value; opening the events stream never counts either. The daemon checks the session for both without using it, so a page left open, even one hearing events, still ends its session 12 hours after its reader last did anything. The header needs no trust: it can only make a session end sooner. The page marks reads only; a changed request a client marks is accepted and simply doesn't count as a use.
  - **Each tab counts from its own last use.** The daemon keeps one last use per session, which any tab moves on; each tab times its idle warning and its end from the requests it sent itself. So a tab left alone warns, and then asks to sign in again, even when another tab kept the session in use.

    Its warning's "Stay signed in" uses the session, which is then still live; signing in again there starts a new session, and the cookie the tabs share is then the new one's. Another tab still holds the old session's CSRF token, so the page answers a `csrf-token-invalid` refusal, and only that one, by reading the session's current token (`GET /api/v1/session`) and sending the request once more; the daemon refused it before any route ran, so it did nothing the first time. Refused again, the request shows its error as any refusal does.
  - **Failed sign-ins wait; none locks out.** Each sign-in from a client counts as failed until it succeeds, and the client's next one waits 1 s after the first, twice as long after each more, at most 5 minutes.
    - A sign-in during the wait is refused with `429`, `sign-in-wait` and `Retry-After`, **unchecked**, so a guess made then never counts; once the wait has passed, the admin password signs in whatever came before.
    - A client is an IPv4 address, or the /64 network of an IPv6 address, which one host can fill with addresses.
    - A success starts its waits over, and a client that has tried nothing for 24 hours is forgotten.
    - At most 1024 clients are remembered: when the table is full the forgotten go first, then the client whose wait ends first, so one that keeps failing is the last to go, however many others fail once.
    - Behind a reverse proxy every request comes from the proxy's address, so **all clients share one wait**; forwarded headers are not read for this either.
    - A wrong password is `401` and `sign-in-failed`.
    - **Known limit:** whoever shares the admin's client (another user of the machine on loopback, anyone behind the same proxy or in the same /64) can keep the admin waiting by sending a wrong password the moment each wait passes. That denies sign-in but never lets a guess count; a browser cookie that gives a browser once signed in a wait of its own would close it, and is left for later.
  - **The sign-in form** (A5, A6, §4.5): one "Admin password" field, `autocomplete="current-password"`, which accepts paste and password managers; an error summary that takes focus and says how to fix the problem; and the requested page once signed in. A session that ends while a page is in use opens a "Sign in again" dialog over it, which keeps what was typed and sends the refused request again once signed in. Two minutes before a session would end unused the page warns (WCAG 2.2.1) and offers "Stay signed in"; Escape keeps it too. While signed in, the header offers "Sign out" at the end of the links' line, apart from the navigation and after its links in the order of Tab.
  - **The body limit covers the session route**: a sign-in's body is at most the API's 128 KiB, refused with `413` before it is read, like any other.
- **API tokens** (M3, §16 decision 93), for programs other than a browser, such as the CLI and MCP connect mode, while sign-in is on. Restore, download, config, pairing and auth routes, and every action of the "Pending changes" page (approve, reject, generate a password, test a new location), accept only a session (with step-up where §10.4 requires it), never a token. Tokens are created, listed and revoked in Settings, and the secret is shown once.
  - **The token.** `ladderback_<id>_<secret>`: a 12-character lower-case base32 ID and a 43-character unpadded base64url secret of 32 random bytes. It is sent only as `Authorization: Bearer <token>` (the scheme in any case), never in a URL or a cookie, the events stream's handshake included. A request with that header is judged as a token request alone: its cookie is ignored, the session route's included, and it needs no CSRF token. Another scheme (a proxy's `Basic`) is not a token and leaves the request to the session's rules. With sign-in off the header is ignored.
  - **The check.** The daemon finds the token by its ID and compares the SHA-256 of its secret with the one it keeps (§9) in constant time (`subtle`); only the digest is kept, and a slow hash would add nothing to 32 random bytes.
    - A missing or unknown token, a wrong secret, a token of an admin password set since, text that is no token and two `Bearer` headers are all `401 api-token-invalid`, so none tells which tokens exist.
    - A failed token counts as a failed sign-in for the client (above) in the same waits: a token request during a wait is refused `429 sign-in-wait` with `Retry-After`, unchecked, and a good token doesn't start the waits over.
    - When the admin password or the tokens can't be read, the request is refused `503 api-tokens-unavailable` and the log says why.
    - The check runs where the session check does: after the request checks and before the body limit, so a refused token request's body is never read.
  - **Permissions** (decision 127), seven rows per token, each at no access or its one level, checked by the daemon per route from one table (`http_adapter::api_tokens::required_permission`):
    - **Backups** (read) opens `GET` and `HEAD` of the events stream, the operations, one operation, the plans, a plan's export as a profile, the repositories, a repository's snapshots, groups and stats as last read, which hub this machine is paired with (`GET /api/v1/pairing`, §4.6), and the session route, which answers a token `signed-out` with the build and no CSRF token: a token has no session, and signing in and out stay a session's (decision 95).
    - **Backup runs** (start-and-cancel) opens starting a plan, cancelling an operation, testing a saved repository and reading a repository's stats now, which opens the repository as a test does and keeps the reading (decision 104).
    - **Previews** (preview) opens the maintenance preview and a profile's preview from its text (decision 95).
    - **Configuration** (propose) opens `GET` and `HEAD` of the proposals and of one proposal, making a proposal, withdrawing one and the dry run (decision 89). A token sees and withdraws only the proposals it made, and another token's is `proposal-unknown`, as one never made is; nothing a token does approves a proposal or changes the configuration.
    - **Snapshot contents** (read) opens a page of a snapshot's folder and a snapshot search (decision 132): the names inside a snapshot. A program without it, a token or an AI agent without one, gets an operation's warnings without the file they name: one operation's detail leaves the warning's `item` out and its `detail` empty, and the events stream sends its `args` empty. It gets a failure as its code alone, without the arguments or the engine's words, either of which can name a file: one operation's detail, the history and the status summary leave the failure's `args` and `detail` out, and the restore's `entry` too, and the events stream sends an `operation-failed` event's `args` empty.
    - **Daemon log** (read) opens the recent log (`GET /api/v1/log`, its lines masked as the daemon log's are, decision 111).
    - **Repository check** (run) opens no route yet.
    - Any token reads its own permissions (`GET /api/v1/permissions`).

    A route the table doesn't name is for a session only, so a new route is closed to tokens until the table opens it.

    A token without the route's permission is refused `403 api-token-permission`, whose `permission` argument names the row the route needs, or `session`. A token's cancel reaches backups only: the daemon refuses its cancel of any other operation with `403 api-token-permission` naming `session` (§4.6).

    A new token gets Backups, Backup runs, Previews and Configuration unless the form says otherwise, and needs at least one row (`api-token-no-permission`). Only a session changes a token's permissions (`PUT /api/v1/tokens/{id}/permissions`), with the current admin password checked as below for the admin password's change; when they differ from the ones it holds, the log says "API token {id} now has {rows}". Upgrading keeps each token's access: `read` became Backups, Snapshot contents and Daemon log, `run` Backup runs, `preview` Previews and `propose` Configuration.

    An operation a token starts records the trigger `api-token` with the token's label and ID, never its secret (§9).
  - **Lifetime.** A token lives until it is revoked or the admin password is set anew: each token keeps the fingerprint of the password it was created under (the first 8 bytes of the SHA-256 of the hash's salt, which a restart keeps and `set-password` changes), and one of another password is refused and deleted the next time the tokens are listed or one is created. Revoking deletes the token; an events stream opened with it ends within 5 s, the recheck the session streams use, and so does one whose token no longer has Backups. There is no expiry; the last use is written at most once a minute per token, and Settings shows it. At most 100 are kept, each with a label of 1 to 64 characters (not blank, no control characters) and at least one permission.
- **Request checks, always on**, auth or not. The UI can set hooks and `password-command`, so an unauthenticated API reachable from a web page would let any site run commands on the machine (DNS rebinding or cross-site POSTs). Therefore:
  - the `Host` header must be a configured name or a loopback address;
  - a request that carries an `Origin` header must match the UI's own origin; requests without `Origin` (curl, scripts, the `ladderback` CLI) skip that match. Mutating requests must use `Content-Type: application/json` whether or not they carry `Origin`: with `Origin` it forces a CORS preflight that the daemon refuses, and without it a browser or extension that strips `Origin` still can't send a cross-site form post. Scripts therefore send the header;
  - the `/api/v1/events` WebSocket handshake checks `Origin` the same way.
  - **The hub's sync routes have a check of their own instead.** In a build with the hub, every path under `/sync/` belongs to a router of its own, in front of the UI's and the API's, so a route the other router has there is never reached and every route added under `/sync/` is behind this check. Agents reach the hub by whatever name it has and prove themselves with signatures (§10.3), so the check takes only what an agent's client sends: a `GET` asking to upgrade to a WebSocket (`Upgrade: websocket`), with no `Origin` and no body.
    - In that order, a request that carries an `Origin`, whatever it names, is refused `403 origin-not-allowed` (the UI never opens these routes), another method `405` with `Allow: GET`, one that doesn't ask to upgrade `426` with `Upgrade: websocket`, and one with a body, any length but a known 0, `413 body-too-large` with a limit of 0.
    - A web page can't pass it: its WebSocket always carries its `Origin`, and its other requests may not set `Upgrade`. So the `Host` check, which guards against DNS rebinding, isn't needed there, nor the JSON rule, which guards bodies.
    - A build without the hub has no agent routes: its paths under `/sync/` answer 404 behind the checks above (decision 122).
  - **How they match.**
    - Configured names come from `ladderback serve --allowed-host NAME` (repeatable; a name or address without a port: the daemon refuses any other value at startup, in the catalog's words and with exit status 2) until the config file has a setting for them, which M8's first release adds with hub mode (§16, decision 136). Behind a reverse proxy, forward the browser's `Host` unchanged and configure that name.
    - `Host` matches regardless of case and port. Loopback means `localhost`, a `127.0.0.0/8` address or `::1`; any other name is refused unless configured, and so are short forms such as `127.1`. A `Host` that is missing, repeated, not ASCII text, or carries user info, a path or a bad port is refused; a request target that names its own authority (HTTP/2's `:authority`) stands in for a missing `Host`.
    - An `Origin` is the UI's own when it is `http://` or `https://` (the latter for a TLS-terminating proxy) followed by exactly the request's `Host` value, compared regardless of case; `null`, a path and a repeated `Origin` are refused.
    - The JSON rule covers every mutating request, which is any method other than `GET`, `HEAD` and `OPTIONS` (`TRACE` and extension methods included), with or without `Origin`. Its `Content-Type` must be `application/json`, with or without parameters, so `application/json; charset=utf-8` passes. Other JSON types (`+json`, `-seq`), a repeated header and a missing one are refused, even for an empty body.
    - No path is exempt from them: `/api/v1/sync/v1`, `//sync/v1` and a query that mentions `/sync/` are the UI's and the API's paths.
  - **Refusals** are `403` with `host-not-allowed` or `origin-not-allowed`, or `415` with `json-required`, in that order of checking. The body is `{"code": "…"}`, the typed `api::ErrorCode` for the UI to render (§8.4). No route ever sends CORS headers.
- **Body limits, always on.** The daemon reads a request's body into memory before a route runs, so a body of any size would let one request take that memory from the backups.
  - Each class of route has a limit of its own, the smallest that fits the largest body the class takes, and one layer enforces it before any route sees the body, so a new route, or one that reads its body another way, is bounded without knowing it: a request to `/api/v1` may carry 128 KiB (twice the 64 KiB a secret field may hold, so a repository's settings fit with a secret at its cap), a profile's preview (`POST /api/v1/profiles/preview`) 2 MiB and 128 KiB (a profile at its 1 MiB cap with each character escaped as two in JSON, and the rest of the body; decision 95), and a request for the web UI none at all.
  - A configuration import, which may need more, gets its own class when its route exists.
  - The hub's sync routes are in front of that layer: their own check above refuses any body, before any of it is read, with the same `413` and a limit of 0.
  - A declared `Content-Length` over the limit is refused before any of the body is read, and a body with no length, or one that lies, is cut off at the limit.
  - A body over its limit is refused with `413` and `body-too-large`, whose body is `{"code": "body-too-large", "args": {"limit": …}}`, the limit as a byte count the UI renders as a size (§8.4); the route never runs, and the request checks above, and with sign-in on the session or API token check, have already passed.
  - A body that cannot be read to its end is refused with `400` and `invalid-body`.
  - The events WebSocket is bounded the same way: a message from its client may hold 1 KiB (the UI sends pings of at most 125 bytes), and a larger one ends the connection.
- **Connections, always on** (#1258). The server bounds the connections it serves, from the plain listener and from a hub's front door alike, so clients that open connections and send little or nothing can't hold the daemon's descriptors.
  - A connection has 30 s to send each request's head, counted from when the server waits for it: a new connection's first request, and each later one on a connection kept alive, so an idle kept-alive connection closes after 30 s too. The bound is on the head only: a slow answer, and a WebSocket once upgraded (the events stream, `/sync/v1`), run as long as they need. 30 s is hyper's own default, ample for any client to send a few KiB.
  - At most 128 connections are served at once; a newcomer past that waits unaccepted, in the listening socket's queue, or on a hub at its front door, until one closes. An upgraded WebSocket keeps its place while it is open. 128 is far past what a person's tabs or a hub's agents hold, and half the 256 descriptors macOS gives a process by default, so the store, the workers' pipes and the repository files keep theirs, on a hub too, whose door holds at most 64 more and its hand-off 1 (decision 120).
  - The server speaks HTTP/1.1 only: nothing Ladderback serves needs HTTP/2, the built-in TLS offers no ALPN, and hyper's head bound covers HTTP/1.1 alone.
  - At shutdown the server takes no connection more, closes the idle ones, and waits for each request in flight.
  - **Known limits:** a body that trickles in after its head, and a client that doesn't read its answer, hold their connection until it ends; the body limits bound what they take, not how long. The bound counts every address alike, so a client beyond loopback that keeps the 128 places busy makes others wait their turn; only the hub's front door gives each address a share (decision 120), and it hands on in order, so a lone agent behind a flood waits rather than being shut out. WebSockets keep their places for as long as they are open, so more than about a hundred agents and tabs at once leave the web UI waiting. On the network, a proxy or a firewall in front of the daemon is what limits who may open connections at all.
- **Security response headers, always on.** Every response carries them, whatever answered it: a file, an API answer, a refusal of a request check or of a body limit.
  - `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`. The page runs its own files and WebAssembly (`'wasm-unsafe-eval'` compiles the module and allows no `eval` of text), no site can frame it, and nothing inline runs but the one script Trunk writes into `index.html` to start the application. That script's file names carry a content hash, so no fixed policy could name it: the entry page's policy adds the `sha256` of each of its inline scripts, computed from the file the daemon serves, and `'unsafe-inline'` is never in it. Trunk has no option to move the script out of the page ([trunk-rs/trunk#288](https://github.com/trunk-rs/trunk/issues/288)).
  - `X-Content-Type-Options: nosniff`, so a browser takes a response for the type it says.
  - `Referrer-Policy: no-referrer`, so the UI's addresses, which name repositories and plans, leave in no request a link or an asset makes.
  - `Cache-Control: no-store` on every answer under `/api/`, a refusal's included, so no caching proxy in front of the daemon keeps one person's answer, a session's included, and gives it to another (#397). The web UI's files don't carry it.
  - On the web UI's files, `Cache-Control: public, max-age=31536000, immutable` only for a name that carries Trunk's content hash (`<stem>-<hash>.<ext>`, or `<stem>-<hash>_bg.wasm`), which a changed file never keeps, and `no-cache` for every other file, `index.html` included, so a release never hides behind a cached copy. The tab icon, `crates/web/assets/brand/favicon.svg` with `favicon-32.png` for browsers without SVG icons, is hashed this way; `default-src 'self'` already lets the page load it.
  - **No `Strict-Transport-Security`.** The daemon serves plain HTTP on loopback by default, and a browser that kept the header would refuse plain HTTP to whatever else later listens on that address. TLS, with its own header, belongs to the reverse proxy in front of the daemon.

  The `@ui` journeys run in Chromium under the policy, and one that makes the browser refuse something fails. A browser whose `'self'` does not cover a same-origin WebSocket would lose live updates under `default-src 'self'` and nothing else.
- **Local users.** Loopback is reachable by every user on the machine, so with sign-in off any local user can set hooks and run commands as the daemon's user. On multi-user machines, set an admin password. Listening on the network with sign-in off widens that to anyone who can reach the address (below).
- **Startup rule.**
  - A loopback address (`127.0.0.0/8`, `::1`) may always be listened on. Any other only with at least one `--allowed-host`, sign-in on or off (decision 87): the request checks then admit that name besides the loopback names, and with none every browser request from the network would be refused anyway.
  - `--allowed-host` does not limit who can connect: any client can send an allowed `Host`, `localhost` included. It stops a web page in a browser being turned against the daemon through DNS rebinding. With sign-in off on the network, anyone who can reach the port can use every route.
  - Without an `--allowed-host`, `ladderback serve --listen` exits with status 1 before binding anything, naming `--allowed-host`. The explicit `--listen` beyond loopback is the consent, as in Backrest, whose default is localhost too.
  - Listening beyond loopback with sign-in on, the log warns that plain HTTP sends the password unencrypted and recommends TLS in a reverse proxy.
  - With sign-in off on loopback, every start warns in the log, and the UI's start page says, that anyone on this machine can use Ladderback and that `ladderback set-password` turns sign-in on.
  - An `--allowed-host` that is not a loopback name is one a reverse proxy can bring anyone to the daemon by, so with sign-in off on loopback the daemon also says on stderr, after it binds, one line for each such name in the catalog's words (`cli-warn-sign-in-off-behind-proxy`, decision 87, #398): that anyone who can reach that name through the proxy can run and change backups, and how to turn sign-in on. Like the network's line below, it is not a log record.
  - With sign-in off on the network, the daemon says on stderr, after it binds and before `listening on`, that anyone who can reach the address can run and change backups and how to turn sign-in on: a line of its own in the catalog's words (`cli-warn-network-sign-in-off`), not a log record, so no `RUST_LOG` setting hides it. The session route then answers `"exposure": "network"`, and every page of the UI says the same in place of the start page's note.
  - There is no trusted-proxy mode yet (below).

  | Threat | What it takes | What Ladderback does | What remains |
  |---|---|---|---|
  | A web page reaching the daemon on the network through a name it controls (DNS rebinding) | A site whose name resolves to the daemon's address, opened in a browser on that network | The `Host` check admits only configured names and loopback, with sign-in off as with it on; the `Origin` and `Content-Type` checks stop cross-site requests | Nothing new: the checks are the ones loopback has |
  | Someone on the network using the daemon with sign-in off | Reaching the listened address (any client can send an allowed `Host`) | The start refuses without an `--allowed-host`; the daemon's warning on stderr, which no log setting hides, and the notice on every page say that anyone who can reach it can use it and how to turn sign-in on | Anyone who reaches it uses every route: runs and changes backups, sets hooks and `password-command` (so runs commands as the daemon's user) and, once restores exist, reads any repository's backups, other machines' in a shared one included. Trusted networks are #504 |
  | The warning going unseen | A log turned off (`RUST_LOG=off`) or sent elsewhere | The warning is not a log record; a stderr nobody reads stops the start | A service whose stderr goes unread by a person: the page's notice remains |
- Optional "trusted reverse-proxy header" mode for SSO behind Authelia or Authentik.

### 10.2 Repository secrets

This section decides where a repository's secrets may come from, how a reference in a repository's settings is resolved, and how every secret is kept out of argv, logs, events and the UI.

Every secret-bearing field can come from any of these sources. That covers the repository password and backend credentials in `options`, such as S3/B2 keys or SFTP passwords:

| Source | Config form | Typical use |
|---|---|---|
| Command | `password-command = "security find-generic-password -s rustic-nas -w"` (rustic-compatible) | macOS Keychain, `secret-tool`, `pass`, 1Password/Bitwarden CLIs |
| OS keyring | `password-keyring = "ladderback/nas"` | Desktops. The repository form can write the entry for a typed password (below). Not available to system services before login or to a root worker reading a user's keyring |
| File | `password-file = "/run/secrets/nas_password"` (rustic-compatible) | **Docker/Podman secrets**, systemd `LoadCredential=` (`$CREDENTIALS_DIRECTORY/…`), Kubernetes secrets |
| Environment variable | `password-env = "NAS_PASSWORD"` | Containers, CI, systemd `Environment=`/`EnvironmentFile=` |
| Inline | `password = "…"` | Accepted (e.g. on import) with a warning: the daemon logs `config-inline-secret` once per secret when it starts and loads the config (a repository saved while it runs is noted on its row at once and logged at the next start), and the Repositories page notes it on that repository's row. Both name the setting (`password`, `options.NAME`), never the value; it is not a refusal. An option counts when its name says it is a credential (`is_secret_option`) and its value has no `${…}` reference, or when its value is a URL with a password written in it. A password in a location (`rest:https://user:password@host/repo`, or a credential in an rclone connection string) is one too, under `location-secret`, which names the setting (`repository`, `repo-hot`) and, for a location after the first, its `position`, never the location, the user name or the password, and says to put a `${VAR}` or `${file:/path}` reference where the password is, or to give it in the backend's own option; for an rclone location, which rclone gets in its arguments and where a reference is refused, it says to keep the credential in rclone's own configuration file instead (decision 37) |

**Substitution in repository fields.** Inspired by Backrest's `${VAR}` expansion, but stricter. `repository`, `repo-hot` and the **values** of `options`, `options-hot` and `options-cold` may reference `${VAR}` (an environment variable) or `${file:/abs/path}` (a file's contents). Substitution is limited to these fields: in hooks it would put secrets into process arguments (I4), and in `label`, `sources` or `tags` it would silently change snapshot identity. It never applies to option names, and never to an inline `password`, which is taken as written. For example:

```toml
[repositories.b2]
repository = "opendal:b2"
password-file = "/run/secrets/b2_repo_password"
options = { bucket = "my-backups", application_key_id = "${B2_KEY_ID}", application_key = "${file:/run/secrets/b2_app_key}" }
```

Grammar and limits (`domain::secrets::Template`):
- `${VAR}` names a variable of `[A-Za-z_][A-Za-z0-9_]*`. `${file:/abs/path}` takes an absolute path that has no `}` in it. There are no defaults (`${VAR:-x}`) and no nesting.
- `$${` is a literal `${`. A text is read left to right, and a value a reference resolved to is never scanned again, so a secret that looks like a reference stays as it is.
- A malformed reference (unterminated, empty, invalid name, empty or relative path, nested) fails the field with the byte offset of its `${`, never with the text.
- A field has at most 16 references (`MAX_REFERENCES`) and is at most 64 KiB (`MAX_SECRET_BYTES`) both before and after expansion.

**Sources and what they give.** Every source goes through the `SecretResolver` port (§3.2), which returns the secret and any warnings, or an error that names the source:

| Source | The secret is | Nothing there |
|---|---|---|
| `${VAR}`, `password-env` | the value as it is, with no trimming | not set: `Missing`. Set to empty: the empty secret |
| `${file:/abs/path}` | the whole contents minus one trailing `\n` (and a `\r` before it) | `Missing` |
| `password-file` | the first line: up to the first `\n`, minus a `\r` before it (as rustic does) | `Missing` |
| `password-command` | the first line of the command's output | the first line is empty or only white space: `Missing` |
| `password-keyring` | the entry's secret | no such entry: `Missing`. No keyring service to ask (on Linux: no Secret Service, no session bus to reach one, or a service that says its keyring is locked, whose unlock prompt was dismissed, or that has no collection, told apart by the Secret Service's own error and the D-Bus error's name; any other failure of the service, a reply it couldn't decrypt or parse included, is `Unreachable`): `KeyringUnavailable`, whose cause tells them apart. A locked keyring is refused as `secret-keyring-locked`, which says how to unlock it (#993), and so is one whose unlock prompt was dismissed, which stays locked, though a dismissed prompt is never asked again nor waited on (decisions 116 and 135); the others as `secret-keyring-unavailable` with what to use instead. On Linux an entry the service finds no item for is `KeyringUnavailable`, locked, too while the service's `default` collection says it is locked, since oo7 finds no items in a locked collection whether the entry is there or not (#483); it is `Missing` only when that collection is unlocked or the service can't say |
| Inline `password` | as written | — |

Options accept only `${VAR}` and `${file:/abs/path}`; commands and the keyring are forms of the repository password. A missing variable or file is never an empty string (unlike Backrest). What a source gives, the whole file, output or value and not only the line taken from it, is limited to 64 KiB (`TooLarge`) and must be UTF-8 (`NotUnicode`). A source that exists but can't be read is `Unreachable`. A file or keyring read that outlives the resolver's limit (a keyring that waits for an unlock, a mount that has hung) fails as `TimedOut`, like a command; the blocked read can't be cancelled and ends when the system lets it go.

A run is refused for that as `secret-keyring-timed-out` or `secret-file-timed-out`, with the source and the limit's seconds, never as `secret-unreadable`, whose advice (check that it is there and readable) is wrong for it (#891). On macOS the usual cause is a keychain prompt nobody answered, so the keyring's words say to answer it with Always Allow and run again; the file's words name a network share that stopped answering.

**Commands.** The command line is split into words POSIX-style and started **without a shell**, so `|`, `;` and `$(…)` in it mean nothing.

The port contract (`app::ports::SecretResolver`) is that a command gets no input, runs in a process group of its own, and is limited in time: one that outlives the resolver's limit fails as `TimedOut` and is stopped by the sequence a hook is stopped by (§6.1): the whole group gets SIGTERM, so a helper that holds a lock or a session can end cleanly (its output pipes stay open until it is reaped, so a handler that writes there isn't ended by SIGPIPE, and are read and dropped meanwhile, so a handler that says more than a pipe holds isn't blocked until the SIGKILL), and SIGKILL 5 s later (`KILL_GRACE`) if the command is still running then.

- Each signal goes once, and only while the command is still unreaped (a group is named by its leader's process id, and once the leader has been reaped and the group has no live member, another process may hold that id). So a command that ends on the SIGTERM is not waited for any longer, and a process it started and left running is not signalled again if it ignored the SIGTERM too: that one is left running.
- A command that is still running when the grace ends takes its whole group with it. The wait for the command to die after the SIGKILL is bounded as well (5 s), so one that no signal reaches, stuck in the kernel, still ends the call with the same error.
- A command whose output goes past the size limit, or can't be read, is killed at once, with no grace, and so is one whose caller gives up while it runs.
- The limit is the command's own: one that has exited in time is never timed out, and what it left holding its output open (gpg-agent) gets one second (`PIPE_GRACE`) and is left running. What was read of a **stdout** left open so is used only as far as a first line whose newline was read: a command that succeeds before that line ended fails as `OutputCut` (refused as `secret-command-output-open`, which quotes nothing it printed) rather than give what may be part of a value (#237, decision 45).
- A command that exits unsuccessfully fails as `CommandFailed` with its exit status (none when a signal ended it) and the first non-empty line of its **stderr**, cut to 512 bytes, with the value it printed on stdout masked (whole, trimmed and line by line), since a helper that rejects a value may quote it. Only the first 8 KiB of its stderr is kept, and it is masked as a cut text (below, "Where masking runs") however it ended: at that cap, when something the command started still held it open as `PIPE_GRACE` ran out, at a failed read, or at the command's own end, which can stop partway through the value it quotes; a value cut there leaves nothing of itself (decision 45).
- Stdout is masked against only when it is whole: read to its end, and empty or ending with a newline. When something the command started still held it open as `PIPE_GRACE` ran out, or it ends partway through a line, which the command's own end can leave with nothing in what was read to say so (killed partway through printing the value, or exiting there), what was read of it can be only part of the value, and stderr masked against that part would show the rest of a value it quotes, so that failure has its status and an empty detail (#233, #237).
- The real resolver and the in-memory fake both build that error with `domain::secrets::command_failure`, and the secret with `domain::secrets::command_secret`, so a scenario on the fake sees what the real one gives. Its stdout itself is never part of an error. One that can't be started is `Unreachable`.

**A command's program.** The program is a name looked up on `PATH` (`security`, `pass`) or an absolute path. The command runs in the daemon's working directory (`/` under launchd or a system unit, the home folder under a user unit), so a program named by a relative path (`./get-pass`, `bin/get-pass`, `~/bin/get-pass`: nothing expands `~`) would be another program, or none, depending on how the daemon was started, and one put there by whoever can write to that folder. The rule is on the configured value, not in the resolver: the configuration refuses it at its key as `Password(RelativeProgram)` and the import as unsupported (§6.1, §6.2), the rule a hook's program follows (#240).

**One start at a time.** A command starts through the spawn gate, as a worker and a hook do (decision 58): no other child of the daemon starts while its pipes are being made, so none can inherit the pipe its secret comes back on, where the platform makes a pipe in two steps (macOS). Its pipes are let go without the gate when the call ends. A start that forks in that moment copies them into its child, close-on-exec, and that child runs none of the daemon's code before its `exec` closes them: nothing reads from them, so no process can read the secret through them (I4). Meanwhile a late write of the command's own descendant can go through rather than fail.

**A command that gives nothing.** A command that exits successfully with no output, or whose first line is empty or only white space, gives no secret: it fails as `Missing`, naming the program, never as the empty secret that a repository would then fail to open with, far from its cause. A variable, a file or a keyring entry that is set to nothing stays the empty secret, since someone set it so.

**Errors.** An error names the source and the problem, as codes (§8.4): the variable's name, the file's path, the program (without its arguments), or the keyring entry. It never holds a value or a command's arguments; the one text a command controls is the `CommandFailed` detail, which has the value the command printed on stdout masked (see above). In a resolved repository the error also names the field it was found in (`repository`, `repo-hot`, `password`, or an option by its name); when several fields fail, the first is reported, in the order password, `repository`, `repo-hot`, `options`, `options-hot`, `options-cold`.

**File permissions.** Ladderback warns (with the path as written, masked of the secrets read with it, I4) if a secret file, whether read as `password-file` or as `${file:…}`, is readable by group or others (`FileReadableByOthers`, mode `& 0o044`), or, in its place, if group or others can change it (`FileWritableByOthers`, mode `& 0o022`): whoever can change the file chooses the secret, and for a repository initialised with it the key it is made with (#1137). Neither applies to files under `/run/secrets`, `/var/run/secrets` and an absolute `$CREDENTIALS_DIRECTORY`, where container runtimes and systemd control permissions. Such a file warns rather than being refused because a `password-file` is shared with rustic and with container setups (a Kubernetes secret is `0644` by default), which keep working; Ladderback's own files, the MCP token file (§10.5), the admin password's hash and the key files (decision 120), are refused instead.

- Only the mode is looked at: a file another user owns, who can change it whatever its mode, is not warned about for that.
- The exemption is for where the file really is, so every link is followed first (the file's path and the directory's): a link in `/run/secrets` that leads to a file in someone's home is warned about like any other file, a link that stays in the directory is not, and a path that can't be followed is never exempt. A path with a `..` component is never exempt, and a `$CREDENTIALS_DIRECTORY` that is empty, relative or `/` (or that leads there) counts for nothing.
- The warning goes on the operation whose job read the file, as `secret-file-readable` or `secret-file-writable` with the path and the mode (`& 0o777`, in octal, such as `0644`), once per path in an operation however many of its reads met the file (#386): a backup's and a maintenance run's come with its start, and a choice of location's right after the run's `Started`, the first moment a run takes a warning.
- The daemon's log says it at WARN each time a job, a choice of location, a snapshot listing or a notification's delivery reads the file, an operation's or not, masked of the secrets that read gave; a read again only to mask a refusal's words says nothing.
- A choice of location that fails, or a job that fails before it starts, puts none on an operation; the log still has it, also when a later secret of the same read is what failed, masked then of the secrets read before the failure and of what the settings hold inline. The secrets after the failing one are not read for the masking, so masking a log line never runs a command or asks the keychain, and a failed lookup stays fast (#539); the case left is a path that happens to hold the value of one of those unread secrets, which the log shows as written.

**Rules.**
- Substitution happens **at job start** in the daemon (`app::secrets::ResolveRepository`), not when the config is loaded. Rotated secrets are picked up without a restart, and resolved values never get written back to `config.toml` or shown in the UI. The UI shows the reference (`${B2_KEY_ID}`), not the value.
- Each distinct reference is read once per job, so a value can't change between two places that use it. Warnings are reported once each.
- **A reference may not be in a field that becomes a process argument**, because argv is visible to other local users in `ps` and `/proc/<pid>/cmdline` on Linux (on macOS, to root; below) (I4), and the engine's masking can't reach it.
  - The pinned `rustic_backend` does that for the repository string of an `rclone:` repository (`rclone.rs`: it is appended to rclone's arguments), and for the options it runs as commands: `rclone-command` (`rclone.rs`), `post-create-command` and `post-delete-command` (`local.rs`); so does the engine's own start of an `rclone:` repository's server, which follows `rclone.rs` (decision 58).
  - **A command line shows whatever is typed into it.** The words of a `password-command`, an `rclone-command`, a `post-create-command`, a `post-delete-command`, a hook and a notification channel's `url-command`, `token-command` or `password-command` become the arguments of the process they start, so a password or a token typed into one is visible to other users of the computer while it runs (`ps`, `/proc/<pid>/cmdline` on Linux, where `hidepid` is off by default). On macOS 27.3, checked on 2026-11-19, a user's `ps -axww` showed other users' processes by their program alone, without arguments; root sees them. The settings' help and the guide say to keep secrets out of a command. A credential typed after a flag of an `rclone-command` (`--pass=…`) gets `rclone-command-secret`, naming the setting and the flag, never the value (decision 37, #1136).
  - Such a reference, in `repository` or `repo-hot` that starts with `rclone:` or in one of these options in `options`, `options-hot` or `options-cold`, is **refused** (`Cause::ReferenceInProcessArguments`, naming the field) before any secret is read, even when the password can't be read either.
  - A reference that supplies the `rclone:` itself (`${REPO}` holding `rclone:…`) shows only in the expansion, so the expansion of `repository` and `repo-hot` is checked too: that is refused once its references were read, and before anything else is done with it.
  - A plain `rclone:remote:path`, an escaped `$${`, and a reference in any other field or option are allowed.
  - An rclone remote's credentials belong in rclone's own config file (the worker keeps `RCLONE_CONFIG`).
  - The command line of that server is never quoted in a failure or in the log, as rustic's errors and its debug record quote it: a line can hold a credential no redactor knows, such as a token typed into `rclone-command`, and a failure is readable with a `read` token and over MCP. The engine's own start doesn't quote it, and a worker's failures of rustic's own `rclone:` backend are rewritten without it (`rclone::without_command`); a worker passes on records up to `info`, so rustic's debug record of the line never leaves it. A start that fails says rclone couldn't start, with the system's reason; a line that can't be split into words says that, with the reason alone (#874).
  - Nor is the line of a `post-create-command` or `post-delete-command`. When one can't start, can't be split into words or exits with an error, rustic's local backend only warns, quoting the line; a worker's log bridge passes that warning on as the option's name and the reason alone (the system's reason, why the line couldn't be split into words, or the exit status), and as the name alone when the warning's shape is one it doesn't know (`worker::logging`). These failures never fail the operation, so no failure's detail holds the line, and the daemon's own opens only read, so they run neither command. What the command itself writes to stderr is the worker's stderr, masked like the rest of it (below) for the secrets the daemon knows (#882).
- **An rclone location holds at most 16 credentials** (`MAX_RCLONE_CREDENTIALS`, counted by `too_many_rclone_credentials` as the redactor reads them, below, those of a location written in a setting included). Each is a secret, in a few forms, that a redactor looks for in every text it masks, so the work grows with their number times the length of the text, and a location over the cap is masked whole, where one credential quoted alone in an error of rclone's would show.

  So a job **refuses** `repository` or `repo-hot` with more (`Cause::TooManyCredentials`, sent as `location-too-many-credentials` naming the field and never the location) right after the check above, before any secret is read and before rclone or a worker sees the location; the answer reads none either, as no refusal that shows nothing a source said does.

  Its words say to keep rclone's credentials in rclone's own configuration file and name the remote in the location. 16 matches the cap on references (`MAX_REFERENCES`).

  Without a cap, measured in a release build on a location at the 64 KiB limit (#228):

  | Location | Needles | A 163-byte line | The location itself |
  |---|---|---|---|
  | `rclone::s3,key=abc,key=abc,…` (8 191 credentials) | 8 191 | 5.2 ms | 2.06 s |
  | quoted values, `key='abc@''%'` | 56 161 | 24 ms | 9.4 s |
  | values with a long shared prefix | 1 771 | 0.6 ms | 0.36 s |

  Building the redactor for the first took 460 ms. A job's output is masked line by line, so that is seconds of every job's run spent masking.
- **A location is a full path when it names a folder on this machine, once resolved too, and so is an option that names a file or a program** (#247, #310).
  - The configuration refuses a relative local location where it is written (§6.1), but can't judge one a reference decides (`${REPO}`, `local:${REPO}`).
  - So a job reads the expansion of `repository` and `repo-hot` as the configuration reads a location all of which is known (`domain::planning::is_relative_location`: `backups/repo`, `./repo`, `~/repo`, `local:repo` and the empty location are relative; `/srv/repo`, `rest:…`, `opendal:…` and a backend rustic doesn't know are not), right after the expansion's `rclone:` check (above) and before the credentials the location holds are counted or rustic or a worker sees it (what each reference held is counted as it is expanded, before that), and refuses a relative one (`Cause::RelativePath`).
  - The repository routes, the snapshot listing, maintenance and a backup start send it as `repository-path-relative` naming the field, the refusal the repository routes give a written one (#309).
  - The refusal holds nothing of the expansion, which may be a secret (I4), and its answer reads no secret, as it shows none.
  - The options are judged then too, each as it is resolved and before what it holds is counted, by the backend each half's resolved location names, by the rule the configuration reads a written option by, all of each value known and a `${` a reference held read as text (`domain::planning::ResolvedBackends::reads_relative`). So `root = "${ROOT}"` holding `backups` beside `opendal:fs` is refused, and so is a plain `root = "backups/repo"` or `post-create-command = "./notify"` whose backend only a reference in the location names (`${REPO}` holding `opendal:fs`, `${HOME}/repo`). The refusal is `repository-path-relative` naming the option, never what it held (#310).
- **A location, an option value and a table of options have caps** (`MAX_LOCATION_BYTES` and `MAX_OPTION_VALUE_BYTES`, 64 KiB as written, the most a template holds; `MAX_OPTIONS`, 64 options in each of `options`, `options-hot` and `options-cold`; all in `domain::secrets`, #236).
  - A redactor looks for every credential a location holds and every option value that is or holds a secret, in each of its forms (below), so the size and the number of these bound how many needles a redactor holds and how long they are; before, a location was refused only when a job read it, and the Repositories page and the daemon's start-up log masked it before any job did, at any length.
  - The configuration refuses one over a cap when it loads, an import when it reads it, and the repository routes as an invalid body (scheduling-and-config.md §6.1, §6.2); the refusal quotes nothing of what it refuses, which may hold a secret.
- The hot and cold halves of a repository (`repo-hot`, `options-hot`, `options-cold`) are resolved with the rest and are fields of the resolved `RepositoryAccess`, so they reach the worker, which opens both halves (§4.1). What they hold is masked like the rest: `Redactor::for_repository` takes everything a repository's settings can hold at once (`RepositorySecrets`), so a half can't be left out of it.
- rustic's own environment variables (`RUSTIC_PASSWORD`, `RUSTIC_PASSWORD_FILE`, `RUSTIC_PASSWORD_COMMAND`, `RUSTIC_REPOSITORY`, `RUSTIC_REPO_OPT_*`) are recognized on import. They're **not** read implicitly at runtime, so one stray variable can't redirect every plan. Use `password-env` explicitly instead.

**What is masked.** The `Redactor` (§3.1) replaces each of these with `***`:
- the repository password;
- every value a `${…}` reference resolved to (`RepositoryAccess.secrets`), wherever it lands, whatever the option or field is called: the repository string, an option such as `endpoint`, or a path in an error;
- the password in the userinfo of any URL in `repository`, in `repo-hot` or in an option value of `options`, `options-hot` or `options-cold`, and the whole userinfo where a `${…}` reference is in it and no `:` outside one is (`rest:http://${file:/path}@host`), for the reference may stand for a user and a password both. A reference is one piece of the URL: a `/`, `?`, `#`, `:` or `@` inside it ends nothing, so the authority of `${file:/path}@host` ends after the host (#457). An S3 `endpoint` is **not** a secret by its name; only credentials embedded in its URL (`https://demo:…@host`) are masked, so a plain endpoint stays readable in diagnostics;
- the value of every option, in any of the three sets, whose name says it holds a credential (`is_secret_option`), **even when written inline**: a name, lowercased with `-` read as `_`, that contains `password`, `passwd`, `secret`, `token`, `credential`, `passphrase` or `delegation`, or ends in `_key` (`sas_token`, `secret_access_key`, `application_key`), or is, as a whole, one of rclone's own names: `pass` (the password of its SFTP, FTP, SMB and WebDAV backends), `key_file_pass`, `key_pem`, `sas_url`, `connection_string`, `sse_customer_key_base64`, `access_grant` (Storj), `master_keys` (Filen), `authorization` (SugarSync), `headers` (WebDAV and HTTP, which take `Authorization,Bearer …`) or `2fa` (Proton Drive's one-time code). `use_password` (a switch), `key` (an SFTP key file path), `access_key_id` and `application_key_id` are not secrets;
- each credential written in an rclone connection string in `repository` or `repo-hot` (`rclone::sftp,pass=…:/backups`, `rclone:remote,key=…:bucket`): the value of a setting, one of the `key=value` pieces between commas up to the `:` that starts the path, whose key names a credential in a connection string (`is_rclone_secret_option`: what `is_secret_option` names, and `key`, which there holds the key of rclone's B2, Swift and Azure Blob backends) and whose value, quotes aside, is not empty.
  - As rclone reads it, a quote `'` or `"` opens only where a value starts, and a value so quoted may hold `,` and `:` without ending its setting; a quote anywhere else is text, so `pass=a='b,key=c'` is two settings. An unquoted `:` inside a value ends it, as rclone reads it, and what follows shows as the path (`sas_url=https://…` masks only `https`; rclone can't use that location either).
  - A setting's value that is a location of its own (crypt's `remote=':s3,secret_access_key=…:bucket'`, or `'remote,pass=…:path'`; a quoted value with no backend and no `:` outside quotes is a local path to rclone) is read the same way, its quotes taken off and a quote written twice read as one, four levels deep counting the location itself: its credentials are masked, count toward the cap, and are credentials written in the configuration (`location-secret`, `config-inline-secret`, the import's notice). A location deeper than that is one credential, masked whole.
  - Each is masked as the location writes it, quotes and `$${` included, as each level reads it, and as rclone reads it last, with `$${` as `${`, without the quotes around it and with a quote written twice inside them as one, since rclone's errors quote it so; a value with a `${…}` reference in it is masked only as written. The rest of the location (the backend's or remote's name, the other settings, the path) stays readable.
  - A location with more than 16 credentials (`MAX_RCLONE_CREDENTIALS`) is masked whole; a job refuses one (see the rules above).
  - The export reads an rclone location more coarsely on purpose: `rclone_secret` splits it at every `,` and `:`, quotes and levels aside, and refuses it for any `key=…` piece whose key names a credential, the path's included, so it refuses more than the redactor masks.

Each is masked raw and as a URL parser prints it (§4.1):

- percent-encoded in full (either hex case);
- as the `url` crate encodes a userinfo, a path (also with `^` encoded, as the newer standard does), a query, a special URL's query (which also encodes `'`) and a fragment (upper-case hex);
- with tab and newlines taken out and with `\` read as `/`, as a parser rewrites them;
- lower-cased, as a host is.

A secret that holds a character a parser splits a URL at (`@`, `#`, `?`, `/`, `:`) is also masked in pieces, because the parser prints each piece as its part of the URL writes it (a host in lower case, a path as it is) and a library may print the parts one by one: each piece of at least 8 bytes (the first 64 of a secret) is masked in all the forms above; shorter pieces are masked only as part of the secret, which is also masked as a parser prints it when it starts in a host, a path or a query and moves on at each delimiter (`canary/Alpha`; decision 31).

Not covered: a host that is not ASCII, which a parser writes in punycode, percent-decoding in a host, and dot segments in a path.

Secrets that overlap or touch are masked as one span, so no tail of one is left. A secret that spans lines is also masked without the white space around it, and line by line for lines of at least 8 bytes (the first 64 lines), because logs reach a reader one line at a time.

A secret is also masked as Rust's `Debug` prints it between its quotes (`"` and `\` escaped, a control or combining character as `\u{…}`), and so are its form without the white space around it and its lines, because a library that logs a value with `{:?}` prints a secret in it so: rustic logs the command it starts `rclone` with that way, the location last (#330). `Debug` escapes each character on its own, so that form is in the printed text wherever the secret is in the text printed. The encoded forms above are not escaped as well: that would add almost as many needles again, for a secret a parser would first have to encode and a library then print with `{:?}`. An escaped form adds at most 6 bytes of needles per byte of the secret (`\u{7f}`), so the three of them at most 18.

The same three forms are masked as Go's `strconv.Quote` writes them between the quotes, because `rclone`, written in Go, quotes what it can't serve as `%q` does (`Failed to create file system for "…"`), and the worker and the daemon log what it writes (#331). Go agrees with `Debug` on `"`, `\`, tab and the line breaks, but writes another control character as `\x01` or `\a`, a format character (a zero-width space), a separator other than the space and a private-use or unassigned character as `\u200b` or `\U000e0001`, and leaves a combining character as it is.

Which characters Go prints (`unicode.IsPrint`: letters, marks, numbers, punctuation, symbols and the space) comes from the Unicode version its `unicode` package was generated from (`unicode.Version`): Unicode 17 for Go 1.27, which rclone 1.76 is built with. `domain` carries them as a table of ranges, `GO_PRINT` (`crates/domain/src/secrets/go_print.rs`), generated from that version's `UnicodeData.txt` by `scripts/gen-go-print-table.py`, so the answer is Go's whatever Rust toolchain builds Ladderback (decision 77).

The redactor asked Rust's `Debug` before, whose escapes change with the toolchain: Rust 1.100 escapes every combining mark, and a secret holding one was no longer masked as Go quotes it (#406). Compared over every character, this is Go 1.27's `strconv.Quote` exactly, and a test holds it there: it compares the count of characters Go escapes and a hash of every character's quoted form with Go 1.27.3's own.

When rclone moves to a Go on a newer Unicode version:

1. Regenerate the table with that version (`python3 scripts/gen-go-print-table.py <version>`, which needs Python 3 and downloads the version's `UnicodeData.txt` from unicode.org).
2. Quote every character with that Go.
3. Pin its count and hash in the test (`every_character_is_quoted_as_go_quotes_it`).

Where an `rclone` was built with a Go on another Unicode version, a character assigned in one version and not the other is printed by one and escaped by the other, and a secret holding one is not masked in that line, as before: that is a residual risk, of the worker's log as much as the daemon's. An rclone built with Go 1.21 to 1.26 (Unicode 15), such as a release before 1.76, escapes the 10,615 characters Unicode 16 and 17 added that the table prints, and one built with an older Go more.

Go's `%#q` writes a secret as it is between backquotes where it can, which its raw form masks, and as `%q` does where it can't; `%+q` (every character that isn't ASCII escaped) is not masked.

A Go-quoted form adds at most 4 bytes of needles per byte of the secret (`\x01`), none when it is the secret or its `Debug` form, so the three of them at most 12.

A secret is also masked as a TOML file writes it (#839), because a program that reads `config.toml`, a rustic profile or a secret helper's own TOML file quotes the line it rejects as written: a helper's error on stderr, a hook's output, a worker's stderr. A basic string writes it with TOML's escapes (`\b`, `\t`, `\n`, `\f`, `\r`, `\e`, `\"`, `\\`, any character as `\xHH`, `\uHHHH` or `\UHHHHHHHH` in either case, which the `toml` crate writes for a control character as `\u0007`), and a multi-line one may break it with a backslash that ends a line, which TOML drops with the line breaks and white space after it.

A person may escape any character, so these forms are too many to list as needles: a text with an escape in it is read again as TOML reads it, every backslash wherever it stands, and a secret found there is masked in the text whole, from the first byte it was read from to the last, the escapes and breaks inside it included. A cut text is read so on either side of the cut, and an escape the cut went through (`\u00`) is masked with the start of a secret before it, or alone where it may be how the secret's first character is written. That masks more than a secret, never less. Where the configuration's own text is shown (the diff of a proposal, decision 89), it passes through the redactor, which masks it so too.

A text masked a line at a time (a worker's or rclone's stderr, a log record) splits a multi-line string where a backslash ends a line. A line that ends so is masked as a cut text is, from where a secret the break may go through begins. Masking keeps nothing from one line to the next, so the rest of that secret begins the next line, after the white space TOML drops (spaces, tabs and line breaks). A text that begins, after that white space, with the last 4 bytes or more of a needle, as written or as TOML reads it, is masked from there to where the needle ends, however it is masked: whole, cut, clipped or together (#861).

Other white space (a no-break space) may be part of the rest of a secret, or stand before it, so a text that begins with it is looked at from both places.

That masks the start of a text that only looks like the end of a secret too, more than a secret, never less (I4 outranks a readable log): a secret that ends in `2026` masks every line that begins with that year, and one that ends in `-proxy` masks every line that begins with `proxy`. A tail of 1 to 3 bytes stays visible: it is too short to tell from other text. So does a piece from the middle of a secret that a line holds whole, between two breaks, unless one of its needles matches it there.

**How long masking takes.** A redactor looks for each needle in one pass over the text (Knuth, Morris and Pratt): each needle keeps, for each of its bytes, where a search goes on after a byte of the text that doesn't match, so each byte of the text is compared at most twice with a byte of each needle, however long and repetitive both are (#236). The tests count those comparisons rather than time them, so they can't flake. Before, each place in the text was compared with up to a needle's length of bytes, the product of the two lengths on a long, repetitive secret. Measured in a release build:

| Masking | Before | After |
|---|---|---|
| 45 needles, 1.48 MB in all, in 64 KiB of `a` | 1.92 s | 4.2 ms |
| A location with 16 rclone credentials, in itself | 121–348 ms | 5.2 ms |
| The same redactor, in 64 KiB of `a` | 247–969 ms | 4.2 ms |
| A URL with a 32 KiB password | 15 ms | 0.3 ms |
| A password at the cap with the characters a URL splits at, in itself (cut, `redact_cut`) | 4.9 ms (31.6 ms) | 3.0 ms (3.3 ms) |

A text read a second time, as TOML reads it, is compared at most four times per byte with each needle: one with a TOML escape in it, one cut with a backslash in it, or one that ends in a line-ending backslash. No escape is read as more bytes than it is written in, so what is read is never longer than the text. The table above was measured before the passes below.

Looking for the end of a needle at the start of a text, and at the start of what TOML read, is one more pass per needle for each: over as many of the needle's last bytes as the start has, each compared at most twice, after one pass over the start itself, up to the longest needle's length. That is at most twice per byte of the text with each needle again for each start, never more for a longer needle, so a text read as TOML reads it is compared at most eight times per byte with each needle. A text that begins with white space TOML keeps has two starts, so two more passes. The tests count these too.

Memory: a needle keeps 4 bytes per byte of it beside its text (a `u32`: a needle is at most `u32::MAX` bytes, half of what a `usize` takes), and masking a text takes 4 bytes per byte of the text, 4 more per byte of each start up to the longest needle's length (where a search of it goes on, as a needle keeps), and 9 more where it is read as TOML reads it (what was read, and where each byte of it starts and ends in the text, each a `u32`), with 4 more per byte of each start of what was read. A text longer than `u32::MAX` bytes with a backslash in it is masked whole.

A secret gives up to about 80 bytes of needles per byte of it, measured: 80.3 on 64 KiB of `\`, `\x01`, `é`, `#`, a capital and DEL in turn with a line break every 1,000 bytes, its forms above, the most of the mixes measured (70.4 with a tab for `\x01` and no line breaks), so its needles and their borders take up to about 400 bytes per byte of secret (401 measured; the Go-quoted forms of #331 added 2.4 of the 80).

**A redactor masks at most 256 KiB of secrets** (`MAX_MASKED_BYTES`), each counted once however many places hold it: the password, what the references resolved to, what the settings hold that is masked (a URL's password, an rclone credential, a credential option), and the proxy credentials the engine adds. That keeps one redactor under about 100 MiB (#248). A real repository's secrets come to a few kilobytes: a password, an S3 key pair and a 2.5 KiB SSH key, 2.7 KiB in all, take 139 KB of needles and borders, so the cap leaves about a hundred times that, and room for four secrets of the 64 KiB a secret may hold. It holds in three places, each before a form is built.

- A resolution (`ResolveRepository`) counts the secrets as it reads them, field by field, and fails at the field that takes them past the cap (`secrets-too-large-to-mask`, which names the field and the cap, never a secret): nothing after it is read, and no job runs.
- The engine refuses a job whose secrets and the proxy credentials of the worker's environment pass it, before a worker starts, with the same typed code (`EngineError::SecretsTooLargeToMask`): its `field` is the proxy variable whose credentials took the count past the cap, such as `HTTPS_PROXY`, and is left out when the job's own secrets did. A backup or a maintenance run stores it as the operation's failure (data-model.md §9), and the repository routes and the snapshot listing answer it as they answer a resolution's (422).
- `Redactor::new` counts what it is given before it builds a form: past the cap it builds none and masks every text that isn't empty whole, more than a secret, never less (I4). That covers every other redactor: a refusal's, which reads the secrets again and stops reading once what it read again passes the cap (the inline secrets of the settings are counted after it, with the rest, by `Redactor::new`); the debug form of the settings; a location a page shows; the one a run's hooks are masked with (below), which past the cap masks each hook's output whole; and the one the in-process retention evaluation (`RusticRetention`) builds from the repository's secrets and the proxy credentials of the daemon's own environment, which past the cap masks the error it reports whole rather than refusing.

A needle longer than `u32::MAX` bytes, which the cap doesn't let through, masks every text whole too.

**Where masking runs.**

- The worker masks every `Log`, `Warning` and failure detail, and its panic report, before it cuts them to size (§4.1).
- The daemon masks what the worker writes to stderr, because the programs a worker starts (rclone, ssh, a post command) write there too.
- It also masks every text in the worker's events (failure details, warnings, progress text, log lines), because a worker rejects a job spec before it has the job's secrets and a parse error can quote the value it choked on, and because the worker doesn't know the proxy credentials below.
- **A hook's output is masked with its run's redactor** (#853). A hook can print any secret it can read: the configuration file, a password file, a variable of its environment. So the daemon builds one redactor per run, once the run's secrets are resolved and before its first hook (`RepositoryAccess::hooks_redactor`), and hands it to every hook of the run, the agent's, the repository's and the plan's, in every phase (`HookSetup::redactor`). It holds:
  - the run's repository's secrets as the run resolved them: the password, what the location and the options hold that a redactor masks, and what their references resolved to;
  - every secret the configuration holds as text, in every repository and at every location (`AgentConfig::written_secrets`), in the forms a redactor knows: a hook that prints `config.toml` shows them as written there, with TOML's escapes (`\u00e4`) or without (above);
  - the credentials of the proxy URLs in the environment the hook runner gives every hook (`HookRunner::environment_secrets`): the allow-list passes them, as it does to a worker (below), and a program the hook starts uses them.

  A run whose secrets can't be resolved is refused before any hook runs, so no hook runs without the redactor. Secrets past `MAX_MASKED_BYTES` mask each hook's output whole (above). Production keeps no hook output yet: a hook's outcome reaches the operation only as its status, in a `hook-warning` or `hook-failed`, so this masking keeps the output safe for when it is stored, logged or shown. A `hook-failed` names the hook by its level and its place in that level's list and says how it ended, and the `hook-warning` an open page is told of carries the phase and the exit status, never what the hook wrote (#480, #369).

  **Out of reach:** a repository with several locations resolves only its password before the run; every location's `${…}` references, the first location's included, are resolved inside the engine, in the job, when that location is chosen (§10.6). The daemon never holds those values, so its redactor masks what the locations hold as written but not what their references resolve to. Nor does a run resolve another repository's secrets (its `password-file`, command or keyring entry, its `${…}` references): that would run commands and open keyrings for a run that doesn't use them. A hook that prints any of these from where it is kept shows it.
- **Masking twice can mask more, never less** (#287): a text the worker masked is masked again in the daemon, and when a secret holds `*`, the character of `***`, a mask and the text beside it can make up that secret, which the second pass masks too (secret `*?`: `*??` masks to `***?`, and that to `*****`). That is kept: skipping what matches inside a run of `*` would leave part of a secret unmasked when a real `*` stands beside it (I4).
- **A text cut at a cap is masked as a cut text** (`Redactor::redact_cut`, decision 45): every whole secret as anywhere else, and the end of what was kept from where it begins a secret, with the bytes of a character the cut went through left out. That masks more than a secret where the end only looks like the start of one, never less. It applies wherever output is cut and then masked: a secret command's stderr and hook output (however they ended, below), a worker's stderr line cut at the message cap, and a text that someone who knew fewer secrets cut and marked with `…` (a worker's event text, a command's detail in a refusal; `Redactor::redact_clipped`).
  - **Output cut by time is a cut text too:** a pipe that was not read to its end (a hook stopped at its timeout, a pipe a process the hook or command started still held open when the grace ran out, a read that failed) and a worker's last stderr line without its newline (a kill can end the worker partway through a write) can end partway through a secret, since a secret written in several writes, or in one larger than a pipe passes whole (`PIPE_BUF`), reaches the reader in parts.
  - **So is output its writer cut short:** a hook or a helper can stop partway through a secret and exit on its own with nothing in what was read to say so, so a hook's stdout and stderr and a secret command's stderr are masked as cut however they ended (decision 45).
  - Text that is masked first and cut after (a worker's own event text, `Problem::command_failed`'s 512 bytes) needs no more.
- The `Debug` forms of `RepositorySettings`, `ResolvedRepository`, `RepositoryAccess` and the worker's `RepositorySpec` show the names of the options of all three sets but no values, no secrets, and the repository strings redacted.

**The daemon's own log is masked while it opens a repository itself** (#330). To evaluate retention for a forget or its preview, the daemon opens the repository in-process (`engine::RusticRetention`), and rustic, its backends and the crates under them (OpenDAL, the HTTP client) then log through the daemon's logger.

rustic names the repository by its location (`repository <location>: password is correct.`, at `info`), and an `rclone:` location holds rclone's settings, credentials among them; it logs each line the `rclone` it starts writes to stderr (`rclone output: …`, at `info`), and rclone quotes what it was asked to serve when it can't; at `debug` it logs the whole `rclone` command, the location last, as `{:?}` prints it (a secret is masked in that form too, above).

- So the daemon's logger is wrapped (`engine::Masked`): from before an open starts anything until its backends, the `rclone` they started and the thread reading its stderr are gone, every record the daemon logs, whatever crate made it, is masked with that repository's redactor, the one its errors are masked with (its password, the secrets of its locations and options, what its references resolved to, the proxy credentials). Masking by record rather than by crate covers the crates under rustic, which log under targets of their own, and the threads they start.
- With two opens running, a record is masked as one redactor of the secrets of both would mask it (`Redactor::redact_together`), so a secret of one that holds or overlaps a secret of the other is masked whole rather than left in part beside the other's mask (#287); a redactor that masks everything (secrets past `MAX_MASKED_BYTES`) masks every record whole while its open runs.
- A record is a whole text, masked as one; its key-values, which the daemon's log doesn't show, are dropped.
- A `rest:` location's password is masked by rustic itself in the name it logs, and an `opendal:` location is logged as `opendal:<scheme>:<name>`, without its options; both are masked all the same.
- OpenDAL runs its tasks on a runtime the whole process shares, which outlives the open: what a task of it might log once the open is gone is not masked. No record of an open is known to come that late; it is a residual risk.

Resolved secrets are passed to workers through the `JobSpec` on stdin, never as argv or environment variables. That holds even when a secret was *sourced* from an environment variable: **a worker starts with a scrubbed environment** (§4.1): only a fixed allow-list of variables that name a place or a setting (`PATH`, `HOME`, the locale, `SSH_AUTH_SOCK`, certificate locations, `RCLONE_CONFIG`, the proxy variables) and nothing else of the daemon's. Two consequences:
- Ambient cloud credentials (`AWS_*`, `AZURE_*`, `GOOGLE_*`, `RUSTIC_*`, `RCLONE_CONFIG_*`) no longer reach a worker. A repository that needs them says so explicitly, with `${…}` in its options.
- A proxy URL with credentials embedded passes as it is. This is a residual risk the user takes by writing it there: the credentials stay in the worker's environment, where the programs it starts use them. They are masked wherever the worker's output shows them, though: the daemon adds the password and the whole userinfo of `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (either case) to the job's redactor. `NO_PROXY` lists hosts, not a URL. Proxy credentials are not a secret source: a proxy URL is read from the environment as it is, never resolved from a reference, so this adds no secret source.

Hook and notification templates never receive secrets (Backrest leaks them this way, [#1170](https://github.com/garethgeorge/backrest/issues/1170)); hooks get the same scrubbed environment when they are built. A notification channel's URL, token and password are secrets from the sources above, never inline, resolved by the daemon for one delivery (§11). A repository's locations each carry their own references, resolved when a job or a probe starts and never shared between locations (§10.6). **Secrets never leave the agent.** Hub maintenance and hub downloads need the repo password, so for hub-managed repos the **hub has its own secret entry** for that repo, configured on the hub. Agents don't push passwords.

Connecting a repository saves the settings **as written**: a `password-keyring`, `password-file` or `${…}` reference stays a reference in `config.toml`, never the value it resolved to; the resolved value lives only inside the job it was resolved for. The `@e2e` scenario covers this with a file reference — no test writes a real OS-keyring entry — and a keyring reference round-trips the same way through the config store.

**Keeping a typed password in the keyring** (#476, decision 110). When the person chooses the system keyring for the password they typed in the repository form, the daemon keeps it in the entry `ladderback/<alias>` through the `Keyring` port and saves `password-keyring = "ladderback/<alias>"`, so the password never reaches `config.toml` or its history. Removing a repository from the configuration never deletes its entry.

- **Writing.** The adapter writes the entry with the same keyring library the resolver reads it with, in one blocking call under the resolver's time limit, which reads the entry first. An entry that holds another secret, text or not, is refused as `keyring-entry-taken` and never overwritten, since it may be the only copy of another repository's password; one that holds the typed password is used as it is. A password over 64 KiB, more than the resolver reads from an entry, is refused before anything is kept. The call can't be cancelled, like a blocked read: a write that outlives the limit, as one waiting on an unlock prompt, may still land after the request was refused, and a later request then finds the entry holding the typed password and uses it.
- **Refusals.** No keyring service to ask is `keyring-unavailable`, and so, on Linux, is an entry the service finds no item for when it can't then say whether its `default` collection is locked, since the entry may be there unseen (#483): nothing is written over an entry that may exist, nor said to be removed. A Secret Service that says its keyring is locked, told the three ways the resolver tells it (the service's own error, the D-Bus error's name, or no item found in a `default` collection it says is locked), is `keyring-locked`, whose message says how to unlock it (#993), and so is one whose unlock prompt was dismissed, which leaves it locked; one with no collection stays `keyring-unavailable`. Any other failure or no answer within the limit is `keyring-unwritable`. The platform's words are the `detail`, masked of every secret of the repository, the typed password first.
- **Undoing.** Connecting keeps the password only after the test passed, and removes an entry it added when the save fails. Creating keeps it only once the settings resolve and before the job runs, so a missing keyring creates nothing; it removes an entry it added when the job fails, but leaves it when only the save fails, since the repository now opens with that password and the entry may be its only copy. A removal that fails leaves the entry holding the typed password, and the request's own refusal is the one reported.

**Saying when the keyring can't be started on demand** (#923, Layer 2 of #877). On Linux the session bus starts the Secret Service when a program first asks for it, if an activation file names it; a service with none runs only once the desktop starts it, so a scheduled run that fires as the session begins finds no keyring, waits (§5) and may fail. Fedora 45's move from gnome-keyring to oo7 left machines in that state ([RHBZ 2567187](https://bugzilla.redhat.com/show_bug.cgi?id=2567187)).

- **The question.** The `Keyring` port's `activation` answers `OnDemand`, `RunningOnly`, `Absent` or `Unknown`. The Linux adapter asks the session bus itself `ListActivatableNames` and, when no file names `org.freedesktop.secrets`, `NameHasOwner` for it, through the `dbus` crate `dbus-secret-service` already builds in. Each call has 0.5 s and the whole question 2 s; a bus that can't be reached, refuses a call or doesn't answer in time leaves it `Unknown`. A question past its 2 s is left to end on its own thread: connecting has only libdbus's default limit of 25 s. Neither call touches an entry, so neither can raise an unlock prompt, and neither carries a secret (I4). macOS answers `OnDemand`, and a platform with no OS keyring `Absent`.
- **The note.** Only the Repositories page asks, through `GET /api/v1/repositories/_notes`, never a run or a scheduler, and only while a repository keeps its password in the keyring (`password-keyring`): with none, no run reads the keyring, so nothing is asked. `RunningOnly` alone is noted, as the code `keyring-not-activatable`, whose message names the two ways out: repair the activation file, or keep the password in a file or a systemd credential. Every other answer notes nothing, so an answer that couldn't be had never sends a person to repair what isn't broken.

**The types that hold a secret wipe it from memory when they are dropped** (#600). A `SecretValue`, the admin `Password` and an API token's secret (`ApiTokenSecret`, `ApiTokenText`) derive `zeroize`'s `Zeroize` and `ZeroizeOnDrop`, so dropping one, or any clone of it, overwrites its bytes before the memory is freed; argon2 wipes the memory it hashes a password in. The secrets adapter wipes what it reads into: a file's bytes and a command's stdout, in buffers sized up front so they never grow, the chunks a command's pipes are read in, and the keyring entry's text. This is defense in depth for I4, not a guard against the user's own programs: processes of the same OS user can already read the daemon's data folder, and on macOS its memory (below). It narrows what memory leaving the process later, in a core dump or a page swapped out to disk, can hold.

Known limits, copies not wiped:

- `rustic_core`'s own, in the worker and in the daemon when it opens a repository for retention;
- the `Redactor`'s needles and every other `String` built from a secret: settings expanded from `${…}`, the job's spec for the worker, a `String` that grew and freed its old buffer;
- the HTTP request and response bodies (a password typed, a token's text shown once), what `set-password` reads from a terminal, an environment variable's copy and the libraries a secret is handed to (a webhook's URL in `reqwest`);
- the session and CSRF tokens, which are not resolved secrets;
- a secret still in use, which can be swapped out.

**No core dumps, no debugger** (decision 98). The daemon, the MCP server and its one-shot command (`ladderback mcp call`) as they start, before they resolve any secret or read an API token or a script of calls, `check-keyring`, `set-password` and `pair` as they start, before they read a secret or prompt for one, and each worker before it reads its job, set their core-dump limit to 0, soft and hard (Linux and macOS), and on Linux clear their dumpable flag, which also refuses `ptrace` and reads of their memory by other processes of the same user (`platform::dumps::refuse`).

A program they start (a hook, a secret command, rclone) inherits the limit but not the flag: it is dumpable again, so the same user can read its memory and environment. A process that can't logs `core-dumps-on` or `debugger-attach-allowed` with the system's words and goes on; a worker writes the code to stderr, which the daemon logs as a warning. Root can still read any process's memory, and macOS still lets a debugger of the same user attach.

**Not yet in place.** `SecretError` and `TemplateError` are mapped to API error codes and localized messages (`secret-*`, `template-invalid`, `location-too-many-credentials` for an rclone location over the cap, and `secrets-too-large-to-mask` for secrets past what a redactor masks) on the repository routes and the snapshot listing, with the words of a command or a platform masked of every secret of the repository, those a reference resolves to included; mapping them to the failure reasons of an operation that runs belongs to the job-runner and operation-log work (the engine's refusal of a job past the cap is already one, `secrets-too-large-to-mask`, above). Seeding a daemon-wide redactor with every secret at config load belongs to the config work. The warning for an inline secret is built (`config-inline-secret`, §16 decision 37).

### 10.3 Agent ↔ hub

This section decides how an agent and the hub prove who they are to each other, and what passes between them ([decision 120](decisions/120-agent-hub-connection-security.md); how a person pairs is [decision 121](decisions/121-pairing-a-machine-with-its-hub.md); the messages and their order are in [multi-machine.md](multi-machine.md) §7.1 and §7.2).

- **Both sides prove themselves at connect.** The agent and the hub each sign, with their Ed25519 keys, a domain-separated message: a fixed label, the hub key, the agent ID, both sides' fresh nonces and the kind of TLS binding, which in built-in TLS mode holds the TLS 1.3 session's exporter value (RFC 9266). The agent proves nothing until the hub has, and refuses a hub whose key isn't the one pinned at pairing. A signature over a bare nonce verifies as nothing.
- **The hub has a key of its own,** kept in its data folder and never in the database, with an offline recovery key pinned beside it. Agents pin both at pairing, so behind a TLS-terminating proxy the proxy's certificate isn't what the agent trusts. The hub rotates its key with a handover the old key signs, recovers a leaked one with the recovery key, and never makes a replacement by itself. Ladderback's own backup plans leave the key files out by default.
- **Every message after the handshake is signed, in both directions,** for one agent and one connection, with a sequence number that leaves no gap and, from the hub, an expiry, so a proxy that ends TLS, or anything between, can read, delay and cut the connection but can't forge, replay, alter or silently drop one message. Commands also carry an ID and the time they were requested, so one that waited too long, or arrives twice, doesn't run. Nothing is encrypted a second time, and no secret crosses the link.
- **A new agent is held pending until a person approves it on the hub.** The hub shows its hostname and key fingerprint and the agent shows the same. A pending agent has no grants, claims, leases or commands, and its reports are kept and not acted on. A pending agent or replacement key lapses after 7 days; a lapsed agent that comes back is told `pending-expired` and pairs again with a new token. Approval, making a token, re-keying and viewing or downloading the Recovery Kit are high-impact actions: a signed-in session and a fresh step-up, and beyond loopback sign-in must be on. The Recovery Kit's page needs sign-in on even on loopback, since a proxy on the hub's machine looks local, and after 7 days only `ladderback recovery-kit` shows it (decision 120).
- **Pairing** uses a single-use token that lapses after 15 minutes by default, can be revoked and carries a one-time key, so the secret itself never crosses the network or goes on a command line. `ladderback pairing-token` on the hub needs no sign-in, as `set-password` doesn't (decision 99): it runs as the user that owns the data folder. A token shown on a screen, in a terminal's scrollback or through a share sheet can be read by whoever sees it until it lapses, is used or is revoked; the QR code is the same secret as the text. A copied data folder is caught by a connection counter beside the machine identifier check (#296).
- **Before a peer has proved itself, the hub bounds what it spends on it:** the size of a frame, the time to the first frame and to the end of the handshake, and the number of connections not yet proved, the oldest closed for a new one. §7.2 of [multi-machine.md](multi-machine.md) has the values. The agent sends nothing to a plain `http://` address that isn't loopback: the refusal comes before it connects.
- **No mutual TLS, no required tunnel, no peer-to-peer.** An agent works behind a reverse proxy, over a tunnel the person already runs, or with built-in pinned TLS. An agent reports to one hub.
- **What a hostile hub or agent can do is bounded** (decision 120): a hub can run a plan (rate limited), cancel an operation, pause scheduled maintenance with a skewed clock or an identity conflict (never a backup) and, from M9, request a restore only into a new folder where the agent allows it, and can't stretch an owner's deadlines; a rogue agent can't hold the prune guard beyond a cap. A hub that is moved or restored is not decided yet.

The protocol carries metadata, logs and restore requests, never file contents or secrets (I4).

### 10.4 Restores

This section decides what confirms a restore or a download, where a restore may write, and how a download reaches the browser that asked.

Restores are the most dangerous action because they can overwrite files.
- **Step-up confirmation** before any restore or download started from a web UI, whether local or on the hub. With auth enabled, re-enter your password; this is required even with a valid session, so an unattended open tab isn't enough. Password managers and paste work (A5). With auth disabled or in proxy-header mode there is no password to re-enter, so the user types or pastes the snapshot's short ID instead. That only guards against misclicks, not against someone at the keyboard.
- **The same step-up approves a proposal** (§16, decision 89). With auth enabled, the password, its attempts sharing the sign-in waits (`SignInWaits`), so a stolen session cookie can't guess it through approve. With auth disabled or in proxy-header mode, the proposal's short ID, which only guards against misclicks; with auth disabled, approval is no safety boundary at all, since an AI agent can send the same request (§10.5).
- **A confirmation is read once, where the request brings it**, into a `StepUpConfirmation`: its `Debug` hides it and it wipes its bytes when dropped, as a password does (I4), so nothing that carries it has to hide it by hand. Nothing typed, or more than the longest password (`PASSWORD_MAX_BYTES`, 1,024 bytes), is no confirmation: the route refuses it as a wrong one (`step-up-failed`) before the daemon is asked, and it counts in no sign-in wait.
- **Default destination is a new folder** on the target machine: `<restore folder>/<host>-<snapshot-short-id>-<timestamp>/`. The restore folder is `[agent] restore-folder` when set (an absolute path, §6.1), else `ladderback-restore` in the agent's home folder. An agent with no home folder Ladderback can use (none, or not UTF-8) and no `restore-folder` refuses a restore into a new folder with `restore-folder-unset` (HTTP 409, as a request sign-in being off refuses is: the configuration doesn't allow it now, and setting it does); it never falls back on the data folder, so restored files never land beside the database and the secrets. Existing files are never touched in this mode.
- **From the hub**, only new-folder restores are possible, and only to agents that set `allow-hub-restore = true` (off by default). The agent runs the restore itself; the hub sends only the request.
- **Restoring in place** (original paths) is offered only in the agent's own UI. Its confirmation dialog states how many files would be added, overwritten or left as they are, using a dry-run `prepare_restore` plan first, and how many files the snapshot doesn't hold would stay: a restore never deletes a file.
- **A restore runs no hooks:** neither the agent's hooks nor a plan's run for it (decided by the maintainer, 2026-11-15).
- Every restore is recorded in the op log with who started it and from where (local UI or hub).
- **A download** hands one entry of a snapshot to the browser that asked, a file as itself and a folder or the snapshot's top as one tar or zip archive, its entries stored, not compressed (§16, decision 114). It is confirmed by the same step-up, through `POST /api/v1/repositories/{alias}/snapshots/{snapshot}/download`, which answers 201 with a ticket: 32 random bytes, never logged or shown. The browser fetches `GET /api/v1/downloads/{ticket}` once, within a minute, and the body streams a piece of at most 64 KiB at a time; a ticket nobody fetches is given up within 10 s of its minute. Both routes are for a session only, never an API token.
- **Downloads take turns.** At most two run at once, each a worker holding the repository's index for as long as the browser reads; a third is `downloads-busy` (409), never queued. A download takes no I7 slot, runs no hooks and isn't queued, but is recorded in the op log as a restore is (kind `download`, triggered by hand), with no entry path. While a restart waits, a new one is `restart-pending` (503, as a restore is), and the stop cuts a streaming download short. An agent that can't draw a ticket's random bytes refuses with `downloads-unavailable` (503).

### 10.5 MCP server

An MCP client is usually a language model acting on text it read elsewhere, so `ladderback mcp` treats every call as untrusted input with no human behind it. The aim is to bound what a confused or prompt-injected model can do, not to stop a local user, who already has the API.

- **No step-up, so no restore.** Restores, downloads, applying forget or prune, adoption, direct config edits, approving a proposal, hub pairing and auth settings have no tool (§4.6). A tool can't stand in for the confirmation in §10.4.
- **No new commands without a person ticking each one in the web UI.** Hooks, `password-command` and secret sources can't be set or changed through MCP directly, so a prompt injection can't add a command run as the daemon's user (I4). A proposal (§16, decision 89) may include hooks, but each command is shown verbatim on the "Pending changes" page, as its program resolved on `PATH` with its arguments as a list, and the proposal can't be approved until a person has ticked each one. A proposal names secret sources, never values, and only a person chooses a `password-file`, `password-command` or environment variable. Approving needs a person's step-up confirmation (§10.4). Running a plan does run the hooks and secret sources a human already configured.
- **With sign-in off, approval is no safety boundary.** Nothing then tells a browser from an agent's HTTP call that leaves out the AI-agent header (below), so an AI agent that can send HTTP requests to the daemon can approve its own proposal; the "Pending changes" page says so. And an AI agent with a shell as the daemon's user can edit `config.toml` directly: proposals guard against a confused or prompt-injected AI agent using its MCP or API access, not against code execution.
- **Enforced by the daemon, not the client.** With auth enabled, connect mode authenticates with an API token whose permissions the daemon checks per route (§10.1, decision 127). Configuration creates, lists, reads and withdraws proposals and runs the dry run; everything the "Pending changes" page does, and reading or setting the dry-run allowlist, accepts only a browser session, so a token can't widen what a dry run reads (§4.2). A leaked token can't restore, edit config or approve even through raw `/api/v1` calls.
- **With sign-in off, an AI agent's requests say so.** The loopback API is open to local processes anyway, as it is to curl; `ladderback mcp` marks every request with the `x-ladderback-ai-agent` header, and a request so marked is held to the `[without-token]` table of `config.toml`, the same rows with a new token's defaults, and refused what it lacks as `403 without-token-permission` naming the row. That limits a confused AI agent, not a process that leaves the header out. The tools the server lists follow the same permissions, as a convenience: a tool it hides is still refused when called (§4.6).
- **Token handling.** Read from `--token-file` (default `<config>/mcp-token`; a file with any group or world permission, or over 4 KiB, is refused, where a `password-file` others can read or change only gets a warning (§10.2): the token file is Ladderback's own, with no rustic or container setup to stay compatible with; a named file that isn't there is refused, a missing default means no token), never from argv, and sent only over `https` or loopback: a token with a plain `http` address of another machine is refused at start.
- **Secrets stay references.** Results show secret references, never values, and no tool's answer holds a repository password or a location's credential. No redactor masks the answers: what keeps them clean is what each tool returns. `list_repositories` tells where a password comes from with no field for its value, a `password-command` by its program alone, a location option by its name, with its value only when that is a reference alone, and a URL with its password masked; `test_repository` names each location by that masked address. Warnings and notices, `list_plans`' and `preview_import`'s among them, carry names, never values, and a profile's parse details are scrubbed of the text they quote. A failure a tool tells of was masked by its run's redactors, of the secrets the run resolved and those its settings write (§10.2). `export_profile` refuses inline passwords (§4.6). The I4 canary test covers every tool.
- **The log a tool reads is the masked log.** `read_log` answers the recent log's lines as the logger kept them, inside its masking, so a line holds no more than the log file does (I4), and it refuses a filter it can't read without echoing the value. In connect mode with sign-in on, it reads them at its API token's permission Daemon log (decision 134). With sign-in off, `ladderback mcp` is held to the `[without-token]` table's Daemon log, which its defaults leave out, and so is a session of its own; a scratch session's table allows it, since its log tells only of made-up files.
- **Pairing is explained, never done.** No tool makes a pairing token, pairs, approves or revokes. `pairing_state` answers only what the machine's pin holds in public, the hub's address, its key's fingerprint and how its certificate is checked; the pin holds no secret and no token is kept once used (I4). That fingerprint is the one a step-up on the hub's own loopback with sign-in off takes, public anyway and only a misclick guard (decision 120). It reads at Backups, and moves no connection counter, since it never connects to the hub. The pairing guide tells the person to paste a token only into `ladderback pair`, never into the chat, since until it is used or lapses whoever holds it can pair a machine. A pin that can't be read is `unknown`, its reason only in the daemon's log, which names the key file and never its text.
- **Commands a person wrote stay out of an agent's export.** A `password-command`'s arguments, a hook's command line and an option rustic runs as a command (`rclone-command`, `post-create-command`, `post-delete-command`) are text a person typed, and one may carry a token, such as a health-check URL in a hook. `export_profile` leaves out the `password-command` (a password read from the environment or the keyring is one too), every such option and every hook, with a `profile-command-left-out` notice naming each by its key (#856); a `password-file` runs nothing and stays.
- **An API token's export has no commands either.** Over the API, a request that carries an API token gets the profile without them whatever it asks, since a token is a program's; a signed-in session gets the whole profile, as `ladderback export-profile` writes it, unless it asks `?commands=left-out`. That query stays, and connect mode always sends it: with sign-in off its requests carry the AI-agent header, but the profile route decides by the token alone. A caller that leaves the query out then gets the whole profile. That is accepted: with sign-in off, whoever reaches the daemon (any local user, and anyone who can reach its address when it listens beyond loopback) can already set hooks and run commands as the daemon's user (**Local users**, §10.1), and a program of the person's own OS user could read `config.toml` anyway (§16, decision 99).
- **Residual risk: text the user wrote.** `export_profile` writes an option whose name doesn't say it holds a credential verbatim, as a profile needs it, so a token typed into one reaches the MCP client. `list_repositories` doesn't mask a password in a location that isn't a URL (`sftp:user:password@host:/path` holds no `://`), and `preview_import`'s notices and refusals name a profile's keys as written. None of this is a secret Ladderback resolved.
- **Headless isolation.** Headless mode takes the data-dir lock (§9). `--scratch` uses a fresh mode-0700 temporary directory, never the user's config or data; its repository's password is a random token in a mode-0600 file there, never on a command line. The sweep of crashed sessions' folders deletes only a folder whose lock it can take, never a link: a live session's folder, or another user's, is left alone.
- **Names inside snapshots need Snapshot contents.** `list_snapshot_folder` and `find_in_snapshots` show the names, sizes and times of the files a snapshot holds, and nothing more: no file's content, no restore, no download (decision 132). In connect mode they reach the folder and search routes, which a token opens only with the permission Snapshot contents (decision 127). Without it both are refused `api-token-permission` naming `snapshot-contents` before the repository is looked up, so the refusal tells nothing of the repository. With sign-in off, `ladderback mcp` is held to the `[without-token]` table and refused `without-token-permission`, and so is a session of its own (headless or scratch). The table's defaults leave Snapshot contents out until a person opens it; a scratch session's table adds it, since its files are made up. Both tools share one function in the MCP server (`snapshot_contents`). A search's work is bounded by its caps, whatever the agent asks (§4.6).
- **Residual risk: untrusted output.** Logs, paths, tags, hostnames, the names inside snapshots and rustic's error details are text a model reads, and an attacker can influence it. Ladderback doesn't sanitize it; the mitigation is that no tool can turn such text into a destructive action. A proposal it shapes still needs a person's approval, and the summary the person reads is written by Ladderback from the changes, never by the agent. Result size caps (§4.6) limit how much reaches the model at once.

### 10.6 Repository locations

A repository may be reached at several locations, tried in order, each with an optional rule about the network (§6.1; §16, decision 80). This is what that adds to the threat model; the rest of §10.2 applies to each location unchanged.

| Threat | What it takes | What Ladderback does | What remains |
|---|---|---|---|
| A rule trusted as if it proved where the machine is | A Wi-Fi name that is copied, a router's address that is copied (ARP carries no proof), or a private address range another network reuses | A rule only chooses which location to try; every chosen location is checked as any is (the repository ID, which a repository with several locations always records, and TLS where the address has it and the check of its certificate isn't turned off). Nothing in the design treats a name or an address as proof | The credentials of the location go to whatever answers at its address |
| Credentials sent in the clear to an impostor | A location that sends credentials where an impostor can read them, on a network the rule admits: `rest:http://…` with a user and password or a credential option; an `https` REST location with `http-insecure-tls` true; an OpenDAL or rclone address over `http://` with a credential; `opendal:ftp` over an `ftp://` endpoint with one | A warning, `location-plain-http-credentials`, on the Repositories page and in the daemon's log, naming the repository, the location's position, a cause (`plain-http`, `unchecked-certificate`, `plain-endpoint`, `plain-rclone`, `plain-ftp`) and whether the location has a rule (`rule`: `network` or `none`; for `network` the page says the rule can't tell the network it is meant for from one made to look like it), and neither the address nor a credential. It is checked on every address of every location, a repository of one location included, each with the options rustic opens that address with, as written and again on what a `${…}` resolves to when its job starts (the second as a log line only). It is a warning, not a refusal. The recommendation is the LAN location first over HTTPS that verifies without the internet (split-horizon DNS with a public certificate, or a private CA given to rustic as `http-cacert`, an absolute path, §6.1, or for an rclone location to rclone as `override.ca_cert` in its connection string), with no rule, and the public address second (decision 80, point 7); never `http-insecure-tls` | On plain HTTP the credentials are sent before any check of the repository's ID can run, and nothing takes them back. An `rclone:` remote set up in rclone's own file is not seen. A rule is no defence: a travel router's wired link or a copied Wi-Fi name passes it |
| A different repository at a location | A misconfigured or hostile server | Every location must hold the repository's ID (decisions 49 and 57); a mismatch is refused, never used, raises a warning, and the run goes on to the next location. The cache slot stays keyed by the ID | An old copy of the same repository passes the check; a backup written to it would fork the history. True of any repository whose address can be spoofed, and likelier on a LAN anyone nearby can join. Only TLS with a trusted authority closes it |
| One server's credential sent to another | Options inherited between locations | A location's options never apply to another; the job's worker gets only the chosen location's secrets (each probe is its own worker, holding one) | A credential reused on purpose by writing it twice |
| A secret in a place it must not be | A location's reference resolved into config, argv, an environment, a log, an event, an operation record or the page | Locations are references like any other (I4); a worker's redactor holds the secrets that worker has (a probe the password's and its one location's, the job the chosen location's) and the daemon writes no text that could hold one (a location's outcome is a code, its source names where a secret was looked for); the operation record keeps a location's address as the entry writes it, with credentials masked, and its outcome code | Nothing new |
| The machine's whereabouts leaking | The current Wi-Fi network's name, or the current router's address, in a log, event or sync message | Never written: logs, events, operation records and sync messages say "on Wi-Fi, not a listed network" or that a rule wasn't met. A name or an address in a rule is the person's own configuration and is shown on the page | A name in `when`, and the router addresses the person chose, are in `config.toml` in plain text. A hub fetching a log sees what logs hold, rustic's lines among them, which name the repository's address (§10.2): the operation records it syncs carry no location or outcome, and a log's lines carry a position and an outcome code, which can say a rule wasn't met but never a name or an address |
| A rule that can't be read used to bypass it | A platform that hides the network name | A rule that can't be evaluated doesn't hold, so the location is skipped, not used (the opposite of the AC power condition, §5); the scheduler skips a run only when every rule is known not to hold, and an unreadable one starts the run and fails it where it is recorded and retried | A run fails, and is retried, where every location has a rule that can't be read |
| A hung backend taking a job with it | A silent address that never answers | A probe is its own worker, killed 8 s after its start; locations that check the server first are probed at once (decision 86), others in their turn, so at most 32 s before the job | Up to 32 s waiting away from home when no rule keeps the run off a silent address |

Reading the network's name takes no privilege Ladderback asks for: NetworkManager's D-Bus API on Linux, whose policy lets an unprivileged process read the properties, and `system_profiler` on macOS, which returned the name to a launchd-started program in the test (decision 80, point 10) and which Apple may redact. The workspace keeps `unsafe_code = "forbid"` (§13.5, item 6).

### 10.7 The release check

The release check (§5; §16, decision 107) is the one request Ladderback makes on its own to a service it doesn't run. This is what it sends, what it reads and how to turn it off.

- **What leaves the machine.** At most once a day, an HTTPS `GET` of `https://api.github.com/repos/nledford/Ladderback/releases/latest`, with `User-Agent: ladderback/<version>` (GitHub asks every client for one) and `Accept: application/vnd.github+json`. No cookie, no token, no referrer and nothing about the machine, its plans or its repositories. GitHub, and anyone who sees the connection's metadata, learns the machine's IP address, that it runs Ladderback, which version, and roughly when it started.
- **Turning it off.** `check-for-updates = false` in `[agent]` (§6.1): the agent then asks nothing and shows nothing, from the next check on, without a restart. The `LADDERBACK_RELEASES_URL` variable points the check elsewhere (the test suites and `just try` use an address nothing answers at); a value that isn't an `http` or `https` address turns the check off, said once in the log, rather than ask GitHub instead.
- **A hostile or broken answer.** The client follows no redirect and gives up after 10 s, connecting included. It reads at most 1 MiB, and of the answer only `tag_name`, `prerelease` and `draft`; a tag that isn't `v` and a SemVer version of at most 64 bytes is unreadable. A version is digits, letters, dots and hyphens only, and the address of its notes is built from it under `https://github.com/nledford/Ladderback/releases/tag/`, never taken from the answer, so nothing of the answer but the parsed version reaches a page, the log or the store. A feed that lies can at worst show a version that doesn't exist or hide one that does; the notice is never acted on.
- **What the log keeps.** A found update at info level, once per version; a failure at debug level, as a kind and the HTTP status, never the answer's body.
- **The page.** The notice's link opens GitHub with `rel="noreferrer"`, so GitHub isn't told the daemon's address. It is shown only where the running version is (with sign-in off or a live session), never on the sign-in page.
- **Proxies.** The standard variables (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`, in either case) are honored, as for notifications, so a machine that reaches the internet only through a proxy can check, and the proxy sees the request as any proxy does.
