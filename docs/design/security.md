## 10. Security

### 10.1 Web UI

- Binds to `127.0.0.1` by default.
- **Sign-in is optional**, as in Backrest (§16, decisions 11 and 70). It is **on** while an admin password is set and **off** otherwise, and the daemon decides which when it starts: `ladderback set-password` turns it on at the next start, and a daemon started with it off stays off. With it on, every `/api/v1` request but the session route's own (`/api/v1/session`, which tells the page where it stands, signs in and signs out) carries a live session's cookie, and the events stream's handshake does too; without one it is refused with `401` and `sign-in-required` before any route runs. The web UI's files are served without a session, so the page can ask for the password.
  - **The admin password.** `ladderback set-password` asks for it twice at a terminal, without showing what is typed, or reads one line of standard input; it never takes the password as an argument, which other users of the machine could read. It takes 8 characters or more and at most 1024 bytes. Only an argon2id hash is kept (the `argon2` crate's defaults, a new salt each time), in `admin-password` in the data folder, created with mode `0600`, never in `config.toml`. A hash file the daemon can't read, or one that isn't an argon2id hash, refuses the start: it never means sign-in off. The daemon checks one attempt at a time (each hash takes about 19 MiB), and a password over 1024 bytes is refused unhashed.
  - **Sessions.** Signing in with the admin password (`POST /api/v1/session`) starts a session: a random 32-byte token in the cookie `ladderback-session`, `HttpOnly; SameSite=Strict; Path=/`, so the page's scripts can't read it and no other site's request carries it. The cookie is also `Secure` when the request's `Origin` is `https://` followed by the request's own `Host`, as from a page a TLS-terminating proxy serves; forwarded headers (`Forwarded`, `X-Forwarded-*`) are never read, since anyone can write them. The daemon keeps each session by its token's SHA-256 and never compares tokens with plain `==` (the type has none), so how long a lookup takes says nothing about how much of a guessed token was right. A session ends **12 hours after its last use**, **30 days after it started** however much it is used, at **sign-out**, and when the **admin password is set anew**, even to the same password: each session remembers the hash it started under, and the daemon sees a new hash file at the next request, with no restart. At most 16 sessions are kept, and the one used longest ago makes room for a new one. Sessions live in the daemon's memory, so a restart ends them all. An open events stream ends within 5 s of its session.
  - **CSRF.** Each session has its own random 32-byte CSRF token, which the session route gives the page and no cookie holds. A changed request (any method but `GET`, `HEAD` and `OPTIONS`) carries it in `X-CSRF-Token`, compared in constant time (`subtle`); without it, or with another session's, the request is refused with `403` and `csrf-token-invalid`. **Signing out needs it too** (`DELETE /api/v1/session`), so another site can't sign the admin out; a request whose session has already ended has nothing to end and is answered as signed out, with the cookie forgotten.
  - **Only what a person does uses a session.** A request the page sends on its own, not because its reader did something (a refresh of the history after an event, the re-reads that follow a run to its end), carries the header `x-ladderback-background`, whatever its value; opening the events stream never counts either. The daemon checks the session for both without using it, so a page left open, even one hearing events, still ends its session 12 hours after its reader last did anything. The header needs no trust: it can only make a session end sooner. The page marks reads only; a changed request a client marks is accepted and simply doesn't count as a use.
  - **Each tab counts from its own last use.** The daemon keeps one last use per session, which any tab moves on; each tab times its idle warning and its end from the requests it sent itself. So a tab left alone warns, and then asks to sign in again, even when another tab kept the session in use. Its warning's "Stay signed in" uses the session, which is then still live; signing in again there starts a new session, and the cookie the tabs share is then the new one's. Another tab still holds the old session's CSRF token, so the page answers a `csrf-token-invalid` refusal, and only that one, by reading the session's current token (`GET /api/v1/session`) and sending the request once more; the daemon refused it before any route ran, so it did nothing the first time. Refused again, the request shows its error as any refusal does.
  - **Failed sign-ins wait; none locks out.** Each sign-in from a client counts as failed until it succeeds, and the client's next one waits 1 s after the first, twice as long after each more, at most 5 minutes. A sign-in during the wait is refused with `429`, `sign-in-wait` and `Retry-After`, **unchecked**, so a guess made then never counts; once the wait has passed, the admin password signs in whatever came before. A client is an IPv4 address, or the /64 network of an IPv6 address, which one host can fill with addresses. A success starts its waits over, and a client that has tried nothing for 24 hours is forgotten. At most 1024 clients are remembered: when the table is full the forgotten go first, then the client whose wait ends first, so one that keeps failing is the last to go, however many others fail once. Behind a reverse proxy every request comes from the proxy's address, so **all clients share one wait**; forwarded headers are not read for this either. A wrong password is `401` and `sign-in-failed`. **Known limit:** whoever shares the admin's client (another user of the machine on loopback, anyone behind the same proxy or in the same /64) can keep the admin waiting by sending a wrong password the moment each wait passes. That denies sign-in but never lets a guess count; a browser cookie that gives a browser once signed in a wait of its own would close it, and is left for later.
  - **The sign-in form** (A5, A6, §4.5): one "Admin password" field, `autocomplete="current-password"`, which accepts paste and password managers; an error summary that takes focus and says how to fix the problem; and the requested page once signed in. A session that ends while a page is in use opens a "Sign in again" dialog over it, which keeps what was typed and sends the refused request again once signed in. Two minutes before a session would end unused the page warns (WCAG 2.2.1) and offers "Stay signed in"; Escape keeps it too. While signed in, the navigation ends with "Sign out".
  - **The body limit covers the session route**: a sign-in's body is at most the API's 128 KiB, refused with `413` before it is read, like any other.
- **API tokens** (M3), for non-browser clients such as the CLI and MCP connect mode, when auth is enabled. A token is `stdg_<id>_<secret>`: the daemon looks it up by `id` and checks the secret against an argon2id hash (§9), so a request costs one hash. Each token carries scopes, `read`, `run` and `preview`, checked by the daemon per route. Restore, download, config, pairing and auth routes accept only a session (with step-up where §10.4 requires it), never a token. Tokens are created, listed and revoked in Settings, and the secret is shown once.
- **Request checks, always on**, auth or not. The UI can set hooks and `password-command`, so an unauthenticated API reachable from a web page would let any site run commands on the machine (DNS rebinding or cross-site POSTs). Therefore:
  - the `Host` header must be a configured name or a loopback address;
  - a request that carries an `Origin` header must match the UI's own origin; requests without `Origin` (curl, scripts, the `ladderback` CLI) skip that match. Mutating requests must use `Content-Type: application/json` whether or not they carry `Origin`: with `Origin` it forces a CORS preflight that the daemon refuses, and without it a browser or extension that strips `Origin` still can't send a cross-site form post. Scripts therefore send the header;
  - the `/api/v1/events` WebSocket handshake checks `Origin` the same way. `/sync/v1` is exempt: agents authenticate with their signed nonce (§7.1).
  - **How they match.** Configured names come from `ladderback serve --allowed-host NAME` (repeatable; a name or address without a port: the daemon refuses any other value at startup, in the catalog's words and with exit status 2) until the config file has a setting for them. Behind a reverse proxy, forward the browser's `Host` unchanged and configure that name. `Host` matches regardless of case and port. Loopback means `localhost`, a `127.0.0.0/8` address or `::1`; any other name is refused unless configured, and so are short forms such as `127.1`. A `Host` that is missing, repeated, not ASCII text, or carries user info, a path or a bad port is refused; a request target that names its own authority (HTTP/2's `:authority`) stands in for a missing `Host`. An `Origin` is the UI's own when it is `http://` or `https://` (the latter for a TLS-terminating proxy) followed by exactly the request's `Host` value, compared regardless of case; `null`, a path and a repeated `Origin` are refused. The JSON rule covers every mutating request, which is any method other than `GET`, `HEAD` and `OPTIONS` (`TRACE` and extension methods included), with or without `Origin`. Its `Content-Type` must be `application/json`, with or without parameters, so `application/json; charset=utf-8` passes. Other JSON types (`+json`, `-seq`), a repeated header and a missing one are refused, even for an empty body. The `/sync/v1` exemption covers that path and its subpaths only, not `/sync/v10`, `//sync/v1` or a query that mentions it.
  - **Refusals** are `403` with `host-not-allowed` or `origin-not-allowed`, or `415` with `json-required`, in that order of checking. The body is `{"code": "…"}`, the typed `api::ErrorCode` for the UI to render (§8.4). No route ever sends CORS headers.
- **Body limits, always on.** The daemon reads a request's body into memory before a route runs, so a body of any size would let one request take that memory from the backups. Each class of route has a limit of its own, the smallest that fits the largest body the class takes, and one layer enforces it before any route sees the body, so a new route, or one that reads its body another way, is bounded without knowing it: a request to `/api/v1` may carry 128 KiB (twice the 64 KiB a secret field may hold, so a repository's settings, the largest body today, fit with a secret at its cap), and a request for the web UI none at all. A configuration import, which may need more, gets its own class when its route exists. A declared `Content-Length` over the limit is refused before any of the body is read, and a body with no length, or one that lies, is cut off at the limit. A body over its limit is refused with `413` and `body-too-large`, whose body is `{"code": "body-too-large", "args": {"limit": …}}`, the limit as a byte count the UI renders as a size (§8.4); the route never runs, and the request checks above have already passed. A body that cannot be read to its end is refused with `400` and `invalid-body`. The events WebSocket is bounded the same way: a message from its client may hold 1 KiB (the UI sends pings of at most 125 bytes), and a larger one ends the connection.
- **Security response headers, always on.** Every response carries them, whatever answered it: a file, an API answer, a refusal of a request check or of a body limit.
  - `Content-Security-Policy: default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`. The page runs its own files and WebAssembly (`'wasm-unsafe-eval'` compiles the module and allows no `eval` of text), no site can frame it, and nothing inline runs but the one script Trunk writes into `index.html` to start the application. That script's file names carry a content hash, so no fixed policy could name it: the entry page's policy adds the `sha256` of each of its inline scripts, computed from the file the daemon serves, and `'unsafe-inline'` is never in it. Trunk has no option to move the script out of the page ([trunk-rs/trunk#288](https://github.com/trunk-rs/trunk/issues/288)).
  - `X-Content-Type-Options: nosniff`, so a browser takes a response for the type it says.
  - `Referrer-Policy: no-referrer`, so the UI's addresses, which name repositories and plans, leave in no request a link or an asset makes.
  - **No `Strict-Transport-Security`.** The daemon serves plain HTTP on loopback by default, and a browser that kept the header would refuse plain HTTP to whatever else later listens on that address. TLS, with its own header, belongs to the reverse proxy in front of the daemon.
  The `@ui` journeys run in Chromium under the policy, and one that makes the browser refuse something fails. A browser whose `'self'` does not cover a same-origin WebSocket would lose live updates under `default-src 'self'` and nothing else.
- **Local users.** Loopback is reachable by every user on the machine, so with sign-in off any local user can set hooks and run commands as the daemon's user. On multi-user machines, set an admin password.
- **Startup rule.** A loopback address (`127.0.0.0/8`, `::1`) may always be listened on. Any other only with sign-in on **and** at least one `--allowed-host`: the request checks admit only that name, and with none every request from the network would be refused anyway. Otherwise `ladderback serve --listen` exits with status 1 before binding anything, naming which is missing. Listening beyond loopback, the log warns that plain HTTP sends the password unencrypted and recommends TLS in a reverse proxy. With sign-in off, every start warns in the log, and the UI's start page says, that anyone on this machine can use Ladderback and that `ladderback set-password` turns sign-in on. There is no trusted-proxy mode yet (below).
- Optional "trusted reverse-proxy header" mode for SSO behind Authelia or Authentik.

### 10.2 Repository secrets

Every secret-bearing field can come from any of these sources. That covers the repository password and backend credentials in `options`, such as S3/B2 keys or SFTP passwords:

| Source | Config form | Typical use |
|---|---|---|
| Command | `password-command = "security find-generic-password -s rustic-nas -w"` (rustic-compatible) | macOS Keychain, `secret-tool`, `pass`, 1Password/Bitwarden CLIs |
| OS keyring | `password-keyring = "ladderback/nas"` | Desktops. The UI can write the entry for you. Not available to system services before login or to a root worker reading a user's keyring |
| File | `password-file = "/run/secrets/nas_password"` (rustic-compatible) | **Docker/Podman secrets**, systemd `LoadCredential=` (`$CREDENTIALS_DIRECTORY/…`), Kubernetes secrets |
| Environment variable | `password-env = "NAS_PASSWORD"` | Containers, CI, systemd `Environment=`/`EnvironmentFile=` |
| Inline | `password = "…"` | Accepted (e.g. on import) with a warning: the daemon logs `config-inline-secret` once per secret when it starts and loads the config (a repository saved while it runs is noted on its row at once and logged at the next start), and the Repositories page notes it on that repository's row. Both name the setting (`password`, `options.NAME`), never the value; it is not a refusal. An option counts when its name says it is a credential (`is_secret_option`) and its value has no `${…}` reference, or when its value is a URL with a password written in it. A password in a location (`rest:https://user:password@host/repo`, or a credential in an rclone connection string) is one too, under `location-secret`, which names the setting (`repository`, `repo-hot`), never the location, the user name or the password, and says to put a `${VAR}` or `${file:/path}` reference where the password is, or to give it in the backend's own option; for an rclone location, which rclone gets in its arguments and where a reference is refused, it says to keep the credential in rclone's own configuration file instead (decision 37) |

**Substitution in repository fields.** Inspired by Backrest's `${VAR}` expansion, but stricter. `repository`, `repo-hot` and the **values** of `options`, `options-hot` and `options-cold` may reference `${VAR}` (an environment variable) or `${file:/abs/path}` (a file's contents). Substitution is limited to these fields: in hooks it would put secrets into process arguments (I4), and in `label`, `sources` or `tags` it would silently change snapshot identity. It never applies to option names, and never to an inline `password`, which is taken as written. For example:

```toml
[repositories.b2]
repository = "opendal:b2"
password-file = "/run/secrets/b2_repo_password"
options = { bucket = "my-backups", application_key_id = "${B2_KEY_ID}", application_key = "${file:/run/secrets/b2_app_key}" }
```

Grammar and limits (`domain::secrets::Template`):
- `${VAR}` names a variable of `[A-Za-z_][A-Za-z0-9_]*`. `${file:/abs/path}` takes an absolute path that has no `}` in it. There are no defaults (`${VAR:-x}`) and no nesting.
- `$${` is a literal `${`. A text is read left to right, and a value a reference resolved to is never scanned again, so a secret that looks like a reference stays as it is.
- A malformed reference (unterminated, empty, invalid name, empty or relative path, nested) fails the field with the byte offset of its `${`, never with the text.
- A field has at most 16 references (`MAX_REFERENCES`) and is at most 64 KiB (`MAX_SECRET_BYTES`) both before and after expansion.

**Sources and what they give.** Every source goes through the `SecretResolver` port (§3.2), which returns the secret and any warnings, or an error that names the source:

| Source | The secret is | Nothing there |
|---|---|---|
| `${VAR}`, `password-env` | the value as it is, with no trimming | not set: `Missing`. Set to empty: the empty secret |
| `${file:/abs/path}` | the whole contents minus one trailing `\n` (and a `\r` before it) | `Missing` |
| `password-file` | the first line: up to the first `\n`, minus a `\r` before it (as rustic does) | `Missing` |
| `password-command` | the first line of the command's output | the first line is empty or only white space: `Missing` |
| `password-keyring` | the entry's secret | no such entry: `Missing`. No keyring service to ask (on Linux: no Secret Service, no session bus to reach one, or a service that says its keyring is locked or whose unlock prompt was dismissed, told apart by the Secret Service's own error and the D-Bus error's name; any other failure of the service, a reply it couldn't decrypt or parse included, is `Unreachable`): `KeyringUnavailable`, refused as `secret-keyring-unavailable` with what to use instead |
| Inline `password` | as written | — |

Options accept only `${VAR}` and `${file:/abs/path}`; commands and the keyring are forms of the repository password. A missing variable or file is never an empty string (unlike Backrest). What a source gives, the whole file, output or value and not only the line taken from it, is limited to 64 KiB (`TooLarge`) and must be UTF-8 (`NotUnicode`). A source that exists but can't be read is `Unreachable`. A file or keyring read that outlives the resolver's limit (a keyring that waits for an unlock, a mount that has hung) fails as `TimedOut`, like a command; the blocked read can't be cancelled and ends when the system lets it go.

**Commands.** The command line is split into words POSIX-style and started **without a shell**, so `|`, `;` and `$(…)` in it mean nothing. The port contract (`app::ports::SecretResolver`) is that a command gets no input, runs in a process group of its own, and is limited in time: one that outlives the resolver's limit fails as `TimedOut` and is stopped by the sequence a hook is stopped by (§6.1): the whole group gets SIGTERM, so a helper that holds a lock or a session can end cleanly (its output pipes stay open until it is reaped, so a handler that writes there isn't ended by SIGPIPE, and are read and dropped meanwhile, so a handler that says more than a pipe holds isn't blocked until the SIGKILL), and SIGKILL 5 s later (`KILL_GRACE`) if the command is still running then. Each signal goes once, and only while the command is still unreaped (a group is named by its leader's process id, and once the leader has been reaped and the group has no live member, another process may hold that id). So a command that ends on the SIGTERM is not waited for any longer, and a process it started and left running is not signalled again if it ignored the SIGTERM too: that one is left running. A command that is still running when the grace ends takes its whole group with it. The wait for the command to die after the SIGKILL is bounded as well (5 s), so one that no signal reaches, stuck in the kernel, still ends the call with the same error. A command whose output goes past the size limit, or can't be read, is killed at once, with no grace, and so is one whose caller gives up while it runs. The limit is the command's own: one that has exited in time is never timed out, and what it left holding its output open (gpg-agent) gets one second (`PIPE_GRACE`) and is left running. What was read of a **stdout** left open so is used only as far as a first line whose newline was read: a command that succeeds before that line ended fails as `OutputCut` (refused as `secret-command-output-open`, which quotes nothing it printed) rather than give what may be part of a value (#237, decision 45). A command that exits unsuccessfully fails as `CommandFailed` with its exit status (none when a signal ended it) and the first non-empty line of its **stderr**, cut to 512 bytes, with the value it printed on stdout masked (whole, trimmed and line by line), since a helper that rejects a value may quote it. Only the first 8 KiB of its stderr is kept, and it is masked as a cut text (below, "Where masking runs") however it ended: at that cap, when something the command started still held it open as `PIPE_GRACE` ran out, at a failed read, or at the command's own end, which can stop partway through the value it quotes; a value cut there leaves nothing of itself (decision 45). Stdout is masked against only when it is whole: read to its end, and empty or ending with a newline. When something the command started still held it open as `PIPE_GRACE` ran out, or it ends partway through a line, which the command's own end can leave with nothing in what was read to say so (killed partway through printing the value, or exiting there), what was read of it can be only part of the value, and stderr masked against that part would show the rest of a value it quotes, so that failure has its status and an empty detail (#233, #237). The real resolver and the in-memory fake both build that error with `domain::secrets::command_failure`, and the secret with `domain::secrets::command_secret`, so a scenario on the fake sees what the real one gives. Its stdout itself is never part of an error. One that can't be started is `Unreachable`.

**A command's program.** The program is a name looked up on `PATH` (`security`, `pass`) or an absolute path. The command runs in the daemon's working directory (`/` under launchd or a system unit, the home folder under a user unit), so a program named by a relative path (`./get-pass`, `bin/get-pass`, `~/bin/get-pass`: nothing expands `~`) would be another program, or none, depending on how the daemon was started, and one put there by whoever can write to that folder. The rule is on the configured value, not in the resolver: the configuration refuses it at its key as `Password(RelativeProgram)` and the import as unsupported (§6.1, §6.2), the rule a hook's program follows (#240).

**One start at a time.** A command starts through the spawn gate, as a worker and a hook do (decision 58): no other child of the daemon starts while its pipes are being made, so none can inherit the pipe its secret comes back on, where the platform makes a pipe in two steps (macOS). Its pipes are let go without the gate when the call ends. A start that forks in that moment copies them into its child, close-on-exec, and that child runs none of the daemon's code before its `exec` closes them: nothing reads from them, so no process can read the secret through them (I4). Meanwhile a late write of the command's own descendant can go through rather than fail.

**A command that gives nothing.** A command that exits successfully with no output, or whose first line is empty or only white space, gives no secret: it fails as `Missing`, naming the program, never as the empty secret that a repository would then fail to open with, far from its cause. A variable, a file or a keyring entry that is set to nothing stays the empty secret, since someone set it so.

**Errors.** An error names the source and the problem, as codes (§8.4): the variable's name, the file's path, the program (without its arguments), or the keyring entry. It never holds a value or a command's arguments; the one text a command controls is the `CommandFailed` detail, which has the value the command printed on stdout masked (see above). In a resolved repository the error also names the field it was found in (`repository`, `repo-hot`, `password`, or an option by its name); when several fields fail, the first is reported, in the order password, `repository`, `repo-hot`, `options`, `options-hot`, `options-cold`.

**File permissions.** Ladderback warns (`FileReadableByOthers`, with the path as written) if a secret file, whether read as `password-file` or as `${file:…}`, is readable by group or others (mode `& 0o044`), except for files under `/run/secrets`, `/var/run/secrets` and an absolute `$CREDENTIALS_DIRECTORY`, where container runtimes and systemd control permissions. The exemption is for where the file really is, so every link is followed first (the file's path and the directory's): a link in `/run/secrets` that leads to a file in someone's home is warned about like any other file, a link that stays in the directory is not, and a path that can't be followed is never exempt. A path with a `..` component is never exempt, and a `$CREDENTIALS_DIRECTORY` that is empty, relative or `/` (or that leads there) counts for nothing.

**Rules.**
- Substitution happens **at job start** in the daemon (`app::secrets::ResolveRepository`), not when the config is loaded. Rotated secrets are picked up without a restart, and resolved values never get written back to `config.toml` or shown in the UI. The UI shows the reference (`${B2_KEY_ID}`), not the value.
- Each distinct reference is read once per job, so a value can't change between two places that use it. Warnings are reported once each.
- **A reference may not be in a field that becomes a process argument**, because argv is visible to every local user in `ps` and `/proc/<pid>/cmdline` (I4), and the engine's masking can't reach it. The pinned `rustic_backend` does that for the repository string of an `rclone:` repository (`rclone.rs`: it is appended to rclone's arguments), and for the options it runs as commands: `rclone-command` (`rclone.rs`), `post-create-command` and `post-delete-command` (`local.rs`); so does the engine's own start of an `rclone:` repository's server, which follows `rclone.rs` (decision 58). Such a reference, in `repository` or `repo-hot` that starts with `rclone:` or in one of these options in `options`, `options-hot` or `options-cold`, is **refused** (`Cause::ReferenceInProcessArguments`, naming the field) before any secret is read, even when the password can't be read either. A reference that supplies the `rclone:` itself (`${REPO}` holding `rclone:…`) shows only in the expansion, so the expansion of `repository` and `repo-hot` is checked too: that is refused once its references were read, and before anything else is done with it. A plain `rclone:remote:path`, an escaped `$${`, and a reference in any other field or option are allowed. An rclone remote's credentials belong in rclone's own config file (the worker keeps `RCLONE_CONFIG`).
- **An rclone location holds at most 16 credentials** (`MAX_RCLONE_CREDENTIALS`, counted by `too_many_rclone_credentials` as the redactor reads them, below, those of a location written in a setting included). Each is a secret, in a few forms, that a redactor looks for in every text it masks, so the work grows with their number times the length of the text, and a location over the cap is masked whole, where one credential quoted alone in an error of rclone's would show. So a job **refuses** `repository` or `repo-hot` with more (`Cause::TooManyCredentials`, sent as `location-too-many-credentials` naming the field and never the location) right after the check above, before any secret is read and before rclone or a worker sees the location; the answer reads none either, as no refusal that shows nothing a source said does. Its words say to keep rclone's credentials in rclone's own configuration file and name the remote in the location. 16 matches the cap on references (`MAX_REFERENCES`). Without a cap, measured in a release build on a location at the 64 KiB limit (#228):

  | Location | Needles | A 163-byte line | The location itself |
  |---|---|---|---|
  | `rclone::s3,key=abc,key=abc,…` (8 191 credentials) | 8 191 | 5.2 ms | 2.06 s |
  | quoted values, `key='abc@''%'` | 56 161 | 24 ms | 9.4 s |
  | values with a long shared prefix | 1 771 | 0.6 ms | 0.36 s |

  Building the redactor for the first took 460 ms. A job's output is masked line by line, so that is seconds of every job's run spent masking.
- **A location is a full path when it names a folder on this machine, once resolved too** (#247). The configuration refuses a relative local location where it is written (§6.1), but can't judge one a reference decides (`${REPO}`, `local:${REPO}`). So a job reads the expansion of `repository` and `repo-hot` as the configuration reads a location all of which is known (`domain::planning::is_relative_location`: `backups/repo`, `./repo`, `~/repo`, `local:repo` and the empty location are relative; `/srv/repo`, `rest:…`, `opendal:…` and a backend rustic doesn't know are not), right after the expansion's `rclone:` check (above) and before the credentials the location holds are counted or rustic or a worker sees it (what each reference held is counted as it is expanded, before that), and refuses a relative one (`Cause::RelativePath`). The repository routes, the snapshot listing, maintenance and a backup start send it as `repository-path-relative` naming the field, the refusal the repository routes give a written one (#309). The refusal holds nothing of the expansion, which may be a secret (I4), and its answer reads no secret, as it shows none. The options are not judged again by the backend a resolved location names (#310).
- **A location, an option value and a table of options have caps** (`MAX_LOCATION_BYTES` and `MAX_OPTION_VALUE_BYTES`, 64 KiB as written, the most a template holds; `MAX_OPTIONS`, 64 options in each of `options`, `options-hot` and `options-cold`; all in `domain::secrets`, #236). A redactor looks for every credential a location holds and every option value that is or holds a secret, in each of its forms (below), so the size and the number of these bound how many needles a redactor holds and how long they are; before, a location was refused only when a job read it, and the Repositories page and the daemon's start-up log masked it before any job did, at any length. The configuration refuses one over a cap when it loads, an import when it reads it, and the repository routes as an invalid body (scheduling-and-config.md §6.1, §6.2); the refusal quotes nothing of what it refuses, which may hold a secret.
- The hot and cold halves of a repository (`repo-hot`, `options-hot`, `options-cold`) are resolved with the rest and are fields of the resolved `RepositoryAccess`, so they reach the worker, which opens both halves (§4.1). What they hold is masked like the rest: `Redactor::for_repository` takes everything a repository's settings can hold at once (`RepositorySecrets`), so a half can't be left out of it.
- rustic's own environment variables (`RUSTIC_PASSWORD`, `RUSTIC_PASSWORD_FILE`, `RUSTIC_PASSWORD_COMMAND`, `RUSTIC_REPOSITORY`, `RUSTIC_REPO_OPT_*`) are recognized on import. They're **not** read implicitly at runtime, so one stray variable can't redirect every plan. Use `password-env` explicitly instead.

**What is masked.** The `Redactor` (§3.1) replaces each of these with `***`:
- the repository password;
- every value a `${…}` reference resolved to (`RepositoryAccess.secrets`), wherever it lands, whatever the option or field is called: the repository string, an option such as `endpoint`, or a path in an error;
- the password in the userinfo of any URL in `repository`, in `repo-hot` or in an option value of `options`, `options-hot` or `options-cold`. An S3 `endpoint` is **not** a secret by its name; only credentials embedded in its URL (`https://demo:…@host`) are masked, so a plain endpoint stays readable in diagnostics;
- the value of every option, in any of the three sets, whose name says it holds a credential (`is_secret_option`), **even when written inline**: a name, lowercased with `-` read as `_`, that contains `password`, `passwd`, `secret`, `token`, `credential`, `passphrase` or `delegation`, or ends in `_key` (`sas_token`, `secret_access_key`, `application_key`), or is, as a whole, one of rclone's own names: `pass` (the password of its SFTP, FTP, SMB and WebDAV backends), `key_file_pass`, `key_pem`, `sas_url`, `connection_string`, `sse_customer_key_base64`, `access_grant` (Storj), `master_keys` (Filen), `authorization` (SugarSync), `headers` (WebDAV and HTTP, which take `Authorization,Bearer …`) or `2fa` (Proton Drive's one-time code). `use_password` (a switch), `key` (an SFTP key file path), `access_key_id` and `application_key_id` are not secrets;
- each credential written in an rclone connection string in `repository` or `repo-hot` (`rclone::sftp,pass=…:/backups`, `rclone:remote,key=…:bucket`): the value of a setting, one of the `key=value` pieces between commas up to the `:` that starts the path, whose key names a credential in a connection string (`is_rclone_secret_option`: what `is_secret_option` names, and `key`, which there holds the key of rclone's B2, Swift and Azure Blob backends) and whose value, quotes aside, is not empty. As rclone reads it, a quote `'` or `"` opens only where a value starts, and a value so quoted may hold `,` and `:` without ending its setting; a quote anywhere else is text, so `pass=a='b,key=c'` is two settings. An unquoted `:` inside a value ends it, as rclone reads it, and what follows shows as the path (`sas_url=https://…` masks only `https`; rclone can't use that location either). A setting's value that is a location of its own (crypt's `remote=':s3,secret_access_key=…:bucket'`, or `'remote,pass=…:path'`; a quoted value with no backend and no `:` outside quotes is a local path to rclone) is read the same way, its quotes taken off and a quote written twice read as one, four levels deep counting the location itself: its credentials are masked, count toward the cap, and are credentials written in the configuration (`location-secret`, `config-inline-secret`, the import's notice). A location deeper than that is one credential, masked whole. Each is masked as the location writes it, quotes and `$${` included, as each level reads it, and as rclone reads it last, with `$${` as `${`, without the quotes around it and with a quote written twice inside them as one, since rclone's errors quote it so; a value with a `${…}` reference in it is masked only as written. The rest of the location (the backend's or remote's name, the other settings, the path) stays readable. A location with more than 16 credentials (`MAX_RCLONE_CREDENTIALS`) is masked whole; a job refuses one (see the rules above). The export reads an rclone location more coarsely on purpose: `rclone_secret` splits it at every `,` and `:`, quotes and levels aside, and refuses it for any `key=…` piece whose key names a credential, the path's included, so it refuses more than the redactor masks.

Each is masked raw and as a URL parser prints it (§4.1): percent-encoded in full (either hex case); as the `url` crate encodes a userinfo, a path (also with `^` encoded, as the newer standard does), a query, a special URL's query (which also encodes `'`) and a fragment (upper-case hex); with tab and newlines taken out and with `\` read as `/`, as a parser rewrites them; and lower-cased, as a host is. A secret that holds a character a parser splits a URL at (`@`, `#`, `?`, `/`, `:`) is also masked in pieces, because the parser prints each piece as its part of the URL writes it (a host in lower case, a path as it is) and a library may print the parts one by one: each piece of at least 8 bytes (the first 64 of a secret) is masked in all the forms above; shorter pieces are masked only as part of the secret, which is also masked as a parser prints it when it starts in a host, a path or a query and moves on at each delimiter (`canary/Alpha`; decision 31). Not covered: a host that is not ASCII, which a parser writes in punycode, percent-decoding in a host, and dot segments in a path. Secrets that overlap or touch are masked as one span, so no tail of one is left. A secret that spans lines is also masked without the white space around it, and line by line for lines of at least 8 bytes (the first 64 lines), because logs reach a reader one line at a time.

A secret is also masked as Rust's `Debug` prints it between its quotes (`"` and `\` escaped, a control or combining character as `\u{…}`), and so are its form without the white space around it and its lines, because a library that logs a value with `{:?}` prints a secret in it so: rustic logs the command it starts `rclone` with that way, the location last (#330). `Debug` escapes each character on its own, so that form is in the printed text wherever the secret is in the text printed. The encoded forms above are not escaped as well: that would add almost as many needles again, for a secret a parser would first have to encode and a library then print with `{:?}`. An escaped form adds at most 6 bytes of needles per byte of the secret (`\u{7f}`), so the three of them at most 18.

The same three forms are masked as Go's `strconv.Quote` writes them between the quotes, because `rclone`, written in Go, quotes what it can't serve as `%q` does (`Failed to create file system for "…"`), and the worker and the daemon log what it writes (#331). Go agrees with `Debug` on `"`, `\`, tab and the line breaks, but writes another control character as `\x01` or `\a`, a format character (a zero-width space), a separator other than the space and a private-use or unassigned character as `\u200b` or `\U000e0001`, and leaves a combining character as it is. Which characters Go prints (`unicode.IsPrint`: letters, marks, numbers, punctuation, symbols and the space) comes from the Unicode version its `unicode` package was generated from (`unicode.Version`): Unicode 17 for Go 1.27, which rclone 1.76 is built with. `domain` carries them as a table of ranges, `GO_PRINT` (`crates/domain/src/secrets/go_print.rs`), generated from that version's `UnicodeData.txt` by `scripts/gen-go-print-table.py`, so the answer is Go's whatever Rust toolchain builds Ladderback (decision 77). The redactor asked Rust's `Debug` before, whose escapes change with the toolchain: Rust 1.100 escapes every combining mark, and a secret holding one was no longer masked as Go quotes it (#406). Compared over every character, this is Go 1.27's `strconv.Quote` exactly, and a test holds it there: it compares the count of characters Go escapes and a hash of every character's quoted form with Go 1.27.3's own. When rclone moves to a Go on a newer Unicode version, regenerate the table with that version (`python3 scripts/gen-go-print-table.py <version>`, which needs Python 3 and downloads the version's `UnicodeData.txt` from unicode.org), quote every character with that Go and pin its count and hash in the test (`every_character_is_quoted_as_go_quotes_it`). Where an `rclone` was built with a Go on another Unicode version, a character assigned in one version and not the other is printed by one and escaped by the other, and a secret holding one is not masked in that line, as before: that is a residual risk, of the worker's log as much as the daemon's. An rclone built with Go 1.21 to 1.26 (Unicode 15), such as a release before 1.76, escapes the 10,615 characters Unicode 16 and 17 added that the table prints, and one built with an older Go more. Go's `%#q` writes a secret as it is between backquotes where it can, which its raw form masks, and as `%q` does where it can't; `%+q` (every character that isn't ASCII escaped) is not masked. A Go-quoted form adds at most 4 bytes of needles per byte of the secret (`\x01`), none when it is the secret or its `Debug` form, so the three of them at most 12.

**How long masking takes.** A redactor looks for each needle in one pass over the text (Knuth, Morris and Pratt): each needle keeps, for each of its bytes, where a search goes on after a byte of the text that doesn't match, so each byte of the text is compared at most twice with a byte of each needle, however long and repetitive both are (#236). The tests count those comparisons rather than time them, so they can't flake. Before, each place in the text was compared with up to a needle's length of bytes, the product of the two lengths on a long, repetitive secret. Measured in a release build:

| Masking | Before | After |
|---|---|---|
| 45 needles, 1.48 MB in all, in 64 KiB of `a` | 1.92 s | 4.2 ms |
| A location with 16 rclone credentials, in itself | 121–348 ms | 5.2 ms |
| The same redactor, in 64 KiB of `a` | 247–969 ms | 4.2 ms |
| A URL with a 32 KiB password | 15 ms | 0.3 ms |
| A password at the cap with the characters a URL splits at, in itself (cut, `redact_cut`) | 4.9 ms (31.6 ms) | 3.0 ms (3.3 ms) |

Memory: a needle keeps 4 bytes per byte of it beside its text (a `u32`: a needle is at most `u32::MAX` bytes, half of what a `usize` takes), and masking a text takes 4 bytes per byte of the text. A secret gives up to about 80 bytes of needles per byte of it, measured: 80.3 on 64 KiB of `\`, `\x01`, `é`, `#`, a capital and DEL in turn with a line break every 1,000 bytes, its forms above, the most of the mixes measured (70.4 with a tab for `\x01` and no line breaks), so its needles and their borders take up to about 400 bytes per byte of secret (401 measured; the Go-quoted forms of #331 added 2.4 of the 80). **A redactor masks at most 256 KiB of secrets** (`MAX_MASKED_BYTES`), each counted once however many places hold it: the password, what the references resolved to, what the settings hold that is masked (a URL's password, an rclone credential, a credential option), and the proxy credentials the engine adds. That keeps one redactor under about 100 MiB (#248). A real repository's secrets come to a few kilobytes: a password, an S3 key pair and a 2.5 KiB SSH key, 2.7 KiB in all, take 139 KB of needles and borders, so the cap leaves about a hundred times that, and room for four secrets of the 64 KiB a secret may hold. It holds in three places, each before a form is built. A resolution (`ResolveRepository`) counts the secrets as it reads them, field by field, and fails at the field that takes them past the cap (`secrets-too-large-to-mask`, which names the field and the cap, never a secret): nothing after it is read, and no job runs. The engine refuses a job whose secrets and the proxy credentials of the worker's environment pass it, before a worker starts, with the same typed code (`EngineError::SecretsTooLargeToMask`): its `field` is the proxy variable whose credentials took the count past the cap, such as `HTTPS_PROXY`, and is left out when the job's own secrets did. A backup or a maintenance run stores it as the operation's failure (data-model.md §9), and the repository routes and the snapshot listing answer it as they answer a resolution's (422). And `Redactor::new` counts what it is given before it builds a form: past the cap it builds none and masks every text that isn't empty whole, more than a secret, never less (I4). That covers every other redactor: a refusal's, which reads the secrets again and stops reading once what it read again passes the cap (the inline secrets of the settings are counted after it, with the rest, by `Redactor::new`); the debug form of the settings; a location a page shows; and the one the in-process retention evaluation (`RusticRetention`) builds from the repository's secrets and the proxy credentials of the daemon's own environment, which past the cap masks the error it reports whole rather than refusing. A needle longer than `u32::MAX` bytes, which the cap doesn't let through, masks every text whole too.

**Where masking runs.** The worker masks every `Log`, `Warning` and failure detail, and its panic report, before it cuts them to size (§4.1). The daemon masks what the worker writes to stderr, because the programs a worker starts (rclone, ssh) write there too. It also masks every text in the worker's events (failure details, warnings, progress text, log lines), because a worker rejects a job spec before it has the job's secrets and a parse error can quote the value it choked on, and because the worker doesn't know the proxy credentials below. **Masking twice can mask more, never less** (#287): a text the worker masked is masked again in the daemon, and when a secret holds `*`, the character of `***`, a mask and the text beside it can make up that secret, which the second pass masks too (secret `*?`: `*??` masks to `***?`, and that to `*****`). That is kept: skipping what matches inside a run of `*` would leave part of a secret unmasked when a real `*` stands beside it (I4). **A text cut at a cap is masked as a cut text** (`Redactor::redact_cut`, decision 45): every whole secret as anywhere else, and the end of what was kept from where it begins a secret, with the bytes of a character the cut went through left out. That masks more than a secret where the end only looks like the start of one, never less. It applies wherever output is cut and then masked: a secret command's stderr and hook output (however they ended, below), a worker's stderr line cut at the message cap, and a text that someone who knew fewer secrets cut and marked with `…` (a worker's event text, a command's detail in a refusal; `Redactor::redact_clipped`). **Output cut by time is a cut text too:** a pipe that was not read to its end (a hook stopped at its timeout, a pipe a process the hook or command started still held open when the grace ran out, a read that failed) and a worker's last stderr line without its newline (a kill can end the worker partway through a write) can end partway through a secret, since a secret written in several writes, or in one larger than a pipe passes whole (`PIPE_BUF`), reaches the reader in parts. **So is output its writer cut short:** a hook or a helper can stop partway through a secret and exit on its own with nothing in what was read to say so, so a hook's stdout and stderr and a secret command's stderr are masked as cut however they ended (decision 45). Text that is masked first and cut after (a worker's own event text, `Problem::command_failed`'s 512 bytes) needs no more. The `Debug` forms of `RepositorySettings`, `ResolvedRepository`, `RepositoryAccess` and the worker's `RepositorySpec` show the names of the options of all three sets but no values, no secrets, and the repository strings redacted.

**The daemon's own log is masked while it opens a repository itself** (#330). To evaluate retention for a forget or its preview, the daemon opens the repository in-process (`engine::RusticRetention`), and rustic, its backends and the crates under them (OpenDAL, the HTTP client) then log through the daemon's logger. rustic names the repository by its location (`repository <location>: password is correct.`, at `info`), and an `rclone:` location holds rclone's settings, credentials among them; it logs each line the `rclone` it starts writes to stderr (`rclone output: …`, at `info`), and rclone quotes what it was asked to serve when it can't; at `debug` it logs the whole `rclone` command, the location last, as `{:?}` prints it (a secret is masked in that form too, above). So the daemon's logger is wrapped (`engine::Masked`): from before an open starts anything until its backends, the `rclone` they started and the thread reading its stderr are gone, every record the daemon logs, whatever crate made it, is masked with that repository's redactor, the one its errors are masked with (its password, the secrets of its locations and options, what its references resolved to, the proxy credentials). Masking by record rather than by crate covers the crates under rustic, which log under targets of their own, and the threads they start. With two opens running, a record is masked as one redactor of the secrets of both would mask it (`Redactor::redact_together`), so a secret of one that holds or overlaps a secret of the other is masked whole rather than left in part beside the other's mask (#287); a redactor that masks everything (secrets past `MAX_MASKED_BYTES`) masks every record whole while its open runs. A record is a whole text, masked as one; its key-values, which the daemon's log doesn't show, are dropped. A `rest:` location's password is masked by rustic itself in the name it logs, and an `opendal:` location is logged as `opendal:<scheme>:<name>`, without its options; both are masked all the same. OpenDAL runs its tasks on a runtime the whole process shares, which outlives the open: what a task of it might log once the open is gone is not masked. No record of an open is known to come that late; it is a residual risk.

Resolved secrets are passed to workers through the `JobSpec` on stdin, never as argv or environment variables. That holds even when a secret was *sourced* from an environment variable: **a worker starts with a scrubbed environment** (§4.1): only a fixed allow-list of variables that name a place or a setting (`PATH`, `HOME`, the locale, `SSH_AUTH_SOCK`, certificate locations, `RCLONE_CONFIG`, the proxy variables) and nothing else of the daemon's. Two consequences:
- Ambient cloud credentials (`AWS_*`, `AZURE_*`, `GOOGLE_*`, `RUSTIC_*`, `RCLONE_CONFIG_*`) no longer reach a worker. A repository that needs them says so explicitly, with `${…}` in its options.
- A proxy URL with credentials embedded passes as it is. This is a residual risk the user takes by writing it there: the credentials stay in the worker's environment, where the programs it starts use them. They are masked wherever the worker's output shows them, though: the daemon adds the password and the whole userinfo of `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (either case) to the job's redactor. `NO_PROXY` lists hosts, not a URL. Proxy credentials are not a secret source: a proxy URL is read from the environment as it is, never resolved from a reference, so this adds no secret source.

Hook and notification templates never receive secrets (Backrest leaks them this way, [#1170](https://github.com/garethgeorge/backrest/issues/1170)); hooks get the same scrubbed environment when they are built. A notification channel's URL, token and password are secrets from the sources above, never inline, resolved by the daemon for one delivery (§11). A repository's locations each carry their own references, resolved when a job or a probe starts and never shared between locations (§10.6). **Secrets never leave the agent.** Hub maintenance and hub downloads need the repo password, so for hub-managed repos the **hub has its own secret entry** for that repo, configured on the hub. Agents don't push passwords.

Connecting a repository saves the settings **as written**: a `password-keyring`, `password-file` or `${…}` reference stays a reference in `config.toml`, never the value it resolved to; the resolved value lives only inside the job it was resolved for. The `@e2e` scenario covers this with a file reference — no test writes a real OS-keyring entry — and a keyring reference round-trips the same way through the config store.

**Not yet in place.** `SecretError` and `TemplateError` are mapped to API error codes and localized messages (`secret-*`, `template-invalid`, `location-too-many-credentials` for an rclone location over the cap, and `secrets-too-large-to-mask` for secrets past what a redactor masks) on the repository routes and the snapshot listing, with the words of a command or a platform masked of every secret of the repository, those a reference resolves to included; mapping them to the failure reasons of an operation that runs belongs to the job-runner and operation-log work (the engine's refusal of a job past the cap is already one, `secrets-too-large-to-mask`, above). Seeding a daemon-wide redactor with every secret at config load belongs to the config work. The warning for an inline secret is built (`config-inline-secret`, §16 decision 37).

### 10.3 Agent ↔ hub

Ed25519 identities, TLS (pinned or CA), and single-use short-lived pairing tokens. The protocol carries metadata, logs and restore requests, never file contents or secrets.

### 10.4 Restores

Restores are the most dangerous action because they can overwrite files.
- **Step-up confirmation** before any restore or download started from a web UI, whether local or on the hub. With auth enabled, re-enter your password; this is required even with a valid session, so an unattended open tab isn't enough. Password managers and paste work (A5). With auth disabled or in proxy-header mode there is no password to re-enter, so the user types or pastes the snapshot's short ID instead. That only guards against misclicks, not against someone at the keyboard.
- **Default destination is a new folder** on the target machine: `~/ladderback-restore/<host>-<snapshot-short-id>-<timestamp>/` (configurable per agent). Existing files are never touched in this mode.
- **From the hub**, only new-folder restores are possible, and only to agents that set `allow-hub-restore = true` (off by default). The agent runs the restore itself; the hub sends only the request.
- **Restoring in place** (original paths) is offered only in the agent's own UI. Its confirmation dialog states how many files would be overwritten or deleted, using a dry-run `prepare_restore` plan first.
- Every restore is recorded in the op log with who started it and from where (local UI or hub).

### 10.5 MCP server

An MCP client is usually a language model acting on text it read elsewhere, so `ladderback mcp` treats every call as untrusted input with no human behind it. The aim is to bound what a confused or prompt-injected model can do, not to stop a local user, who already has the API.

- **No step-up, so no restore.** Restores, downloads, applying forget or prune, adoption, config edits, hub pairing and auth settings have no tool (§4.6). A tool can't stand in for the confirmation in §10.4.
- **No new commands.** Hooks, `password-command` and secret sources can't be set or changed through MCP, so a prompt injection can't add a command run as the daemon's user (I4). Running a plan does run the hooks and secret sources a human already configured.
- **Enforced by the daemon, not the client.** With auth enabled, connect mode authenticates with an API token whose scopes (`read`, `run`, `preview`) the daemon checks per route (§10.1). A leaked token can't restore or edit config even through raw `/api/v1` calls. With auth disabled, the loopback API is open to local processes anyway, as it is to curl.
- **Token handling.** Read from `--token-file` (default `<config>/mcp-token`; a file readable by group or others is refused, as for `password-file` in §10.2), never from argv, and sent only over `https` or loopback.
- **Secrets stay references.** Results show secret references, never values. The `Redactor` is seeded with inline config secrets at load, not only with the values a job resolves, so `list_repositories`, `preview_import` and logs can't echo them. `export_profile` refuses inline passwords (§4.6). The I4 canary test covers every tool.
- **Headless isolation.** Headless mode takes the data-dir lock (§9). `--scratch` uses a fresh mode-0700 temporary directory, never the user's config or data.
- **Residual risk: untrusted output.** Logs, paths, tags, hostnames and rustic's error details are text a model reads, and an attacker can influence it. Ladderback doesn't sanitize it; the mitigation is that no tool can turn such text into a destructive action. Result size caps (§4.6) limit how much reaches the model at once.

### 10.6 Repository locations

A repository may be reached at several locations, tried in order, each with an optional rule about the network (§6.1; §16, decision 80). This is what that adds to the threat model; the rest of §10.2 applies to each location unchanged.

| Threat | What it takes | What Ladderback does | What remains |
|---|---|---|---|
| A rule trusted as if it proved where the machine is | A Wi-Fi name that is copied, or a private address range another network reuses | A rule only chooses which location to try; every chosen location is checked as any is (the repository ID, which a repository with several locations always records, and TLS where the address has it and the check of its certificate isn't turned off). Nothing in the design treats a name as proof | The credentials of the location go to whatever answers at its address |
| Credentials sent in the clear to an impostor | A location that sends credentials where an impostor can read them, on a network the rule admits: `rest:http://…` with a user and password or a credential option; an `https` REST location with `http-insecure-tls` true; an OpenDAL or rclone address over `http://` with a credential; `opendal:ftp` with one | A warning, `location-plain-http-credentials`, on the Repositories page and in the daemon's log, naming the repository, the location's position and a cause (`plain-http`, `unchecked-certificate`, `plain-endpoint`, `plain-ftp`) and neither the address nor a credential. It is checked on the location as written and again on what a `${…}` resolves to (the second as a log line only). It is a warning, not a refusal. The recommendation is HTTPS on the LAN with the server's own certificate authority, given to rustic as `http-cacert` (an absolute path, §6.1) | On plain HTTP the credentials are sent before any check of the repository's ID can run, and nothing takes them back. An `rclone:` remote set up in rclone's own file is not seen. Until the rule slice, a location has no rule, so a plain-HTTP LAN location is tried on every network |
| A different repository at a location | A misconfigured or hostile server | Every location must hold the repository's ID (decisions 49 and 57); a mismatch is refused, never used, raises a warning, and the run goes on to the next location. The cache slot stays keyed by the ID | An old copy of the same repository passes the check; a backup written to it would fork the history. True of any repository whose address can be spoofed, and likelier on a LAN anyone nearby can join. Only TLS with a trusted authority closes it |
| One server's credential sent to another | Options inherited between locations | A location's options never apply to another; the job's worker gets only the chosen location's secrets (each probe is its own worker, holding one) | A credential reused on purpose by writing it twice |
| A secret in a place it must not be | A location's reference resolved into config, argv, an environment, a log, an event, an operation record or the page | Locations are references like any other (I4); a worker's redactor holds the secrets that worker has (a probe the password's and its one location's, the job the chosen location's) and the daemon writes no text that could hold one (a location's outcome is a code, its source names where a secret was looked for); the operation record keeps a location's address as the entry writes it, with credentials masked, and its outcome code | Nothing new |
| The machine's whereabouts leaking | The current Wi-Fi network's name in a log, event or sync message | Never written: logs, events, operation records and sync messages say "on Wi-Fi, not a listed network". A name in a rule is the person's own configuration and is shown on the page | A name in `when` is in `config.toml` in plain text. A hub fetching a log sees what logs hold, rustic's lines among them, which name the repository's address (§10.2): the operation records it syncs carry no location or outcome, and a log's lines carry a position and an outcome code, which can say a rule wasn't met but never a name |
