## 15. Risks

| Risk | Mitigation |
|---|---|
| `rustic_core` is pre-1.0, so its API changes | Pin one revision for both crates. All usage goes through the `engine` crate. Contract tests run against a temp repo in CI |
| The pinned revision is unreleased code | Move to the first release with `Progress::error`. Until then, upgrade the pin only deliberately, with the kill test and contract tests green |
| A `rustic_core` upgrade adds or changes option fields | Ladderback-owned option types with a parity test per mapped struct (§6.1) |
| Divergence from rustic CLI profile semantics (list replacement, hook levels, `use-profiles`) | Golden tests: parse the rustic repo's `config/*.toml` examples and compare against expected plans; export round-trip test (§6.2) |
| rustic CLI behaviour Ladderback's export relies on changes (e.g. `[forget] filter-*` starts working, `[snapshot-filter]` semantics change) | Export golden test runs against the rustic CLI version CI pins |
| A long backup collides with prune's `keep-delete` window | Worker deadline, owner prune guard and duration warnings (§7.3); 6-day default `keep-delete` |
| Clock skew between agent and hub weakens the deadline | Clock offset recorded per agent; warning above 5 min; the 1 h margin absorbs smaller skew |
| SQLite failure on unusual filesystems | Daily copy, `db rebuild`, CI on btrfs and Docker volumes (§9) |
| Config upgrades break existing installs | Schema version and migrations from M1b; refuse newer schemas (§6.1) |
| Leptos 0.8 → 0.9 migration | Keep UI components thin and logic in `api`/view-models. Migrate once 0.9 is stable |
| Hard-coded strings creep into the UI and make localization a rewrite | Generated message IDs, the unused-ID lint and Playwright pseudolocale runs from M1b (§8.4) |
| Accessibility erodes as the UI grows | Invariants A1–A6 (§0); one component set with contract tests; role-and-name-only test locators; axe-core in CI; a screen-reader pass in each milestone's definition of done (§4.5) |
| ICU4X data bloats the daemon binary | Measured in M1b: with every locale's data compiled in, ICU4X adds 1.1 MB (4%) to the stripped release daemon, so v1 doesn't trim it. Generate data for the shipped locales only if a later change makes it much larger (§8.4) |
| The bundled time-zone data bloats the daemon binary | Measured at M1b: the copy of the IANA database adds 248 KB (0.7%) to the stripped release daemon and nothing to the web UI's wasm, which looks up no zone. Kept, because without it a host with no `tzdata` reads every zone as UTC (§16 decision 30) |
| macOS TCC permissions | Signed, notarized builds; detect denials and link to the settings pane. Document this in setup |
| Memory use on very large repos | Worker isolation. Restore and `dump` need the full index (`to_indexed()`); measure early with a large test repo. Document `--no-cache` and cache dir options |
| Hub is a single point of control | Agents back up without the hub. Agent owner leases last 7 days without renewal, so an outage longer than that pauses agent-run maintenance; backups continue |
| Test-first discipline erodes under schedule pressure | Red-first check, mutation testing on changed code and the definition of done (§13); no coverage gate to game |
| Fakes drift from real adapters, so green tests prove nothing | Port contract tests run against both the fake and the real adapter (§13.3) |

| 21 | Robustness rules | **Four rules, enforced by tooling where a tool can, recorded 2026-11-08 (§13.5).** Never crash in non-test code (clippy `deny` at every production crate root). A test that can't run says so with `testkit::skip!`, and `just test` lists the skips. Parallel agents each get their own worktree, target directory, ports and scratch folder. Why: the daemon runs unattended and owns the operation queue, so one panic silently stops backups; the inputs that reach it come from other processes, files and networks; a silent skip reads as a pass; and agents sharing a tree or a port break each other's builds. |
| 22 | One time library | **Time goes through `jiff`, never `chrono`** (recorded 2026-11-08). `croner` is used with `default-features = false, features = ["jiff"]`, and `just architecture` bans `chrono` from `domain` and `app`. Why: Ladderback already models time with `jiff` (`Timestamp`, `SignedDuration`, the `Clock` port), and so does `rustic_core`; `jiff`'s time-zone handling and `Span`/DST arithmetic are what scheduling needs; `chrono` would add a second model of time and conversions between the two. `chrono` still reaches the build transitively through `rustic_backend`'s OpenDAL FTP service (`suppaftp`), which can't be turned off; no Ladderback crate depends on it. |
| 23 | Request checks: JSON for every mutating request | **Every mutating request (any method except `GET`, `HEAD`, `OPTIONS`) must be `Content-Type: application/json`, whether or not it carries `Origin`** (recorded 2026-11-08, §10.1). The `Origin` match applies only when `Origin` is present. Why: with auth off, a cross-site `text/plain` form post can set hooks and `password-command`, and a browser or extension that strips `Origin` would otherwise let it through unchecked. Cost: curl and scripts must send the header. |
| 24 | Project name | **The project is named Ladderback** (recorded 2026-11-08), renamed from Steading before any release because of a name clash. It is inspired by Backrest, not derived from it. Why: nothing was released, so no user had data, keyring entries or snapshots under the old name, and stored identifiers changed without migration. |
| 25 | Who decides a forget's deletions | **The daemon decides, the worker deletes** (recorded 2026-11-09, §7.3). `RunMaintenance` resolves the alias, runs an `Identify` read each time (the repo ID is never persisted in config), lists snapshots, partitions them (I6), and evaluates each managed plan's retention in-process through the `Retention` port — the real one is `rustic_core`'s `ForgetGroups` behind `adapters/engine`, over one default group, so an exported profile's semantics match a manual forget. The exact snapshot IDs go to the worker, which only calls `delete_snapshots`. A policy that is set and keeps nothing is refused before selection, per plan whose group holds snapshots (`RetentionKeepsNothing`, HTTP 422); an empty policy keeps everything. Manual forget, prune and check share one route, `POST /api/v1/repositories/{alias}/maintenance`, and the I7 slot is taken before the engine runs (`MaintenanceBusy`, HTTP 409). Two §7.3 items are deferred, not decided away: the pre-forget dry run and approval threshold (step 4) waits for the UI slice that shows it, and unmanaged groups are partitioned by the fixed `(host, label, paths)` key — the repository's `group-by` moves that grouping when adoption lands (step 3), which reads it. Why: retention is policy, so it belongs in the core where I6 lives; the worker stays a thin engine; and refusing keeps-nothing stops a whole plan's history going away by one mis-typed count. |
| 26 | What an adoption writes | **A rewrite with the plan's tags, nothing else** (recorded 2026-11-09, §7.3 step 3). The daemon picks the group (an orphaned group by its `(agent, plan)` tags, or the unmanaged group whose `(host, label, paths)` equals the destination plan's host, label and sources — the agent's hostname standing in when the plan names none, and the sources normalized the way rustic records them, through a `NormalizeSources` port because that reads the disk), and hands the worker the exact IDs with `PlanTags`. The worker rewrites each snapshot file with the two `ladderback-*` tags, keeping the user's own tags, saves it (a new ID over the same tree) and removes the original. Saving and removing are two writes, so a worker stopped between them leaves both; a copy is known by its original's tree and time and the plan's tags, a run that finds one keeps it rather than saving another, and the summary counts exactly one copy per original, never a snapshot the plan already held or a backup's that ran meanwhile. More than one plan matching one group is refused (`AdoptionAmbiguous`, HTTP 422, naming them) — which plan history belongs to is the owner's decision; no match is `AdoptionNoMatch` (422); a destination plan that isn't configured for that repository is `PlanUnknown` (404), checked before the repository is listed. A body that names `into` or `from` for another kind is `InvalidBody` (400); an unknown kind stays `MaintenanceKindUnknown` (404). Adoption takes the I7 slot (`OperationKind::Adopt`, migration `0003`), runs through the one maintenance route with `{"kind":"adopt","into":…,"from":…}`, and its summary counts what it created. Why: matching is policy, so it lives in the domain where I6's partition already is; the rewrite is mechanical, so the worker does it; and refusing ambiguity stops one keystroke giving a plan another's whole history. |
| 27 | Profile interop: what an import refuses, what an export says | **An import refuses what it would have to guess at; an export is a profile the stock `rustic` reads, and says or refuses what rustic would do differently** (recorded 2026-11-10, §6.2). Settled: (1) a plan's ID is the slug of the entry's `name`, else its label, else the last folder of its first source, else `plan`, and any clash, with the configuration or inside the profile, is refused, never numbered; (2) one host for every plan, with no plans and no agent hostname in the configuration, becomes the agent's hostname, and a plan that names the agent's hostname drops it; (3) `RUSTIC_PASSWORD*`, `RUSTIC_REPOSITORY` and `RUSTIC_REPO_OPT_*` fill only what a profile leaves out, and are kept as references, never as values; (4) `keep-tags` and `keep-ids` are refused, because dropping them would let a forget remove what rustic keeps, and a key rustic itself refuses is refused, naming its path and line (`[repository]`, which rustic reads leniently, gets a notice); (5) every `${` a profile wrote into a repository value is escaped, so a profile can't make the configuration read a file, and a secret in a profile is kept as written with a warning that names the field; (6) an exported entry is named by the plan's ID, so a round trip gives the same plan, its forget has `group-by = ""` and one comma-joined `filter-tags` entry, and it never prunes; (7) a plan with no retention is exported, with a notice that rustic's `forget` refuses to run until a `keep-*` option is set; (8) a repository, hot repository or rclone connection string with a password or a secret piece is refused naming the key, an option with a user or a password in an address (with or without its scheme) is left out like any secret option, and the value is never shown; (9) a tag with a comma is refused naming the tag; (10) a non-empty `[snapshot-filter]` beside retention is refused, because rustic's forget then reaches fewer snapshots than a plan's does, except the filter an export writes, and so is `profile-substitute-env = true`; (11) a profile is bounded by what it can multiply or repeat: 100 000 items across the plans, 32 names in `use-profiles`, 200 different keys left out, and a value that stays under 64 KiB once escaped. Why: a profile is input nobody vetted, and a guess about what a setting means is how a forget removes snapshots a person meant to keep; the export is the way back to the stock CLI, and what it can't say in rustic's words has to be said, or it is found out when a forget does something else. Cost: a profile with a `keep-tags`, or a `[snapshot-filter]` and retention, has to be edited before it imports, and a repository with credentials in its address has to move them into options before it exports. The golden checks need `rustic` 0.11.4 and skip where it isn't installed, so CI runs them once a separate change installs it. |
| 28 | Repositories page and its routes | **A form that tests, connects or creates a repository over three underscore-prefixed routes, saving a typed password inline** (recorded 2026-11-10, §4.2, §4.4). `POST /api/v1/repositories/_test`, `POST /api/v1/repositories` and `POST /api/v1/repositories/_init` take the configuration's own `settings`; the underscore keeps an alias, which is a slug, from ever colliding with `/repositories/{alias}`. `GET /api/v1/repositories` now answers rows, not bare aliases (a clean cutover; the Snapshots page reads the alias from a row), with the location masked and the password as its source, never its value (I4). Three choices carry the weight. (1) **A `command` password source is refused over HTTP.** It would make this the first route that runs a program, and that belongs behind authentication and scopes (§10.1); a file written by hand still takes one. (2) **A typed password is saved inline in `config.toml`** (written 0600, as are the copies of earlier versions the history keeps), with no keyring write yet: the keyring needs a design of its own, and the file already holds a password the same way for a repository written by hand; the form says where the password goes. (3) **Connecting is test, then save, under one lock in the composition root**, so two connections at the same moment both survive; the configuration store has no transactional update, and a later writer must take the same lock, or the store grows one. A refusal carries the engine's own words as `detail`, shown in `lang="en"`, and nothing else of rustic's is parsed: a wrong password and a missing repository are not yet typed. With auth off these routes are as open as every other mutating route, which §10.1's request checks alone guard: a caller can have the daemon open or create a repository at any location it can reach, and name a file, an environment variable or a keyring entry as the password's source. No value read that way is ever returned. |
| 29 | Config history: symlinks, order and flushing | **A save follows a symlinked `config.toml` and writes the file at its end; the history stays beside the link; its order is a number, not the clock** (recorded 2026-11-10, §6.1). The atomic write resolves the link, through any chain of them and to a target that doesn't exist yet, and renames the temporary file over the target in the target's folder, so the link is never replaced. The alternative, refusing to save through a link, would have made the dotfile-manager setup unusable. The history stays in `history/` next to the link, in the config folder, because the target's folder is typically a repository that gets committed and pushed, and a kept version may hold a password. History versions are named `<six-digit number>-<UTC stamp>.toml`, the number counting up from the highest in the folder and ordering them (pruning keeps the 10 highest), so a clock set back can't make a save drop the newest versions; the `history/` folder and the config folder are flushed after a version is written, and a failure to flush fails the keep, so a version reported as kept survives a power loss. Why: a link replaced by a regular file silently cuts the config from the file the user keeps under version control; names that sort by wall-clock time put the newest versions first for deletion after a clock is set back; and an unflushed directory entry can lose the only copy of the old file once it is replaced. |
| 30 | Time-zone data | **The build carries the IANA time-zone database: the workspace turns on `jiff`'s `tzdb-bundle-always`** (recorded 2026-11-10, §3.2, §8.4). `jiff` opens the system's database when it finds one and the bundled copy only when it finds none. Why: with `jiff`'s defaults the bundle is on only for Windows and wasm, so on Linux and macOS a host without `tzdata` (`scratch`, or a base image that leaves it out; M5's image may be one) knew no zone, and daemon text read every zone as UTC with no warning, as a schedule that names a zone (M2) would have run at the wrong times. The other way, leaving the bundle out and making a missing database an error at startup, would make every image install `tzdata` and leave the browser's build to rely on a default. Cost: about 248 KB (0.7%) on the stripped release daemon (35,547,920 B before, 35,795,744 B after, macOS arm64, `--no-default-features`), and nothing on the web UI's wasm, which looks up no zone (1,306,384 B before, 1,306,354 B after). Limits: the bundle replaces a missing database, not a missing zone, so a system database without a zone (a Debian base with `tzdata` but not `tzdata-legacy` has no `Europe/Kiev`) leaves that zone unknown, and a zone that doesn't resolve must be refused where a person types it (M2's schedule form) and not read as UTC. The bundled rules are as old as the release, so the system's copy, which the operating system keeps current, wins when there is one. |
| 31 | A secret a URL parser splits | **A piece of a secret is a needle of its own from 8 bytes; shorter ones are masked only as part of the whole secret** (recorded 2026-11-10, §10.2). A parser splits a secret at `@`, `#`, `?`, `/` and `:`, and a library may print the parts one by one; each piece of at least 8 bytes (the first 64 of a secret) is masked in every form the secret is, and the whole secret is also masked as the parser prints it across parts (a host in lower case, a path as it is). Why: a floor of 8 bytes is what keeps the pieces from masking ordinary text (the same floor as a line of a secret that spans lines); a shorter piece of a secret that also holds long ones leaks only a few characters, and in the whole URL it is masked with the rest. Not covered: a non-ASCII host (needs an IDNA library in the domain), percent-decoding in a host and dot segments in a path. |
| 32 | Worker messages that outgrow the cap | **The cap stays at 1 MiB and the sender splits what is too long; no list in a message grows with a repository** (recorded 2026-11-10, §4.1, §9; #83, #76). Two lists met the cap: a forget's snapshot IDs in the job spec (about 15,000 of them filled it) and a listing in its one result message (about 2,500 snapshots). Decided: a forget or adoption runs as jobs of at most `MAX_JOB_IDS` (5,000) IDs, one operation and one merged summary; a listing is a series of `snapshots` events of at most 512 KiB with a closing count; each snapshot is cut to 64 paths, 64 tags and 1 KiB a text, with `paths_truncated` and `tags_truncated` saying so; a listing past 200,000 snapshots fails rather than lists in part; `prepare`'s reads time out after 10 minutes. Why: every other way keeps a bound the cap was meant to give. Splitting is safe because each job touches only snapshots the selection named (I6), so a run that stops partway leaves done what was done, says so, and the next run selects what is left.
