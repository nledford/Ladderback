## 4. Components

This section decides how the work divides between the worker process, the daemon, the hub, the web UI and the MCP server, and how the web UI and the command line meet the accessibility invariants.

### 4.1 Worker process (the engine boundary)

This section decides what runs in a worker process, how the daemon talks to it, and how a job is stopped, bounded and cleaned up after.

Each operation (backup, forget, prune, check, restore, ls, dump, stats) runs in a **child process**:

```
daemon ──stdin: JobSpec (JSON)──► ladderback worker
daemon ◄─stdout: NDJSON Event stream── (progress, log, warning, result)
daemon ──SIGTERM → (grace) → SIGKILL──► cancel
```

Why a subprocess instead of `spawn_blocking`:

1. **Cancellation.** `rustic_core` has none, but a process can be killed. The worker installs a SIGTERM handler that stops emitting events and exits; without it the grace period would be meaningless.

   A backup that is archiving winds down instead (decision 50): its source (`CancellableSource`) lists, opens and reads nothing more, so rustic ends the backup its own way, writing its last packs and saving the index of every pack the worker wrote, and the backend that takes a snapshot first (`refusing_snapshots_once_cancelled`: the hot half when there is one, rustic writes the cold half only after it) refuses the snapshot that comes next. A snapshot write that had begun before the cancel finishes, in both halves, and the snapshot stays. The worker then exits with 143 and writes no more events, so the operation ends `Cancelled`.

   A backup past its deadline winds down the same way (item 4). The daemon's SIGTERM reaches the worker alone, so the `rclone` or `ssh` its backend saves through runs on during the wind-down; a SIGTERM sent to the whole group from outside ends them too, and then the index may not be saved.

   A file the cancel cut mid-read is left out; the blobs it had chunked, like the trees of the partial backup, are indexed but no snapshot uses them, which a check doesn't warn about and a prune removes while their packs are unused, or repacks past its unused limit once a later backup reuses some of their data.

   The wind-down lasts until the daemon's SIGKILL at the end of its grace period, or 30 s when the daemon is gone.

   Killing is safe for data:
   - A backup killed before it saved its index (a SIGKILL, a crash, a wind-down past the grace period) leaves packs no index lists and no snapshot: a check warns about each, and the next prune cleans them up.

     On the local backend it also leaves `*-tmp-*` files, which nothing in rustic removes. Once a job has opened a repository, the worker deletes the ones older than 24 h from each half that is a local folder (the cold half, and the hot half of a hot/cold repository), but only where the backend writes them: `config-tmp-…` in the half's root and `<id>-tmp-…` in `keys`, `snapshots`, `index` and `data/<xx>`. A job that fails to open its repository (a mistyped path, a wrong password, a missing hot half) deletes nothing.
   - Prune writes new packs and index files, then deletes the old index files, then the packs. A kill at any point leaves extra data or duplicate index entries, not missing data; the next prune deduplicates and finishes the job. This only holds without `early-delete-index` (I2).
   - M1a proves this with a kill test against a scratch repo, for the local backend and for OpenDAL's `fs` service. It kills real workers right after a chosen progress event, of a backup and of a prune that has packs to repack, spreading the kills over the events of an uninterrupted run, and then checks that the repository is sound and still takes a backup. OpenDAL's `fs` service writes in place unless `atomic_write_dir` is set, which can leave half a file under its final name, so the guarantee above holds for an `opendal:fs` repository only with `atomic_write_dir` (a directory on the same filesystem).
2. **No runtime nesting.** The backends' internal Tokio runtimes never meet the daemon's runtime.
3. **Isolation.** Memory from large indexes is returned to the OS when the worker exits, and a panic or out-of-memory kill in the engine can't take down the daemon.
4. **Deadline enforcement** (I3, §7.3; decision 55). `rustic_core`'s `backup()` writes the snapshot itself and offers no hook before that write. Instead, once the worker has written `Started` for a job with a deadline budget, a watchdog thread compares wall-clock time against `index_read_at + budget` and, once it notices the deadline has passed, first asks for the cancel of item 1, so the backend refuses every snapshot write from then on, then writes `Failed { DeadlinePassed }` as the last line and ends the worker with 75.
   - The watchdog's first check runs before the job's work starts, so a zero budget stops the job before it writes anything. After that it waits for the time left to the deadline, but at most `watchdog_interval` (5 s by default) at a time, and these waits don't count the time a machine is suspended, so it notices the deadline when it comes, and one that passed during a suspend within one interval of waking. A snapshot write that starts in that gap after a wake is not refused, as it wasn't before decision 55; the prune margin covers it.
   - A writer stuck on a full pipe can't hold the exit back: the watchdog tries the stream once, and goes on whether or not it could write the failure.
   - A job that isn't archiving a backup ends at once (`process::exit(75)`).
   - A backup that is archiving winds down as a cancelled one does (item 1): it starts no snapshot write and saves the index of the packs it wrote, and the job ends the worker with 75 once rustic returns, so a check finds nothing to warn about and the next backup reuses the data; a failure the watchdog couldn't write, the job writes then, as the last line.
   - A snapshot write that had begun at the deadline finishes, in both halves of a hot/cold repository: that write is what the prune margin covers, and ending the worker during it could leave the snapshot in one half alone. The operation is still `deadline-passed`, and in that case its snapshot exists, as after a cancel that comes once the snapshot was written.
   - The watchdog waits for the wind-down 30 s at most, which bounds a worker whose daemon is gone, and then exits with 75.
   - The watchdog stops once the backup has returned: the snapshot is written, and the result goes out before the repository's index is dropped, so a deadline that passes meanwhile can't turn a finished backup into a failure.
   - The daemon also stops the worker at the deadline, with its grace period (below).
5. **Privilege separation (later).** On servers, the worker can run as root to read `/etc` while the daemon and web UI run unprivileged. This uses a small setuid-free helper started via a systemd unit, or `sudo` with a fixed command. Before building it, hooks and `password-command` must be restricted to root-owned config, or the unprivileged UI could escalate to root through them.

Each running worker of a repository whose ID is known gets its own `cache_dir`, a cache slot `<cache folder>/<repo-id>/<slot>`, because rustic's cache has no cross-process locking: the slot is the lowest number no other running worker of that repository uses, and it is free again when the worker exits.

- **Lock.** The worker also holds an exclusive `flock` on its slot directory for as long as it runs, and a daemon looking for a slot skips directories whose lock is held, so a worker that outlived a restarted daemon never shares its cache with a new one; a worker that finds its directory held runs with `no_cache`. A lock is only taken while the slot's path still names the folder locked, not a link, so a slot removed while its lock was held is never held through the folder that was removed.
- **Cache folder.** The daemon passes its cache folder (below, under **Config**) to the engine at start, made 0700 when it isn't there yet; every folder made under it (the repository's folder, the slot, and the cache folder again when it was removed meanwhile) is always 0700.
- **No cache folder.** With no cache folder (no home directory and no `LADDERBACK_CACHE_DIR`), or one that can't be made or written to (the daemon makes and removes a file of its own in it at start), the daemon says so once in its log and its workers run with `no_cache`, which costs each job a fresh read of the index and nothing else (§16, decision 59).
- **No known ID.** Without a known ID, the worker runs with `no_cache`; a daemon job of a saved entry that records none therefore runs after an identify, with the ID it found (§16, decision 81), so only an identify, an initialisation and a job of a repository a request gave run that way.
- **Why a job has no slot.** When the daemon has a cache folder and gives a job that opens a repository no slot, its log says why in one line at the info level, with the operation's ID and the job's kind: the job names no ID, or none of the repository's slots is free (a look at the slots that fails is logged the same way). A worker that finds the lock of the slot it was given held runs with `no_cache` without a line of its own: the daemon gave it a slot.
- **A cache rustic can't write.** rustic itself treats a cache it can't write (a full or read-only disk) as a warning and goes on.
- **Tidy at start.** Each time it starts, before it listens, the daemon tidies the cache folder: it removes every slot no worker holds of a repository no entry records (and that folder once empty), every other repository's slots above the highest one in use (slot 0, a slot another process's worker holds, or one whose lock can't be looked at), and rustic's unfinished `<id>-tmp-` files over a day old in the slots kept.

  While an entry records no ID, no repository counts as one no entry records, since the tidy can't tell which folder is that entry's: every repository keeps its folder until the entry's next job records the ID.

  It touches a slot only while it holds the slot's lock, only folders named as a repository ID and slots named by their number, and never follows a link; the log says what went and its size (§16, decision 61). It runs with `nice` (and `ionice` on Linux) as configured per agent.

**Event protocol** (module `engine::job`, §8.3):

```rust
enum WorkerEvent {
    Started { op_id: Uuid, pid: u32, index_read_at: Timestamp }, // taken just before the index is read
    ProgressStart { key: u32, kind: ProgressKind /* Spinner|Counter|Bytes */, prefix: String },
    ProgressLength { key: u32, len: u64 },
    ProgressInc { key: u32, inc: u64 },    // coalesced: at most ~4 msgs/s per key
    ProgressTitle { key: u32, title: String },
    ProgressFinish { key: u32 },
    Warning { item: Option<String>, during: String, code: WarningCode, detail: String }, // from Progress::error; detail = rustic's text
    Log { level: Level, message: String },   // logs are never localized (§8.4)
    Snapshots { snapshots: Vec<SnapshotResult> }, // a batch of a listing, before its Result (below)
    Result(OpResult), // BackupSummary | ForgetSummary | PruneStats | CheckReport | …
    Failed { code: ErrorCode, args: Vec<(String, MsgArg)>, detail: Option<String> }, // codes from `api` (§8.4)
}
```

`ProgressBars` is implemented by `EventProgressBars`, which writes these events. Per-file errors raised through `Progress::error` become **warnings**, so an operation can end as `Succeeded`, `SucceededWithWarnings` or `Failed` (§3.1). The worker builds a `Redactor` (§3.1) from its `JobSpec`'s repository and `repo_hot`, password, options, `options_hot`, `options_cold` and resolved secrets (`RepositorySpec.secrets`, copied from `RepositoryAccess.secrets`) and passes every `Log`, `Warning` and error through it (I4); §10.2 lists what it masks. A worker stopped by its watchdog emits nothing more; the daemon records the operation as `Failed { reason: DeadlinePassed }`.

**Message cap.** The daemon reads the worker's stdout one line at a time and the worker reads its stdin to the end, and each side reads at most `MAX_MESSAGE_BYTES` (1 MiB, in `engine::job`) of a message plus one byte to tell it from a longer one (§13.5, rule 2).

An event line past the cap fails the operation as `EngineFailed` with the cap in its detail, and the daemon kills the worker; a worker answers a `JobSpec` past the cap with `InvalidJobSpec`; the daemon refuses to start a worker for a spec it would reject. A line that never ends therefore never grows a buffer past the cap.

The worker keeps its own lines under the cap: it cuts each text field (log messages, warning items and details, failure details) to 64 KiB, after redaction, so a cut can never keep the start of a secret.

**What does not fit the cap is split by its sender (decision 32).** The cap stays at 1 MiB, and no list in a message grows with a repository: whoever sends one splits it, with a bound on each piece.

- *A job names at most `MAX_JOB_IDS` snapshots* (5,000, in `app::ports`; an ID is about 70 bytes of the spec). `RunMaintenance::execute` splits a forget's or an adoption's list into jobs of at most that many and runs them one after another as one operation, with one summary: the IDs removed (or the copies made) of every job, in order.

  The first job to fail, or a cancel during a job or seen as one ends, ends the operation as it would a single job and starts no more. A cancel that fired before a job's engine was up ends the operation cancelled, even when the job's result is ready at once.

  Every job touches only snapshots the selection named, so what earlier jobs did stays done and is not the operation's to undo; the operation records a warning that says how many were done, and the next run selects what is left. The engine refuses a job that names more with `EngineError::Unavailable`, as it does a spec past the cap.
- *A listing is a series of `snapshots` events.* `Ls` emits `Started`, then `Snapshots { snapshots }` events, newest first, each serialized to at most 512 KiB (one snapshot alone in an event may be longer, up to about 800 KiB), then `Result(Snapshots { count })`, where `count` is what the events carried: the daemon hands the list on only when its own count agrees, and fails the job (`EngineFailed`) otherwise, so a listing that lost a batch is never taken for the whole. This replaces "`Ls` emits `Started` and one final result".

  A repository with more than `MAX_LISTED_SNAPSHOTS` (200,000) fails the listing with its count in the failure's detail rather than being listed in part, and the daemon refuses a listing whose texts weigh more than `MAX_LISTED_BYTES` (256 MiB): the list it holds is bounded in both, and a partial list would make forget decide on history it can't see.

  A listing's worker reads the repository's whole index too, so at most two listings run at once, of every repository together, taking turns from a `ReadTurns` of their own as folder reads do (below; #710): the wait counts against `READ_TIMEOUT`, and a listing whose turn comes after its time is up starts no worker.
- *Stats is one result.* `Stats` opens the repository, emits `Started`, reads the snapshots and then every index file, and ends with `Result(Stats { snapshots, total_bytes, stored_bytes, raw_bytes })`: the snapshot count, the sum of their `total_bytes_processed`, and the sums of the indexed blobs' lengths in their packs and of their raw lengths, packs marked for deletion left out (§16, decision 104). A read, never written to the operation log.
- *A download is a series of pieces.* `Dump` names the snapshot, the entry (its keys from the snapshot's top; none is the top) and the archive format, and runs with a backup's deadline, as a restore does. It emits `Started`, then `Dumping { found, name, host }` (a file and its size, or an archive; the entry's shown name; the host the snapshot records, which names the top's archive), then `Piece { bytes }` events, each at most 64 KiB of the entry (`PIECE_BYTES`) written as base64, about 87 KiB of text, and `Result(Dump { bytes })`. The pieces are the entry's own bytes, never masked: a redactor could change a file's contents. A snapshot or an entry that isn't there ends it at once with `SnapshotUnknown` or `EntryUnknown`.

  A file is rustic's dump of it. A folder or the top is an archive written as it is read (`tar`, or `zip` with every entry stored): each entry reached through the trees as `ls` lists it, its contents dumped straight into the stream, so no file is held whole; a zip writer keeps each entry's name until it writes the central directory at the end. A zip entry's name separates folders by `/` only, each `\` in a name written as `_`, so no extractor takes it for a folder; a tar entry keeps its exact name. Devices, pipes and sockets are left out (§16, decision 114).
- *A snapshot is cut to a size one message holds.* A listed snapshot carries at most 64 paths (`api::MAX_SNAPSHOT_PATHS`) and 64 tags (`api::MAX_SNAPSHOT_TAGS`), and no text (a path, a tag, the host, the label) of more than 1 KiB, a cut text ending in `…`. That is under 800 KiB for any snapshot, even with every character escaped, so each fits a message alone.

  The worker sets `paths_truncated` or `tags_truncated` when it left something out or cut it, and the DTO carries both (the UI does not show them yet); a cut host or label ends in `…`. When tags are cut, the `ladderback-*` tags that say who owns a snapshot are kept first, so a forget never takes an owned snapshot for an unowned one. The DTO validates the 64 limits (it refuses a snapshot beyond them); the worker is who cuts, for transport.
- *A folder of a snapshot is read a page at a time.* `Browse` names the snapshot, the folder (the names that lead to it from the snapshot's top, each as rustic records it) and the position its page starts at. It emits `Started`, then one `Result(Folder)`: the page, or that the repository has no such snapshot (`SnapshotUnknown`) or the snapshot no such folder (`FolderUnknown`). Like a listing, it is a read: it waits at most `READ_TIMEOUT`, holds no slot and writes nothing (§16, decision 102).

  A page holds the folder's entries in the order its tree records them, at most 1,000 (`domain::browse::PAGE_ENTRIES`) and at most 512 KiB serialized, with the folder's total and where the next page starts, so it is one message whatever the folder holds. The folder is reached through the trees, one name at a time, and an entry whose name is longer than 4 KiB (no file system writes one) is left out but keeps its position.

  A worker may hold the folder's whole tree, 350 MiB for one of 300,000 entries, so at most two folders are read at once, by all browses of every repository together (`app::reads::READS_AT_ONCE`, one `ReadTurns` shared through the configuration catalog): two reads that hang hold up every other browse until the read timeout ends them. The rest wait for a turn, in no set order; the wait counts against `READ_TIMEOUT`, so a read that waits ends as `TimedOut` no later than one that started at once, and a browse dropped while it waits takes no turn.
- *A repository's reads wait a bounded time.* `RunMaintenance::assess` gives up an identify or a listing after `READ_TIMEOUT` (10 minutes) with `MaintenanceError::TimedOut`, which stops the worker, holds no slot and writes nothing.

**What is implemented of this protocol (M1a, plus the secrets work of M1b):**

- A job is `Fake | Identify | Backup | Prune | Check` (decision 80 adds `Probe`, which opens one location with its own credentials and reports the repository ID it holds, so a location that hangs is killed rather than the job). The repository password travels as a plain string on stdin only, and `JobSpec` also carries `cache_dir` and `watchdog_interval_ms`.
- A repository with a hot half (`repo_hot`) is opened through both halves. `options` apply to both, `options_hot` to the hot half only and `options_cold` to the cold half only (rustic's own rule), and the job's repository string is the cold half.

  rustic reads the hot half's config first and requires the keys of the halves to match, so a missing hot half fails the job at the open. It keeps keys, snapshots, index files and tree packs in the hot half and reads them from there, so a check fails when a snapshot is missing from it; file data is in the cold half only.

  A `RepositorySpec` that leaves the hot fields out, as an older daemon's would, is refused as `InvalidJobSpec` (`options_hot` and `options_cold` have no default) instead of being opened as a cold-only repository.
- The first line of a worker's stream, once its spec has parsed and the redactor is installed and before it opens anything, is a `Log` at the debug level reading `job accepted`, with nothing of the job in it: it is the proof of life the daemon's start timeout waits for (below). A spec that doesn't parse gets `Failed(InvalidJobSpec)` alone. `Started` is written when the job's clock starts: right before `to_indexed_ids()` for a backup, before `prune_plan` for a prune, before `check` for a check, and after opening the repository for `Identify`. Progress that rustic begins earlier (listing snapshots) never reports, and only `Log` and `Failed` can precede `Started`.
- `ProgressInc` is coalesced on the leading edge: the first goes out at once, the rest are added up and sent at most every 250 ms per key, and the remainder is flushed before `ProgressFinish`. A source rustic could not read (`scan`, `archival`) is a `SourceUnreadable` warning; any other `Progress::error` is `Unknown`.
- `Failed.code` is `deadline-passed` only when the deadline ended the job (the watchdog writes it, or the job as the worker ends when the watchdog couldn't); the codes the engine adapter reads from what rustic reports (`repository-not-found`, `repository-config-not-found`, `repository-replaced`, `credentials-refused` with its `half`, `password-not-accepted`: `translate` in `client/translate.rs`) aside, all else rustic reports is `operation-failed` with `detail` = rustic's one-line message, after redaction. Exit codes: 75 deadline (the watchdog's, or the job's once a backup has wound down at its deadline), 143 SIGTERM, 74 events could not be written. The client maps `Failed { DeadlinePassed }`, and EOF with exit code 75, to `DeadlinePassed`.
- Stopping a job sends SIGTERM, waits the grace period (`STOP_GRACE`, 35 s, past the worker's own 30 s limit on a wind-down, so a backup that archives saves its index before the SIGKILL could land; decision 50), then SIGKILL; `stop()` returns once the process has exited, and the job's events end without a result.

  While it waits, `stop()` reads and drops what the worker still writes: a backup winding down (item 1) whose events went unread until the pipe was full would otherwise stay blocked writing one, and the SIGKILL would leave its packs unindexed. Dropping a running job kills the worker at once, but after a result it has 10 s to finish.

  At the deadline the daemon stops the job, with the grace period, so a backup that archives can wind down (item 4), and so it does when the worker reports the deadline first; it checks the deadline on every event too, so a stream that never pauses can't hold it off. Once the worker has exited, the operation is recorded `deadline-passed`, whatever the exit code, so its end time can be up to the grace period past the deadline, as a cancelled one's is past the cancel. A result stands even when it arrives past the deadline: its snapshot is already written.
- Two timeouts keep a hung worker from holding the daemon.
  - A new worker has one deadline of 30 s (`WorkerEngine::with_start_timeout`), counted from the start of the write of the job to its stdin, to take the job: it ends with the worker's first complete line of any kind, which is normally the `job accepted` log line above. Opening the repository, which a slow backend can make take longer, comes after that line and is not bounded by this timeout.

    A worker that doesn't read a spec larger than the pipe's buffer (64 KiB on Linux) leaves the write blocked, so `run` kills it with its process group and fails with `EngineError::StartTimedOut`.

    A worker that took its job and then says nothing is killed with its group by the job's event stream, which ends with a single `Failed(EngineStartTimedOut)`; `run` doesn't wait for it, because that would delay a user's cancel until the first event. Either way the operation fails as `EngineStartTimedOut` without having started.

    After its first line a worker is not on this clock: how long it takes from there is for the job's deadline and for cancel.
  - Once a worker's event stream has ended, the process has 10 s to exit (`with_exit_timeout`): one that stays alive is killed, and the operation fails as `EngineExitTimedOut`.

  A timeout too long to represent, such as `Duration::MAX`, never passes. The wait inside `Control::stop()` after SIGKILL has no timeout of its own: its signature can't fail, and a SIGKILL can't be refused short of an uninterruptible sleep.
- Backup chooses the parent with `PlanTags::parent`: explicit `ParentOptions.parents`, or rustic's own match when it returns `None`. Extra tags are `UserTag`s, which never start with the reserved `ladderback-` prefix in any case, so they can't make a snapshot look like another plan's (I6); the worker refuses such a tag in a spec too.
- A backup's snapshot names the build that wrote it. `ladderback worker` is handed the program and its build as `ladderback --version` prints them (`ladderback 0.3.0+3f937cf`, §16, decision 90), and the backup sets the snapshot's `program_version` to that text, which rustic would otherwise fill with its own `rustic <version>`; `rustic snapshots --long` shows it as "Generated by". It is not a tag: retention groups and ownership (I6) never read it, and it holds nothing of the job's secrets (I4).
- Prune always runs with `instant_delete = false` and `early_delete_index = false`, and `keep_delete` is a `KeepDelete`, never under rustic's 23 h default; the worker refuses a shorter one too. Its summary counts `packs_marked = unused + repack`, `packs_deleted = packs_to_delete.remove` and `packs_recovered = packs_to_delete.recover`.
- Check sends each finding as a warning of its level (`check-warning` for rustic's `Warn`, `check-error` for anything else) in rustic's own words, masked and cut like every warning, the errors first so that the operation's cap on warnings never keeps a tidy-up in place of an error, then counts the findings by level; a check that ran to its end succeeds, with warnings when it found anything (§16, decision 51).
- A backup's spec carries its plan's snapshot host (§3.1) and its whole `SourceFilter` as `SourceFilterSpec`. The worker maps the filter's globs and glob files onto rustic's `Excludes` and the rest onto `LocalSourceFilterOptions`, and the host onto `SnapshotOptions::host`; with no host, rustic records the machine's own name.

  The worker parses the host again as a `Hostname` and refuses one that isn't (`InvalidJobSpec`), before it opens the repository. A spec without `filter`, as an older daemon's would be, is refused the same way; a spec without `host` means no host.

  The job spec's size cap bounds every pattern and path the filter lists, but rustic reads each glob file whole, so a very large glob file costs the worker's memory, never the daemon's. The worker runs in the daemon's working directory, and rustic reads a glob file from the working directory, so every `glob-files` and `iglob-files` path is a `GlobFile`, an absolute path: the configuration refuses a relative one at its key when it loads (`Value(GlobFile)`, §6.1), and an import refuses it as unsupported (§6.2). The worker doesn't check the paths again.
- The `Redactor` masks each secret raw, fully percent-encoded with either hex case, and as the url crate encodes a userinfo (rustic quotes URLs that way); a secret a URL parser splits (`@`, `#`, `?`, `/`, `:`) is also masked piece by piece from 8 bytes, and as it is printed across the host, path and query. A password in the repository URL is masked as written and decoded, and also when a raw `/` in it ends the authority early.
- **Worker environment.** A worker is started with `env_clear()` and only the variables of an allow-list from the daemon's environment (module `engine::environment`): `PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `TZ`, `LANG`, `LC_ALL`, `SSH_AUTH_SOCK`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `SSL_CERT_FILE`, `SSL_CERT_DIR`, `RCLONE_CONFIG` and the proxy variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`, each also in lowercase. Names are matched exactly.

  Everything else, such as `AWS_*`, `AZURE_*`, `GOOGLE_*`, `RUSTIC_*`, `RCLONE_CONFIG_*` and the variable a secret reference was read from, is not passed; a repository that needs a credential gets it through `${…}` in its options (§10.2).

  A proxy URL with credentials embedded passes as it is, so those credentials stay in the worker's environment (a residual risk the user takes by writing them there; no secret source is added for them), but they are masked wherever the worker's output shows them: the daemon adds the password and the whole userinfo of each of `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` (either case, with or without the scheme; `NO_PROXY` lists hosts, not a URL) to the job's `Redactor`.

  The base is the daemon's own environment, read at each job, unless `WorkerEngine::with_environment` replaces it; tests and a composition root that has read its environment already use that.
- **Masking by the daemon.** The programs a worker starts (rclone, ssh) write to its stderr without going through its `Redactor`, so the daemon builds a `Redactor` from the job's repository and `repo_hot`, password, the three option sets and secrets, and the proxy credentials above, and masks each stderr line before logging it. A line cut at the cap is masked as a cut text (§10.2, "Where masking runs"), and so is a last line the stream ended without its newline, which a kill can leave partway through a write; both are logged ending in `…`.

  It masks every text a worker's events carry as well: failure details, warnings, progress text (which then only names a step, and goes no further: decision 82) and log lines, and the failure it reports for a line it can't read.

  The worker masks its own, but it rejects a job spec before it has the job's secrets, and a parse error can quote the value it choked on, and it knows nothing of the proxy credentials. The worker cuts a text after masking it and marks the cut with `…`, so the daemon masks a text that ends in the mark as a cut text too. A fake job has no secrets of its own and masks only the proxy credentials.
- OpenDAL's local file service is the repository string `opendal:fs` with the option `root`.
- A worker leads a process group of its own. A stop sends SIGTERM to the worker alone, so a backup winding down (item 1) keeps the programs it started, then SIGKILL to the group after the grace period; a kill is the group's. A worker that exits by itself, at its deadline (75), on a broken event stream (74), on a SIGTERM (143) or by crashing, gets the group a SIGKILL as well, so the `rclone` of an rclone backend, which `process::exit` doesn't stop, ends with the worker.

  On Linux the daemon sees the exit with `waitid(WNOWAIT)` and signals the group while the worker is an unreaped zombie, which still holds its process id. nix has no `waitid` on macOS, so there the worker is reaped first and the group is signaled by the id it had.

  POSIX keeps a process id from being reused while a process group of that id has a live member, so the window left is a group with no live member, whose id a new process takes and makes itself leader of between the reaping and the signal.

  The worker keeps the event pipe on a close-on-exec descriptor of its own and points descriptor 1 at `/dev/null`, so no program it starts inherits the pipe or can write into the stream. Once the worker has exited, the daemon reads what is left in the pipe for one more second at most, so a process the worker left behind that holds the pipe open can't keep the events from ending.

  On Linux the worker asks for SIGHUP when its parent dies (`PR_SET_PDEATHSIG`) and handles it as a SIGTERM once its parent is no longer the process that started it. The kernel sends that signal when the parent *thread* ends too, and the daemon starts workers on tokio's blocking pool, whose threads end after 10 s without work while the daemon lives on: a SIGTERM there stopped a backup that outlived its thread, which failed with 143 (#448). Elsewhere a worker whose daemon died ends at its next event, when the pipe is broken.
- A progress or log callback that finds the event stream unwritable (the daemon is gone) ends the worker at once with code 74, and so does the job's own write failing. A panic is written to stderr with the job's secrets redacted. The worker's stderr is a pipe the daemon reads on a task of its own, never the terminal: a worker in a process group of its own is a background job to a terminal with `stty tostop`, and a write to the terminal would suspend it. Each line, cut at the message cap, goes to the daemon's log as a warning (target `ladderback::worker`), without holding up the events, and the reading ends with the worker like the events' does.
- Integration tests run the worker through `engine-worker`, this crate's own binary, which does what `ladderback worker` does.
- Every child the daemon starts, a worker, a hook, a password command or the `rclone` that serves an `rclone:` repository it opens to evaluate retention, starts through the spawn gate (`spawn_gate::hold`, decision 58): one start at a time in the process, so none inherits another's pipes where the standard library makes a pipe in two steps (macOS).

  The gate is held for the start only, not while the child runs, nor while `rclone` comes up: the engine starts that server itself, as rustic's backend does, and waits for its address outside the gate. That wait, and the one for `rclone version`'s answer, end 2 minutes after the open began, well inside the use case's read timeout: an `rclone` that hasn't answered by then is killed and reaped, and the open fails (#326).

  Async code waits for the gate on tokio's blocking pool (`spawn_gate::hold_blocking`), so a start whose `exec` stalls never holds up the runtime's threads.

### 4.2 Daemon (agent)

This section decides what the daemon does: its HTTP server and API, the scheduler and job runner, logging, configuration, start-up and shut-down, and the commands it shares with the command line.

- **axum 0.8** HTTP server. It serves the embedded UI, `/api/v1/*` (JSON) and `/api/v1/events` (WebSocket for live updates). It binds to `127.0.0.1:9898` by default. Request checks, body limits and the security response headers (§10.1) apply whether or not auth is enabled: a request is checked first, then, with sign-in on, its session or API token (§10.1), then its body is read up to the limit of its route class (128 KiB for `/api/v1`, none for the UI) before a route runs, and every response carries the headers.

  It listens through `http_adapter::GatedListener`. Where the platform makes a socket and accepts a connection in two steps (macOS), that listener makes the listening socket and accepts each connection while it holds the spawn gate (decision 66), so a child started meanwhile never inherits them; Linux accepts as tokio does.

  An accept takes the gate on the runtime's thread when it is free at once, and otherwise waits for it, and accepts, on tokio's blocking pool. A failed accept is handled as `axum::serve` handles its own: a connection its client gave up on is passed over, and any other failure is logged and tried again a second later.
- **Scheduler** (§5). It turns plans into jobs and respects the agent's concurrency limit and each plan's overlap policy (decision 75). `app::schedule::Scheduler` is the loop: `src/main.rs` spawns the composition root's `Background` task (`src/composition.rs`) once the daemon listens, which runs the queued backups recovery handed back and then the loop, and aborts it once serving has ended, after axum's graceful shutdown has let the open requests finish or the stop has given them up (shut-down order, below).

  It starts a plan's run through the `PlanRuns` trait, which the composition root's plan runner implements: not a port, but the use cases the root wires, so a scheduled run is a manual run's use case with another trigger. Every backup, scheduled, started by hand or held from before the start, takes its place in one `app::queue::RunQueue`, and runs once its turn comes.
- **Job runner.** It spawns workers, consumes events, writes the op log (queued, running, finished; a write the store refuses never changes how the operation ends, §9) and broadcasts to UI clients: a job's start, progress and warnings as the worker reports them, and how an operation ended once the run's last write to the log is done (§4.4). If a hub is configured, it also writes events to the sync outbox.
- **Store.** SQLite via `sqlx`, in WAL mode (§9).
- **Logging.** `serve` installs `env_logger` first, writing one plain line per record to stderr, with millisecond timestamps and colour as §4.5 decides it: none with `--plain`, otherwise by what `anstream` reads of `NO_COLOR`, `CLICOLOR_FORCE` and `CLICOLOR`, and then of whether stderr is a terminal.

  The default level is `info`, because env_logger's own would hide the worker's warnings (§4.1); `RUST_LOG` directives layer on top of that default, and an unset, empty or blank value means the default. It logs `ladderback <build> starting` before it binds, the build as `--version` names it (`0.3.0`, or `0.3.0+3f937cf` between releases; decision 90).

  The lines the daemon says itself (`listening on`, the refusals that stop it, and the warning that sign-in is off on the network, which no `RUST_LOG` setting may hide: §10.1) are not log records: they are written through `output::to_stderr` (§4.5), so a log that nobody reads stops the daemon with 141 at the first of them, before it serves, whereas once it serves the logger drops what it cannot write and the backups go on.

  A stop is logged as it happens (decision 92): `stopping (SIGTERM)` or `stopping (SIGINT)` at the signal, a warning for each step given up and what that leaves, and last `stopped after 2.4 s: open requests 0.0 s, operation log 0.1 s, workers 2.3 s, tasks 0.0 s`, at WARN with `(gave up)` after a step given up; a stop the service manager cut short has no last line. `ladderback worker` installs no logger.
- **Config** (§6.1). `config.toml` in the platform config dir, `LADDERBACK_CONFIG_DIR` when set (a non-empty value; tests and a second daemon use it). The platform folders:
  - macOS `~/Library/Application Support/ladderback` for both config and data, `~/Library/Caches/ladderback` for the cache.
  - Linux `$XDG_CONFIG_HOME|$HOME/.config/ladderback`, `$XDG_DATA_HOME|$HOME/.local/share/ladderback` and `$XDG_CACHE_HOME|$HOME/.cache/ladderback` (a relative `XDG_CACHE_HOME` is ignored, as the XDG specification says).

  `LADDERBACK_DATA_DIR` overrides the data dir, which holds `ladderback.db` and the agent ID, and `LADDERBACK_CACHE_DIR` the cache dir, which holds the workers' cache slots and nothing that is needed.

  No home directory and no override is a typed exit for the config and data dirs, not a guess; for the cache dir it only means workers without a cache (§16, decision 59). A service with no home directory sets `LADDERBACK_CACHE_DIR` (under systemd, to its `CacheDirectory=`).

  `serve` reads the config before it binds: a file this build cannot read — unreadable, too large, missing or newer schema, invalid — is a typed startup exit (the catalog's `cli-config-*` messages) that names the file and the version it found; it never starts on a silent empty configuration, and never prints "listening on" first. An empty configuration is fine: an agent with nothing to do still serves.
- **Start-up order.** `serve` goes in this order:
  1. It creates the data folder and takes its lock (`<data>/ladderback.lock`, §9) before it reads anything, so a second process on the folder is refused before it touches the configuration.
  2. It reads the configuration, opens the operation log, makes the event bus and starts the notifier (§11).
  3. It ends the operations that log still shows as running, announcing each, and reads the queued ones (`RecoverOperations`, §9, decision 91).
  4. Only then does it build the engine and the router's state, bind the listener and print `listening on`. On macOS, building the state runs the Full Disk Access probe once, and a grant found missing is one warning in the log (§16, decision 115).
  5. Then it runs the queued backups again and starts the scheduler (§5, decision 73).

  A start that can't lock the folder (`cli-data-dir-in-use`, or `cli-cannot-lock-data-dir` when the file system has no locks) or can't end those operations (`cli-cannot-recover-operations`) is a typed exit like the configuration's: it prints no `listening on` and serves nothing.

  A recovery that ended operations logs one warning with their count, and a queued operation the queue can't run again is announced once the log has its end. A start refused after recovery (the agent ID, the program's own path, the listener) stops before the notifier can deliver what recovery announced, so those notifications are lost (decision 91).
- **Shut-down order** (decision 92). On Ctrl-C or SIGTERM `serve` first stops what could start or end a run: it stops the background task, so the scheduler starts no run and the persistent queue hands on no more (decision 73), asks the workers to stop (step 2 waits for them), and freezes every run of an operation where it stands (`composition::runs::Runs`), so no run is polled again: it is dropped where it stands, killing a hook it was running, and starts no worker, runs no further hook, and records and announces no end, whatever its worker, its deadline or its turn in the queue do meanwhile.

  `serve` listens for both signals before it binds its listener, so one that comes from then on, and so any from the moment it says `listening on`, takes this stop once it serves, or is ignored when the start is refused; one before that, while it locks its data folder and recovers its log, gets the default action and kills it (#628).

  A restart asked for in Settings takes the same stop once it is due (decision 94): at once for a restart now, and for one that waits once no operation runs. Its `stopping (…)` line names who asked, `restart asked by the signed-in admin` or `restart asked with sign-in off`.

  A backup's run writes the engine's result on its running operation before any ending hook runs, so a backup stopped in its after hooks keeps its snapshot ID on a record ended `daemon-shut-down`, and History links the snapshot.

  Then it logs that it is stopping and stops serving (axum's graceful shutdown), and waits for each step of its stop within a bound of its own and within what is left of its limit, 65 s (`shutdown::LIMIT`, the sum of the bounds), so no step can keep it from exiting and the service manager, which waits 75 s, never cuts a stop short.

  The steps, in order:
  1. The requests still open, 5 s (`REQUESTS_BOUND`), after which they are left to end with the daemon (axum serves each connection on a task of its own, which the runtime drops as the daemon exits; a job one asks for meanwhile is stopped with the workers or never started).
  2. The workers, 40 s (`WORKERS_BOUND`: the grace and 5 s to reap): `engine::Workers::stop` stops every running job as a cancel stops one, SIGTERM and then SIGKILL after the grace, so a backup that archives winds down and saves the index of the packs it wrote (decision 50).

     A job asked for from then on is neither started nor answered, so its run waits for the daemon to end.

     The events of a job stopped so never end, so its run neither records nor announces an end, nor runs a hook for one: it ends with the daemon, and step 3 records its end.
  3. The operation log (`SqliteStore::close_ending_running`), which waits for the log's calls in flight, so a write a running operation began commits or fails as it would have rather than being cut off, then ends every operation the log still shows as running as failed with `daemon-shut-down`, finished at that moment, in one transaction, and closes: no connection, and so no `-wal` or `-shm` file, outlives the daemon, and a write made after it is refused.

     An operation an orderly stop interrupts is recorded, not announced: nothing is published, and the next start has nothing of it to end.

     It waits 20 s at most (`LOG_CLOSE_BOUND`, the `SAVE_BOUND` a run gives one write of its own, past the store's own bound on a call of about 15 s): a busy store still finishes, and one that hasn't by then is stalled, so the daemon logs a warning and stops without it.
  4. What the runtime's tasks were still doing, in what is left of the limit (`Runtime::shutdown_timeout`): a blocking task still running then is left behind with the process.

  An operation the log shows as queued stays queued, the persistent queue's again at the next start (§9, decision 73). A stop that doesn't commit step 3's ends (the daemon killed while it stops, a power cut, the step given up or its write refused) leaves the operations running in the log, and the next start ends each `daemon-stopped` and announces it, as after a crash (§9, decision 91). Last it lets go of the data folder's lock (§9), so no other daemon recovers the log while this one could still be writing it, and logs how long the stop and each step took.

  A start refused once the log is open (`cli-cannot-recover-operations`, an agent ID it can't read or its own path it can't find), and a daemon that can't listen, close the log the same way before they exit, with no stop to log. A daemon told to stop exits with status 0; one asked to restart in Settings exits with status 75, which its service manager starts it again on (decision 94).
- **Operations API.** `POST /api/v1/operations` with `{"plan": …}` starts a backup of a named plan and answers `202` with the operation's ID, after the operation is in the log as queued and its cancel switch is parked, so a cancel sent at once is accepted, and one that fires before the engine is up ends the operation cancelled once its before-hooks have run; refusals are typed (`plan-unknown`, `invalid-body`, `config-unavailable`, and the secret and template codes of the Repositories API, 422, with the same arguments and a `detail` masked of every secret of the repository, I4, when the plan's repository has a secret that can't be resolved; nothing is queued then, #309).
  - E2 grows it into the operations page: `GET /api/v1/operations?after=<cursor>&limit=<n>&plan=<id>` answers the keyset history page, newest first, running operations included — the page's initial state over REST, which a client that then subscribes closes the gap a late subscriber has (§4.4).
  - `GET /api/v1/operations/{id}` answers one operation's detail with its warnings; an operation that failed carries `failure-code`, and beside it `failure`, `{code, args?, detail?}` as a refusal's error is shaped: the arguments its message takes, by name, and the engine's own words, which the engine masked of every secret of the job (I4, #474); a backup the schedule started that was refused for a setting of its repository (scheduling-and-config.md §5) carries its refusal as a request to start it is refused with, what a platform or a command said as `detail`, masked of the repository's secrets.

    `failure` is a field added to the published `/api/v1` shape (operations.md §12.1), so `failure-code` stays as it was.
  - `POST /api/v1/operations/{id}/cancel` takes the empty JSON body `{}` (the JSON-body rule applies to every mutating method) and cancels politely: the worker stops, the finally-hooks run, the operation ends `cancelled`.

    Cancel reaches an operation whose cancel switch is parked: a running one, and a queued one this daemon started or the persistent queue has handed on, which ends `cancelled` without reaching the engine. A queued operation from before a restart that the queue hasn't handed on yet (it is still on its way, or the configuration couldn't be read, decision 73) has no switch, and is `operation-not-running` (409) like a finished one.

  An unknown ID is `operation-unknown` (404), a cursor that isn't an operation ID `invalid-cursor` (400), and `limit` is clamped, never refused.

  Operation IDs are UUIDv7, which is what the log orders by. A second backup of the same plan runs beside the first; I7's slot rule is maintenance-only.

  The agent, repository and plan hooks (§6.1) wrap every API-started run, read from the configuration as it stands when the run starts.
- **Plans API.** `GET /api/v1/plans` answers `{"plans": […]}`, one row per configured plan in the order the configuration writes them:
  - `id`.
  - `repository` (its alias).
  - `scheduled` (whether it has a schedule; one without runs only when it is started).
  - `next-run`, the scheduler's planned run as RFC 3339 in UTC, or `null` for a plan without a schedule and for a scheduled one the scheduler has planned no run for (it hasn't yet, or the schedule has no run left).
  - `warnings`, left out when there is none: one `glob-never-matches` per glob of the plan that can never match (scheduling-and-config.md §6.1, #510), which the start page shows in a Notes column that it adds only when a plan has one.

  A planned run that can't be read is no reason to hide the plans: they are listed without it, and the daemon's log names the store's code. A configuration the daemon can't use is refused with its `config-*` code (503), as the bullet on such a configuration below says.

  One plan is read, created, changed and deleted for a session only (decision 96; the API tokens' scopes don't reach these routes, decision 93). `GET /api/v1/plans/{id}` answers the plan's table in the file's keys, each default left out, hook commands as the file's text (I4). `POST /api/v1/plans` adds the plan the body holds after the last one (201), `PUT /api/v1/plans/{id}` puts it in that plan's place (200; another `id` in the body is refused at `id`, since renaming is #425), and each answers the plan as saved; `DELETE /api/v1/plans/{id}` answers 204 and leaves the plan's snapshots in the repository (I6).

  A refusal saves nothing: a body that is not a plan's table is `invalid-body` (400); a plan the file wouldn't load is `plan-invalid` (422) with the `field` at fault, as its key in the plan's table (`schedule.cron`), and the `problem`; a plan the configuration doesn't hold is `plan-unknown` (404) with the `plan`; deleting a plan a notification rule names is `plan-in-use` (409) with the `plan` and the `rule`; a configuration that can't be read or written is its `config-*` code (503). None holds a value of the plan.

  The start page lists them, with each next run in the reader's own time zone; the operations page offers a start button for each.

  Without plans, the start page says to connect a repository first, since a plan backs up to one by name, and links to the Repositories page; it always links to where a plan's format is described, §6.1 at the tag of the build's release on GitHub, so a build from `main` between releases links to the previous release's text (`routes::PLAN_FORMAT_URL`, #477).
- **Full Disk Access API** (§16, decision 115). `GET /api/v1/full-disk-access` answers `{"state": …, "opens-settings": …}`: what the agent's Full Disk Access probe found last (`granted`, `missing`, `unknown`, or `not-applicable` off macOS), and whether this browser may ask for System Settings, which only a request from a loopback peer that names a loopback host may, on macOS. `POST /api/v1/full-disk-access/check` takes the empty JSON body `{}`, runs the probe again and answers the same body.

  `POST /api/v1/full-disk-access/settings` takes `{}` too and opens System Settings at the Full Disk Access pane, then shows the daemon's program in Finder, answering `204`: `full-disk-access-not-local` (403) for any other request, and `full-disk-access-settings-unopened` (409 off macOS, 500 when `open` failed, its words in the daemon's log only). The routes take a session only: no API token scope reaches them.

  The start page warns while the state is `missing`: a region named by its heading, "Full Disk Access is missing", with why it matters, the numbered steps, **Open Full Disk Access settings** (the row's Filled Primary) when `opens-settings` is true, and **Check again** (Outlined). A pressed one is busy until the daemon answers, the other unavailable meanwhile. When a check makes the warning go, focus moves to the page's heading.
- **Repositories API.** `GET /api/v1/repositories` answers `{"repositories": […]}`, one row per configured repository in alias order:
  - `alias`.
  - `maintained-here` (whether this agent maintains it, §7.3: `true` only for `maintenance = "local"`; a row without it reads as `false`, so a page offers no maintenance it can't run).
  - `create-offered` (whether the row offers to create the repository, decision 53: `true` while its entry records no `repository-id`, the newest operation of a plan that backs up to it failed `repository-not-found` and none of them ever succeeded, so never while nothing is on record; left out when `false`, and `false` for every row when the operation log can't be read, which the daemon logs at WARN).
  - `repository` and `repo-hot` (where it is, with any password in a URL masked by the domain's `Redactor`).
  - `password`, where the password comes from (`{"source": "inline"}`, or `file` with `path`, `keyring` with `entry`, `env` with `name`, `command` with `program`), never its value (I4).
  - `warnings`, left out when empty: one `{code, args}` per secret written as text in the config (`config-inline-secret`, with `field` naming the setting, such as `password` or `options.secret_access_key`, and `location-secret` for a password in a location, with `field` `repository` or `repo-hot` and `kind` `rclone` for an rclone location, whose credential belongs in rclone's own configuration file, or `url` for any other; locations first, decision 37), which the page writes as a line of text in the password cell.

  `GET /api/v1/repositories/_notes` answers `200 {"notes": […]}`, what the page notes of the machine above its list, each a `{code, args}`: today only `keyring-not-activatable`, while the Linux keyring runs but nothing can start it on demand and a repository keeps its password in it (§10.2, #923). It has no refusal: an answer the daemon can't get from the session bus, or a configuration it can't read, notes nothing. No API token's scope opens it. The page reads it once, apart from the list, and shows each note as a `role="note"` paragraph with a warning icon beside its words.

  Three routes take `settings` (`repository`, `repo-hot`, `password`, and the three option sets, as in `config.toml`; any other key is `invalid-body`):
  - `POST /api/v1/repositories/_test` opens the repository, saves nothing and answers `200 {id}`.
  - `POST /api/v1/repositories` with `{alias, settings, maintain-here?, keep-in-keyring?}` tests, then saves with the ID it read (`repository-id`, §7.3), with `maintenance = "local"` when `maintain-here` is `true` and with no `maintenance` otherwise (absent is `false`), and answers `201 {id}`.
  - `POST /api/v1/repositories/_init` with `{alias?, settings, keep-in-keyring?}` creates a repository where none exists and answers `201 {id, saved}`, saving it, with its ID and with `maintenance = "local"`, when it has an alias (decision 48).
  - `keep-in-keyring: true` (absent is `false`) keeps an `inline` password in the system keyring entry `ladderback/<alias>` and saves `password-keyring` naming it instead (§10.2, decision 110): after the test when connecting, before the job and after the settings are resolved when creating. It needs an alias and an `inline` password of at most 64 KiB, the most the resolver reads from an entry; anything else is `invalid-body`.

  `POST /api/v1/repositories/{alias}/init`, with any JSON body (the page sends `{}`), creates the repository the configuration already holds under `alias`, as an imported profile leaves one, where its entry says and with the password its entry names, and answers `201 {id}`.
  - It records only the new repository's ID in the entry (`repository-id`), and only while the entry still names the location it was created at, and leaves the rest of it, `maintenance` included, as it was (decision 53).
  - An alias the configuration doesn't hold, or that is no alias, is `repository-unknown` (404, with the `alias`), an entry that already records a `repository-id` is `repository-exists` (409), and any other whose row the list wouldn't mark `create-offered`, nothing on record included, is `create-not-offered` (409, no arguments), all before anything runs. Then, since the log doesn't say where the failure behind the offer happened, Create first asks the engine to open the repository where the entry says now, and initialises only when that fails `repository-not-found`: a repository that opens is `repository-exists`, and any other failure `create-not-offered` (decision 53 §7).

  The two underscore routes cannot collide with `/repositories/{alias}/…`, since an alias is a slug.

  A `password` is `inline` with `value`, `file` with an absolute `path`, `keyring` with `entry` or `env` with `name`; a `command` source is `invalid-body`, because it would be the first route that runs a program, and that belongs behind authentication (§10.1).

  Refusals are typed and carry the engine's own words as an optional `detail`:
  - `invalid-body` (400; so are settings over their caps, a location or an option value of more than 64 KiB as written or an option set of more than 64 options, scheduling-and-config §6.1, #236; nothing runs).
  - `repository-alias-invalid` (422).
  - `repository-alias-taken` (409).
  - `repository-already-configured` (409, with `alias`, the one the configuration already has for the repository at that location or with that ID: a repository has one alias, §7.3; a taken alias is refused first).
  - `repository-exists` (409, with the redacted location).
  - `repository-not-found` (404, no arguments: the job found an empty folder on this machine, local or OpenDAL `fs`, where the repository should be, decision 53).
  - `repository-config-not-found` (404, no arguments, `detail` the engine's words, masked: the engine found no repository config file where it looked, and nothing tells an empty place from one out of reach; Create is never offered for it, decision 112).
  - `credentials-refused` (503, a REST server refused the repository's credentials with 401 or 403, decision 85; with `half`, `cold` or `hot`, the half whose server refused, for a hot/cold repository, decision 112).
  - `repository-path-relative` (422, with the setting, `field`, that names a path on this machine by a relative one, a password file included: scheduling-and-config §6.1; nothing runs; a value both over its cap and relative is refused for its length, as `invalid-body`).
  - The secret and template codes (422): `secret-missing`, `secret-unreadable`, `secret-keyring-unavailable` (a keyring source on Linux with no Secret Service to ask: no session bus, no daemon, or a missing collection or a dismissed unlock prompt, §10.2), `secret-keyring-locked` (a keyring source whose Secret Service says its keyring is locked; the message says how to unlock it, #993, §10.2), `secret-not-text`, `secret-too-large`, `secret-command-failed`, `secret-command-output-open`, `secret-command-timed-out`, `secret-keyring-timed-out` and `secret-file-timed-out` (a keyring or a file that didn't answer within the resolver's limit, with `seconds`, as the command's code; §10.2), `secret-in-process-arguments`, `secret-expansion-too-long`, `secrets-too-large-to-mask` (the secrets a job masks come to more than 256 KiB, with `limit`, §10.2; `field` is the setting where they passed it, the proxy variable such as `HTTPS_PROXY` when the engine counted the daemon's proxy credentials, and is left out when the job's own secrets did), `template-invalid` and `location-too-many-credentials` (an rclone location with more than 16 credentials, §10.2).

    Each comes with the setting (`field`) and, for a source, where it is read from (`source`), and for the platform's or a command's words a `detail` with every secret of the repository masked (I4); the snapshot listing answers with the same codes and logs the code and that detail.
  - The keyring codes (422, with the `entry`, `service/name`; nothing is saved or created; `keep-in-keyring` only, §10.2): `keyring-unavailable` (no keyring service to keep the password in), `keyring-unwritable` (the keyring refused it, failed or didn't answer within the resolver's limit) and `keyring-entry-taken` (the entry holds another secret, which is never overwritten). The first two carry the platform's words as `detail`, with every secret of the repository masked (I4); the form shows all three at the password field.
  - `password-not-accepted` (503, no `detail`: the password opens none of the repository's keys).
  - `credentials-refused` (503, the server refused the login, also when Create would make the repository there).
  - `operation-failed` (422, `detail` is what rustic said).
  - `engine-unavailable` (503).
  - `repository-timed-out` (503).
  - `repository-replaced` (503, the snapshot listing only: the location holds another repository than the ID the configuration recorded).
  - The `config-*` codes (503).

  The snapshot listing and a snapshot's folder read tell a read the engine ran and failed by the code of its failure, as the maintenance routes do, with the same statuses (#637, decision 112): only the engine's own words and an engine that can't run are `engine-unavailable`, the words in the log alone.

  Connecting tests and saves, and Create looks, creates and records the ID, under one lock, so two connections made at the same moment both survive and two Creates of one entry create it once; the lock is the composition root's, and a later writer of the configuration must take it too.

  Each of the three jobs has a deadline of 2 minutes (`REPOSITORY_JOB_BUDGET` in `domain`, a constant, not a setting), counted from the request's start of the job, the engine's start included, and Create's look and its initialisation are a job each, so it holds the lock for at most two deadlines: the use case races the job against a timer on the `Clock` (wall-clock, like every deadline here, so a machine that slept through the time finds it passed on waking) and checks it on every event, so a worker that keeps talking can't hold it off; the events already waiting behind the one that finds the time up are read first, for the result may be one of them.

  When it passes, the job is dropped, which kills the worker and its process group at once, and the request is refused with `repository-timed-out` and saves nothing; the lock is released as the request returns, either way.

  A result that arrives as the time runs out stands, since a repository it created is already there; a creation that was killed may have left part of a repository, and creating again says `repository-exists` only if its config was already written.

  The worker's own start timeout (§4.1) is separate and shorter, and the worker's watchdog (§7.3) is for backups only: neither covers a backend that takes the job and then never answers.
- **Repository locations (decision 80).** A row of a repository reached at several locations carries `locations`, every location in the order a job tries them, the first first, and leaves it out for a repository of one location, which `repository` names: each is `{position, repository, repo-hot?, options?, when?}`, with `position` from 1, the addresses masked as `repository` is, and `options` as `{set, name, reference?}` per option (`set` is `options`, `options-hot` or `options-cold`; `reference` is the value only when it is references alone, such as `${LAN_KEY}`, which say where a secret is and never hold it; a value written in the configuration is never shown, as it may be the secret).

  Its `warnings` add one `location-plain-http-credentials` per location that sends its credentials where an impostor could read them, with `position`, `cause` (`plain-http`, `unchecked-certificate`, `plain-endpoint`, `plain-rclone`, `plain-ftp`) and `rule` (`network` when the location has a rule, which can't tell the network it is meant for from one made to look like it, else `none`), never the address or a credential (security.md §10.6), and `locations` (`one` or `several`), for a repository of one location too; `location-secret` and `config-inline-secret` carry an optional `position` for a location after the first.

  `when` is a location's rule, its alternatives in the order written, each `{network, only?, except?}` (`network` is `wired` or `wifi`; `only` and `except`, the Wi-Fi networks by name as the configuration writes them, are left out when empty), left out for a location with no rule.

  The row's `warnings` also carry the notes about the rules, for any entry with one, a repository of one location included:
  - `location-every-ruled` when every location has a rule.
  - `location-last-ruled-no-retry` with `plan` for each scheduled plan backing up to it that doesn't retry while its last location has a rule.
  - `location-rule-name-unreadable` with `position` for a rule that names Wi-Fi networks while the last read of the name failed (decision 80, point 10).
  - `location-rule-mixed-link` with `ipv4` and `ipv6`, the kinds of link (`wired`, `wifi`, `other`) each family's traffic leaves by, while the link the daemon last read is mixed (decision 80): a rule holds only if it holds for both. The first listing with a rule reads the link once in the background, so the note may show from the next listing on.

  The page shows each alternative in words under its location ("May be tried on a wired network."), then where the location is skipped, a VPN that carries all traffic included, and the notes as the row's other warnings are shown; a Test that skipped a location for its rule says so.

  `POST /api/v1/repositories/{alias}/test`, with any JSON body (the page sends `{}`), probes every location of the saved entry in order, past the one a job would use, each in a worker of its own with only its own secrets, and answers `200 {locations: [{position, address, outcome, source?}]}`: `outcome` is a location outcome code (`used` for one that answers and holds the repository, `silent`, `refused`, `not-a-repository`, `other-repository`, `password-not-accepted`, `secret-unavailable`, or the code of a setting that can't be used, such as `template-invalid`), and `source` names where a secret was looked for (`env LAN_KEY`) or the setting that can't be used, never a value.

  It records nothing: no operation, no repository ID. An entry of one location is tested too, and while it records no repository ID, whatever repository it holds counts as its own.

  An alias the configuration doesn't hold is `repository-unknown` (404, with the `alias`), a body that is not JSON `invalid-body` (400) before anything runs, a repository password that can't be read the secret codes (422), and a configuration the daemon can't use the `config-*` codes (503).
- **Maintenance API.** `GET /api/v1/repositories/{alias}/groups` lists the repository's snapshots by owner, read live through the engine like a snapshot listing (no slot, nothing stored):
  - `plans` (every plan of this agent on the repository, in the configuration's order, with `count` and the newest `snapshots`).
  - `orphaned` (tagged history no plan of this agent owns, with the plans it could be adopted into).
  - `unmanaged` (untagged history by host, label and paths, with the plans whose host, label and sources equal the group's).

  A group lists at most 500 snapshots (`MAX_GROUP_SNAPSHOTS`) and `count` is the real total; no list is built past its cap.

  `POST /api/v1/repositories/{alias}/maintenance/preview` takes the body of a start (`kind`, and for `adopt` the plan `into` and the group `from`) and answers `200` with what the run would do:
  - A `forget` says per plan which snapshots its retention lets go (`total`, `remove` and at most 50 `listed`, `MAX_PREVIEW_SNAPSHOTS`) and what it leaves alone (I6).
  - An `adopt` the snapshots it would rewrite.
  - A `prune` the engine's dry run (`packs-marked`, `packs-deleted`, `packs-recovered`, `bytes-deleted`, and `keep-delete-hours`, I2).
  - A `check` whether it reads data.

  A prune's dry run opens the repository as the prune does: an identify first, so the plan names the repository ID and reads through the repository's cache. The groups and the preview of a forget, an adoption or a prune carry `warnings`, left out when empty: `maintenance-other-hosts` (with `count` and `hosts`, the first five by name) when a repository this agent maintains holds snapshots from other hosts (§7.3); a prune's preview lists the repository's snapshots for it.

  A forget's and an adoption's preview names a `selection` (16 lower-case hex digits: a fingerprint of the exact set of snapshot IDs), and `POST /api/v1/repositories/{alias}/maintenance` takes it: the run is refused with `maintenance-selection-changed` (409) when what it would act on is no longer that set, before the slot is taken and before anything is removed, so what a person reviewed is what a run acts on (I6). Without a `selection` a start selects as it finds the repository. A `selection` on a prune, a check or a preview, a text that is not a selection, and a key the body does not know are `invalid-body` (400).

  Only a repository this agent maintains (`maintenance = "local"`, §7.3) is maintained through these routes: of any other, a preview and a start of every kind, adoption included, are refused with `maintenance-not-owner` (409, with the `alias`) before the engine is reached and before anything is logged, while its groups are still listed (I1).

  Refusals are typed:
  - `repository-unknown`, `plan-unknown`, `maintenance-kind-unknown`, and `repository-not-found` when a read found an empty folder on this machine (local or OpenDAL `fs`) where the repository should be (404, decision 53), `repository-config-not-found` when it found no repository config file (404, with the engine's masked words as `detail`, decision 112), and `credentials-refused` when a REST server refused the repository's credentials (503, decision 85, with the refused `half` of a hot/cold repository).
  - `maintenance-not-owner`, `maintenance-busy` (start only), `maintenance-selection-changed` (409).
  - `retention-keeps-nothing`, `adoption-no-match`, `adoption-ambiguous`, `operation-failed` (422, the last with the engine's own words as `detail`) and the secret and template codes of the Repositories API (422: the same thirteen, with the same arguments and a `detail` masked of every secret of the repository, I4).
  - `repository-read-timed-out` (504: a read, each plan's retention read of a forget included, waits at most `READ_TIMEOUT`, then the worker is stopped).
  - The `engine-*` and `config-*` codes, `protocol-violated`, `deadline-passed` and `repository-replaced` (503, the last when the location holds another repository than the ID the configuration recorded, §7.3).
  - `operation-failed` as 503 too when the operation log fails (with its own words as `detail`), and, with no `detail`, when a hook failed, the repository already exists or a plan's retention policy is not one the engine accepts.

  A preview takes no maintenance slot and writes nothing to the operation log. A snapshot the wire cannot carry is left out of its list and still counted; the groups and previews do not say that a snapshot's paths or tags were cut (the snapshot listing does).

  `PUT /api/v1/repositories/{alias}/maintainer` with `{"maintain-here": …}` turns maintenance of a saved repository from this agent on (`maintenance = "local"`, replacing `hub`) or off (`none`, leaving `hub` as it is), and answers `204`; asking for what the entry already says writes nothing (decision 48). It runs under the configuration's write lock, which a maintenance start holds too while it reads again that this agent maintains the repository and takes its slot (I1). Refusals: `repository-unknown` (404, with the `alias`), `invalid-body` (400), `maintenance-busy` (409, with the `operation`) when it is turned off while a forget, prune, check or adoption of it runs here, the `config-*` codes (503), and `operation-failed` (503, with the log's words as `detail`) when the operation log can't say what runs.
- **A configuration the daemon can't use.** Every route that reads `config.toml` reads it on each request, and a file that can't be read or used is refused as a save of it is (#347; the mapping is scheduling-and-config.md §6.1): `GET /api/v1/plans`, `GET`, `PUT` and `DELETE /api/v1/plans/{id}`, `POST /api/v1/plans`, `GET /api/v1/repositories`, `POST /api/v1/operations`, `GET /api/v1/repositories/{alias}/snapshots`, `…/groups`, `…/maintenance/preview`, `…/maintenance` and `…/maintainer` answer 503 with the same `config-*` code and arguments, so a hand edit with a mistake in it is `config-invalid` with the `file`, the `line` when the reader knows it, and a `detail` that starts with the setting (`repositories.demo.colour`) and never holds a value of the file (I4); a file that can't be read is `config-unavailable` with the `file` and the system's words.

  A snapshot listing the engine can't start is still `engine-unavailable`, by its code alone. A listing, or a read of a snapshot's folder, that ran out of `READ_TIMEOUT` (waiting for its turn included) is `repository-read-timed-out` (504), by its code alone, over HTTP as through MCP.

  The Repositories page says it in the list's place, the Operations page where the plans' buttons would be (and a refused start or cancel above them), and the Snapshots page where the repositories to pick from would be, each in a `role="alert"` paragraph with the daemon's words marked as English (§8.4).
- **API tokens API (§10.1, decision 93).** With sign-in on, the admin's session lists, creates and revokes API tokens; a token never opens these routes (`403 api-token-scope` naming `session`), and with sign-in off each answers `409 sign-in-off`.
  - `GET /api/v1/tokens` answers `{"tokens": […]}`, oldest first: `id`, `label`, `scopes` (`read`, `run`, `preview`, `propose`), `created-at` and `last-used-at` (RFC 3339, `null` for a token never used), never the secret.
  - `POST /api/v1/tokens` with `{"label": …, "scopes": […]}` answers `201` with `{"token": {…as listed}, "secret": "ladderback_<id>_<secret>"}`, the whole token text, this once; refusals are `api-token-label` (400, argument `max`: a label of 1 to 64 characters, not blank, no control characters), `api-token-no-scope` (400), `api-token-limit` (409, argument `limit`: 100 are kept) and `invalid-body` (400, as for an unknown field or scope).
  - `DELETE /api/v1/tokens/{id}` revokes the token and answers `{}`; an ID kept by no token is `api-token-unknown` (404, argument `token`).

  A request with a token is refused `api-token-invalid` (401), `sign-in-wait` (429, with `Retry-After`) or `api-token-scope` (403, argument `scope`) before its route runs (§10.1).

  Each route answers `api-tokens-unavailable` (503) when the admin password or the tokens can't be read or no random bytes can be drawn; the log says which.
- **Proposals API (§16, decision 89; #518).** An API token with the `propose` scope, a session, or any client while sign-in is off proposes configuration changes for a person to confirm, lists and reads proposals and withdraws one. Only a person approves or rejects one, from a session (or any client while sign-in is off), with step-up to approve: no token scope opens those routes. A token sees and withdraws only the proposals it made; a session, or any client while sign-in is off, sees them all.
  - `POST /api/v1/proposals` with `{"changes": […], "rationale": …}` answers `201` with the proposal, `pending`. Each change is `{"kind": "add-plan" | "change-plan", "plan": {…}}`, the plan as its table in the file's keys (as the plan routes take it), or `{"kind": "remove-plan", "plan": "<id>"}`. The changes are checked in order against the configuration as the ones before them leave it, by the configuration's rules and nothing else: no secret is resolved, no command runs and no location is contacted. The proposal records the SHA-256 of `config.toml`'s bytes, read before the check, as the revision it was drafted against.
  - `GET /api/v1/proposals` answers `{"proposals": […]}`, newest first; `GET /api/v1/proposals/{id}` answers one: `id` (12 characters of lower-case base32), `proposed-by` (the token's label as it was then, `null` for no token), `status` (`pending`, `applying`, `applied`, `failed`, `rejected`, `withdrawn`, `expired`, `stale`), `created-at` and `expires-at` (RFC 3339, 48 hours apart), `decided-at` (when a person approved or rejected it, `null` before; a proposal a hand edit sent back to `pending` keeps the time of the approval it stopped), `changes` (as proposed, each plan as the file writes it), `rationale` and `reasons` (a rejection's reason per change, an empty one for a change given none; empty until rejected).
    - The answer to a created proposal also lists its `warnings`, each with its `kind`: `same-sources` (`change`, `plan` and the `other` plan it leaves backing up the same sources) and `glob-never-matches` (`change`, `glob`); the proposal is kept all the same.
    - Reading brings each pending proposal up to date first: `expired` from its expiry on, `stale` once one of its changes no longer applies to the configuration. A plan the daemon saves brings them up to date at once.
  - `POST /api/v1/proposals/{id}/withdraw` withdraws a pending proposal and answers it `withdrawn`.
  - `GET /api/v1/proposals/{id}/review`, a session's only, answers the proposal as the "Pending changes" page shows it: `proposal`, `summary` (a line per change, `adds-plan`, `removes-plan`, or `changes-plan` with the `settings` it changes), `diff` (the unified diff of `config.toml` the changes would write, rebuilt against the file as it is, every secret masked), `revision` (that file's revision keyed with a key the daemon draws each start, never the file's own SHA-256: decision 89, amended 2026-11-16), `diff-hash` (the SHA-256 of `diff`), `changed-since-drafted`, `needs-forget-preview` (a change could delete snapshots, so it is approved only from its forget preview), `rejected` (how many of the proposer's kept proposals were rejected) and `short-id` (the first 6 characters of the ID).
  - `POST /api/v1/proposals/{id}/forget-preview`, a session's only, with no body, answers the forget preview of a pending proposal (decision 89, point 8): `{"repositories": […], "digest": …}`, one per repository its changes touch, in the order they name them, and the digest an approval brings, absent while a repository couldn't be read. The digest binds, per repository, the snapshots whose fate the proposal changes (`forgets-more` and `forgets-less`), nothing else. It reads each repository as a forget's preview does and changes nothing; a proposal no longer pending is `proposal-not-pending`.
    - A repository read is `{"kind": "compared", "repository", "before", "after", "forgets-more", "forgets-less"}`: `before` and `after` what a forget would do under the configuration as it is and as the proposal makes it; `forgets-more` and `forgets-less` the snapshots only `after`, or only `before`, would forget, per plan.
    - A side is `{"kind": "forgets", "plans": […]}`, what it would remove of each plan as a forget's preview lists it (`plan`, `total`, `remove`, `listed`); `{"kind": "keeps-nothing", "plan"}`, a forget refused because that plan's policy keeps nothing; or `{"kind": "not-maintained"}`, where this agent doesn't maintain the repository.
    - A repository not read is `{"kind": "refused", "repository", "error"}`, told as the maintenance routes tell it, each secret of its settings masked.
  - `POST /api/v1/proposals/{id}/approve`, a session's only, with `{"revision": …, "diff-hash": …, "confirmation": …}`: the review's revision and diff hash, and the step-up (the admin password with sign-in on, the short ID or the whole ID with it off). Under the write lock it rebuilds the diff, applies the changes and answers the proposal `applied`; a hand edit made meanwhile is kept and the proposal goes back to `pending` with `proposal-changed`, and a write that fails leaves it `failed`. The apply runs in a task of its own, which a client that hangs up doesn't stop. A saved file the store can't record is still answered `applied`, and the store shows the proposal `applying` until the daemon's next start, which ends every proposal it finds `applying` as `failed`.
    - A proposal that could delete snapshots is approved only with `"forget-digest"`, the forget preview's digest (decision 89, amended 2026-11-17). The revision and diff hash are checked first. Then, without a digest, the approval is refused `proposal-needs-forget-preview`; with one, the daemon reads the preview again under the same write lock, and a digest that isn't the one it reads, or isn't a digest at all, is refused `proposal-forget-preview-changed` (409), the proposal left pending.
  - `POST /api/v1/proposals/{id}/reject`, a session's only, with `{"reasons": […]}`, one per change, each at most 1000 characters, answers the proposal `rejected`.

  Refusals: `invalid-body` (400, as for a plan's table the file can't hold); `proposal-empty` (422); `proposal-invalid` (422, arguments `change`, from 1, `field`, the setting at fault, and `problem`, a plan's problem, `unknown-plan`, `in-use` or `hooks`, never a value: `hooks`, with field `hooks`, for a change that gives a plan hooks other than those it has, removal included, which no proposal may do until approval confirms each command); `proposal-too-large` (422, arguments `what`, `changes` or `rationale`, and `limit`: 50 changes, 4000 characters, the count checked before any change is read); `proposal-limit` (409, argument `limit`: 20 pending per token, and with no token for all such clients together); `proposal-unknown` (404, argument `proposal`, also for a proposal another token made).

  More refusals: `proposal-not-pending` (409, argument `status`); `proposal-changed` (409: the file or the diff is not the one the review showed); `proposal-rate` (429, 30 proposals an hour per proposer) and `proposal-after-rejection` (429, none for 5 minutes after one of the proposer's proposals is rejected), both with the argument `seconds` and `Retry-After`; `proposal-reasons` (422, arguments `problem`, `count` or `too-long`, and `change`, the number of changes or the change whose reason is too long); `step-up-failed` (403), `sign-in-wait` (429) and `sign-in-unavailable` (503), as for a restore; `proposals-unavailable` (503, the log says why); and a configuration that can't be read, as every route that reads it says it.

  An approval of a proposal that could delete snapshots is also refused `proposal-needs-forget-preview` (409, after step-up: the approval brought no forget preview's digest) or `proposal-forget-preview-changed` (409: the forget preview read again after step-up isn't the one the approval brought, or a repository it touches couldn't be read; a `forget-digest` that isn't a digest is refused so before step-up).

  Each status change is a `proposal-changed` event, the proposal's ID and status only. The 200 newest ended proposals are kept as history; keeping a new proposal forgets the oldest beyond them. A kept proposal whose changes can't be read back is answered with none, and a pending one goes stale (or expired, past its expiry).
- **Restart API (decision 94).** For a session only: no token scope opens it (`403 api-token-scope` naming `session`); with sign-in off, anyone may, as on every route.

- **Profile commands** (§6.2).
  - `ladderback import-profile <file.toml> [--repo-name <alias>] [--json]` reads a rustic profile and adds its repository and plans to `config.toml` in one save, and prints what it added.

Notices are warnings on standard error, in the catalog's words; the profile of an export is the only thing on standard output besides the import's summary. A refusal is a typed error on standard error, exits with 1, and changes nothing: an import writes no file, an export prints no profile.

No value is printed or kept, and core dumps and debugger attach are off before the first read (I4).

It is left out for a repository of one location and for an operation that opens none.

### 4.3 Hub

This section decides what the hub adds to what an agent has.

Everything an agent has, plus:

- **Agent registry**: agent ID, identity public key, hostname (unique), version, last seen, online status, clock offset.
- **Aggregated op log.** It receives operation records and summaries from agents. Raw logs stay on the agent and are fetched on demand.
- **Plan registry.** Agents publish their plans (minus secrets), so the hub knows the retention policy for each `ladderback-plan` tag.
- **Repo ownership registry.** It maps each rustic repository ID to its single maintenance owner (I1, §7.3).
- **Maintenance runner** for **hub-managed repos** (§7.3): forget, prune and check, serialized per repo by `OperationStore::try_start` (I7).
- **Downloads.** For hub-managed repos, the hub opens the repository with its own secret and streams `dump` output to the browser. No file contents cross the sync protocol.
- **Notifications** (§11).

Live updates come from one WebSocket per tab carrying `UiEvent` (operation started/progress/finished, agent online/offline). The page fetches initial state over REST. The daemon forwards an operation's warning events to subscribers unchanged, and its progress events as `LiveProgress` shows them (below): coalescing happens once, in the worker (§4.1), and the daemon never re-coalesces.

Progress bars are stateful per key on the way out (`app::progress::LiveProgress`): a page is told of the bar the engine began last that is still open, with its **step** (§3.1), as `operation-progress` with `step`, `current`, `total` and `unit`, what the bar counts: `bytes`, or `count` for a counter or a spinner, and `count` when a daemon older than the field leaves it out (§16, decision 83) (`Begin` publishes 0, `Advance` adds, `Length` sets the total, a title names the step; a change to an older open bar, or a finished bar, publishes nothing), so a page sees current-of-total numbers of one step, not deltas.

The engine adapter maps rustic's text for a bar to the step; the text never leaves it, and a text it doesn't know is no step (§16, decision 82).

How an operation started and how it ended are not the worker's to announce but the run's that records them (decisions 41, 68).
- It publishes one `operation-started` once the log has the write that says the operation is running, with the log's start time, so a page that reads the history on hearing it finds the run there; a maintenance run, whose `start` already wrote it running, publishes it once as it begins its jobs, however many it takes.
- It publishes one `operation-succeeded` or `operation-failed` after its last write to the operation log, from the operation as it ended and after its ending hooks have run, so a page that reads the history on hearing it finds the end there.
- A write the log refused, or gave up on after `SAVE_BOUND` (§9), does not hold either announcement back: the history then shows the operation as the log last had it, and the run's `Finished::recording_errors` holds the write.
- A cancelled operation announces no end, and one cancelled before the log had it running announces no start either; a run of several engine jobs announces once.

A job that is no operation (the repository's ID, a snapshot list, the groups, a preview, initialising a repository) publishes nothing at all, no start, end, progress or warning (#308): the history has no row for it, and a run that reads first keeps none of what its read said.

The events WebSocket answers a client's ping with a pong, so a live page survives an idle network.

**Settled in the live-pages build** (`crates/web/src/backend.rs`, `ws.rs`, `routes.rs`):

- **State model.** Each live page holds its state in one `RwSignal`. The operations page's is `OperationsState`: the history rows (newest first) plus the live progress of a run still going. The initial REST fetch builds it; every `UiEvent` is applied to it by a pure function (`apply`) in the host-tested module, so a missed event cannot be represented wrongly; an event about an operation the state doesn't hold is ignored — the reconnect's re-fetch brings the whole story, never a half-invented row.

  Nor does an event take a row back, whatever order it and a read of the history arrive in: a start moves only a queued row, and progress and warnings reach only a row that has not ended.

  A run that warned on its way to the end becomes `succeeded-with-warnings`, not a plain success. A `failed` event keeps its typed code for rendering through the catalog.
- **Reconnect and merging.** The socket dropping is a failure like any other: after `reconnect_backoff(attempt)` (doubling from 1 s, capped at 30 s) the loop re-fetches the whole history and resumes the stream; a fetch that fails leaves the page in `Phase::Unreachable` and the loop keeps trying, so a daemon that comes back is a page that heals.

  Each stream that opens, the first and every reconnect's, reads the history once more (decision 68): the page hears nothing told before its stream opened, such as the start of a run its first read had queued (#305). The first read does not wait for the stream, and events heard while the later one is out are applied as they come.

  The re-fetched page is `merge`d: the store's page is the truth for what it holds, but a status an event advanced is never regressed (the store can answer with what it held before news the stream has told since, and an end event can beat it when the log lost its final write), and a live row the page doesn't hold yet stays, newest — dropping it would unshow a run the reader is watching.

  At the stage the page's row already has, a run still going keeps its status, start and progress as the events left them and gains the warning codes the store has and the row lacks: mid-run, that is a before-hook's warning (#328) or a secret file other users can read that the run's start met (#386), which no event tells and the run's start write puts in the store; a run's other warnings reach the store only with its end.

  A row the read moves on, from queued to running or from running to ended, takes the store's row and keeps each warning code the page heard that the store lacks. A row names each code once, as the history does (#508), so a code is added only when the row lacks it: the store's first, in the order the first warning of each was recorded, and those only the events told after them.

  A run that ended takes the store's end whole, which has every warning (so `succeeded-with-warnings` where the end event left `succeeded`) and the result an end event doesn't carry; the status's change is no second end, so nothing more is announced.
- **Settle-poll.** A start announces "Backup started." at once, then polls the history until the operation ends (120 s, every 250 ms), merging each page: the first `UiEvent` may lose the race with the announcement, and a cancelled run emits no `UiEvent` at all. A cancel does the same, without an announcement of its own. A poll that runs out of its budget without an end says so politely ("Still waiting for Ladderback to say how the run ended."), so a reader is never left watching a row that quietly stopped moving; the connection's own loop keeps the page healing behind it.
- **Leaving the page (#300).** The connection, its reconnects and re-reads, and every settle-poll last as long as the reader's visit to the page and no longer: the page begins a `visit::Visit` as it is built and ends it as it goes (Leptos's `on_cleanup`), and each of those tasks runs through `Visit::during`, which ends it at its next await, whether it is waiting on the stream, on a read, or out a back-off or a poll's pause.

  The task is dropped there, and the events stream it holds closes with it; a task the end finds ready to go on goes no further, so nothing is applied to a page that is gone, and a settle-poll that ends this way says nothing. Coming back builds the page again, with one stream of its own. A pause is the page's too, and ends with it (§4.5, "Live updates").
- **Announcements.** The end of a run (finished, cancelled, failed — failed assertively) is announced from a status-transition effect over the state, not from the code path that happened to see it, so the events stream and the settle-poll both arrive at exactly one announcement. It names the kind of run that ended ("Check finished.", "Backup finished."), so a check's end is never told as a backup's.
- **Rows (#192).** The first column is Operation, and each of its cells is its row's header (`<th scope="row">`): a backup is named by its plan, a maintenance run, a restore or a download by what ran and the alias of the repository it ran on or read ("Check of demo", "Restore from demo", "Download from demo", #893), or by what ran alone when the log kept no alias ("Restore", for a restore an earlier version logged). Its Cancel button and its progress bar are named the same way ("Cancel the restore from demo", "Restore progress from demo"), and so is the announcement of its end ("Restore finished.").

  The Result column, before Actions, lists what a succeeded run produced (a backup's short snapshot ID, its files, the source it went through, what it added and how long it took; a check's findings; the count a forget, a prune or an adoption reached) and, for a failed run, says first why it failed: its `failure` in the catalog's words, the engine's own marked as English (`lang="en"`, WCAG 3.1.2), as the alert of a refusal says them (#474). It is empty for any other row.

  One item alone, such as a failed run's reason with nothing after it, is said as a sentence, and two or more as a list, one an item (`Said` in `operations.rs`): a list of one is heard as a list and draws a marker that sets nothing apart (#430).

  A placeable in an item (a path, an address, a snapshot's ID: `runs` in `repositories.rs` finds each between the catalog's isolation marks) is a `.placeable`, an inline block that moves to the next line whole rather than breaking where a line runs out ("home-" / "laptop.password"), and breaks inside only when it is wider than the cell, then first after a separator (`address_parts`, a `<wbr>` after each part).

  The table takes its name from the page's heading (`aria-labelledby` the `<h1>`, whose `id` is `page-heading` on every page), not from a caption that said "Operations" again under the heading (#431).

  A run whose choice used one of several locations says so after that, whatever became of the run, a failed one included: "Used location 2 of 2: rest:https://backup.example.net/laptop", the address as the run recorded it with credentials masked (decision 80; the earlier locations and their outcomes are in the summary's `locations`, which no page shows until an operation detail view exists). Each Cancel button names the run it stops.

  A restore's or a download's Result names first the entry of the snapshot it read, whatever became of the run: "Entry /home/docs/notes.md", by its path from the snapshot's top (`/` is the top), as the log keeps it (`entry`, §9): each name as the snapshot's tree shows it (rustic's escaped form undone, its controls made visible), masked of the repository's secrets (I4), and, when longer, cut to at most 1,024 bytes, its end after "…", so the entry's own name stays (#847).

  A backup the schedule started that was refused before it ran (§5) is a failed row like any other: its Started cell is the moment it was refused, the time it was queued, as it never started, and its Result says why as the refusal of a run by hand does: the refusal's code, its arguments, and what a platform or a command said as the detail, masked of the repository's secrets (I4).
- **Re-read on an end.** An end event carries no result, and the run tells of its end only after its last write to the log, so the page reads the history again when an end arrives (`backend::asks_for_a_reread`) and merges it, and the row's Result shows without a reload; a run started elsewhere, which the page did not hold, comes in with it.

  One re-read is out at a time (`backend::Rereads`), across the stream's reconnects too, and the read a stream's opening asks for is one of them: ends and openings that arrive while one is out are owed one more after it, and only one, so no run of reconnects has more than two reads waiting.

  A re-read that gets no history (a refusal, no answer, or none within `backend::REREAD_PATIENCE`, 10 s, after which its fetch is aborted) is tried again after 1, 2 and 4 s, and then left to the next end or the next reconnect's re-fetch.

  Its `@ui` journeys play the daemon, so an end reaches the page after the page is listening, one holds a re-read's answer back while the stream drops and another run ends, and one holds the stream's opening back while a run starts.
- **Sort.** The history arrives newest first; that is the default. The sort button cycles newest → oldest → newest, and each press is announced politely. A first press announces *newest first*, because the page's default is the daemon's order, not the button's. The Started cell carries the raw RFC 3339 instant in its `title`, so the order is testable without the locale's text; the visible text is `DATETIME($when)` through the catalog (`ui-instant`).
- **Starting a plan.** The page has a start button for each plan, named with its plan ("Start backup of demo-home", one message with the plan as its argument), as a row's Cancel is ("Cancel demo-home"). Each is an Outlined Primary `Button` with the Play icon, busy while its start's request runs; a row's Cancel is a Small `Button` of words alone, busy while its cancel's request runs.

  A row's Cancel shows "Cancel" alone (`ui-cancel`), the word its name begins with (2.5.3), so it takes one line in the 8rem Actions column at 1280 px (#430). A reader tabbing through the plans hears which one each button runs (2.4.6, 4.1.2), and the visible label is the name (2.5.3).

  The buttons are one row of actions (`.actions`, drawn only when there is a plan), so each stands apart from the next by the row's gap rather than touching it, and on a small screen with larger text they wrap one under the other (#284).
- **Stable table and rows (#124).** The table is built once, and its rows follow the state in place, so an update to a row never replaces a control a reader has focused (2.4.3). What the page shows (loading, unreachable, empty or the table) and the ids of the rows in the order the sort gives are memos: only a change of those rebuilds the table, and a progress report, a start or an end changes neither.

  A row is keyed by its operation's id and reads each fact it shows through a memo of its own (status, started instant, progress), so an update reaches only the cells it is about; the Cancel button and the progress bar are present or absent by a memo of a boolean, and an ended run loses its button because it is no longer a control.

  The sort order and the header's `aria-sort` follow the sort signal, so a press is answered by the table itself and not by the next update. `StatusBadge` and `Progress` take signals for this. The decisions (`shown`, `ordered`, `progress::percent`, `badge_of`, `OperationsState::row`) are pure and host-tested.

  **Known limit:** a row that changes place (runs joining the history, a sorted view where a run's order changes) is moved in the table, not built again, and keeps its state; a move may still cost a control in that row its focus, and no journey covers a move.

  The shared `Table` (below) gives focus back after a move; this page keeps the limit until it moves onto that component.
- **Stable columns (#194).** The table's columns have fixed widths (`table.operations` in `style.css`, `table-layout: fixed`), so a run that starts, shows its progress and ends changes what its row says, not where the columns are. An automatic table resized every column whenever one cell's content did, and the table jumped as a run started and ended.

  Where the table has at least 48rem (a container query on `.table-frame`, the `<div>` around it: a query on the table itself left its columns as they were), each column but Result is as wide as what it holds needs, in rem so it grows with the text (Operation, Status and Actions 8rem, Started 11rem), and Result takes the rest: 368 px of 928 at 1280 px, where shares gave it 18 % beside an empty Actions column and a finished backup's facts broke inside ("Snapshot" / "ba5cc73e", #430).

  Below that, as at 320 px or with 200 % text on a laptop (the query's rem is the reader's text size), the columns keep fixed shares: Operation 20 %, Status 19 %, Started 22 %, Result 18 %, Actions 21 %.

  The progress bar fills its cell, up to 16rem, rather than setting the cell's width, so a running row neither widens Status nor makes the page scroll sideways at 320 px.

  The sort button follows the Started header's text in a `.sort-header` that wraps: a gap apart on one line when the column has room, below the text when it hasn't, never touching or over it (the shared `Table` lays its header out the same way). A word breaks inside only when it is wider than its column, as on a small screen or with 200 % text.

  A fixed column can't grow to hold its content, so what doesn't fit would run over the next column: the space around the text in this table (a cell's padding and a badge's, `min(0.5rem, 1.25vw)`, and a button's, `min(0.375rem, 1.25vw)` through `--button-padding`, 6 px a side on a wide screen) follows the screen's width rather than the text's size, the Started header's sort button puts its arrow above its label where the two don't fit side by side (`flex-wrap: wrap`), and a Result list's markers sit inside its items (`list-style-position: inside`, no indent), so at 320 px with 200 % text every column still holds one letter of the largest text and nothing leaves its cell.

  Not every word fits whole at 320 px: the headers and a row's longest words need about 350 px beside one another, and the table has 248 px of text room, so the shares favour the operation's name, the sort button and the Cancel button's label.
- **Unreachable and loading.** `Phase::Unreachable` replaces the page's `<h1>` with "Cannot reach Ladderback" (the page is already open in the browser the daemon served, so this is a state of the page, not a navigation). `Phase::Loading` shows "Loading…" until the first answer arrives; the `@ui` loading scenario covers it by delaying every `/api/v1/` answer (the world's `answerDelayMs`, set by a Given that names the seconds), and that scenario is the phase-2 guard-class addition §13 asks for.
- **Journey fixtures.** The `@ui` Givens write a config.toml with one demo plan (two, backing up the same source, where a journey tells plans apart) and a scratch copy of the `demo-repo` fixture repository into the daemon's config dir. Each source file's content is unique to its number, so the repository cannot collapse the backup into one deduplicated chunk and end before the journey can watch it: `small` (10 000 × 2 KiB, about two seconds) ends a run after its Running row has been there to read; `big` (50 000 × 2 KiB, about ten) outlives a cancel or a mid-run reload. Demo data appears only where the daemon isn't the source (loading, empty states); no operation row is ever hardcoded.
- **Scripted daemon.** A journey that must watch a control while updates arrive plays the daemon itself (`ui-tests/support/scripted-daemon.ts`): the history, the plans and the events stream answer as the steps say, so each update reaches the page when a step sends it and the result does not depend on how fast a real backup reports.

  It counts the events streams the page has open and has opened, and its reads of the history, so a journey can tell that a page the reader left stops listening. Only the daemon's answers are played: the page is the real one, and a request the script doesn't answer (a start or a cancel, unless a step has the script queue the backup or accept the cancel itself) goes on to the real daemon.

**Settled in the stats build** (`crates/web/src/stats.rs`, §16 decision 104):

- **Where it is.** On the Snapshots page, the repository picked ends with its stats, under the heading "Stats of demo", after its history, so the page's earlier stops and the navigation are as they were. It shows the last reading kept, as a table named by that heading, a row for each figure with its header (Snapshots, Total size, Stored size and Compression), then when it was read, in the viewer's zone. A repository never read says so ("No stats have been read yet."), and one that stores nothing has no compression to show ("None: the repository stores no data yet."). The stats are looked at again whenever the history is, so a check that ended shows the reading it took.
- **A look that fails.** A look the daemon refuses shows its refusal in an alert, which the next look answered takes away; one that gets no answer leaves the page's heading to say the daemon is out of reach. Either way the section says no more than it knows: what an earlier look told stays, and with none it shows no line rather than "No stats have been read yet." Each look is numbered when it is sent, so one sent before a read was answered never puts its older reading back over the read's.
- **Reading.** **Read the stats now** asks the daemon to read them; it says "Reading the stats…" (polite) while it waits, and then "Stats read." with the new figures, focus staying on the button. A refusal or failure is said assertively in an alert under the button, and the figures shown before stay; a later look leaves that alert until the next read is asked.
- **Figures per locale.** Counts and sizes go through the catalog's `NUMBER` and `size` (§8.4), and compression is a whole percent, so a locale writes each as it writes numbers. The figures are data under the pseudolocales.
- **The API.** `GET /api/v1/repositories/{alias}/stats` answers the last reading kept (`latest`, or none); `POST` reads them now and answers the reading, or refuses: `repository-unknown` (404), a secret's refusal, or `engine-unavailable` (503) for a repository that can't be opened, with nothing kept. Like the listing, a read is refused for nothing that runs on the repository. An API token reads the last reading with its `read` scope, and needs `run` to read them now, which opens the repository as testing it does and keeps a reading (§10.1).

**Settled in the proposals build** (`crates/web/src/proposals.rs` for the decisions, `proposals_page.rs` for the glue; §16 decision 89 and its 2026-11-16 amendment):

- **Where it is.** "Pending changes" (`/proposals`), linked after Plans. Its one heading names the list of the pending proposals, newest first, each a Review button named for the proposal and who proposed it (the API token's label, or no token). The list is keyed by the proposal's ID, so a read again never replaces a focused button; one whose proposal goes while it holds focus hands focus to the heading. With sign-in off the page says that approving there is a convenience, not a safety boundary (point 7).
- **A review.** Review opens the proposal in a section below the list, its heading ("Proposal …") taking focus: what it changes in Ladderback's words (a line per change, and for a changed plan the settings it changes), the AI agent's words apart from them under their own heading, whether the file changed since the proposal was drafted, how many of the proposer's proposals were rejected before, and the masked diff of `config.toml`.
- **Approve and Reject.** Approve takes the step-up field: the admin password with sign-in on, the proposal's short ID with it off. A wrong one is said in the field, cleared first so a second wrong try is said again; any other refusal is the page's alert. A proposal that could delete snapshots offers no Approve and says why (point 8). Reject has a reason field per change, counted from 1; the spaces around a reason are dropped, so a blank field gives that change none. Once applied or rejected, the page says so, reads the list again, closes the section and hands focus to the heading.
- **Their buttons.** Approve and Reject answer one decision, so only Approve, its main action, is the Filled Primary; Reject is Outlined, in a proposal that offers only Reject too, and not in the color of errors, since rejecting deletes nothing. While a request waits, its button is busy and the other, if offered, unavailable, and the page says so beside it.
- **The forget preview.** A proposal that could delete snapshots offers "Show what it would forget", Outlined, busy while the daemon reads the repositories, and unavailable while a rejection waits. Reject stays available while it reads: rejecting deletes nothing and the preview only reads, so a read that can take minutes doesn't hold the decision. Under "What it would forget", each repository's heading, then what retention forgets of each plan now and after the proposal (or why it forgets nothing there), whether the proposal changes nothing it forgets, and a table of the snapshots it would forget only after, then of those it would no longer forget, each plan's captioned. A repository that couldn't be read says why in an alert.
- **Left out, on purpose.** Approving a proposal that could delete snapshots, the count in the navigation, a command's tick, secrets and maintenance claims, and retrying a failed apply: later steps of #518.

### 4.5 Accessibility

Accessibility is designed in from the first screen, not audited in at the end. The target is WCAG 2.2 AA (A1–A6, §0).

**Supported assistive technologies** follow the supported platforms:

- Orca with Firefox on Linux;
- VoiceOver with Safari on macOS;
- keyboard-only use in any current browser. Safari reaches links and buttons with Tab only when "Press Tab to highlight each item" is on, or with Option+Tab; the manual pass uses that setting.

**Structure.**

- **Native HTML first:** `<button>`, `<a>`, `<table>` with `<th scope>`, `<dialog>` opened with `showModal()`, `<details>`, `<time datetime>`. ARIA only where no native element exists, and then following the WAI-ARIA Authoring Practices pattern for that widget. The progress bar is the one exception: a `role="progressbar"`, because a native `<progress>` draws the value it exposes, which is throttled, and can hold neither the step nor the text the bar shows (§16, decision 83).
- **Page skeleton:** landmarks (`header`, `nav`, `main`), exactly one `<h1>`, descriptive headings and labels with no skipped levels (2.4.6), and a "Skip to content" link. Text in another language, such as rustic's verbatim English messages, carries its own `lang` (3.1.2).
- **Route changes** (path navigation): the router updates `document.title` (page, then machine, then "Ladderback") and moves focus to the new page's `<h1>` (`tabindex="-1"`). Screen readers read the focused heading, so the announcer stays silent. Changing filters, sorting or pages updates the URL query without moving focus.
- **Pointer targets:** at least 24 × 24 CSS px (2.5.8). Nothing needs dragging (2.5.7) or works only on hover.
- **Tooltips and popovers** can be dismissed with Escape, stay open while hovered, and stay until dismissed (1.4.13). The `title` attribute never carries information on its own.
- **Sessions** end after **12 hours unused** and after **30 days** however much they are used (§10.1). Only what the reader does counts as use: what the page reads on its own, and its events stream, never keep a session alive.

  **Two minutes before** a session would end unused, the page warns in a dialog that takes focus on its one button, "Stay signed in", which keeps the session; Escape keeps it too, and closing it returns focus to where it was (2.2.1 Timing Adjustable; two minutes leaves a screen reader or a switch user ample time over the 20 seconds 2.2.1 asks for).

  The 30-day end is not warned of: 2.2.1's 20-hour exception covers it, and the warning is skipped when the lifetime ends the session first.

  Expiry never discards unsaved form input: a "Sign in again" dialog opens over the page, which stays as it was, and the request the daemon refused is sent again once signed in. The sign-in form is one "Admin password" field with `autocomplete="current-password"` (paste and password managers work, A5, A6) and the form's error summary; while signed in, the header's line ends with "Sign out", after the navigation.

  Escape closes that dialog without signing in: the requests that waited end with their refusal, which their pages say (Operations where its table goes, never as a daemon it can't reach), and so does a request still on its way then, unless the dialog has opened again meanwhile, when it waits in it; so the dialog never opens again under the reader on its own (#903). The next request the reader asks for that is refused, such as following a link, opens it again; until the page signs in, the reads it sends on its own end with their refusal.

  With sign-in off, **Settings says an admin password set since Ladderback started**, below its heading, as the page opens: "Admin password set. Restart Ladderback to turn sign-in on. The restart section below does it where a service manager runs Ladderback.", or, for a file Ladderback couldn't read, that it is damaged and the password must be set again, in the section below or with `ladderback set-password` (§10.1, decision 70). It is plain text in the page's reading order, not a live region: it comes from the read the page makes as it opens, or from the one it makes once the password is set in Settings, when a polite message says it too.

  **Settings' "Admin password" section** (#617, §10.1) sets the password with sign-in off and changes it in a session; with the daemon unread it is left out. Its form has "New password" and "New password again" (`autocomplete="new-password"`, the first's hint giving the 8-character minimum), and, in a session, "Current password" first (`autocomplete="current-password"`); every field is a password field, which accepts paste and password managers (3.3.8). Its button is "Set the admin password" or "Change the admin password". The page checks only that each field is typed and that the two new passwords agree; the daemon's refusal (too short, too long, a wrong current password, a wait) joins the same error summary, linked to its field.

  A password set in Settings clears the fields, and the section's "no admin password yet" gives way to the restart message above, which the page shows even when its read after the set fails, since the daemon has said the password is set. A changed one ends the page's session, so the sign-in page shows, saying "Admin password changed. Sign in with the new password." under its heading, and signing in returns to Settings. A reader who leaves Settings before the change is answered still gets that sign-in page next: forgetting the session is the page's step, not the section's.

| Skeleton (the still shape of content on its way) | Hidden from a screen reader (`aria-hidden="true"`), with no role and nothing in it to focus, so it is never a stop for Tab. Never a stand-in for words: the caller says the wait in words ("Loading…"), visible, beside it, and marks the region it stands for `aria-busy="true"` until the content arrives; the content then takes its place without moving focus, and nothing announces it (the announcer stays the page's). Still in every motion setting, no shimmer and no pulse: it starts by itself beside content the reader can use, may stay past 5 s on a slow daemon, and nothing on the page could pause it (2.2.2; the skeleton's notes below). Its shape is the content's, from the reader's text, so the page doesn't jump when the content comes. No tone: it is not a status. No size: it is sized from the content it stands for and the reader's text |
| Alert (an inline message about a page's state) | An icon and words, never color alone: the icon, one Lucide shape per tone, is an image (`role="img"`) named for its tone ("Information", "Success", "Warning", "Error"), so a screen reader hears the tone before the words. Not a live region (no `role="alert"`, no `aria-live`) and never a stop for Tab. Dismissible with a `Dismissal`: a Ghost Small icon-only Dismiss button at the line's end, its name shown by a tooltip; Enter, Space or a click tells the page, which takes the alert away, and focus on the button moves to the control the page names (2.4.3). The caller's duties: urgent text said through the announcer's assertive region too; one failure said once; words that say what happened and what to do. Takes `Primary` (information, the default), `Success`, `Warning` and `Error`; no `Secondary` and no `Inherit` (the alert's notes below). No size and no placement: its words are the page's text, on a line of their own |

**Exceptions.** A page that builds its own version of a widget the set has gives the reason in its pull request and lists it here, with where it lives. None is listed yet.

**The shared vocabulary** (§16, decision 108). A shared component takes its color, size, placement and side from one vocabulary, `crates/web/src/variants.rs`, each tone, size and placement a class of `style.css` (DESIGN.md, "Shared Vocabulary"), as each is built or reworked (#776); the spinner was the first to draw with it, the icon the second, the button the third, and the tooltip the first to take a side. As decision 108's amendments allow, it takes a tone and a size only where they mean something: the step-up field, the tooltip, the table and the tabs take neither, each its row saying why.

The badge, and the status badge built on it, draws `Success`, `Warning` and `Error` in their status tones' pairs and keeps its own pairs for `Primary` and `Secondary`, the Loading and Empty pairs (decision 103). A component's row above names any tone it leaves out because it makes no sense there, its default tone where it isn't `Primary`, and any size it draws at lengths other than the shared scale's, with the reason:

- **Tone:** `Primary` (Ladder Blue, `--accent`; the default, unless a component's row names its own, as the icon's does), `Secondary` (`--muted`), `Success`, `Warning` and `Error` (the status hues `--success`, `--warning` and `--error`), and `Inherit` (`currentColor`, for a part inside another component, such as a spinner in a button). A tone's class sets `--tone`, which the component draws with. A tone never carries the meaning alone (1.4.1, A2): the component says it in words or an icon too. Each tone's token is at 4.5:1 on `--bg` and `--surface` in both schemes (`just test-contrast`), and under forced colors every tone draws in the text's own color (`currentColor`, which the mode makes `CanvasText`), so the words tell them apart.
- **Status pair:** a pair of colors for a part tinted in a status tone, its words on its fill, for each of `Success`, `Warning` and `Error` (`StatusTone`, whose `pair()` gives its two utilities): `--success-fg` on `--success-bg`, `--warning-fg` on `--warning-bg` and `--error-fg` on `--error-bg`, a pale fill under dark words in light colors and a deep fill under pale words in dark ones. Every status-tinted part of a shared component draws from these, never a pair of its own. The words are at 4.5:1 on their fill in both schemes, and the Warning and Error fills at least 0.1 apart in OKLab lightness, Error's the further from the page, so the two neighboring hues never read as one (decision 108). Under forced colors the system's colors replace both, as for any text.
- **Size:** `Small`, `Medium`, `Large` and `XLarge`, one scale every component shares: a size's class sets `--size` to 1em, 1.5em, 2em or 3em, which the component draws its length with, so a size grows with the reader's text (1.4.4) and a spinner and an icon of one size line up. A component that needs other lengths may deviate, saying why in its row. No default in the vocabulary: each component picks its own.
- **Placement:** `Inline` (the default: in the line of text, as wide as what it holds), and `Start`, `Center` and `End`, a line of its own with the part at its start, middle or end, in logical properties, so `Start` is the right in a right-to-left page. The class goes on the line, an element of the component's own around its part, never on the part's root: it sets the line's `display`, which a root's own `display` would override (a badge) or which would stretch a boxed root across the line (a button).
- **Side:** where a part that floats beside a control stands (a tooltip, later a popover, #784): `Above` (the default: a note above a control leaves the lines below it, where the reader goes next, in view), `Below`, and `Start` and `End`, before and after the control in the page's direction, so `Start` is the right in a right-to-left page. A part with no room on its side flips to the opposite one, then to the other axis (`End` before `Start`, `Above` before `Below`), and with room on none stands where it overflows least. Not a `Placement`, which aligns a part in its own line. No class: the page measures the control and places the part (`components/tooltip/rules.rs`, `place`).

The gallery's "Shared vocabulary" demo shows every value named in words, each status pair as its name in its words on its fill, and `features/ui/components.feature` checks each tone's color and swatch, each tone but `Inherit` apart from the text around it, `Inherit` following that text inside an outer tone, every tone in the system's text color under forced colors, each status pair's words and fill in light and dark colors, and the placements in both directions.

**Live updates (A3).** `UiEvent`s update the page visually, but only the **announcer** talks to screen readers.

- **Two regions:** a polite `role="status"` and an assertive `role="alert"`. Both sit in the static `index.html`, outside the Leptos mount point, empty and never `display: none`, so they exist before anything is written to them.
- **Polite:** an operation finished, an agent came back. **Assertive:** only a failure that needs the user now, such as a failed restore.
- **Writing:** each message clears the region and sets the text on the next tick, so a repeated message is announced again.
- **Bursts are merged:** the same message within 2 s is said once, and ten agents changing at once become one summary ("3 backups finished, 1 failed").
- **Modal dialogs** make the rest of the page inert, including the regions. While one is open, announcements queue and are spoken when it closes.
- **Progress** is never written to a region. The start and the finish are announced.
- **Focus survives an update (2.4.3).** An update to a row changes text, values and the presence of what it is about; it never rebuilds a control the reader may be on. A control goes only when it stops being one, as a Cancel button does when its run ends. A row's Cancel button or progress bar that goes while it holds focus, its row staying, hands focus to the row's header, which names the run (`components::hand_focus_when_gone`; #438, and for the bar the Progress row above), and the run's end is announced as any other. A row that leaves the page, or a table built again (a change of what the page shows), takes the header with it, and focus then falls to the page.
- **Pause:** the Operations page, the one page that follows the daemon live, has a "Pause live updates" control (2.2.2). While paused, the page stops changing and a banner counts pending changes; the announcer holds what happens by itself and still answers what the reader does. Resuming shows every change at once and says once how many runs ended (decision 65).

**Settled in the first build** (`crates/web/src/announcer.rs` for the timing, `live.rs` for the regions):

- **Where it lives:** the timing is pure logic over an injected clock in a module of the `web` binary, so `cargo nextest run -p web` runs its tests on the host; the glue that writes the regions and owns the one timer is `live.rs`. The regions in `index.html` carry `role`, `aria-live` and `aria-atomic="true"`, are visually hidden with a class and never `display: none`, and the app mounts into `#app` beside them.
- **Merge window:** 2 s, from the first polite message, not the last, so a steady trickle cannot postpone the write for ever. The messages in it are joined with a space in arrival order (catalog messages are whole sentences) and a text already in the batch is said once. A page that wants a summary ("3 backups finished, 1 failed") builds it and sends it as one message; the announcer only merges. At most 16 messages are held for one write, so a modal left open cannot grow the queue without bound.
- **Write, clear, then set:** the region is cleared when the window closes and set 50 ms later. A message for a region that is still waiting to be set joins that set. Blank text and progress updates are ignored.
- **Modal dialogs:** opens are counted, so nested modals hold messages until the last one closes. Closing flushes everything held at once, without a new 2 s window, assertive first. A close with no modal open is ignored. A polite message sent inside an open window and held by a modal joins the same batch. A write already waiting for its tick when a modal opens is made after it closes. A page that unmounts a dialog while it is open (a route change) must tell the announcer it closed, because a removed `<dialog>` raises no `close` event.
- **Assertive messages wait for a modal too:** the design's "announcements queue" covers them, and it is the behaviour that works. A modal makes the rest of the page inert, and VoiceOver and JAWS say nothing for a live region in inert content (w3c/aria#1854), so an assertive message let through would be lost, and it is the urgent one.

  They skip the merge window; two for the same region that arrive within the 50 ms before the first is set, or while a modal is open, are joined into one set. The same limit of 16 holds per region.

  A failure that happens inside a dialog belongs in a `role="alert"` inside that dialog (the Dialog contract above), which needs no announcer. Moving the regions into the open dialog instead was left out: it needs a design change, and the real Dialog component is the place to revisit it.
- **Route changes:** `document.title` follows the path. An unknown path is the not-found page, with its own `<h1>`, and so is `/_gallery` in a build without the gallery. Each page's `<h1>` takes focus when it is shown after a navigation. The page load itself leaves focus at the top, where the skip link is, unless the address names a section by its fragment, as Settings' Language section does when it loads the page again after a save (`/settings#language`): that section's `<h2>` (`tabindex="-1"`) then takes focus once, as it is shown, so a keyboard or screen reader user is not dropped at the top (`page::focus_when_named`).
- **The skip link handles its own activation:** its click handler moves focus to `<main>` and stops the click. Left alone, the router takes the click on `#main` and only scrolls to it, so focus stays where it was. The router ignores a click that something else has already stopped, so it needs no option, and the address and the history stay as they were (a `rel="external"` on the link, tried first, worked too, but called an in-page link external and left a `/#main` entry that Back had to step over).
- **The gallery** is the `gallery` feature of `web`: off by default and off in a release build, which `just architecture` checks. `just web-test` builds the UI with it, and `just test-ui` runs the scenarios against that build.

What a key does in each layout, which tab a press or an arrival newly selects, which tab is the Tab stop, each tab's and panel's `id` and ARIA attributes, the list's name and orientation and whether a panel is a stop of its own are `tabs/rules.rs`'s, decided on the host. The direction the arrows follow in a row is read on each key from the focused tab's computed `direction` (`l10n::Direction::of_computed`, which the tooltip reads its control's with too), so a part of a page set right to left mirrors the keys; a column's keys don't mirror.

  Its `orientation` (#934) is `Orientation::Horizontal`, the default, `Vertical` or `Responsive`. A vertical list stands at the panels' start in a column at most half their width, its words wrapping, on a Slate Note rule at its end, and the selected tab's bar lies on that rule. Responsive tabs are their own inline-size container, and a container query (at least 42rem, in rem so larger text needs more room) draws them as a column, a row below that; the window's width would draw a column in a narrow part of a wide page. The tabs' container takes no width from its content, so a caller gives responsive tabs a width, as a block has. The query repeats the vertical rules, since the tabs' styles stay custom CSS until #931, and a container query can't style its own container, so a `.tabs-layout` box inside the tabs carries them.

  The layout is CSS's alone, so `Tabs` reads it back: a responsive list's computed `flex-direction` sets its `aria-orientation` and its arrow keys, read once it is drawn and whenever the tabs or their list change size (a `ResizeObserver`, let go with the tabs). The size watch reports in the rendering update that draws a new layout, before it is painted, so a key never meets a layout on the screen that the tabs haven't heard of. A change of layout redraws nothing: the selected tab, the focus and every panel stay. A vertical set is a column at every width, its list half of a narrow screen; tabs that must suit one too are `Responsive`.

  It takes its `id` (the start of every tab's and panel's), its name (`TabsName::Label` or `TabsName::LabelledBy`), the tabs and its activation. The tabs are a `TabSet`, a first tab and the rest, so a set without a tab, a `tablist` with nothing to select, can't be built; each tab is its words, what its panel holds (`Holds::Text`, a stop of its own, or `Holds::Controls`, whose first control is the stop) and the panel. Nothing is announced on a switch: the screen reader says the selected tab, and the announcer stays the page's.

  `Manual` is for a panel that costs something to show, such as a read from the daemon, so `Tabs` tells its caller which tab is selected through an optional `selected: RwSignal<usize>`, the tab's index in the set, set once for each change and never for a press on the tab already selected; the caller reads it and loads that panel. It is the tree's own way (`selected`, which follows what the tree selects), and the tabs stay the one owner of the selection, so a caller can't name a tab the set doesn't hold. Words that say how a `Manual` set is chosen go beside it, and `described_by` ties them to the list.

  The selected tab is bold with a 3px Ladder Blue bar on the Slate Note rule, under it in a row and at its end in a column, told by weight and a shape, never color alone (1.4.1). Each tab draws its own stretch of the rule, edge to edge with the next, and the list's rule runs on under the last line, so when the row wraps at 320 px with 200 % text, every tab whole, a tab selected on an earlier line still has its bar over a rule and the tabs beside it their rule. Under forced colors the rule and the bar are `CanvasText`, as the focus ring is, since `Highlight` need not reach 3:1 on `Canvas`; the bar stands apart from the rule by its thickness and from the ring by its place, the weight kept.

- **The spinner** is `Spinner` (`components.rs`), a twelfth component, for a wait for something the page can't show yet: a track and a quarter arc of one SVG circle, stroked in the drawing's color, the arc turning once in 0.9 s, linear. Under forced colors the arc follows the vocabulary's rule, the text's own color whatever the tone, and the track is `GrayText`.   The caller's duties under WCAG 2.2 AA, which the component can't meet for it:

  - **Busy.** The region it stands for carries `aria-busy="true"` until it is filled.
  - **Moving (2.2.2, Pause, Stop, Hide).** Moving content that starts by itself, runs longer than 5 seconds and is shown beside other content needs a way to pause, stop or hide it. A spinner the reader started, one that is over within 5 s, or one that is all the page shows while nothing on it can be used yet (the preload animation W3C counts as essential, which holds only when no reader can do anything meanwhile) needs nothing.

- **The link** is `Link` (`components/link.rs`), for a way to a page of the app or to another site: a native `<a href>`, always underlined, so a link in a line of text is never told by its color alone (1.4.1). Where it goes is parsed once into a `Destination` (`components/link/rules.rs`, decided on the host), never a raw string the component would guess about: a `Route`, a path of this site, starting with one `/` and holding no space or control character (`//host` and `/\host` are other sites), or an `Outside` address, `http` or `https` in any case, with a host. `javascript:`, `data:` and anything else are refused where the page builds the link.
  - *A route* is a plain `<a href>` inside the router, whose location it reads, not the router's `A`. The router takes every same-origin link's press as a route change (the page titled, focus to its `<h1>`, never a reload) and leaves a press with a modifier key, or with another button than the first, to the browser (a new tab or window). `A` sets its own `aria-current` from the path alone, so a link to a page of a list (`/operations?page=2`) would be current on every page of it, and a second `aria-current` would race it. A route is written as the browser keeps it, so the location can match it and it can't leave the site: no empty, `.` or `..` segment and no backslash, plain or percent-encoded; printable ASCII, and a caller percent-encodes what the browser would.
  - *The current page* comes from the router's location, path and query, never a caller's flag that can drift. `Matching::Exact` is current where the path and the query match (an empty query is none, a trailing slash is ignored), for the brand and a page of a list. `Matching::Section` is current on the path or a page below it at a `/`, whatever the query, for the navigation: `/snapshots` on `/snapshots/demo/3f2a`, never on `/snapshots-old`. The router's `A` reads the path alone: it is Section, and with `exact` it is Exact without the query, so the brand's `A exact` at `/` differs from Exact only on `/?query`. A current link has `aria-current="page"` and is bold (The Weight Not Color Rule).
  - *An outside link* has `rel="external noreferrer"` and no `target`. `external` keeps the router off it: an outside address is never routed, even one that turns out to be the app's own, so it is always a page load. `noreferrer`, which implies `noopener`, tells the other site nothing of the page. It opens where the reader is, and the reader's browser offers a new tab. It says it leaves in words and with an icon: "(goes to another site)" (`ui-link-outside`) after its words, out of sight, so its name begins with the words a sighted reader sees (2.5.3), and Lucide's external-link glyph (`Icon`, decorative, `Inherit`, at the text's size) after its words.
  - *The look.* Its tone's color (`--tone`), underlined at a token's thickness (`--link-underline`, never under a pixel), drawn `--link-underline-offset` under the baseline to clear the descenders, with ink skipping, and thicker under the pointer (`--link-underline-hover`); focus keeps the global ring. Under forced colors it is `LinkText`, its underline and icon with it.
  - *Vocabulary.* Tone: `Primary` (Ladder Blue, the default) and `Inherit` (the text around it, still underlined, for a link inside a status sentence or an Alert). No Secondary and no status tone: a link is not a status, and its color would be the only thing that told it apart. No size: a link is the text around it.

  Its color pairs are the contrast gate's link pairs, `--accent` on `--bg` and on `--surface`: 6.70:1 and 6.09:1 in light, 8.76:1 and 7.59:1 in dark. Being underlined, the link needs no 3:1 against the text around it, which only a link told by its color alone does.

  The caller's duties under WCAG 2.2 AA: words that say where it goes, in their sentence or alone (2.4.4); an action is a `Button`, not a link.

  Not taken from daisyUI's link and Flowbite's typography links, the references: an underline only under the pointer, a color per status (Success, Warning and Error links), visited colors (an app's links keep no reading history), links drawn as buttons (a Button that goes somewhere is Button's, or a later decision) and an option to open a new tab.

- **The skeleton** is `Skeleton` (`components/skeleton.rs`), for the still shape of content on its way, standing where the content will. **Beyond the web UI.**

- **Notifications:** every message has a plain-text form (email has a text part). Meaning never depends on color or emoji, and every message says what happened and what to do next.
- **CLI:** color is never the only signal, and `NO_COLOR` is honored. Spinners and redraws are off when output isn't a TTY, or with `--plain`. Every command that reports state has `--json`.
- **CLI output,** as built:
  - *Colour.* `--plain` is a global flag, taken before or after a command's name. It turns off the colour of the daemon's log and of `clap`'s help and usage errors. `clap` colours those while it parses, before the flag has a value, so the raw arguments are scanned for the exact token `--plain`, never after a bare `--`. Without it, `clap` and `env_logger` both ask `anstream`, which reads the environment: a non-empty `NO_COLOR` means none, whatever else is set; a non-empty `CLICOLOR_FORCE` forces colour even into a pipe; `CLICOLOR=0` means none; and otherwise colour needs a terminal. Ladderback's own sentences have none to turn off.
  - *`--json`.* A command that reports state prints one document, as compact JSON on one line of standard output, and nothing on standard error. Its keys are kebab-case and its text is codes and arguments, never a sentence (§8.4), so a script reads the same document in every language. `import-profile` is the only such command: `export-profile` prints a profile, `serve` is the daemon and `worker` speaks the worker protocol, so `clap` refuses `--json` on them with 2.

    An import that saved the profile prints `{"repository": …, "plans": […], "notices": […]}`, with `notices` always there and each notice `{"code": …, "args"?: …}`. Once the command line is understood, every failure is `{"error": {"code": …, "args"?: …, "detail"?: …}}`, the REST API's typed error (`api::ErrorDto`), except one that cannot be a document: the document itself cannot be written.
  - *Statuses,* the same with and without `--json`: 0 when the command did what it was asked, 1 when it refused or could not start, and 2 when the command line was not understood: by `clap`, in its own words before any command runs, leaving standard output empty, or by `serve`, which refuses an `--allowed-host` that no request could match, in the catalog's words (§10.1). The worker is not a command a person runs, and ends with the statuses of §4.1.
  - *Nobody reads.* A pipe has no reader once the program at its other end has ended (`ladderback import-profile nas.toml | head -1`), and `print!` and `eprint!` panic on it (§13.5).

    Commands print through `output::to_stdout` and `output::to_stderr`, which return the failure, and the binary denies `clippy::print_stdout` and `clippy::print_stderr` so that a later `println!` cannot bring the panic back.

    A write that fails because nobody reads ends the command, quietly, with 141: 128 and the number of SIGPIPE, the status a shell shows for a program that a closed pipe killed. That covers the import (its words and its document), the export, `clap`'s help, version and usage errors, and the daemon's startup lines.

    A write that fails for another reason, a full disk say, is said as `cannot write the result: <reason>` on standard error, and the status is 1; `clap`'s own messages are the exception, which say nothing and keep `clap`'s status, as they did when `clap` printed them itself.

    A standard output that is not open at all is no failure: the runtime reopens it as `/dev/null`, so the command prints into the void and ends as it would have. The worker is left as it was: its standard output is the protocol stream, and it already ends with 74 when that stream breaks (§4.1).

### 4.6 MCP server

`ladderback mcp` lets AI agents and scripts drive Ladderback through the [Model Context Protocol](https://modelcontextprotocol.io): newline-delimited JSON-RPC 2.0 over stdio. Stdout carries only protocol messages; logs go to stderr. The MCP SDK (target `rmcp` and its modules, `rmcp::…`) logs at `warn` at most, whatever `RUST_LOG` says, a directive for one of its modules such as `rmcp::service=debug` included: at `debug` it would log every request and result whole, a profile's password with them (I4), and MCP clients keep a server's stderr in their own logs.

**Protocol.** MCP revisions `2025-06-18`, `2025-11-25` and `2026-07-28`. The first two are negotiated in `initialize`; from `2026-07-28` each request names its revision in `_meta` and `server/discover` lists those served. Older revisions are refused, because results rely on `structuredContent` and `outputSchema`, which arrived in `2025-06-18`. A line from the client over 1 MiB is dropped unread and the session goes on: a request in it gets no answer, as its ID was never read, so the client waits until its own timeout. Implemented:

- **Lifecycle:** `initialize`, `notifications/initialized` and `ping` for the revisions that have them, `server/discover` from `2026-07-28`, and shutdown on stdin EOF.
- **Tools:** `tools/list` and `tools/call`.
- **Progress and cancellation:** progress notifications, sent only when a request carries `_meta.progressToken`; `notifications/cancelled` for a pending call.
- **Errors:** a tool that doesn't exist, and a `tools/call` whose params aren't a call's shape (arguments that aren't an object, which the SDK would answer as a missing method), are JSON-RPC error `-32602`. A failure inside a tool is a result with `isError: true` and two text contents. The first is the same `{code, args}` payload the API returns, as JSON (§8.4), unchanged, so a client branches on the code. The second is the catalog's sentence for it (`error-<code>`, with the same arguments and the detail), which tells the AI agent, or the person it relays the refusal to, what to do next. A refusal has no `structuredContent`: clients check it against the tool's `outputSchema` whether the result is an error or not (the official TypeScript SDK throws when it doesn't conform), and a refusal isn't that shape.
- **The sentence's language:** an MCP client sends no `Accept-Language`, so the sentence is in the locale of the environment `ladderback mcp` runs in, found as for the CLI's own messages (`LANGUAGE` ahead of `LC_ALL`, `LC_MESSAGES` or `LANG`, and ignored under `C`; §8.4) once when the session starts, and `en-US` when it asks for none. The sentence holds only what the `{code, args}` and detail beside it already hold, which are redacted where the code is built (I4).
- **Arguments a tool can't take:** an argument the tool needs left out, one it doesn't take, or a value it doesn't take (another type, a negative or fractional number) is the tool's refusal `invalid-arguments`, its `field` naming the argument and its `problem` saying what is wrong: `missing`, `unknown-key` or `invalid`. It never holds the value given, and the tool doesn't run. A refusal rather than a protocol error, because the agent reads a refusal and can call the tool again, while some clients show a protocol error only to the person, or retry the call as it was.
- **Not localized:** tool `title`s and `description`s are fixed English, like API field names (§8.4).

**Placement.** `adapters/mcp` is an inbound adapter beside `http`, with no rule of its own. Its tools call one `Backend` trait defined inside the adapter, with two implementations:

- **In-process:** built in the composition root (`src/composition/mcp_server.rs`) over the handles the router of `serve` reads (`Catalog`, `Operations` and the rest), called directly.
- **Connect:** an HTTP client that depends only on `api`, never on `adapters/http` (§3.2).

A parity contract suite runs every tool both implementations offer against both, so the two modes can't drift; the proposal tools are connect mode's alone (below).

| Mode | Command | What it drives |
|---|---|---|
| **Connect** | `ladderback mcp --connect [URL] [--token-file PATH]` | A running agent, through `/api/v1`, like any other API client. The URL defaults to `http://127.0.0.1:9898`. The token is read from `--token-file`, or else from `mcp-token` in the configuration folder if it is there, and sent as a Bearer token (decision 93), only to `https` or loopback, and never through a proxy. Refused at start, exit 1: a named file that isn't there, a file others can read, and a token over plain HTTP beyond loopback, even with sign-in off (decision 87). Without a token, sign-in on is `sign-in-required`. The server starts even when the daemon isn't up yet, and connects on the first call. A request that changes something whose reply was lost is never resent: the tool reports `daemon-answer-lost`, since whether it took effect is unknown |
| **Headless** | `ladderback mcp --headless` | An in-process agent session wired by the composition root, as `serve` does but without HTTP or the scheduler. Its folders are `serve`'s, with the same overrides (`LADDERBACK_CONFIG_DIR`, `LADDERBACK_DATA_DIR`, `LADDERBACK_CACHE_DIR`, §4.2); it takes no folder flags. It takes the data-dir lock (§9), so a data dir that `serve` or another session has open is refused by that lock and connect mode is the answer. It starts with `serve`'s recovery (decision 40). Operations run only while the session lives: at stdin EOF it stops as `serve` does (decision 92): its workers stop, what runs ends `daemon-shut-down`, and what is queued stays queued for the next `serve` (decision 73). It doesn't catch SIGTERM, so a session ended that way leaves its operations to the next start, as after a crash |
| **Scratch** | `ladderback mcp --scratch` | A headless session in a new mode-0700 folder in the temporary folder (`ladderback-scratch-*`) holding config, data, a password file (mode 0600) and a local repository, seeded with one plan, `scratch`, over procedurally generated files. The session holds the folder's own data-dir lock, taken before the folder gets its name, and deletes the folder on exit. The next scratch session sweeps the folders crashed sessions left: those whose lock it can take, never a link or a folder a live session holds. For demos and for agents testing Ladderback itself |

**Tools.** Each maps onto one use case or read-side query. Results are `structuredContent` built from `api` types, declared by each tool's `outputSchema` and mirrored as JSON text. Output schemas leave out the fields' descriptions, which their names make plain, and give error and warning codes as plain strings, so `tools/list` stays small; tools and their input fields keep their descriptions (decision 95).

**Input schemas.** Some clients turn a tool's input schema into a function declaration of a narrower schema language, so each argument's schema keeps to what all of them take. An optional argument has its one type and is left out of `required`, the form [Gemini's function declarations](https://ai.google.dev/api/generate-content#schema) take: one `type` per field, an OpenAPI 3.0 subset, and Gemini CLI rewrites a type list with null before sending one. It isn't [OpenAI's strict mode](https://developers.openai.com/api/docs/guides/function-calling#strict-mode) form, every field required and null in a type list, which a client opts into. No argument has a `format`, which [strict mode takes on strings only](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas), or a `minimum`, which [Claude's strict tool use refuses](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations): the argument's description says its bounds. The server refuses a value of another type, or a negative or fractional number, as `invalid-arguments`, and clamps a whole number beyond the bounds, as paging does.

**Paging.** Every `list_*` tool takes `limit` and `cursor`, so one call can't flood the client's context. `limit` defaults to 50 and is clamped to 1..200, never refused. A page's `next` is the cursor of the page after it: the key of its last item (a plan's ID, a repository's alias, a snapshot's ID), and for operations the history's own cursor. The server pages the whole list either backend returns, so both modes page alike.

There is deliberately no tool that restores, downloads, applies forget or prune, adopts, approves a proposal, edits config or pairs: each needs a human confirmation or could change what commands run (§10.5). They can be added later only with a confirmation that MCP can carry honestly.

A proposal is not an edit: the web UI's "Pending changes" page is the confirmation, and with sign-in on, approving there needs a browser session with step-up, never a token; with sign-in off, approval is a convenience, not a safety boundary (decision 89). The proposal tools will be offered in connect mode against an agent only, and left out of `tools/list` elsewhere: headless and scratch modes have no web UI to approve in, and plans are view-only from the hub (decision 2). Until #518 lands, every mode offers the same 13 tools, none of them a proposal tool.

**One-shot calls.** `ladderback mcp call TOOL [NAME=VALUE …]` calls tools without a client, through the dispatch `tools/call` uses, so the tools, their checks and their results are the same. With no mode named it connects to `http://127.0.0.1:9898`; `--connect URL` (exactly one address), `--token-file`, `--headless` and `--scratch` are the modes above, and a headless call is refused while `serve` holds the data folder. A `NAME=VALUE` value is read as the type the tool's input schema gives the argument: an integer or `true`/`false` where it is one and written as one, text otherwise, so a wrong value is the tool's own `invalid-arguments`. `--args JSON` gives the arguments as one object instead.

`--script FILE` makes the calls a file holds, one `{"tool", "arguments"}` object to a line, in one session; `-` reads standard input, each call answered before the next line is read, so a run's operation ID can be waited for. A script stops at the first failed call unless `--keep-going`. A line that isn't a call, or is over 1 MiB, is said on stderr by its number, never its text nor a tool it names, and counts as a failed call. A one-shot `wait_operation` has no client to cancel it or to tell its progress: it waits its length.

A headless or scratch session lasts as long as its calls: it ends after the last, and its stop ends a backup still running then, as when a headless session's client leaves. So a `run_plan` given alone on the command line with `--headless` or `--scratch` is refused, exit status 2, before the session starts, rather than reported as a success whose backup the session's end then stops; in a script, a `wait_operation` after it waits for the backup to finish. In connect mode the backup runs on in the daemon.

Each call prints one JSON line on stdout: `{"tool", "ok": true, "result"}`, the result being the call's `structuredContent`, or `{"tool", "ok": false, "error"}`, its `{code, args}`, or the reason as text for a result that couldn't be written as JSON. A refused call also says the catalog's sentence for its refusal on stderr (`ladderback: ` and the sentence), in the CLI's locale, as `import-profile` says a refusal; stdout keeps its JSON lines unchanged, and the sentences come in the order of the calls.

The exit status is 0 when every call worked, 1 when one failed or the session couldn't start, and 2 for a command line that can't be read (an unknown tool, a word that isn't `NAME=VALUE`, an argument given twice, `--args` that isn't an object, an address after `--connect` that isn't one) or a `run_plan` alone in a session of the command's own, before any session starts. It prints JSON lines whatever is asked, so it takes no `--json`, which is refused like any unknown flag. Proposal tools stay connect mode's, as over MCP (decision 95).

**Hub.** M3 drives one agent. Connect mode against a hub, with an `agent` argument on the tools that need one (plan IDs are unique per agent only), arrives with remote control in M9.

**Known limits.** There is no `operation_log` tool: no per-operation log exists, and `get_operation` carries the failure and warnings (decision 95). `list_snapshots` has no tag, path or time filter. `status` sees queued and running operations only among the newest 200, so an older one still queued behind a long run isn't listed. A headless session leaves backups queued before it started, and those still queued when it ends, to the next `serve`. A headless session ended by SIGTERM rather than at EOF leaves what it ran to the next start's recovery. A cursor whose item has gone since (a plan removed, a snapshot forgotten) is `invalid-cursor`: start the list again.

Connect mode reads a whole list, and an operation with all its warnings, within its 8 MiB answer cap, so a repository with tens of thousands of snapshots, or an operation with thousands of long warnings, is `daemon-answer-too-large` from `list_snapshots` and `get_operation`; the end of `wait_operation` answers with the operation's summary instead, its warnings unlisted. Only for an operation's detail does the code name the `operation`, and only then does its message point to the web UI, where the operation can be read. `cancel_operation` and each step of a wait read the operation's summary alone, the history page of one just past its ID, which the cap never reaches.

A profile near its 1 MiB cap can't be previewed through `preview_import`: the call that carries it, written as JSON with the rest of the message, passes the 1 MiB an incoming MCP message may hold, so it is dropped unread (decision 95). In connect mode a request has 30 s to be answered, so listing the snapshots of, testing or previewing a forget of a repository slower than that to read is `daemon-unreachable`, though the daemon may still be reading.

**Testing.** `features/automation/mcp.feature` runs as `@e2e` scenarios. The runner speaks JSON-RPC to `ladderback mcp --scratch`, and to `ladderback mcp --connect` against `ladderback serve --listen 127.0.0.1:0`, reading the chosen port from the `listening on` line on its stderr. Each tool's input and output schemas are checked against example calls. The I4 canary test (§10.2) scans every tool result, including `list_repositories`, `export_profile` and `preview_import` with inline secrets.
