# Decision 104: A repository's stats

**A repository's stats are four figures: how many snapshots it holds, their total size, the size it stores, and what compression saved. They are read when a person asks, on the Snapshots page, and after each check this agent runs, and every reading is kept for a year, so the charts of M6 (#579) can show them over time** (recorded 2026-11-15, §4.1, §4.4, §9; which figures, when they are read and that they are kept decided by the maintainer on #565, 2026-11-14).

## Why

- **Two reads, four figures.** The snapshot count and the total size come from the snapshots (`get_all_snapshots`). The total size is the sum of each snapshot's `total_bytes_processed`: the size of the sources the snapshots hold, added up, so a file kept by ten snapshots counts ten times. It is not restic's `restore-size`, which walks every tree; a snapshot with no summary counts nothing.
- **What is stored, from the index.** The stored size and compression come from the index (`infos_index`): the stored size is the sum of every indexed blob's length in its pack, after compression and encryption; compression is the share of the blobs' raw size it saved, a whole percent rounded down, 0 when nothing was saved and none when nothing is stored. Not the sum of the backups' `data_added_packed`, which counts a shared blob twice and ignores what a prune freed.
- **As rustic counts.** The stored size is what `rustic repoinfo` prints as the total size in packs, and the raw size its total size. Packs marked for deletion (I2) are left out, as rustic leaves them out of its totals. An index entry that two index files hold, which an interrupted prune leaves until the next prune, counts twice here as there: with rustic 0.11.4 on a scratch repository, a copied index file doubled every count.
- **A read, not an operation.** As a listing is (§9), a read asked for takes no I7 slot, writes nothing to the operation log and is refused for nothing that runs on the repository: rustic reads freely while a repository is written, and its lock-free design keeps a read safe then. There is no new kind of operation.
- **After a check, inside its slot.** A check that ends with a result reads the stats before its end is recorded, so no forget or prune of this agent starts meanwhile (I7). A read that fails is noted in the daemon's log and never fails the check. A cancel meanwhile stops only the read: the check ends at once with its own outcome, and nothing is kept.
- **Compression as a whole percent saved.** restic's `stats` shows a compression ratio (raw size over stored size) next to the space saving; Ladderback shows only the share saved, a whole percent, because a percent is one figure a person reads at a glance, and the catalog's arguments carry whole numbers, which a locale formats as its own percent (§8.4).
- **Another host.** rustic has no repository lock, and a read needs no maintenance owner (I1): a repository the hub or another agent maintains is read like any other. A prune another host runs at that moment can't be seen, and the reading may count some entries twice, as rustic's would.
- **Kept a year.** Each reading is a row of `repo_stats` (§9), the repository's alias and ID, the time it was taken and the figures. Saving one drops the alias's readings taken more than 365 days before it, the retention the operations have (§9), so an alias read again keeps a year of readings.
- **The repository the name stands for now.** The last reading is shown only when it was taken of the repository the alias's entry records now: after an alias is removed and saved again for another repository, the old repository's reading is not shown. A reading or an entry that recorded no ID can't be told apart, so it is shown.

Known limits: a reading taken while this agent or another host rewrites index files can count some entries twice, as rustic's `repoinfo` would then; the next reading is right again. The readings of an alias removed and never read again stay until it is. A daemon stop during the read after a check ends that check as it ends every run still going (`daemon-shut-down`, decision 92). The charts themselves are #579.
