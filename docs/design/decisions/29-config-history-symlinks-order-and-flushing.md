# Decision 29: Config history: symlinks, order and flushing

**A save follows a symlinked `config.toml` and writes the file at its end; the history stays beside the link; its order is a number, not the clock** (recorded 2026-11-10, §6.1). The atomic write resolves the link, through any chain of them and to a target that doesn't exist yet, and renames the temporary file over the target in the target's folder, so the link is never replaced. The alternative, refusing to save through a link, would have made the dotfile-manager setup unusable. The history stays in `history/` next to the link, in the config folder, because the target's folder is typically a repository that gets committed and pushed, and a kept version may hold a password. History versions are named `<six-digit number>-<UTC stamp>.toml`, the number counting up from the highest in the folder and ordering them (pruning keeps the 10 highest), so a clock set back can't make a save drop the newest versions; the `history/` folder and the config folder are flushed after a version is written, and a failure to flush fails the keep, so a version reported as kept survives a power loss. Why: a link replaced by a regular file silently cuts the config from the file the user keeps under version control; names that sort by wall-clock time put the newest versions first for deletion after a clock is set back; and an unflushed directory entry can lose the only copy of the old file once it is replaced.
