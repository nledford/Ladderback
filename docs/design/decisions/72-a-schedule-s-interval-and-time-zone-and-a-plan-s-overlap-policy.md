# Decision 72: A schedule's interval and time zone, and a plan's overlap policy

**`config.toml` reads and writes a schedule's `every` and `timezone` and a plan's `overlap`, the keys §5 names: `every` is a length of time from 1 minute to 366 days, a schedule has exactly one of `cron` and `every`, `timezone` is `UTC` or a name in the IANA time zone database, `overlap` is `skip` (the default) or `queue`, and the file stays at `schema = 1`** (recorded 2026-11-12, §6.1; #272). The scheduler (decision 60) needs all three; before, the file had only `cron`, and §6.1 listed the rest as not yet read.

1. **`every` is written as a jitter is.** The same reading of a length of time (`6h`, `90 minutes`, `1d 12h`; a month or a year, which have no fixed length, refused), within the limits decision 60 puts on an `Interval`: at least 1 minute, a cron expression's finest step, and at most 366 days, the cap on a jitter. Text that is no length of time and one out of those limits are both refused as `Value(Interval)` at `plans[N].schedule.every`. A save writes it as the daemon writes a duration (`every = "1h 30m"`).
2. **A schedule has exactly one of `cron` and `every`.** Neither or both is `Cadence(Missing)` or `Cadence(Several)` at the schedule table (`plans[0].schedule`), the way the password sources are judged at the repository (`Password(Missing | Several)`): no key is the wrong one, the table is. A schedule with only a `jitter` or a `timezone` says nothing of when it runs, and is refused rather than read as no schedule.
3. **`timezone` is `UTC` or an IANA name, in any case.** The config adapter looks it up in the system's copy of the time zone database, or the one built in where the system has none (`jiff::tz::db()`), and the zone is kept under the name the database spells it, which is how a save writes it: `europe/berlin` loads as `Europe/Berlin`. `domain` does no I/O, so it doesn't look the name up: `ScheduleZone::new` takes the zone the adapter found, keeps the name it has in the database and refuses a zone with none. A fixed offset (`+02:00`), a POSIX TZ string and the zone the database keeps for "unknown" (`Etc/Unknown`) name no zone and are refused as `Value(TimeZone)` at `plans[N].schedule.timezone`. With no `timezone`, cron runs in the machine's local time (§5). An `every` schedule may name one too; it plays no part there, since an interval is real time (decision 60, item 4).
4. **Two zones are equal when their names match** (`ScheduleZone`). The rules a zone is loaded with depend on which copy of the database was read, and a configuration names the zone, not its rules: a file read on a machine whose database is newer is still the configuration it was, and a save over it changes nothing.
5. **`overlap` is a plan's, not its schedule's.** It is `skip` or `queue`, in lower case, refused otherwise as `Value(Overlap)` at `plans[N].overlap`. It decides what a run that comes due while the plan's last run is still going does (§5): it is about the plan's runs, not when they come due, so it sits beside `schedule`, not in it. `skip` is the default and, like every default, isn't written (§6.1, "Layout of the written file"). The daemon's layout puts `overlap` right after `schedule`; a save that sets `queue` over a file without the key adds it after the plan's last setting, as a save adds any setting (decision 69).
6. **The schema stays at version 1.** New optional keys are a compatible change to `config.toml` (operations.md §12.1): every file version 1 described still loads, and means what it meant. A bump would need a migration that does nothing, and a migrated file is written again in the daemon's layout (§6.1, "A migrated file is written as the current version"), so every hand-written file would lose its comments and layout on the first start of the new build, for no change in meaning. An older build refuses a file that uses the new keys as `UnknownKey`, at the key; downgrades are unsupported (§12.1).

Accepted: the names a machine accepts are those its own database holds, so a file can load on one machine and be refused on another: a name a newer database adds is refused by an older one, and the built-in copy is used only where the system has no database at all, not for a name a partial one lacks; a `timezone` on an `every` schedule is read and written but changes nothing; an older build stops at a file with the new keys rather than ignoring them.

Rejected: `schema = 2` for the new keys (a migration that changes nothing and rewrites every hand-written file); refusing a `timezone` on an `every` schedule (a schedule switched from `cron` to `every` would need its zone removed too, for nothing); comparing zones by their rules (a configuration would differ from itself between two machines); `overlap` in the schedule table (what it decides is how the plan's runs meet, not when they come due); fixed offsets as zones (a zone with a daylight saving time would be written as the half of the year it was set in); a domain type that looks its name up in a database it is handed (the system's database is files on disk, and `domain` has no I/O).
