# Decision 51: What a check's findings are

**A check that ran to its end succeeds, whatever it found, and each finding is one of the operation's warnings** (recorded 2026-11-11, #187). The worker sends each of rustic's findings as a warning with the code of its level, `check-warning` (rustic's `Warn`: something to tidy, such as a pack no index lists) or `check-error` (rustic's `Error`), and rustic's own words as its detail; the result counts them by level. So a check that found anything ends as succeeded-with-warnings, and its findings are kept, masked (I4) and capped (§4.1), wherever an operation's warnings are: the operation log, `GET /operations/{id}` and the page.

A check that found errors is not `Failed`. The design keeps the two apart: [architecture.md §3.1](../architecture.md) has `check.failed` for a check that couldn't run and the `CheckFoundErrors` event, notified as `check.errors`, for one that ran and found errors, and [operations.md](../operations.md) lists both as notification events. Ending a check that found errors as `Failed` would make the two one. The page tells the difference instead: it announces a check that found errors assertively, from the result's error count, and lists what was found, the errors first.

The page and the messages call rustic's `Error` findings errors, not damage, and send the user to the disk or the service the repository is on and to a second check, not to a repair. rustic reports more than damage at that level: a file of the daemon's cache of the repository that it couldn't read or that differs from the repository's, a file the backend failed to read, a pack with no time set, which its prune corrects. Each is a reason to look again, and rustic's own words, at the end of each message, say which it is. Nor do they send the user to `rustic repair`, which rewrites the index or snapshots of a repository this agent maintains (I1, I6). A `check-warning` says that no snapshot's data depends on what it names only when the check found no error: a repository that lost an index file reports its packs as unnamed and its blobs as missing.

The domain has no `CheckFoundErrors` event yet, and the notifications are M2's. The result's `errors` count is kept so that M2 can raise the event from it, without a second reading of the findings.

Findings travel as warnings rather than as a list in the result, so no one message grows with the repository: the Operation already counts every warning and keeps the first 10,000, each cut to 4 KiB. rustic finds the packs to tidy before the damage in the trees, so the worker sends every error first: those an operation keeps hold every error up to the cap, and the page never announces errors over a list with none in it. An older reader reads the two codes as `unknown`, so nothing a 0.1 record or response meant changes.
