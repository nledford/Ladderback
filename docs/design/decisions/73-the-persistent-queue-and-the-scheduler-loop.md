# Decision 73: The persistent queue and the scheduler loop

**A restart runs a queued backup again under its own ID, on the repository it was queued for, built from the configuration of that moment; anything else it held queued ends `daemon-stopped`, and the log says why. One loop in `app` runs the scheduled plans, each in its schedule's time zone, keeps each plan's planned run in the log, and checks for a wake before it starts a run** (recorded 2026-11-12, §5, §9; #274, #195). Amends decision 40, point (1), as that decision foresaw: recovery still ends every *running* operation as `daemon-stopped`, and no longer ends the *queued* ones.

Decided:

1. **Recovery leaves the queue alone.** `OperationStore::recover` ends the running rows and reads the queued ones, oldest first (by ID, a UUIDv7), in one transaction under the write lock, so a crash during it leaves the log as it was. A queued row this build can't read stays queued as it is, and the daemon's log names it by the store's code alone: the store's account of a row repeats what the row holds, which nobody has checked for a value (I4).
2. **The queue runs once the daemon listens.** After `listening on`, a background task (`Background` in `src/composition.rs`) reads the configuration once and hands each queued operation to `RecoverOperations::resume`, oldest first. A backup of a plan the configuration still has, whose plan still backs up to the repository the operation names, runs under its own ID and trigger (`Queued::resumed`: it is in the log already, so it isn't recorded again), with its cancel switch parked before its run starts. Any other queued operation ends `failed` with `daemon-stopped` at that moment, as decision 40 ended them all: a maintenance operation, a backup of a plan the configuration no longer has, a backup whose plan now backs up to another repository, and a backup whose job can't be built (point 3). Each is said in the daemon's log, with the operation's ID, by a code (`QueuedEnd`), never by a refusal's words.
3. **A queued backup whose job can't be built ends `daemon-stopped`, and the log says why:** its repository is gone, or the configuration can't be read. One whose secret is refused, on the repository it was queued for, ends `failed` with the refusal's own code and arguments instead, masked as a refused scheduled run's (§5, #490): one write, announced, and heard by the schedule as any run's end. The configuration counts both ways: the background task's own read fails, and the whole queue ends; the read that builds one backup's job fails, and that backup ends. That read is checked for a changed repository too (point 2), in case the configuration changed between the two reads. Then the scheduler starts, and waits for a configuration it can read.
4. **The scheduler** (`app::schedule::Scheduler`) keeps each scheduled plan's planned run in `schedule_state` (migration 0006) through the `ScheduleStore` port, and sleeps until the first of them, and at most the wake check's 30 s. Each turn it reads the configuration again: a plan first found is planned from the run kept for it before the start, else from now; a plan whose cadence, time zone or jitter changed is planned again from now; a plan no longer scheduled is forgotten. A schedule is read in the time zone it names, else in the machine's local zone (§5, decisions 60 and 72). It checks for a wake before it starts any run that is due, so a run that came due while the machine slept is `NextRun::resume`'s to decide (decision 60, point 5), whichever timer fired first. A due run's AC power condition is checked as it starts (decision 63); the catch-up runs after a wake wait once, all together, for the network. A run that doesn't start is said in the log, never queued. The following run is planned from the moment the due run started or was skipped. The loop reads a plan's `overlap` with the rest of its configuration (decision 72) and doesn't apply it: a due run starts whatever is running, until the overlap policy and the limit on concurrent runs are built (#276).
5. **Jitter comes from the `Random` port** (§3.2), the one the sign-in work needs too: the branch that merges second adds its method to the port rather than a second port.
6. **The daemon stops the background task when it stops serving.** A run already started goes on until the runtime drops it, and the next start ends it as `daemon-stopped`; a queued backup not yet handed on stays queued for the next start.

Why:

- **The job is built again, not kept.** A job holds the repository's resolved password, and nothing that holds a secret is ever written down (I4). Building it from the configuration of the restart also runs what the person has configured now: a plan whose sources changed while the daemon was down backs up as it is configured, and a plan that is gone doesn't run.
- **A backup whose plan moved to another repository ends.** The operation names the repository it was queued for, and its history would put a snapshot written elsewhere under that repository. Ended, the history stays true; the plan's next scheduled run backs up to the repository it names now. An operation queued before its repository's ID was known names none, so it can't be told apart from any, and runs.
- **Maintenance isn't resumed.** The log keeps a maintenance operation's kind and repository, not the request: which snapshots a forget selected, an adopt's source and destination. Running a forget or a prune again without what was asked of it could delete what the person never chose (I2, I6). It ends as before; the person can start it again.
- **A backup that can't be built ends rather than wait.** Left queued, it would show as queued with nothing to run it until the next restart. Ended, the history says it didn't run, and the next scheduled run, or the person, runs the plan again. An unreadable configuration is no exception: the daemon reads it once for the whole queue, and has no later moment at which to try again.
- **The order "wake, then due runs"** makes catch-up off mean skipped whichever of the loop's timers fires first after a sleep; starting a due run before the check would turn a missed run into a run on time.
- **The following run is planned from the start, not from the planned time,** so a run that started late (a slow wake, a long network wait) doesn't leave a run already due behind it.

Cost: a queued backup whose plan was edited while the daemon was down runs the edited plan, unless the edit moved it to another repository; a backup queued before its repository's ID was known runs even then. A cancel that reaches a queued operation before the background task has handed it on answers `operation-not-running`, as for an operation nothing runs; it can be cancelled once it runs.
