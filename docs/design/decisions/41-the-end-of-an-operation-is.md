# Decision 41: The end of an operation is announced from the run

**The run that records an operation announces how it ended, once, after its last write to the operation log; the engine's own end is no news to a page** (recorded 2026-11-10, §4.2, §4.4, §9; #134). The daemon turned the engine's `Succeeded` and `Failed` into `operation-succeeded` and `operation-failed` as the events went by, before the run applied them, ran its ending hooks or wrote the end, so a page that read the history on hearing the news could find the operation still `running`; the reads a maintenance run makes (the repository's ID, the snapshot list) and each job of a forget that needs several announced an end of their own too. Decided: (1) the end event waits for the ending hooks (each up to 5 minutes), because the log's end includes what they warned of, so it can't be written, and so can't be announced, before they have run; until then the page shows the run as running, where it used to show it ended, and a cancel is refused as not running, because the run's cancel switch is dropped when the engine is done, as it always was; (2) a final write the log refuses, or leaves unanswered past `SAVE_BOUND`, is given up on and the end is announced anyway: the history keeps the operation as the log last had it (running), `Finished::recording_errors` holds the refusal, and nothing tells the page (no marker, code or message), so after a restart decision 40's recovery ends such a row as `daemon-stopped` though the run succeeded, a maintenance run's repository keeps its I7 slot until then (a page told the forget ended can be refused the next maintenance run as busy), and a stalled log delays the end event by up to 20 s; (3) a failure the run finds out itself (an engine that exited without a result, a deadline that passed, an event out of order, an engine that can't start or doesn't take its job in time, a before-hook that stops the run) is announced now, where only the engine's own `Failed` was, and a cancelled run still announces nothing; (4) the engine's end for a read (the identify and list reads, a repository test, init or connect) is no longer published as an operation's end, and a forget that runs as several jobs announces once; (5) left as it was: `failure` still words an engine's rejection of a job as `engine-unavailable` and a hook's failure as `operation-failed`, where the log stores `invalid-job-spec` and `hook-failed`; the Operations page doesn't refetch on an end event, and its `merge` never regresses a status an event advanced; `settle` still says "Still waiting…" after 120 s when the final write never lands; start and progress events for reads still publish; a success that only hooks warned about shows as a plain success until the next fetch. Why: a client that is told an operation ended and then reads the history must find the end there. Rejected: announcing at the engine's end and refetching on it (the page would still race the write), and holding the news until the log takes the write however long that takes (a stalled disk would silence the page, and the log never holds a run, §9). Logging a refused write to the log is #135's.
