# Decision 127: What each API token, and an AI agent without one, may do

**Each API token has its own permissions: seven rows, each at no access or at the one level it has (Backups at read, Backup runs at start-and-cancel, Previews at preview, Configuration at propose, Snapshot contents at read, Daemon log at read, Repository check at run). They replace the four scopes, and the daemon checks them per route from one table. Only a signed-in person changes a token's permissions, with the current admin password, and the daemon's log says so. With sign-in off, a request `ladderback mcp` marks as an AI agent's is held to the `[without-token]` table of `config.toml`, with the same rows and the defaults of a new token** (recorded 2026-11-20, §10.1, §10.5; #962). It amends decisions [20](20-mcp-server.md), [89](89-agent-proposed-setup.md) and [93](93-api-tokens.md).

## Why

A scope opened too much at once: `read` gave the names inside every snapshot and the daemon's whole recent log along with the list of plans, so a token that only watches backups could read both. With sign-in off, an AI agent could do everything the API does. A row per kind of access lets a person give a program what its job needs, and the same rows say what an AI agent may do on a machine with no sign-in.

## The decision

- **The rows.** Backups (read): plans, repositories, snapshots, operations, status, the events stream, a plan's profile without its commands. Backup runs (start-and-cancel): start a plan, cancel a backup, test a saved repository and read its stats now, both of which open the repository. Previews (preview): the maintenance previews (forget, prune, check and adoption) and a profile's preview. Configuration (propose): make, read and withdraw its own proposals, and dry-run a draft plan. Snapshot contents (read): the folders inside a snapshot. Daemon log (read): `GET /api/v1/log`. Repository check (run): no route opens it yet; it is there so that a token made today keeps no access to a check a later route offers.
- **One table, and a session's routes stay a session's.** `http_adapter::api_tokens::required_permission` maps each method and path to a row, to any token, or to a session only; a route it doesn't name is a session's. A token without the row is refused `403 api-token-permission`, whose `permission` argument names the row, or `session` (which replaces `api-token-scope` and its `scope` argument).
- **On the wire, every row.** `PermissionsDto` is a map of the seven rows by their kebab names, each `none` or its level; a row left out is `none`, and a level a row doesn't have is `400 invalid-body`. A token is listed with its permissions; one with none at all is refused `api-token-no-permission`.
- **A token asks what it may do.** `GET /api/v1/permissions` answers the asking token's permissions; for a request without a token, the `[without-token]` table when sign-in is off and `ladderback mcp` marked it as an AI agent's, and every row otherwise: a session's request reads every row whatever headers it carries.
- **Changing them takes a person.** `PUT /api/v1/tokens/{id}/permissions`, `{"permissions": {…}, "current-password": …}`, is a session's only, so no token raises its own. The password is checked as a step-up is, a wrong one counting as a failed sign-in (`current-password-wrong`); the answer is the new permissions. When they differ from the ones the token holds, the daemon's log says "API token {id} now has {rows}", and a creation "API token {id} ({label}) created, with {rows}", the label and rows only, never a secret.
- **Upgrading keeps each token's access.** Migration 0017 turns `read` into Backups, Snapshot contents and Daemon log; `run` into Backup runs; `preview` into Previews; `propose` into Configuration. No token gains a route it couldn't reach before.
- **Without a token.** A new token's defaults, and the `[without-token]` table's, are Backups, Backup runs, Previews and Configuration. `config.toml` writes only the rows that differ from them, and every change made elsewhere in the configuration (a plan, a repository, an import, an approved proposal) keeps the table as it was. With sign-in off, a request with the `x-ladderback-ai-agent` header is refused what its rows lack, `403 without-token-permission` naming the row, and a route only a session may use, naming `session`; a request without the header is not held to them, as before. With sign-in on, the table plays no part: a token or a session decides.
- **Snapshot contents covers the files a warning names.** An operation's warning names a file twice, as its item and in the engine's own words. A program without Snapshot contents, a token or an AI agent without one, gets each warning without either: one operation's detail leaves `item` out and `detail` empty, and the events stream sends the warning's `args` empty; its code and phase stay. A migrated `read` token holds Snapshot contents, so it loses nothing.
- **And the files a failure names.** A failure can name a file in its arguments and in the engine's own words, and a restore's operation names the entry it read. A program without Snapshot contents gets a failure as its code alone, as it gets a warning: one operation's detail, the history and the status summary leave the failure's `args` and `detail` out, and the `entry`, and the events stream sends an `operation-failed` event's `args` empty. A session, and a request without the AI-agent header with sign-in off, sees all of it, as before.
- **An open events stream follows its permissions.** The stream asks every 5 s, as a session's does, whether what opened it still has Backups: a token revoked or changed to lack it, or a `[without-token]` table that no longer allows it or can't be read, ends the stream; otherwise it shows from then on what the permissions held now allow.
- **`ladderback mcp` offers what its permissions open** (the step after, #962). It marks every request it sends with the AI-agent header, and `tools/list` gives only the tools its permissions open: in connect mode those `GET /api/v1/permissions` answers, and in a session of its own the `[without-token]` table, which there also holds each call as the daemon holds an AI agent's request, warnings and failures without the files they name included. Permissions it can't read hide no tool, since the daemon, or the session's own check, still refuses what they don't allow. The `[without-token]` table's defaults leave out Snapshot contents, so with sign-in off the folder and search tools (decision 132) wait for a person to open it.
- **And the web UI sets them.** The token form gives each row a group of its own, No access or its level, starting at a new token's defaults, and a token's row lists its permissions. Changing them is a dialog that takes the admin password. A Settings tab of its own, AI agents, sets the `[without-token]` table through `GET` and `PUT /api/v1/settings/without-token`, a person's only: with sign-in on, the admin's session and the current admin password; with sign-in off, any request but an AI agent's, with no password to give.

**Amended by decision 132** (2026-11-20, #953): Snapshot contents also opens the snapshot search (`GET /api/v1/repositories/{alias}/find`), which names what a folder's page names; Backups alone doesn't.

**Amended by [decision 134](134-an-agent-reads-the-log-a-page-at-a-time.md)** (2026-11-20, #957): the MCP tool `read_log` reads `GET /api/v1/log`, so the row Daemon log opens it too, and an AI agent without a token reads the log only where the `[without-token]` table opens that row.
