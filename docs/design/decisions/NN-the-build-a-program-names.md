# Decision NN: The build a program names beside its version

**A program names its build, not only its version: `0.3.0` for a clean build of the commit its release tag `v0.3.0` names, otherwise the version with the short commit as SemVer build metadata, `0.3.0+3f937cf`, and `.dirty` after it when tracked files had uncommitted changes. `build.rs` asks `git`; a packager may name the commit instead, and no `git` gives the plain version, never a failed build. `--version`, the startup log line and the web UI's header say it; the daemon tells a page the build's parts as fields of their own, only with sign-in off or a live session** (recorded 2026-11-14, §3.1, §4.2, §4.5, §7.2, §10.1, §12.1; approved by the maintainer). From #516.

## Why

Every build between two releases said the last release's version: on 2026-11-13 three machines running `main`, most of 0.3.0, all said "Version 0.2.0", and telling them apart took the git log. SemVer's build metadata (SemVer 2.0 §10) is the place for the commit: it is ignored for precedence, so `0.3.0+3f937cf` still compares as `0.3.0`, and a release keeps the plain version people and tools expect.

## Decided

1. **The display rule** (`BuildDto::display`, `crates/api`): the version alone when the commit is unknown, or when the build is a release and clean; otherwise `<version>+<the commit's first 7 hex digits>`, then `.dirty` when tracked files had changes. A dirty build at its release tag is not the release, so it shows `+<commit>.dirty`. Untracked files don't count.
2. **A release is a clean build of the commit the tag `v<version>` names.** A tag of another version doesn't make one; `git tag --points-at HEAD` is asked, so a commit with several tags is a release if one of them is its version's.
3. **How the build is found.** `build.rs` asks `git` about the package's own work tree (`rev-parse`, `tag --points-at`, `--no-optional-locks status --porcelain --untracked-files=no`) and hands the answers to the program as compile-time variables (`src/build_info.rs`). A work tree around the package that isn't its own (a source archive unpacked inside another repository), no `git`, or `git` failing all mean the commit is unknown: the plain version. The script runs again when the commit, a tag, the index or a tracked file changes, so `.dirty` stays right; that costs a rebuild of the program's own crate after an edit to any tracked file, docs included. What the answers mean is `src/build_info/probe.rs`, which the build script compiles and the program's tests test.
4. **A packager names the commit** in `LADDERBACK_BUILD_COMMIT` (7 to 64 hex digits; anything else is a Cargo warning and ignored), which wins over `git`. Such a build is between releases and clean: the variable is for builds between releases. A packager building a release from a source archive, with no `git`, sets nothing and gets the plain version.
5. **The daemon tells a page the parts, not the shown form.** The session answer (`GET /api/v1/session`, and a sign-in's answer) carries `version`, `commit` (`null` when unknown), `dirty` and `release` as fields of their own, so nothing parses `0.3.0+3f937cf`, and the web UI shows `display()` of them. They are told only to a page that may see the pages, with sign-in off or a live session, never to one that has yet to sign in: the build says which fixes a daemon lacks, which a stranger needn't learn (§10.1). The header shows nothing until the daemon has told it.
6. **The web UI shows the daemon's build**, not its own: the page the daemon serves is built with it, and the build that matters is the one running. A tab left open across an update and a restart keeps the old page's code until it is reloaded, and its header names the build the daemon last told it; a notice that offers the reload is [#531](https://github.com/nledford/Ladderback/issues/531).
7. **The release smoke test expects the checkout's build** (`scripts/smoke-release.ts`, `scripts/build-identity.ts`), unless `--version` names one: the nightly and pull request builds (§12.1) name their commit, and a build at a release tag is the plain version.
8. **With the hub,** `Hello.agent_version` (decision 88) carries `display()`, so a mismatch names the exact build.

Left out: `git describe` output (`0.2.0-14-g3f937cf`), which reads as a pre-release and sorts before `0.2.0` in SemVer; the build time, which makes two builds of one commit differ; and the version in the page's own wasm, which can't name the daemon it talks to.
