# Decision 57: Recording the ID of a repository a job opened

**The first job of any kind that opens a saved repository whose entry in `config.toml` records no repository ID has the daemon record the ID it read, as `repository-id` in that entry: one key added to the entry as the person wrote it, every other byte of the file left alone, written only when the result reads back as the configuration with that ID and nothing else changed; an entry edited since the job read it, one that records an ID, or an ID another entry records is left as it is, and every outcome is a line in the daemon's log** (recorded 2026-11-11, §6.1, §7.3; #200, #229). Entries written by 0.1.0, by `import-profile` or by hand record no ID (decision 49), so for them the duplicate check fell back to an identical location, `repository-replaced` never ran, and a row could offer Create (decision 53) for a repository a check had already opened, until the entry was removed and connected again.

1. **When.** Every job that opens a saved repository (a backup, a listing, the reads behind the history view, a check, a forget, a prune, an identify) carries the entry it was made from, as it was read (`ResolveRepository::resolve_saved`), and the engine names the repository it opened when the job starts (`EngineEvent::Started { repository }`). The daemon's engine (`RecordOpened`, around the worker engine) records that ID in the entry when the entry records none. A job that opened the repository and then failed has opened it all the same. An initialisation and a connection record their ID themselves, as before (decisions 49 and 53); a test of settings carries no entry. A maintenance operation that identifies the repository first records it from that job; the jobs after it name the ID and don't try again.
2. **What is recorded.** The rule is the configuration's (`AgentConfig::record_id`): the ID is recorded only while the entry is still the entry the job read, and records no ID. An entry edited, moved, re-imported or removed since is `Changed`: the ID the job read may not be the repository the entry names now, so the next job that opens it records it. An entry that now records the very ID the job opened, and is otherwise as the job read it, was recorded by an earlier job made from the same read (two backups of one repository, say): that is `Recorded`, and nothing is said about it. An ID recorded is never replaced: a location that opens another repository fails `repository-replaced` (§7.3). An ID another entry records is not recorded (`SameRepository`): the two are one repository under two aliases, which `AgentConfig::new` refuses (decision 49), so recording it would make a file the daemon refuses to load.
3. **How it is written: an edit, not a re-render.** Every other save renders the whole file in the daemon's layout (§6.1, "Layout of the written file"), which would drop a person's comments, blank lines and key order for the sake of one key they never asked for. The record adds `repository-id = "…"` to the entry where it is written (`toml_edit`), a `[repositories.<alias>]` table, a quoted alias, an inline table or contiguous dotted keys alike: after the entry's last key, indented as that key's own line is, and in an inline table before its closing brace. A file whose lines end in CRLF gains a line that ends in CRLF, and a byte order mark at its start stays; a file whose lines end both ways is not edited. It then checks the result two ways before it may replace the file: it is the old file with one run of bytes inserted and every other byte as it was, and the store's own load reads it as the configuration with the ID recorded and nothing else changed. Otherwise nothing is written (`NotInPlace`): `Form` for an entry the edit can't reach or that has the key already, a file with mixed line endings, and a file in an older schema version, which the load migrates and only a save writes in the new one; `ReadBack` for a result that fails either check, among them dotted keys of two entries written in turns, which the edit would regroup; `TooLarge` for a result larger than the store reads, so a file close to that size never becomes one the daemon can't load. The old file is kept in `history/` first and the new one written atomically, as every save does, so a crash part-way leaves the old file or the new one. As every save, too, it leaves the file readable by its owner alone (mode 0600) and owned by the daemon's user, and adds a version to the history: after an import of more than ten entries, their first jobs can push every version from before the import out of the ten the history keeps.
4. **One write at a time.** The record holds the daemon's configuration write lock, the lock a connection, an initialisation and a Create hold from reading the configuration to saving it, so none of them undoes the other. A job never waits for it: when another write holds it, the record is skipped (`Busy`) and the next job that opens the repository tries again. Inside the store's own gate, the file's bytes are read again just before the replace, and a file changed since the record read it is left as it is (`ChangedMeanwhile`), so a hand edit made in that time is kept. A hand edit elsewhere in the file made before the record read it is kept as well: the key is added to the file as it is then. What remains is the moment between that last read and the rename, as for every save. A job cancelled while its record is being written lets go of the write lock, though the write itself runs on inside the store's gate; a connection or a Create that takes the lock then can read the file before the record lands and save over it. The ID is lost, and the next job that opens the repository records it.
5. **No lock across processes.** Two daemons can't share a data folder (the data folder's lock), so only another kind of process writes the file beside the daemon: a person's editor, which point 4 covers as far as any write can, and the CLI's `import-profile`, which saves the whole configuration without the daemon's lock. An import at the same moment as a record races as an import does with a connection or a Create today: one of the two writes can be lost, and the history keeps the file each replaced. A lock file both take was not worth a new failure mode for a race no person's timing makes likely.
6. **What the person is told.** A line in the daemon's log for each ID it was given: recorded, or not recorded and why (`Changed`, `SameRepository`, `Form`, `ReadBack`, `TooLarge`, `ChangedMeanwhile`, the lock held, or the file unreadable or unwritable, a read-only file among them), each naming only the entry's alias and the repository ID, neither of which opens the repository (I4), and the store's error, which leaves every value of the file out. `SameRepository` is a warning that names both entries, since only removing one of them ends it; every `NotInPlace` outcome and a file the store can't read or write are warnings too, the rest information. An outcome nothing but a person's edit of the file changes (`SameRepository`, `Form`, `ReadBack`, `TooLarge`) is logged once per entry and outcome while the daemon runs, not at every job that opens the repository; a different one after an edit is logged again, and the rest are logged every time. A record that isn't made changes nothing about the job. No notice in the UI: the file changes only by the key the person would have got by connecting, and the history keeps the file as it was.
7. **Decision 53's gap.** A row offers Create only while its entry records no ID. A repository that any job has opened, a check that no backup has followed included ([#229](https://github.com/nledford/Ladderback/issues/229)), now records one, so its row no longer offers Create when its drive is unplugged and a backup then fails `repository-not-found`. What stays open is an entry whose record could not be made (a read-only file, an entry in a form the edit can't reach): it is offered as before, and its log says why.

Accepted: a file a person wrote changes without their asking, by one key, with the old one in the history, its mode and owner as a save leaves them; a record lost to a race with `import-profile`, to a held lock or to a cancelled job waits for the next job that opens the repository; a lasting reason not to record is logged once a run, so a log that has rotated since no longer says it.

Rejected: a one-off `ladderback` command that records the IDs, which leaves every entry nobody runs it for as it is; leaving it to a reconnect and saying so in the docs, which leaves the gaps above open for everyone who doesn't; recording through the ordinary save, which re-renders the whole file and drops the person's comments and layout; waiting for the write lock in the job, which would hold a backup behind a connection waiting on a slow repository; a lock file shared with `import-profile` (point 5).
