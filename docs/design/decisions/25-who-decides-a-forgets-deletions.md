# Decision 25: Who decides a forget's deletions

**The daemon decides, the worker deletes** (recorded 2026-11-09, §7.3). `RunMaintenance` resolves the alias, runs an `Identify` read each time (the repo ID is never persisted in config), lists snapshots, partitions them (I6), and evaluates each managed plan's retention in-process through the `Retention` port — the real one is `rustic_core`'s `ForgetGroups` behind `adapters/engine`, over one default group, so an exported profile's semantics match a manual forget. The exact snapshot IDs go to the worker, which only calls `delete_snapshots`. A policy that is set and keeps nothing is refused before selection, per plan whose group holds snapshots (`RetentionKeepsNothing`, HTTP 422); an empty policy keeps everything. Manual forget, prune and check share one route, `POST /api/v1/repositories/{alias}/maintenance`, and the I7 slot is taken before the engine runs (`MaintenanceBusy`, HTTP 409). Two §7.3 items were deferred, not decided away: the pre-forget dry run (step 4) is decision 44, and its approval threshold is not built; and unmanaged groups are partitioned by the fixed `(host, label, paths)` key — the repository's `group-by` moves that grouping when adoption lands (step 3), which reads it. Why: retention is policy, so it belongs in the core where I6 lives; the worker stays a thin engine; and refusing keeps-nothing stops a whole plan's history going away by one mis-typed count.
