# Decision 93: API tokens

**An API token, `ladderback_<id>_<secret>`, lets a program other than a browser use `/api/v1` while sign-in is on: it is sent only as `Authorization: Bearer`, checked by the SHA-256 of its secret, and allowed only the routes its scopes open; a route the scope table doesn't name is for a session only. A failed token shares the sign-in waits, and a new admin password revokes every token** (recorded 2026-11-14, §3.1, §9, §10.1; decided by the maintainer on #566). Decision 70 left tokens out; this is how they work. It amends §10.1, which named the prefix `stdg_` and an argon2id hash of the secret.

## Why

- **Only `Authorization: Bearer`, and then only as a token.** A URL lands in logs and browser history, and a cookie is what a session is (I4). A request whose `Authorization` header says `Bearer` is judged as a token request alone: its cookie is ignored, so a request is never half one and half the other. Another scheme (a proxy's `Basic`) is not a token and leaves the request to the session's rules. The events stream's handshake carries the header too.
- **No CSRF token for a token request.** A browser never attaches `Authorization` to another site's request, and a script on another origin can't set it without a CORS preflight the daemon refuses. The request checks (Host, Origin, a JSON body for a changed request) still apply, unchanged and first. The token is checked where the session is, after them and before the body limit, so a token request that is refused is refused before its body is read, as a request without a session is.
- **Two refusals, and neither says which tokens exist.** A missing, malformed or unknown token and a wrong secret are all `401 api-token-invalid`, so an unknown ID can't be told from a wrong secret. A good token on a route its scopes don't open is `403 api-token-scope`, naming the scope the route needs, or `session` for a route only a session may use.
- **Tokens that can't be read are a refusal of their own.** When the admin password, the tokens in the database or the random bytes for a new one can't be had, the token check and the token routes answer `503 api-tokens-unavailable`, and the daemon's log says why. It is neither `sign-in-unavailable`, which says nobody could sign in, nor a `401`, which would tell a program its token is bad when the daemon couldn't look.
- **A failed token is a failed sign-in.** It counts for its client (an IPv4 address, or an IPv6 /64) in the same waits, and a token request during a wait is refused `429 sign-in-wait`, unchecked, with `Retry-After`. A good token does not start the waits over: only the admin password does, so whoever holds a token with one scope can't clear the waits to guess the password. The cost: on loopback a program with a stale token makes the admin's browser wait too; the refusal says why.
- **SHA-256, not argon2id.** The secret is 32 random bytes, so a slow hash adds nothing against guessing, and checking one would cost every request about 19 MiB and a turn at the one-at-a-time gate sign-in uses. Only the digest is kept; it is compared in constant time, after the token is found by its ID.
- **The prefix names the product.** `ladderback_` makes a leaked token easy for a secret scanner to recognise; the ID is 12 characters of lower-case base32 and the secret 43 of unpadded base64url. The secret is shown once, when the token is created.
- **No expiry.** A token lives until it is revoked, and Settings shows when each was last used, so one nobody uses is seen. The last use is written at most once a minute per token, so a busy program doesn't write on every request.
- **Revoking deletes the token.** The next request with it is refused, and an events stream opened with it closes within 5 s, the recheck the session streams use.
- **Sign-in off: no tokens.** The token routes answer `409 sign-in-off`, and an `Authorization` header is ignored: every route is open anyway. Tokens kept from when sign-in was on stay unused until it is on again, under the same password.
- **A new admin password revokes every token, as it ends every session.** Setting the password is how the admin takes back control after a leak, so it can't leave a token alive that a stolen session created. Each token remembers the fingerprint of the password it was created under, and one created under another is refused, and deleted the next time the tokens are listed or one is created; tokens outlive a restart, so the fingerprint is the SHA-256 of the hash's salt, which is the same after a restart, new with every `set-password`, and says nothing of the password.
- **Scopes per route, in one table.** `read` opens every read route and the events stream; `run` starts a plan, tests a saved repository and cancels a running **backup** (the daemon refuses a token's cancel of anything else, §4.6); `preview` opens the maintenance preview. `propose` belongs to the proposal routes of decision 89 and opens nothing yet. Everything else (configuration, maintenance itself, the session, the token routes) is for a session only, and a route missing from the table is too, so a new route is closed to tokens until someone opens it. Scopes don't imply each other. Decision NN since opens reading the session route to `read`: a token is told `signed-out` and the build, never a session.
- **An operation a token started says so.** Its trigger is "API token", with the token's label and ID, never the secret.
- **Bounds.** At most 100 tokens; a label of 1 to 64 characters, required; at least one scope.

Left out: per-repository or per-plan scopes, tokens on the hub, and creating a token from the command line (creation needs a session).
