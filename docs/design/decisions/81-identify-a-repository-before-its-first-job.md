# Decision 81: A job of an entry that records no repository ID runs after an identify

**A daemon job made from a saved entry that records no repository ID first runs an identify of that repository, which records the ID (decision 57), and then runs with the ID it found, so it gets a cache slot and its operation names the repository from its start; an identify that fails ends the job with its reason, and the job never runs without the ID** (recorded 2026-11-12, §4.1, §6.1, §9; #421). An entry written by `import-profile`, by hand or by 0.1.0 records no ID, and decision 57 recorded it only when the job that opened the repository started: too late for that job. The engine keeps a cache by the repository's ID (§4.1), so that job ran with none, reading the whole index and every tree of its parent snapshot from the repository, one request each; and its operation was queued naming no repository and kept naming none. On a real repository of about 895,000 files and 152 GiB behind a REST server, that first backup took 27 min 33 s, and the next one, with the ID recorded and the cache in its slot, 5 min 10 s.

Decided:

1. **Where.** In `app::repositories::RecordOpened`, the decorator around the daemon's engine through which every job runs: a manual, scheduled, retried or resumed backup, a snapshot listing, a maintenance preview or group, a check. One place covers every path, including any added later. The identify runs when the job is handed to the engine, after the before-hooks, so a repository hook that mounts a drive has run first; it runs in the operation's own run, so it never holds up the answer to a request or the scheduler's loop. An identify and an initialisation are not preceded by one: they are how the ID is found, and each records the ID it opened, as before.
2. **What the job runs with.** The ID the identify read, set on the job's repository access. The engine then gives the job a cache slot (§4.1), and the job's own `Started` names the repository. The identify's events are not the job's: the operation's history shows the job alone.
3. **A failed identify.** A repository the identify can't open is one the job couldn't open either, so the job ends as failed with the identify's reason, the code the job's own open would have given (`repository-not-found` for a folder that is not there, say). An identify the engine refuses to start refuses the job with the same error. The job never runs without the ID. An engine that refuses to start the job itself, after a good identify, can't refuse it through `Engine::run`'s error any more, since the run has begun: the refusal ends the job's events, as the reason that error gives (`engine-unavailable`, say). The snapshot listing and the maintenance reads, which answer a refusal otherwise than a failure, read the reason back as the refusal (`TryFrom<FailureReason> for EngineError`), so they answer as the job's own start made them answer before. A start that timed out stays a failure there: a worker that took its job and then sent nothing fails with the same reason, and both answer the two alike.
4. **Stopping.** Stopping the job stops whichever of the two runs: the identify while it runs, the job once it does. Nothing is started after a stop. A stop never waits for the job's start: a cancel stops a job without reading its events again, so a stop that waited for the start would never return, and its operation would stay queued, its place in the run queue taken and a shutdown waiting. A stop that comes while the engine starts the job only marks the run stopped; a job the engine starts after that is stopped before anything it reports is passed on, and a start that is dropped kills its worker, as dropping any job's start does.
5. **The operation names its repository from its start.** `Operation::start_on` names the repository the engine reported opening when the job started, in a target queued without one; a target that names a repository keeps it, since the engine opens only the repository a job names (§7.3). A queued operation of such an entry names none: it holds nothing under I7 (§9), and `Target::is_on` treats a target that names none as on any repository.
6. **Maintenance.** No change: every maintenance start already identifies the repository before it asks the operation log for the repository's slot (`RunMaintenance::assess_with`, §9, "Resolved 2026-11-09"), so its operation always named its repository and I7's guard covered it, in 0.2.0 too. The operations that named no repository were backups, which hold no slot. A scenario keeps it so (`features/maintenance/forget.feature`).
7. **A job without a cache says why.** When the daemon has a cache folder and gives a job that opens a repository no cache slot, its log says why in one line at the info level, with the operation's ID and the job's kind: the job names no repository ID (an identify, an initialisation, a job of a repository a request gave), or none of the repository's slots is free (a look at the slots that fails is logged the same way). A worker that finds the lock of the slot it was given held runs without a cache with no line of its own: the daemon gave it a slot. An engine with no cache folder says so once, when the daemon starts.

Accepted: one more short worker (it reads the repository's config and keys) before each job of such an entry, until the ID is recorded; an entry whose record can't be made (a read-only file, an entry in a form the edit can't reach, decision 57) pays it on every job, and its log says why it isn't recorded. A queued operation of such an entry names no repository until it starts.

Rejected:

- **Identifying before the operation is queued**, in the start route and the scheduler: it holds the request's answer or the scheduler's loop on a worker, runs before the before-hooks a drive may need, and has to be added on every path that queues a job.
- **A cache kept by the repository's location for a job with no ID**: two keys for one repository, a cache the next job (with the ID) doesn't find, and a location a reference changes at each start.
- **An engine test that a backup with no ID gets a cache folder**, as #421 proposed: slots are kept by the ID by design (§4.1), and the app now guarantees the ID, which `record_id.feature` and `cache.feature` test.
