# Decision 42: A maintenance start the client drops, and the writes the log refuses

**A maintenance run is assessed on the request's own future and started on a task nothing drops, so a client that hangs up can't cut the write that takes the repository; and the daemon logs each write the operation log refused, once, at WARN, with its code** (recorded 2026-11-10, §9, I7; #135). Settled: (1) the one call that read, decided and started a run is replaced by two steps of `RunMaintenance`: `assess` makes every decision from reads (the configuration, the secrets, the repository's ID, a forget's or an adoption's listing), stores nothing and takes no slot, so dropping it leaves nothing behind; `start` is the `try_start` that takes the I7 slot and records the run as running. No one-call form is left for a caller to drop by mistake; (2) the route awaits `assess`, then spawns a task that starts the run, parks its cancel switch, answers the route over a one-shot channel, runs the operation to its end and logs how it ended, as the start of a backup already does (the run announces the end to the pages once, after its last write to the log, as decision 41 has it, and the task logs it once, in the daemon's own log), and a task that ends without answering is `Unavailable`; (3) each write the operation log refused during a run (`Finished::recording_errors`) is logged as `operation <id>: a write to the operation log failed (<code>); its history may be incomplete`, at WARN, once for each, with `StoreError::code` (`store-unavailable` or `store-corrupt`) and never the failure's own words, which nobody has checked for a value (I4). Why: a dropped future runs no code, so for the cut that happens, the handler dropped when its client hangs up while `try_start` waits for the log, neither "the caller re-reads the row" nor "the caller ends it as failed" can run, and SQLite may already have committed the start: the row says `running`, holds the repository (I7) and has no runner until the next start's recovery (decision 40). The fix that needs no code after the cut is to not cut the write; the part of the request that can still be cut is the reads, which hold nothing. Rejected: (a) spawning the whole of what that one call did, the reads and the start together: a client that hangs up on a repository that never answers would leave its worker running for up to `READ_TIMEOUT`, and a retrying client would stack them, where today the hang-up stops the worker; (b) a guard that spawns on drop to re-read the row, or to end it as failed: a second owner of the operation, writing the log after the client has gone through the same log that was slow enough to be cut, and one that reports as failed a run nobody gave up on; (c) making the store's write undroppable: the write then completes and the caller still doesn't learn that it did, which is the same row with no runner. Cost: a client that hangs up after the assessment leaves a run it never learned the ID of; it goes on, shows in the history and can be cancelled there, as a backup's start already does and as any response lost after the server accepted the request does. A busy repository is refused by the task, so a client that hung up is not told, and that refused start has no end to log or announce, since no operation began (the identify read in `assess` has already published an `operation-started` for it, which decision 41 left as it was and decision 68 stopped). The refusals that need no slot (an unknown repository, a policy that keeps nothing, an adoption that matches no group) are still made before the log is touched. Tests: `a_maintenance_start_cut_short_at_any_await_point_leaves_the_repository_free` (the composition root) cuts the route at both points its future waits at, each reached whatever the threads do (#172): during its reads, and at the one-shot channel twice, once the start has reached the log, whose write can't commit while a second connection holds the write lock, and once the log has stored it. A start cut at the channel must still be stored as running, and the repository takes another operation after each cut. `crates/adapters/store/tests/cancellation.rs` pins what a cut start leaves in SQLite, and `crates/adapters/store/src/pool_tests.rs` that a start cut after its commit holds the repository.
