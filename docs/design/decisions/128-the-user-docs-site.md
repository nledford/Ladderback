# Decision 128: What builds the user docs site, and from where

**mdBook, at a release the Justfile pins (0.5.4), builds the user docs site from `docs/guide/` where it is: `book.toml` and `SUMMARY.md` live in that folder, and `just docs-site` builds it into `docs/guide/book/`. The design documents stay off the site, and its pages link to them, and to any other file outside `docs/guide/`, on GitHub. A link that doesn't resolve fails the build, and `just lint` runs it. The site meets WCAG 2.2 AA like the product, with mdBook's theme fixed where axe-core found it short, and axe-core checks it on each change. The `Docs site` workflow publishes it from `main` at `https://nledford.github.io/Ladderback/` with GitHub's own Pages actions (#1177, #216).**

## Why

People running Ladderback need guides of their own: the design documents are for contributors. mdBook is Rust tooling, installed as one prebuilt binary with `cargo binstall` like the project's other tools; readers get static pages with search built in and no runtime of ours. Its pages are plain Markdown, so the same files still read well on GitHub, where the README, the released install script's error message and the Containerfile's label already point.

## Decided

- **The version is pinned** (`mdbook_version` in the Justfile): `just setup` installs it, CI reads the same line, and `just docs-site` refuses another release, since another can render pages and anchors differently.
- **In place, not moved.** The guide's pages stay in `docs/guide/`: `crates/adapters/config/tests/guide.rs` reads them, and every released `install.sh` carries a link to `docs/guide/install.md#by-hand` that a move would break. The maintainer's scope notes on #1177 (2026-11-20) settled this over the earlier `docs/user/` plan.
- **Links:** a link inside the site is relative, and links a folder (`./`) rather than its `README.md`, which mdBook builds as `index.html` but links as a `README.html` it never writes. A link to a design document or any other file outside `docs/guide/` is a full GitHub link to `main`, since the site doesn't publish its target. `scripts/check-site-links.ts` checks both offline, against the files git has: the page or file exists, a page is in `SUMMARY.md`, and an anchor is one of the target's headings, made the way mdBook makes them (GitHub makes the same for the headings the guides use). Links elsewhere aren't fetched.
- **Two parts, by who reads them** (the maintainer, #216, 2026-11-22). `SUMMARY.md` marks them with mdBook's part titles. **Using Ladderback** comes first and is for the casual user of PRODUCT.md, who installs once and does everything else in the web UI: the landing page, installing the recommended way for each system, and Getting started, from a first repository to a test restore and sign-in. Its pages show no `config.toml` and no command beyond installing, starting, updating and removing Ladderback, and link to no design document; what the web UI can't do yet they name as a known limit, not a detour through a terminal. **Advanced** is for people at home in a terminal and rustic users: the other ways to install, the service, `config.toml`, profile import, secrets, remote access and API tokens. Links into `docs/design/` appear only there.
- **Anchors linked from outside the site stay.** A section that moves to another page, such as `install.md`'s "By hand" and "Docker image (not supported yet)", leaves a short section under the same heading that points to its new place, since released scripts, the Containerfile's label and the web UI link those anchors.
- **Accessibility:** axe-core (WCAG 2.2 A and AA rules) is clean on every page in each of mdBook's five themes, at a wide and a narrow window, with the search results and the theme list open, and on a result's page with its matches marked. `docs/guide/theme/` holds the fixes, each with its reason: link, code and search-match colors with too little contrast, links underlined in text, code that wraps rather than scrolls, 24px targets, a skip link, the sidebar toggle made a keyboard-reachable button, and a `<title>` for `toc.html`, the sidebar mdBook frames in each page only when JavaScript is off (`toc.html.hbs`, mdBook's own template with that one line added, #1216).
- **A copied template is checked against mdBook's.** The fixes add files rather than replace mdBook's templates, so a new mdBook keeps them working; `toc.html.hbs` is the one copy, since a page without script can't be fixed by script. `just docs-site` builds the site again without it and fails unless the two `toc.html` files differ by exactly its `<title>` line (`scripts/check-theme-override.ts`), so a pinned mdBook that changes its template, or starts writing a title of its own, can't leave the copy stale. Known limit: the `<iframe>` that frames `toc.html` (in mdBook's `index.hbs`) has no `title`, which only copying all of `index.hbs` would fix; a reader with JavaScript off and a screen reader hears an unnamed frame. rust-lang/mdBook#3274 asks mdBook for both titles, and the copy goes once a release has them.
- **Checked on each change:** `just docs-site-a11y` runs those scans (`ui-tests/scripts/docs-site-a11y.ts`, with the repository's Playwright and `@axe-core/playwright`), and the workflow below runs it on every change to the site, so a violation fails the pull request, or keeps `main`'s build from being published. The scans cover the site as a reader with JavaScript on gets it, and `toc.html` as one without it does: it carries no script, so it takes only the default theme (`default-theme` in `book.toml`), and is scanned in that one.
- **Publishing:** the `Docs site` workflow (`.github/workflows/docs-site.yml`, development.md §13.8) checks the site on a pull request that touches it, and on a push to `main` checks it again, then deploys that build with `actions/configure-pages`, `actions/upload-pages-artifact` and `actions/deploy-pages`. Only its deploy job may write, to Pages alone, and no job name is one the "Protect main" ruleset requires. The repository's Pages source must be "GitHub Actions", which the maintainer sets once before a first manual run from `main`.

## Not decided here

- **Screenshots** regenerated from the `@ui` journeys (#1178), and how the site follows the UI's locales (§8.4); it is English only for now.

## Rejected

- **Moving `docs/guide/` into a new `docs/user/`:** it breaks the released install script's link and the guide's tests for no gain to readers.
- **Zola:** Rust too, but a docs layout, navigation and search come from a third-party theme the project would own.
- **MkDocs Material, Docusaurus, VitePress:** each adds a Python or Node toolchain to the contributor setup for the site alone, and the last two ship a JavaScript application to readers.
- **GitHub's own rendering of `docs/guide/`,** as until now: no navigation between pages, no search, and no landing page beyond a folder listing.
- **A link-check plugin for mdBook:** a second binary to pin and install, where a TypeScript check fits the existing tooling, its `node --test` tests and `just lint`.
