# Decision 53: Creating an imported repository from its row

**A saved repository's row on the Repositories page offers Create once a job found no repository at its location, while its entry records no repository ID and nothing on record has reached the repository, and Create initialises it where its entry says, with the entry's own password reference, recording only the new repository's ID in the entry; a job that finds an empty folder on this machine (a local location or OpenDAL's `fs`) where its repository should be fails with the new code `repository-not-found`, and a Create the row doesn't offer is refused with the new code `create-not-offered`** (recorded 2026-11-11, §4.2, §4.4; #193). An imported profile adds its repository's entry to `config.toml` but doesn't initialise the repository, and the page offered no way to create it short of typing its location and password into the form again.

1. **When a row offers Create.** Only a row whose entry records no repository ID is offered: an entry that records one names a repository Ladderback has opened, since a connection, an initialisation and a Create record the ID they read (decision 49), so it was there whatever the log says. Such a row is marked `create-offered` when the newest operation of a plan that backs up to the repository failed `repository-not-found` and no operation of those plans ever succeeded, with warnings or without. A row with nothing on record is not offered: a folder that isn't there, as on a drive that isn't plugged in, never fails `repository-not-found` (§4), so that failure is the evidence that the location can be reached and holds no repository, and nothing short of it is. A newly imported repository is offered once its first backup finds its folder empty, and one that is already there never is. A connection's test writes no operation, so only a backup's or an adoption's failure counts. A repository a backup once reached and that is gone now is more likely on a drive that isn't plugged in, whose mount point may be an empty folder, than never made, and a Create there would put a new, empty repository in the old one's place; the form still creates it for whoever means to. It reads the entry and the operation log alone, one row per plan and, only for a repository whose newest operation found none, one probe per plan of the partial index `ops_succeeded_by_plan` (migration `0005`), which holds successes alone, so its cost doesn't grow with the plan's failures; it opens no repository and resolves no password to decide. An operation log that can't be read offers Create on no row and is logged at WARN: a row that offers to create a repository that is there would only be refused, but one that hides Create costs nothing the form can't do. Create records the ID, so the row stops offering it once the list is read again; a second Create from a page that wasn't is refused `repository-exists`.

   A success stands in for "reached", and a gap follows from that, accepted. A backup that opened the repository and then failed (a source it couldn't read, its deadline) doesn't count, so a row whose backups all failed, the newest `repository-not-found`, offers Create; a wrong Create there needs the drive unplugged and its mount point an empty folder, for `repository-not-found` is only said of a folder that is there (§4). Decision 57 closes it ([#200](https://github.com/nledford/Ladderback/issues/200)): the daemon records the ID the first time any job opens the repository, a backup that failed after it opened it included, and an entry that records one is never offered. History is read through today's plans, so renaming or deleting a plan forgets what it did, its successes included; that opens no easier way in, for a plan with nothing on record offers nothing, and an offer then needs a job to find the location's folder there and empty, as above.
2. **What Create does.** `POST /api/v1/repositories/{alias}/init` (any JSON body; the page sends `{}`) initialises the repository the configuration holds under the alias, with the entry's location, hot half, options and password reference, and answers 201 with its ID. It records only the new repository's ID in the entry, as an initialisation does (decision 49); the rest of the entry, `maintenance` included, is left as it was: who maintains a saved repository was decided when it was saved (decision 48). It holds the daemon's configuration write lock from reading the entry to recording the ID, as a connection does, so two Creates of one entry at once create it once and refuse the second. The ID is recorded only while the entry still names the location the repository was created at: an entry moved or removed meanwhile, by a hand edit of `config.toml` or the CLI's import, neither of which takes the daemon's lock, records nothing, and Create still answers 201, for the repository was created.
3. **What a refusal says.** Only an alias the configuration doesn't hold is `repository-unknown` (404). An entry that records a repository ID is refused `repository-exists` (409) before anything runs, with the entry's location redacted: the repository was there when the ID was read. Not `repository-already-configured`, which names another alias to use instead, not the one asked for. Any other entry whose row doesn't offer Create (§1), nothing on record included, is refused with the new code `create-not-offered` (409) before anything runs, decided from the log as the list decides it, so a request from a page shown before the log changed, or from no page at all, gets the page's answer. Not `repository-exists`: nothing says a repository is there, only that no job found the location empty; its message says to run a backup first, or check that the drive or location can be reached. An operation log that can't be read refuses it `operation-failed` (503) with the store's words, before anything runs. Every other failure keeps its own code: a configuration that can't be read its `config-*` code; once the entry is found, what the entry's job gives, redacted with the entry's settings (I4): `repository-exists` (409), a secret's code, `repository-not-found` (404), `operation-failed` (422), and the engine's and timeout codes; an ID that can't be recorded afterwards, its `config-*` code. That last leaves the repository created and its entry without an ID, so the row still offers Create and every retry is refused `repository-exists` (409), which is true: it is there. The offer stops once a backup of it succeeds (§1), or once the next job that opens it records the ID (decision 57). The use case reports a lookup that found no entry as its own type, apart from the job's failure, so no failure can be read as an unknown alias.
4. **`repository-not-found` only of a folder on this machine that is there and holds nothing of a repository.** When a repository doesn't open, and only then, the worker looks at its folders: when every half is a folder on this machine (a local location, or OpenDAL's `fs` at its root) that is there and holds nothing of a repository, the job fails `repository-not-found` (no arguments and no detail), and anything else fails with the error opening gave, as before. A repository that opens costs no extra look. A repository folder that isn't there, or isn't a folder, is no answer: it is what an unplugged drive looks like (§1). Nor may a job make one: OpenDAL's `fs` makes its root folder when its backend is set up, so on an unplugged drive the first job would leave an empty folder at the mount point, on the system disk, and the next would find no repository in it and offer Create there. So every job but Create whose `fs` root folder, of either half (`options_cold` or `options_hot` over `options`, as rustic reads them), isn't there fails `operation-failed` before the backends are set up, as a missing local folder fails, and nothing is made; Create still makes it. rustic's local backend makes nothing when it opens (`LocalBackend::new`, `local.rs` L46-71, only reads its options; its `create()` is Create's). Read at rustic rev `01fe284`, unchanged on rustic_core `main` at `d658ed9`, each half is looked at so:
   - the folder is there and is a folder (`fs::metadata`, through symbolic links), and `try_exists()` is `Ok(false)` for each of `config`, `keys`, `data`, `index` and `snapshots` in it; a folder that can't be read (`Err`) is no answer. rustic's own local backend uses `Path::exists()` (`local.rs` L218), which reads a folder that can't be read as empty, so the worker doesn't ask it, and `fs` is the same folder, looked at the same way;
   - a folder holding any of `keys`, `data`, `index` or `snapshots` without `config` is no answer: an initialisation cut short, or a repository that lost its config file. A Create there would mix a new repository's keys and packs into what is left of the old one, so the job fails `operation-failed` and the row never offers Create; what is there is the person's to repair or remove;
   - with a hot half, both halves must be such folders: a hot folder that isn't there is an unplugged drive as much as a cold one.

   Every other backend is no answer, so a missing repository there fails `operation-failed` as before, its row never offers Create, and the form creates it. A missing root on a server or a store (sftp, WebDAV, FTP, S3: every OpenDAL service but `fs`) is the remote form of the unplugged drive: rustic's OpenDAL backend lists no config file wherever the service answers NotFound (`opendal.rs` L604-609), which a server says of a share that isn't mounted or a path that moved as readily as of an empty folder, and a Create would make the root there. rustic's REST backend answers an empty list for any HEAD that isn't a success, a refused password (401) included (`rest.rs` L234-249; since decision 85 a 401 or 403 there fails `credentials-refused` instead), and rclone serves through it. Reported upstream as [rustic-rs/rustic_core#652](https://github.com/rustic-rs/rustic_core/issues/652), the local backend's `exists()` in its Related section.
5. **404, the API's status for what isn't there.** The repository routes and maintenance answer `repository-not-found` with 404, the family of the API's other refusals of something that isn't there (`repository-unknown`, `plan-unknown`, `operation-unknown`), as `repository-exists` is 409. Not 422, `operation-failed`'s: nothing about the request was wrong. Not 503: the daemon could do it, there is nothing to do it to. The web UI's advice to try again stays `operation-failed`'s alone.
6. **On the wire.** `repository-not-found` and `create-not-offered` are new error codes, a compatible change under §12.1 (new codes, not renamed or removed ones): a job that used to fail `operation-failed` at an empty local or OpenDAL `fs` folder now fails `repository-not-found`, and that shows in a REST refusal, the operation history, a webhook and a hook's `LADDERBACK_ERROR`. A client that matched `operation-failed` for that case sees the new code instead. `create-not-offered` is only ever a refusal of `POST /api/v1/repositories/{alias}/init`, which is new here.
7. **Create looks before it creates; the offer is a hint.** The log doesn't say where a job ran. Since decision 52 a maintenance operation records the alias of its repository, and a backup names its plan, but no operation records the repository's location (`Job::target()`), and a location can change under the same alias. So the offer can rest on a failure at another location: the entry's location edited since, the profile re-imported or its plan pointed at another alias, a plan deleted and added again under the same ID. Before Create initialises, it asks the engine to open the repository where the entry says now (`Job::Identify`, the same resolved settings), and initialises only if that fails `repository-not-found`: a folder on this machine that is there and holds nothing of a repository (§4). A repository that opens is refused `repository-exists`; any other failure, a folder that isn't there (an unplugged drive), a path that isn't a folder, a folder holding a repository's keys, packs, index or snapshots without its config file, a REST, rclone or remote OpenDAL location, is refused `create-not-offered` (409), and nothing is made. Remote roots are never offered: a missing root on a server is the remote form of the unplugged drive, and only this machine's file system tells a folder that is there and empty from one that isn't there. A timeout or an engine that won't start is refused as itself. This check, not the offer, is what keeps Create from making a missing folder, so a stale offer is harmless: it ends in a refusal. The reverse is accepted: a success recorded against an old location hides the offer for the new one, and the person creates the repository through Connect → Create. The look and the initialisation are two jobs under the configuration lock, so the lock is held for up to two repository-job budgets, and a drive unplugged in the moment between them is not caught.

   What remained open is the case §1 names: an unplugged drive whose mount point is an empty folder that exists looks to the engine exactly like a real empty folder, so the look passes and Create makes a repository there. "Nothing reached it" is read from successes of the plans' own operations only: maintenance runs (`forget`, `prune`, `check`, `identify`) carry no plan and never count, and a success whose write to the log was dropped (backups never wait on the log) is not on record either. Only a recorded repository ID tells the two folders apart, and decision 57 records one the first time any job opens the repository, a maintenance run's included ([#229](https://github.com/nledford/Ladderback/issues/229)), so a row is offered Create only for a repository no job has opened, or one whose record couldn't be made, which the daemon's log names.

On the page, the button is named after its row (**Create demo**). A created repository is said below the list, and the list is read again, so the row offers Create no more and its button goes. Focus moves to the short confirmation, "Created demo.", where a screen reader reads it, so nothing is announced; the repository's ID is a sentence of its own after it, outside the focused element, so a screen reader doesn't read 64 hex digits unasked. A refusal is the row's alert; the list isn't read again, so focus stays on the button (§4.4).

Accepted: a newly imported repository is created from its row only after a backup to it has failed `repository-not-found`, one step more than pressing Create; the form still creates it at once for whoever types its location and password.

Rejected: offering Create on a row with nothing on record, which offered it to every newly imported repository, one already there or on a drive that isn't plugged in included, where a Create makes the folder it is given; asking each repository whether it exists as the list is drawn, which opens every saved repository, resolving its password, on each page load; a Create that saves `maintenance = "local"` as the form's Create does, which would change a choice the person made on import; failing `repository-not-found` for a REST repository on rustic's empty listing, which would read a wrong password as a missing repository and offer to create one over it; failing it for any OpenDAL service on rustic's empty listing, which on a server can't tell an empty root from one that isn't there and would make the root; failing it for a folder with a repository's keys, packs or snapshots but no config file, which would create a new repository among the old one's remains.
