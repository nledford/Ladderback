# Decision 109: How a restore is started from the web UI

**A restore takes one entry of one snapshot, by default into a new folder under the agent's restore folder, or in place over the original files from the agent's own web UI only, and never deletes a file. Every restore is confirmed by step-up first, the admin password with sign-in on and the snapshot's short ID otherwise, through two routes a browser session alone reaches. An agent runs one restore at a time, with no hooks** (recorded 2026-11-15, §10.4, §4.5; that a restore runs no hooks, and that it never falls back on the data folder, decided by the maintainer on #563, 2026-11-15).

## Why

- **No hooks.** A restore runs neither the agent's hooks nor a plan's. A plan's hooks prepare a backup of its sources (a database dump, a mount); none of them is written for a restore, and running one there would run a command nobody chose for it.
- **The restore folder.** A new folder is `<restore folder>/<host>-<short ID>-<YYYYMMDD-HHMMSS>/`, made exclusively, with the folders above it: one already there is refused untouched. The host is the one the repository's listing records, never one a request gives, made a safe name of one folder; the time is the agent's own. The restore folder is `[agent] restore-folder` (an absolute path), else `ladderback-restore` in the agent's home folder.
- **No data-folder fallback.** An agent with no home folder it can use and no `restore-folder` refuses a restore into a new folder with `restore-folder-unset` (409, as a request sign-in being off refuses is: the configuration doesn't allow it now, and setting it does). Restored files never land beside the database and the secrets.
- **In place never deletes.** It runs rustic's own restore with delete off, so a file the snapshot doesn't hold stays. Before it can be confirmed, its dialog shows a dry run (`prepare_restore`): the files it would add, overwrite or leave as they are, and the entries it leaves alone. The dry run is a read: it writes nothing and records no operation. In place is offered only in the agent's own web UI; asked for from elsewhere it is `restore-in-place-not-here` (403).
- **From the hub.** The hub sends only the request, for a new folder, and only to an agent that sets `allow-hub-restore = true`; any other agent refuses it with `restore-hub-not-allowed` (403) before anything runs. The rule lives on the Restore aggregate now; the hub's route to it is M5's.
- **One restore per agent.** A second restore while one runs is `restore-running` (409, naming the one that runs). A restore runs with a backup's deadline, counted from the index read, can be cancelled, and is recorded in the operation log with where it was asked for; a failed one is announced as `restore.failed`.
- **Step-up, the password or the short ID.** With password sign-in on, the admin password, typed again even with a live session; its wrong tries count in the address's sign-in waits (`step-up-failed`, 403; 429 with `Retry-After` during a wait), so a stolen session can't guess it through restore. With sign-in off or by a proxy's header, the snapshot's short ID (or its whole ID, in either case, the spaces a paste brings dropped), which guards only against a misclick. The step-up field (§4.5) is a `current-password` field a password manager fills, or the short ID as text that can be selected, with a button that copies it; nothing blocks a paste (WCAG 3.3.8).
- **For a session only.** `POST /api/v1/repositories/{alias}/snapshots/{snapshot}/restore/preview` and `…/restore` are reached by a browser session, never by an API token: no scope opens them (§10.5, decision 93), so MCP can't restore. The confirmation is never logged or shown (I4): every type that carries it hides it from its debug output.
- **Read to its end, page or not.** Once a restore starts, the page watches its operation to its end even when the person moves to another page, and says how it ended there: a restore is long, and its end is what the person waits for.

Known limits: the short ID guards against a misclick only; with sign-in off, any process that can reach the API can confirm a restore, as it can start a backup. The page stops watching a restore when the browser tab closes or after the waits that give up on an operation; the Operations page still shows its end. Download (#564) is not part of this decision.
