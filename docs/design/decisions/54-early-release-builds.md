# Decision 54: Early release builds; the Linux archives published from 0.3.1

**From M2, cargo-dist builds the release archives every night and on release PRs, and a smoke test checks each binary on clean systems; nothing is published until M5's release packaging** (recorded 2026-11-11). A release binary differs from a development build: no default features, the dist profile (release with thin LTO), the web UI built with `--release`, and the glibc of the machine that built it. Nothing built one before, so M5 would have met every problem at once.

**Amended** (2026-11-14, #582): **from 0.3.1, each release publishes the two Linux archives, with a `SHA256SUMS` file.** They were built and smoke-tested on every release PR and thrown away, while a build from source took about 58 minutes on a 4 GB Raspberry Pi and reset it once (#538); a download takes seconds. macOS still waits for signing (decision 71); cargo-binstall, the installers and the install script's use of the archive stay with M6 (#357). See "Publishing" below.

**Amended** (2026-11-15, #601): **the release binaries embed their dependency list.** From 0.3.1 they run on machines that never built them, and an advisory published after a release says nothing about a binary already installed unless something can tell which crates it holds. dist builds with `cargo auditable build` (`cargo-auditable = true` in `dist-workspace.toml`), which stores each crate's name and version, compressed, in a section of the binary, so `cargo audit bin`, or any tool that reads that list, checks an installed binary without its source. The list covers the daemon's crates only: the web UI it embeds is a separate trunk build, so its crates (Leptos among them) aren't listed, and `cargo audit` on `Cargo.lock` at the release's tag covers both.

cargo-auditable (MIT OR Apache-2.0) is a build tool, not a dependency of the code. `release-builds.yml` installs version 0.7.7 with taiki-e/install-action, the action already pinned there, which checks the download against the SHA-256 its manifest records, with `fallback: none`, so a version missing from that manifest fails the build rather than installing an unchecked one; after the build, a step checks that the binary has the list's section. The list is data the binary never reads, so it changes nothing the binary does. A build from source (`just install`) has no list.

- **Tool.** cargo-dist 0.34.0 (Apache-2.0 OR MIT), which §12 already names, installed by `scripts/install-dist.sh` from the official release with a pinned SHA-256 per host. It runs build-only, `dist build --artifacts=local --target <t>`, from our own `.github/workflows/release-builds.yml`. dist's generated workflow isn't used: it would write `.github/workflows/release.yml`, release-plz's file; it runs on every pull request and on tag pushes; and it uses a shared build cache and a `curl | sh` installer. `dist-workspace.toml` has no `ci` key, so dist neither writes nor checks one.
- **What it builds.** The `ladderback` package alone (`dist = false` for the workspace, `dist = true` in its `[package.metadata.dist]`; dist's `packages` key didn't limit the build), with `default-features = false`, which `just architecture` checks against the `Justfile`'s `release_flags`, and `precise-builds`, so the features are the package's own.
- **Targets.** `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu`, built on Ubuntu 22.04 runners, so the binary needs glibc 2.35 at most and runs on Debian 12, Ubuntu 22.04 and newer; the smoke test fails above 2.35. `aarch64-apple-darwin` only: dist can't build a universal macOS binary yet (axodotdev/cargo-dist#77). A published macOS archive also needs Developer ID signing and notarization (decision 71).
- **Smoke test.** `scripts/smoke-release.ts` (§12.1): the version, no pseudolocales or gallery, the dynamic libraries and glibc floor, `serve` with its UI, and one backup into a scratch repository, natively or in Debian 12, Ubuntu 22.04, Ubuntu 24.04 and Fedora containers pinned by digest.
- **Workflow.** Nightly, by hand, on pull requests labelled `release`, which release-plz puts on each release PR, and for each release ("Publishing"). No build cache, read-only contents, archives kept 7 days as run artifacts, uploaded before the smoke test. A failed nightly run opens an issue from a separate job that alone holds `issues: write`. Not a required check.
- **Publishing** (amended 2026-11-14, #582). When release-plz tags a version, `.github/workflows/release.yml` calls `release-builds.yml` for that tag, with the same flags and smoke test, and the macOS build allowed to fail. The build checks out the tag, which fetches it, so the binary names itself as the release, and the smoke test is given that version (`--version`), so a binary that says `x.y.z+<commit>` fails it (decision 90). An archive replaces any earlier one of the same name in the run, so a rerun's build, not a failed one, is what gets published.

  A separate job, the only one that can write to the release, runs none of the build's code, and downloads the run's two Linux artifacts, checks each against its build's `.sha256`, writes one `SHA256SUMS` for both, checks it, and attaches the three files with `gh release upload --clobber`, so a rerun of a failed run attaches them again. A missing archive fails the run. The release exists before its archives, about an hour earlier, and stays without them if a build fails until the failed jobs are rerun: a draft release that waits for them would need release-plz's release step split in two, which the hour doesn't justify.
- **wasm-bindgen on aarch64 Linux.** Its aarch64 Linux release is a gnu build that needs glibc 2.38, so on Ubuntu 22.04 trunk can't run the one it downloads; that job builds `wasm-bindgen-cli` at the `Cargo.lock` version from source, which trunk then finds on the `PATH`.
