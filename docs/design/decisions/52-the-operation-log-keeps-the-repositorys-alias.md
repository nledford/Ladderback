# Decision 52: The operation log keeps the repository's alias

**A maintenance operation's row in the log keeps the alias of the repository it ran on, as this agent named the repository when the run started** (recorded 2026-11-11, #192). Migration `0004_operation_repository_alias.sql` adds the nullable column `repo_alias` to `operations`; a forget, an adoption, a prune and a check write it when they start, and the Operations page names their rows by it ("Check of demo"). A backup's row is named by its plan and writes none.

The log already holds the repository's ID (`repo_uuid`), but a reader doesn't know a repository by its ID, and the page can't turn one back into an alias without the configuration as it is now. That answer is wrong for a log: an alias renamed since the run would rename every row the old alias ran, and a repository removed from the configuration would leave its rows unnamed. A row says what the run was, so it keeps the name the run had. The alias is read back as strictly as every other column (§9): one that doesn't parse is `StoreError::Corrupt`, never a silent default.

Adding a nullable column rewrites no row, so the migration is safe on a log an earlier build wrote: its rows read back with no alias, and the page names them by what ran alone ("Check"). No row is filled in from the configuration after the fact, for the reason above. Its cost is a downgrade: the migration is a one-way door, and a build older than this one refuses the upgraded log with `OpenError::NewerSchema`, so going back to one means going back to a copy of the log from before the upgrade.

The wire changes without breaking a client: `OperationSummaryDto` gains an optional `repository`, and a backup's `OperationResultDto` an optional `snapshot` and `bytes-processed` (the bytes of the source it went through, changed or not, kept in the backup's `summary_json` only when the engine reported them). `bytes` stays what it was, the data the backup added, so a client that read it before reads the same number.
