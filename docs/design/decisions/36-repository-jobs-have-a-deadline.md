# Decision 36: Repository jobs have a deadline

**A test, a connection or an initialisation from the Repositories page gets 2 minutes (`REPOSITORY_JOB_BUDGET`, a constant), and a repository that has not answered by then is refused with `repository-timed-out` (503) and its worker killed** (recorded 2026-11-10, §4.2, #98). The connection and a saving initialisation hold the configuration lock across the job, so a backend that never answers (an `sftp:` host that drops packets, an `rclone` remote that never starts) held every other save until the worker's own timeouts ran out, which for a hang after the first line are none. Two minutes is long for a healthy open, which reads a few small files, and short enough that a person waiting on the page gives up on the lock before they give up on the daemon. It is not configurable: a setting would be a second way to hold the lock for a long time, and nothing in the design asks for one. The deadline is the daemon's, on the `Clock`, not the worker's watchdog, because that starts after the worker reports it started and is for backups (§7.3); a code of its own, not `deadline-passed`, because the message tells a person to check the repository, not that a backup stopped. No `@e2e` scenario: a real worker can be hung (a `rest:` server that takes the connection and never answers), but the binary's clock is the system's, so it would take the whole 2 minutes, and a test-only way to shorten it would be a second code path in the daemon. Fake-clock scenarios cover the use cases and the composition root, and `adapters/engine/tests/repository_deadline.rs` runs the use case against the real worker stuck on such a server, with a fake clock moved once the worker is stuck, and checks that the worker's connections end.
