# Decision 38: The command line's output

**`--plain` is a global flag, `import-profile` takes `--json`, every command a person runs ends with 0, 1 or 2, and one whose output nobody reads ends quietly with 141** (recorded 2026-11-10, §4.5; #120). Settled: (1) `--plain` turns off the colour of the daemon's log and of `clap`'s help and usage errors, and `NO_COLOR`, `CLICOLOR` and `CLICOLOR_FORCE` need no code, since `clap` and `env_logger` both ask `anstream`; (2) `import-profile --json` prints one compact document on one line of standard output, and nothing on standard error, made of codes and arguments and never of a sentence: the repository, the plans and the notices, or the refusal as the REST API's typed error under `error`; (3) every failure of it is a document, including those that stop an import before it starts: a missing configuration folder and a runtime that did not start have codes of their own (`config-folder-unknown`, `runtime-unavailable`), and a name that is no alias is `repository-alias-invalid`, as over REST; the one that stays a sentence is a document that cannot be written; (4) the statuses, with and without `--json`, are 0 for done, 1 for refused or could not start, and 2 for a command line that was not understood, by `clap`, which leaves standard output empty, or by `serve`, for an `--allowed-host` that no request could match (§10.1); the worker is no command a person runs, and keeps the statuses of §4.1; (5) `export-profile` has no `--json`, because its standard output is the profile, and `serve` has none, because it reports no state and its standard error is its log; (6) a closed pipe ends a command with 141, 128 and the number of SIGPIPE, and nothing said, because commands print through `output::to_stdout` and `output::to_stderr`, which return the failure, and the binary denies `clippy::print_stdout` and `clippy::print_stderr`; a write that fails for another reason is said as `cannot write the result` and ends with 1, except `clap`'s own messages, which stay as `clap` had them; (7) the daemon stops with 141 at its first startup line when nobody reads its standard error, and once it serves, its logger drops what it cannot write. Why: a script that parses `--json` should not need a second parser for the failures that come before the import starts; `print!` and `eprint!` panic when nobody reads, a panic is the crash §13.5 forbids, and 141 is what a shell shows for a program that a closed pipe killed, so a pipeline sees what it sees from any other tool; a daemon that cannot say where it listens should not start unnoticed, and one that is serving must not stop backups over a log pipe. The worker is left as it is: its standard output is the protocol stream (§4.1), and it already ends with 74 when that breaks.
