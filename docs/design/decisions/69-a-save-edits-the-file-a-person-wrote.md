# Decision 69: A save edits the file a person wrote

**A save over an existing `config.toml` (Connect, Create, an edit in the web UI, `import-profile`) edits the file as it is: what the save changes is set, added or removed where the file writes it, and every other byte, comments, blank lines, key order and a value's own spelling among them, stays as written; the edit is written only when it reads back as the configuration saved and fits under the size cap, and otherwise the save writes the daemon's layout, as every save did before** (recorded 2026-11-12, §6.1; #257). Before, each save rendered the whole file again, so the first one dropped what a person had written around the settings; recording a repository's ID was already an edit (decision 57).

1. **What changes.** The configuration the file holds and the one saved are each written in the daemon's layout (§6.1, "Layout of the written file"), and the two texts are compared key by key. A setting whose text differs is set in place, keeping the comment on its line; a setting only the saved one has is added after the last setting of its table, and a table it adds (a repository, a `[plans.retention]`) after the last table of its kind, or at the end of the file for a section the file didn't have (`[agent]`, `[hooks]`, the first repository or plan); a setting only the file's has is removed with its line. Plans are matched by their ID. A value is written as the daemon writes it once a save changes it, so `jitter = "5 minutes"` stays until the schedule changes and then becomes `"5m"`; a value written as an inline table is replaced whole, while a table written with a header of its own (`[repositories.nas.options]`) is changed key by key. A hook list written as tables of its own (`[[hooks.run-before]]`) is a list in the daemon's layout, so a save that changes it writes it again whole, as `run-before = [...]` under `[hooks]`, and the comments in its tables go with them.
2. **What stays.** Whatever reads the same before and after the save in the daemon's layout is not touched, however the file writes it: quoting, spacing, `'…'` strings, a list over several lines with comments between its items, a duration or a hook in another form, a default said out loud (`maintenance = "none"`), and the order of keys and tables.
3. **What goes.** A repository or a plan the save removes goes with everything written in it, down to the first blank line after its last setting, and with the comment directly above its header, up to the nearest blank line: that comment describes the entry, and left behind it would describe the next one. What is written above that blank line stays where it is, because it belongs to what comes before: a key put out of use at the end of the entry above, a note about the whole file. A setting that is removed goes with its line and the comment directly above it, the same way. A section every setting of which is back at its default is removed as the daemon's layout leaves it out. The history keeps the file before each save (§6.1, "History").
4. **The check before the write.** The edit must parse, read back exactly as the configuration saved (a load of it gives the same `AgentConfig`), and be no larger than 1 MiB. When it can't be made or fails the check, the save writes the daemon's layout instead, as a first save does: so does a save over a file that isn't valid UTF-8 or a configuration, one in an older version of the format (a load migrates it as a whole), one whose lines end both ways, and one whose plans the save puts in another order. A save never fails for the edit's sake: the person asked for the change, and the old file is in the history.
5. **Line endings.** As decision 57: a file whose lines end in CRLF keeps CRLF on every line, the new ones too, and a byte order mark at its start stays.

Accepted: a save that can't be edited in drops the comments as before, without saying so; a section a save adds to a file that lacked it goes at the end of the file rather than where the daemon's layout puts it; a line the save adds is not indented to match the lines around it; a comment with no blank line between it and the entry below is that entry's, so it goes when that entry goes, whatever it says; a hook list written as tables loses the comments in them when it changes.

Rejected: refusing a save the edit can't make, which would stop a person's change for the sake of their layout; keeping the comments of a removed entry, which would leave them above the next one; matching a key's form before changing it (a duration in words stays in words), which needs a writer per value kind for a cosmetic gain; a format-preserving writer of the whole configuration, which `toml_edit` doesn't give and would duplicate the layout `write.rs` owns.
