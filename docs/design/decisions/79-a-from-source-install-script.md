# Decision 79: The install script: the Linux archive, or a build from source

**`scripts/install.sh`, run as `curl -fsSL https://raw.githubusercontent.com/nledford/Ladderback/main/scripts/install.sh | bash`, installs the newest release: on 64-bit Linux from the release's archive, checked against the release's `SHA256SUMS`, and elsewhere by building it from source. It installs only what needs no administrator rights, after asking once, and never runs `sudo`** (recorded 2026-11-12, §12; the archive added 2026-11-14, #603). The README's steps stay beside it, as "By hand".

Decided:

1. **The Linux archive, and from source elsewhere** (amended 2026-11-14, #603). When this was decided there was no binary to download, so the script built from source everywhere.
   - **The archive on Linux.** Linux releases carry archives from 0.3.1 (decision 54, #582, #599), so on Linux on x86_64 or aarch64 with glibc 2.35 or newer, running 64-bit programs (`getconf LONG_BIT`, as 32-bit Raspberry Pi OS runs on a 64-bit kernel whose `uname -m` says `aarch64`), the script downloads the newest release's archive and its `SHA256SUMS` from `releases/latest/download` (GitHub's latest release leaves out release candidates, as the source path's tag does).
   - **Its downloads.** It downloads with the bounds every download has (point 2) and following a redirect only to HTTPS (`--proto '=https'` holds for redirects too: the archive and `SHA256SUMS` come through the same redirects, so one to plain HTTP could swap both).
   - **Where the binary goes.** It checks the one against the other, and installs the binary where `cargo install` puts a build: `bin` under `--root`, else under `CARGO_INSTALL_ROOT`, `CARGO_HOME` or `~/.cargo`. It writes it beside the old one and renames it over it, so an update either way replaces the same file, whole, and a service goes on running that path; the service is restarted as before, by `ladderback install-service`, which the script names. That path needs none of the build's tools and asks nothing.
   - **When it builds from source.** The script builds from source, and says why in one line, on macOS (no archive until #344, decision 71), on any other system, without curl, when the release has no archive for the system (`SHA256SUMS` or the archive answers 404, as in the hour before a release's archives are attached), and with `--from-source`.
   - **Failures.** Any other failed or stalled download stops it and suggests `--from-source`; an archive that doesn't match its checksum stops it, naming the file.
   - **The build.** Building from source does what the install guide's steps do: it clones the repository, checks out the newest release and runs `just install --force`: cargo won't overwrite a binary it didn't install, such as one an earlier run took from the archive.
2. **What it installs, and what it doesn't.**
   - **What it checks.** It checks git, a C compiler (`cc`), Node.js 26 or newer with npm (raised from 20 on 2026-11-14, #583: Ladderback requires a Node.js line upstream still supports, and 26 is the current LTS line; Node 20, which no longer is, couldn't run `just install-restart`, the update command the install guide gives, which is TypeScript), Rust, just 1.40 or newer and trunk.
   - **rustup and just.** rustup comes from its official installer, `https://sh.rustup.rs`, with `-y` only when the person passed `--yes`, so rustup asks its own questions otherwise; just comes from `cargo +stable install --locked`, as the install guide says.
   - **trunk.** trunk comes from its own release archive (added 2026-11-14, #538): the script pins a trunk version and the SHA-256 of its archive for each system trunk publishes one for (Linux x86_64 and aarch64, the static `musl` builds; macOS arm64 and x86_64), downloads that archive before it installs anything else, refuses it and stops, having installed nothing, when its SHA-256 differs, and puts `trunk` in `${CARGO_HOME:-~/.cargo}/bin`.
   - **Download bounds.** Every download, trunk's archive and rustup's installer, gives up after 30 s without a connection or 60 s averaging under 1 KiB/s, after curl's three retries, and stops the script with a message that says it stalled; it has no limit on its whole time, so a slow link that still moves finishes (added 2026-11-14, #583). This needs no Rust, so it holds without rustup too.
   - **Building trunk.** Only on a system with no archive is trunk built, at the pinned version, `cargo +stable install --locked -j <n> trunk@<version>`, with one job per 2 GB of the memory `getconf _AVPHYS_PAGES` reports free, at least one and no more than the processors online. A new trunk is adopted by changing the version and the four hashes, each taken from the release's `<archive>.sha256` asset after checking it against the downloaded archive.
   - **Asking once.** Before any of that it lists what it will install and how, and asks once, on the terminal (`/dev/tty`: standard input is the script itself); `--yes` skips the question, and with no terminal and no `--yes` it refuses.
   - **What it never installs.** A missing C compiler, git or Node.js (or one older than 26, named with the version found) it never installs: it prints the command for the system's package manager (`xcode-select --install` and Homebrew on macOS, apt, dnf, pacman, else where to get it; for Node.js on Debian and Ubuntu, whose packages are older than 26, nodejs.org and NodeSource's signed apt repository, and nodejs.org on macOS without Homebrew and on Fedora and other systems, where the system's packages may not hold 26) and stops before changing anything.
   - **On macOS.** On macOS the C compiler and git count only once `xcode-select -p` finds the Command Line Tools: every Mac has `/usr/bin/cc` and `/usr/bin/git`, which without them only offer to install them.
   - **Without rustup.** Without rustup, the Rust on the `PATH` must be at least the checked-out release's MSRV and have the `wasm32-unknown-unknown` target, and a missing just is named with its prebuilt releases, as the install guide says, as is a missing trunk on a system trunk publishes no archive for.
   - **The `PATH`.** rustup's folder (`~/.cargo/bin`) goes first on the script's `PATH`, as rustup's installer puts it in new shells, so its cargo is used before one the system's packages installed.
3. **Its own source folder, never deleted.** The source lives in `${XDG_DATA_HOME:-~/.local/share}/ladderback/source`, or where `--dir` says. The first run clones it there, later runs `git fetch --tags`. A folder that holds anything but a clone of Ladderback's repository, or a clone with uncommitted changes, is refused and left as it was. The web UI's build rewrites its stylesheet, `crates/web/tw-out.css`, which releases up to v0.2.0 track: after `just install`, whether it succeeded or not, the script puts back that one file when the release tracks it, so the next run doesn't refuse the clone as changed. Later releases ignore the file (#381), and the script leaves it as the build wrote it.
4. **What it builds.** The newest `v*` tag that isn't a release candidate (no `-`), the selection the install guide's `git checkout` line makes; no such tag is an error.
   - **The pinned Rust.** With rustup, it builds with the Rust the checkout's `rust-toolchain.toml` pins (decision 78), whatever the person's environment names: `RUSTUP_TOOLCHAIN` outranks the file, and `RUSTC` or `CARGO_BUILD_RUSTC` has cargo run another compiler, so the script unsets them before it builds the release, for the rest of its own run, which leaves the person's shell as it was, and says which it ignored.
   - **Installing it.** It installs the pinned version, with the components and targets the file lists, when rustup lacks it (`rustup toolchain install <version> --no-self-update`, naming the version, which works on every rustup that reads the file), rather than relying on rustup's automatic install, which rustup has deprecated (rust-lang/rustup#4836); a release that names no version there is refused. Without rustup it checks the Rust on the `PATH` against the MSRV instead (item 2).
   - **wasm-bindgen.** On 64-bit ARM Linux with a glibc older than 2.38 it builds the wasm-bindgen the checkout pins first, in the checkout so that the pinned Rust builds it, the install guide's workaround.
   - **The build and after.** Then `just install`, with the arguments after `--`; every release from v0.2.0 on has that recipe, and the script builds only the newest. It ends with the installed binary's `--version` and the next steps: `ladderback serve`, `ladderback install-service`, and on macOS the Full Disk Access grant. When the `PATH` the script was started with doesn't lead to the binary, it says to open a new terminal (after installing rustup) or which folder to put on the `PATH`. Running it again updates.
5. **`main`'s script.** The command fetches the script from `main`. The script pins no version itself: it builds the newest release tag, so what gets installed is a release, while fixes to the script reach everyone at once. `main` is protected (§13.8): the script that runs has passed review and CI.
6. **A partial download runs nothing.** The script is a set of functions and its last line calls `main`, so a download cut short defines functions and runs none. Nothing it runs reads its standard input, which is the rest of the script when it is piped into bash.
7. **Tested as `@e2e` scenarios.** `features/cli/install_script.feature`, with steps in `tests/steps/install_script.rs`, runs the script as `curl … | bash` does, bash reading it from standard input, with stand-ins for every tool on the `PATH` that record their calls, a scratch home, the real git cloning a local repository with releases of the scenario's choosing (the scratch home's git configuration rewrites Ladderback's address to it), and a `curl` stand-in serving the newest release's archives and `SHA256SUMS` from a folder the scenario writes, with a 404 for a file that isn't there. Nothing is downloaded or built, and `LADDERBACK_INSTALL_TTY` points the question at a file or at nothing, so no real terminal is asked. They run on Linux and on macOS, whose bash is 3.2. shellcheck isn't a CI check; run it by hand when the script changes.

Why:

- **One command is what people expect** of a self-hosted tool, and the install guide's steps are six tools and a `git checkout` line to copy exactly. The script runs those same steps, so the two can't disagree about what gets installed.
- **The archive where there is one** (#603). It is the release's own binary, smoke-tested by the release's workflow, installed in seconds; a build takes 20 to 40 minutes, needs Rust, trunk and Node.js 26, and has to be bounded on a Raspberry Pi. Only a 404 falls back to building: a rate limit, a server error or a stall stops, so a long build never hides a network failure the person can fix, and a checksum that doesn't match stops too, since a mismatch means a damaged download or one that isn't the release's, and building instead would hide it. The checksum comes from the same release as the archive, so it catches a damaged or swapped download, not a release replaced whole; the source path trusts the same repository.
- **No `sudo`.** A script piped from the web that asks for root asks for the most trust there is, and system packages differ in name and version from one distribution to the next (Debian 12's Node.js is 18). rustup, just and trunk install into the person's home; the rest is one command the person runs knowingly, and the script names it exactly.
- **Ask once, or not at all.** Installing rustup, building just and installing trunk change the person's home and take minutes, so the script says what it will do before doing it. Under a pipe with no terminal it can't ask, and guessing yes would install what nobody agreed to.
- **Never delete a folder.** `--dir` may point at a folder that holds the person's own work; refusing costs a rerun, deleting can't be undone.
- **The pinned Rust, whatever the shell says.** A version manager can export `RUSTUP_TOOLCHAIN` into every shell, and it outranks `rust-toolchain.toml`: the first real run on Fedora built with the 1.99.1 a version manager named, and stopped with cargo's "rustc 1.99.1 is not supported" rather than anything the script said. The release is tested with the version it pins, so the script builds with that one rather than refuse; it names what it ignored, so nobody wonders why their setting had no effect. Installing that version explicitly keeps the script working when rustup stops installing a missing toolchain on its own.
- **trunk's release, not a build** (#538). Building trunk compiles hundreds of crates (`swc_*`, `oxc_*`); with cargo's default of a job per processor, a Raspberry Pi 4 with 4 GB and 2 GB of swap ran out of both and reset, taking everything else on it down. trunk publishes an archive with a `.sha256` for each common system, so the build is needed only where there is none, and there it is bounded. Pinning the SHA-256 in the script, as `scripts/install-dist.sh` and `scripts/install-rustic.sh` do, means a changed archive is refused rather than trusted because it came from the same place as its checksum. The Linux archives are the `musl` ones: the `gnu` builds of trunk 0.22.1 need glibc 2.39 and OpenSSL 3 (`libssl.so.3`), so they don't run on Debian 12 or Ubuntu 22.04, which the install guide supports; the static `musl` build runs on both.
- **Scenarios, not `node:test` or a shell test framework,** because the red-first check (§13.1) and `just test` run only Rust tests and the scenarios in `features/`: tests they can't see would leave a `behaviour` change with no red-first proof and no CI run. A shell test framework would also be a new dependency.

Alternatives:

- **cargo-dist's shell installer**, which downloads a release archive and checks its SHA-256, as this script now does on Linux: a second script beside this one, which the source path still needs for macOS (#344) and for `--from-source`, and dist hosts nothing for Ladderback (`installers = []`, decision 54).
- **Building from source after any failed download**: an install that always ends with Ladderback, but a rate limit or a stall would turn a download of seconds into a build of 40 minutes, needing tools the person may not have, without saying what went wrong.
- **Installing the archive into `~/.local/bin`**, as the install guide's own download steps do: the usual folder for a person's programs, but an update from a build would leave the built binary in `~/.cargo/bin`, earlier on a PATH rustup's installer set, and a service would go on running it.
- **`cargo install --git`**: it can't build the web UI the binary embeds (the `Justfile`'s `install` recipe), so it would install a binary with no UI.
- **A script that installs the system packages too, with `sudo`**, as some installers do: one command fewer for a person on a supported distribution, but root for a script from the web, and a table of package names to keep right for every distribution.
- **Bounding the build of trunk everywhere** (#538's option B), with `-j` from the free memory and a refusal below a floor: no download to trust, but every install still compiles trunk for minutes, and a floor turns away machines the release archive serves in seconds.
- **trunk's `gnu` archives on Linux**: dynamically linked against glibc 2.39 and OpenSSL 3, they fail to start on the older distributions the install guide supports.
- **A URL pinned to a release tag**: the script would match the release, but the README would change at every release and a fix to the script would reach no one until the next.
- **Refusing when the environment names another Rust,** with the script's own message, as the Rust check without rustup does: clearer than cargo's error, but it stops an install that can succeed, and the person would have to unset a variable their version manager sets in every shell.

Cost: the script is a second way in beside the install guide's steps, and both change when the build's tools do. The pinned trunk ages until someone moves the pin, and the install guide's own `+stable` build of trunk may be newer than the script's. The scenarios replace the tools with stand-ins, so a change in what a real tool prints (`node --version`, `just --version`) shows only when someone runs the script for real, and the archive path is tested against a fake release, so it is proven on a real machine only after a release. From the archive only `--root` of the options after `--` applies. The script itself is not checksum-verified: the person trusts `main` over HTTPS, or downloads it and reads it first, as the README shows.
