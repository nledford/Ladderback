# Decision 115: Detecting a missing Full Disk Access grant

**On macOS, the agent's Full Disk Access probe lists `~/Library/Safari`, a folder only that grant opens: a refusal (`EPERM`) means the grant is missing, a listing means it is granted, and any other answer means unknown. The daemon runs it through the platform adapter, behind an app port, when it starts, before each backup and on "Check again". A backup's source item refused with `EPERM`, after a probe that found the grant missing, gets the warning `full-disk-access-missing` instead of `source-unreadable`. The start page warns while the grant is missing, with a button that opens the System Settings pane and shows the installed program in Finder for a browser on the same Mac, and the steps for any other; the log says it once at start, and `install-service` names the program to grant** (recorded 2026-11-16, §3.1, §4.2, §12; #558).

## Why

- **In the daemon, not the worker.** The maintainer's call of 2026-11-14 put the probe in the worker, where the backup reads, because it wasn't known whether a grant on the launchd-started daemon reaches the worker it spawns (roadmap §17, question 2). #281's test on macOS 27.3 answered it: the grant reaches the worker child ([operations §12](../operations.md#12-packaging-and-deployment), decision 71's "Tested on a Mac" item, PR #833). So the daemon's probe answers for its workers, and running it there keeps the rule in `domain` and `app`, with a fake port for the scenarios, rather than a new worker job kind that the engine adapter would need the platform adapter for. This changes the maintainer's call, for them to confirm.
- **`~/Library/Safari`, under `HOME`.** Safari ships with macOS, and TCC guards its folder with Full Disk Access alone. The user's TCC folder, the other candidate, is missing on macOS 27.3. A missing Safari folder is unknown, never missing: a false alarm would send a person to System Settings for nothing. The folder is under the `HOME` the daemon runs with, so a daemon the tests start, with a scratch home, never probes the person's own folder, and never shows the warning on a developer's Mac without the grant.
- **`EPERM` only.** TCC refuses with `EPERM` ("Operation not permitted", `os error 1`); a file's own permissions refuse with `EACCES` ("Permission denied", `os error 13`), which no grant fixes. A source item is refused for want of the grant when the engine's detail contains `(os error 1)`, the form Rust's `io::Error` writes: rustic puts its own words after it.
- **The probe before that backup decides.** A refused item gets the new code only when the probe that ran before its backup found the grant missing; unknown never changes the code. A grant given since start is seen at the next backup.
- **A code of its own, per item.** `full-disk-access-missing` replaces `source-unreadable` on each item it explains, so the operation's warnings and its notification say why (§13.7.1), and an item refused for another reason keeps `source-unreadable`.
- **The button only for the same Mac.** Opening System Settings and Finder acts on the desktop of the person the daemon runs as, so the daemon does it only for a request from a loopback peer naming a loopback host, with the session's sign-in when sign-in is on; any other browser sees the steps. It runs `/usr/bin/open` twice with fixed arguments, the pane's address and then `-R` with the daemon's own path, and an environment cut to the variables a system program needs (I4): nothing a request says reaches the command.

Cost: a probe on every start and backup, one directory listing; on Linux the probe answers "not applicable" without a call.
