# Decision 70: Sign-in

**One admin password, set at the terminal and kept only as an argon2id hash, starts sessions that end 12 hours after a person last used them and 30 days after they started; only what a person does counts as use** (recorded 2026-11-12, §10.1, §4.5; #279). Decision 11 made sign-in optional; this is how it works when it is on. The details are in §10.1.

Why:

- **On or off, decided at start.** Sign-in is on while `admin-password` exists in the data folder, and the daemon decides once, when it starts. A daemon that could turn sign-in on by itself would leave a page open without one; one that turned it off when the file went away would open the API to anyone. A hash file the daemon can't read refuses the start, so a damaged file never means sign-in off.
- **The password never passes through argv or `config.toml`.** `ladderback set-password` reads it at the terminal, without echo, or as one line of standard input, so a script can pipe it in. An argument would show in other users' `ps`, and a config setting would put the hash where the config's history and exports go (I4).
- **12 hours unused, 30 days in any case.** A working day of leaving the tab open is kept; a stolen cookie stays good for at most 30 days. The 30-day end is not warned of: WCAG 2.2.1's 20-hour exception covers a time limit over 20 hours, and a person signs in again once a month. The idle end is warned of 2 minutes before it comes, with "Stay signed in", as 2.2.1 asks.
- **Only what a person does uses a session.** The Operations page re-reads the history after every event, and its events stream stays open. Had those counted, a page left open on a busy machine would never be signed out, and the 12 hours would mean nothing. The page marks what it reads on its own with `x-ladderback-background`, and opening the events stream never counts. The header needs no trust: it can only make a session end sooner, so a client that sends it harms only itself.
- **Each tab counts from its own last use.** The daemon keeps one last use per session; a tab times its warning from what it sent. Sharing the time between tabs would need a channel between them for a gain no one asked for: a tab left alone warns, and its "Stay signed in" finds the session live.
- **A tab whose CSRF token is stale reads the current one once.** Signing in again in one tab replaces the session the tabs share, so another tab's next change is refused as `csrf-token-invalid`. That tab reads the session's token and sends the request once more, rather than telling the reader to reload and lose what they typed: the daemon refuses before any route runs, so nothing happened the first time, and the token read comes from the session route, which only the cookie, never another site, can reach. Only that refusal is retried, and only once, so a token that is wrong for another reason still shows its error.
- **A new admin password ends every session**, even when it is the same password. Each session remembers a fingerprint of the hash file it started under; a new salt makes a new fingerprint, and the daemon sees it at the next request without a restart. Setting the password is how the admin takes back control after a leak, so it can't leave a stolen session alive.
- **CSRF on every changed request, sign-out included.** `SameSite=Strict` already keeps other sites' requests from carrying the cookie, and the request checks refuse a foreign `Origin`; the token is a second, independent wall. Signing out needs it so another site can't sign the admin out.
- **Tokens are compared in constant time and looked up by their SHA-256.** A token has no `==`, so no code can compare one in a time that depends on where it differs; the CSRF token is compared with `subtle`, and sessions are kept by the SHA-256 of their cookie's token, so a lookup compares digests, whose matching prefix says nothing of the token.
- **Two crates, both approved by the maintainer:** RustCrypto's `argon2` for the password's hash, and `subtle` for the constant-time comparison (2.6.1, already in the lock file through other crates). `sha2` was already a dependency.
- **`Secure` only for an `https://` `Origin` of the request's own `Host`.** The daemon serves plain HTTP; only a page served over HTTPS by a proxy should get a cookie the browser keeps from plain HTTP. `X-Forwarded-Proto` is written by whoever sends the request, so it is never read.
- **Failed sign-ins make the next one wait; none locks out.** A lockout would let anyone who can reach the daemon lock the admin out. The wait doubles from 1 second to at most 5 minutes per client (an IPv4 address, or an IPv6 /64), and a sign-in during the wait is refused unchecked, so guessing costs 5 minutes a guess while the admin, once the wait passes, gets in. Behind a reverse proxy every client shares the proxy's wait: trusting forwarded addresses would let an attacker name a fresh address for every guess. The cost: whoever shares the admin's client (another user on loopback, anyone behind the proxy) can keep the admin waiting by failing the moment each wait passes; that denies sign-in without making a guess count, and a cookie giving a browser once signed in a wait of its own is left for later (§10.1).
- **Beyond loopback only with sign-in on and an `--allowed-host`.** The request checks admit only configured names, so without one every request from the network would be refused anyway; requiring it makes that a refusal at start, not a page that never loads. The log warns that plain HTTP sends the password unencrypted.

Left out: the trusted-proxy SSO header mode (decision 11, tracked separately), API tokens (§10.1, M3), sessions that survive a restart, and more than one user.
