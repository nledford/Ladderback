# Decision 156: A paired agent knows another agent's snapshots from a listing at most a day old, and lists each repository it maintains before a sync when it has none

**A paired machine's `ReposSnapshot` says `others_snapshots: true` for a repository whose last listing, at most a day old on the machine's clock, held a snapshot another agent tagged that is recent on that clock at the report (decision 62's 30 days), and for a repository with no such listing. Every listing the daemon runs (the Snapshots page, a preview, a prune's look for other hosts) notes, for the repository it opened, the newest such snapshot's time and the time the listing started. Before each sync with the hub, the machine lists, once, each repository it asks to maintain (`local`) with a recorded ID and no listing from the last day, unless an operation holds it here; a failed listing is tried again at the next sync. Nothing is kept across a restart.**

## Why

- **From the listings, and a listing before a sync only when none stands.** The sync asks for its grants every 15 minutes (decision 151). Opening each repository and listing its snapshots that often would cost a remote repository's bandwidth and lock nothing better: the listings the daemon already runs show the same snapshots. An engine decorator beside the record of an opened repository's ID (decision 81) sees every listing and its repository, so no page or job has to remember to tell the sync. A machine whose repositories nobody opens would otherwise never be granted a lease, so the sync lists those with no listing standing itself, without a person.
- **A listing stands for a day.** Another agent's backup made after a listing isn't seen until the next one. Listing each maintained repository again once a day bounds how long a repository another machine has started backing up to can be called free to one day, at the cost of one read of each `local` repository a day. A listing more than a day off the clock either way, as after the clock is set back, stands for nothing, so a wrong clock lists again rather than trusts an old answer.
- **The newest time, not a yes or no.** Kept as the newest other agent's snapshot's time, the answer is judged at each report against the machine's `Clock`, so a snapshot that turns 31 days old stops counting without another listing.
- **What counts as another agent's** is decision 62's rule, which the other-hosts warning already uses: a snapshot whose `ladderback-agent:` tags name another agent, or disagree. One that names this agent, as an earlier installation's history once adopted (decision 62's rewrite), and one no agent tagged, don't. A listing is kept with the machine ID it was judged for, and one judged for another ID counts as none.
- **No listing means "holds them".** `true` only feeds the hub's refusal of an `agent:<id>` claim (§7.3): it turns a grant into a refusal or a renewal into none, never adds a grant, and leaves the request the agent's release logic and the hub use as it was. `false` for a repository the agent hasn't looked at lately would let a machine that backs up to a repository another agent prunes take its lease, which is I1's failure. Nobody pruning is the safe direction.
- **Not while an operation holds the repository.** A listing beside a maintenance running here would wait on the repository's lock or slow it; that operation's own lease covers the repository meanwhile, and the next sync lists it.
- **In memory.** A value from before a restart may be weeks old, and the repository may have been adopted or rewritten since; listing again is cheap next to that risk.

## Consequences

- A freshly paired machine, or one just restarted, lists each `local` repository before its first sync, and is granted its lease at that sync when the listing shows none. The listing delays that session by up to a listing's read time.
- Each `local` repository is read once a day for this, beside the listings a person opens.
- A listing that fails (the repository unreachable, its password not saved) leaves the repository reported as holding another agent's snapshots, so its lease isn't granted or renewed; the daemon warns once until a listing succeeds, and lists it again at every sync, which may be every few seconds while reports flow.
- A snapshot whose tags were cut short (`tags_truncated`) is judged on the tags it kept, as the other-hosts warning judges it.
- Within a day of a listing the value can be stale: another agent's backup made since the last listing isn't seen until the next. The hub's other check, another agent's report of the repository, still refuses a claim on a repository that agent reports.
- Decision 151's consequence that `ReposSnapshot` always says `others_snapshots: false` no longer holds; decision 151 says so.
