# Decision 87: Listening on the network with sign-in off

**With sign-in off, `ladderback serve --listen` takes an address beyond loopback, as Backrest does, but only with an `--allowed-host`, as with sign-in on. The daemon then says on stderr, in a line of its own that no log setting hides, that anyone who can reach the address can run and change backups and how to turn sign-in on, and every page of the web UI says the same** (recorded 2026-11-13, §10.1, §4.2; #503, approved by the maintainer). It amends decision 70's startup rule ("beyond loopback only with sign-in on") and decision 11's ("refuses non-loopback binds without auth").

The term is in the glossary first (§3.1): the agent's **exposure** is who can reach it at the address it listens on, this machine (loopback) or the network.

## Why

Backrest binds to localhost by default and lets authentication be turned off; opening it to the network is the deliberate step (its README; its maintainer in [garethgeorge/backrest#1121](https://github.com/garethgeorge/backrest/issues/1121)). The old rule refused a home-LAN setup that works in Backrest, which surprises people migrating from it, one of Ladderback's audiences. Here too the explicit `--listen` beyond loopback is the consent: the default stays `127.0.0.1:9898`, and a daemon that starts and says plainly what it exposes is better than a refusal whose way out is a password the person doesn't want or a proxy in front of a loopback daemon. Only Backrest's documentation and that issue were read; no code was.

## Decided

1. **The rule no longer asks whether sign-in is on.** A loopback address may always be listened on; any other only for at least one `--allowed-host` (`http_adapter::startup_rule(addr, allowed_hosts)`). Without one the request checks would refuse every browser request from the network anyway, so it is a refusal at start, naming `--allowed-host`, sign-in on or off. `cli-refuse-non-loopback` is gone.
2. **The request checks are unchanged.** The `Host` check still admits only a configured name or a loopback address, so a DNS-rebound name (`evil.example` resolving to the daemon) is still refused with `host-not-allowed` before any route runs, and the `Origin` and `Content-Type` checks still stop a cross-site request. No route gains or loses a check; with sign-in off on the network, the API answers whoever reaches the address, as it answers anyone on loopback today. `--allowed-host` does not limit who can connect (any client can send an allowed `Host`, `localhost` included); it stops a browser being used against the daemon through DNS rebinding. With sign-in off on the network, anyone who can reach the port can use every route.
3. **The warning is a line the daemon says itself, not a log record.** `ladderback: warning: sign-in is off and Ladderback answers on the network at <address>, …` is the catalog's `cli-warn-network-sign-in-off`, written through `output::to_stderr` (§4.2, "Logging") after the address is bound and before `listening on`, so it names the port really taken. A `log::warn!` record would go wherever `RUST_LOG` sends it, and `RUST_LOG=off` or `error` would silence it; this warning is the one thing that tells whoever started the daemon that its API is open, so nothing may hide it. Like every line the daemon says before it serves, one nobody can read stops the start (exit 141). The issue asked for "a WARN"; this is stronger, and the `@e2e` scenario proves it with the log turned off.
4. **Every page says so.** The session route's answer gains `exposure: "network"` when the daemon listens beyond loopback (left out on loopback, so every existing answer is unchanged, §12.1). With sign-in off on the network, the web UI shows `ui-sign-in-off-network` at the top of every page, not only the start page: a person who opens a deep link must see it too. On loopback the start page keeps its note that anyone on this machine can use Ladderback. The UI reads the session once per load, as it does for the standing; if that read fails the page shows neither note until it is reloaded, the same limit the loopback note has.
5. **With sign-in on, nothing changes**: the plain-HTTP warning stays a log record, as decision 70 has it.
6. **The tests bind `0.0.0.0:0`.** It is beyond loopback by the rule, every runner has it, and port 0 picks a free port, so no scenario needs a `skip!`; requests reach the socket through `127.0.0.1` with an explicit `Host` header, which is what the request checks read.
7. **Behind a proxy, the same line per name (#398, 2026-11-14).** With sign-in off on loopback, an `--allowed-host` that is not a loopback name is one a reverse proxy can bring anyone to the daemon by. The daemon says, on stderr as in point 3, one `cli-warn-sign-in-off-behind-proxy` line for each such name, after it binds; the log line that anyone on this machine can use Ladderback stays.

## Risk that remains

Anyone who can reach the address can use every route: run and change backups, set hooks and `password-command` (and so run commands as the daemon's user), and, once restores exist, read whatever any repository holds, other machines' backups included in a shared repository. That is the trade Backrest's users make too, and the daemon, the README and every page say it. The proxy-less ways to narrow who may reach it, such as trusting only some networks, are #504.

Left out: a setting in `config.toml` (the flag is per start, as `--allowed-host` is), and a confirmation flag such as `--i-know`: the warning is enough for Backrest's users, and a flag would only be added to service files once and forgotten.
