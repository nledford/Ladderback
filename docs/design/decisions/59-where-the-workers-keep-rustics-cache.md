# Decision 59: Where the workers keep rustic's cache

**In Ladderback's own cache folder, one cache slot per running worker, and never a reason to refuse a start** (recorded 2026-11-11, §4.1; #258). The cache folder sits beside the config and data folders: `LADDERBACK_CACHE_DIR` when set to a non-empty value, else `~/Library/Caches/ladderback` on macOS and `$XDG_CACHE_HOME/ladderback`, or `~/.cache/ladderback`, on Linux. A worker of a repository whose ID is known keeps rustic's cache in `<cache folder>/<repository ID>/<slot>`.

Why:

- **The platform's cache folder, not the data folder.** Nothing in it is needed: a lost cache is read again from the repository, and a user who clears caches loses only time. rustic tags each slot with a `CACHEDIR.TAG`, which backup tools can be told to skip.
- **An override of its own, like the config and data folders,** naming the folder itself. Every daemon a test, a UI journey or `just try` starts points it at a scratch folder, so no test writes to a developer's real cache, and `tests/isolation.rs` fails when one does. A service with no home directory sets it: the systemd unit M2's service install writes points it at the unit's `CacheDirectory=` (`$CACHE_DIRECTORY`), a folder systemd makes, gives the service user and labels for SELinux. The unit can also set `CacheDirectoryMode=0700`.
- **Slots straight under it.** The folder already ends in `ladderback`, so the engine's root no longer adds a `ladderback` segment of its own; the default path is the one §4.1 named before, `~/.cache/ladderback/<repo-id>/<slot>`.
- **Private folders.** The cache folder is made 0700 when the daemon makes it at start, as the XDG base directory specification asks of the folders it makes, and so is every folder missing above it; a cache folder already there keeps its mode: it is the user's, or systemd's (a `CacheDirectory=` is 0755 unless the unit says otherwise). Every folder under it is always made 0700: the repository's folder and the slot, and the cache folder itself when it was removed while the daemon runs and the next job makes it again. So rustic's files sit under a folder of the daemon's user alone, however wide the cache folder is. The cache holds rustic's encrypted index, snapshot files and tree packs, and its names hold repository IDs, never a secret (I4).
- **No folder, or one that can't be made or written to, means no cache, said once in the log.** At start the daemon makes the folder if it must and then makes and removes a file of its own in it; if either fails, it warns once, naming the folder and the OS's reason, and its workers run without a cache, rather than every job warning again. The daemon never refuses to start over a cache: without one, each job reads the index from the repository, as every job did before. A slot a worker later can't make or lock is said in that job's log, and the job runs without a cache; a write to the cache that fails once rustic has it (a full disk) is rustic's own warning, and the job goes on.
- **A relative `XDG_CACHE_HOME` is ignored,** as the specification says; it would name a folder under whatever directory the daemon was started in. The config and data folders still take a relative `XDG_CONFIG_HOME` or `XDG_DATA_HOME` as it is, an older choice this decision leaves alone.
- **A slot is free once its worker's process is gone,** a moment after the operation has ended: a job of the same repository that starts within that moment takes the next slot, with a cold cache.
- **Two daemons sharing one cache folder** (one `LADDERBACK_CACHE_DIR` for both) are kept apart by the slots' locks: a race for a slot that one of them loses means that job runs with a cold cache, or none, never a write to a slot another worker holds.
- **Nothing bounds or cleans the cache yet** (#262). Each slot is a full copy of what rustic caches for its repository, so a repository that often runs several workers at once keeps several copies; a repository that is removed or initialised again leaves its folder behind; and a worker that is killed can leave a `-tmp-` file in its slot.

Only `serve` builds an engine; `import-profile` and the other commands open no repository.
