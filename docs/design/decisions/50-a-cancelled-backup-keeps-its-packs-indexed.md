# Decision 50: A cancelled backup keeps its packs indexed

**A backup cancelled while it archives winds down through rustic's own end of a backup: the index of every pack it wrote is saved, and no snapshot is written** (recorded 2026-11-11, §4.1; #188). Before, SIGTERM ended the worker at once. rustic saves a backup's index only every 5 minutes or 50,000 blobs and at its end, so a cancel left the packs written since the last save with no index listing them: `rustic check` warned about each until a prune removed them, and the next backup saved the same data again.

rustic_core (rev `01fe284`) has no cancellation and no hook between its index save and its snapshot write (`Archiver::archive`), and saving an index file is not public. Decided, without patching it:

1. The worker backs up through the public `Repository::archive`, with the `LocalSource` that `Repository::backup` would build wrapped in a `CancellableSource`. Once the cancel is asked for, the source lists, opens and reads nothing more, and gives up its size scan, so rustic finishes the backup as it finishes any: the packers write their last packs and the indexer saves the index of all of them. The index is rustic's own, of this worker's packs only: nothing else in the repository is read or rewritten, so concurrent backups and prunes see what a finished backup would leave, and nothing is deleted (I2).
2. The backend a snapshot is written to first is wrapped so that it refuses a snapshot once the cancel is asked for: the hot half of a hot/cold repository, since rustic writes the cold half's copy only once the hot half has it, and otherwise the repository. That refusal is what keeps the partial backup from becoming a snapshot; a cancel that comes after the snapshot was written leaves it, as before, and a cancel between the two halves' writes can't leave it in one half alone.
3. SIGTERM asks for the cancel. When no backup is archiving, the worker exits at once (143), as before. When one is, the handler ends the event stream and the job ends the worker, with 143, once rustic returns; the daemon records the operation `Cancelled` as before. The wind-down is bounded by the daemon's grace period (its SIGKILL), and by 30 s when the daemon is gone.
4. The daemon's stop sends its SIGTERM to the worker alone, no longer to the worker's process group: the `rclone` or `ssh` that an rclone or SFTP backend started is in that group, and it would end at once, leaving the wind-down nowhere to save to. The group still gets the SIGKILL, at the end of the grace period or once the worker has exited. A SIGTERM sent to the whole group from outside (a service manager stopping everything) still reaches those programs, and then the index may not be saved.

What a cancel leaves: the packs it finished, indexed, and no snapshot. The blobs of a file cut mid-read and the trees of the partial backup are indexed but unused; a check doesn't warn about them, and a prune removes them while their packs are unused, or repacks those packs past its unused limit once a later backup reuses some of their data. A worker killed before the index is saved leaves unindexed packs, as before; so does a backup stopped at its deadline, which doesn't wind down (#209).

Rejected: `Repository::repair_index` after the cancel, because it reads and rewrites every index file of the repository and would index another backup's packs in flight, racing that backup and a prune; explaining the packs in the check's result instead, which leaves the data to be saved again.

The backend wrapper names `bytes::Bytes`, which rustic_core's backend traits use and don't re-export, so `adapters/engine` depends on `bytes` (already in the lock file, through rustic_core), with the maintainer's approval.
