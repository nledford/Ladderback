# Decision 83: A progress bar a screen reader can reach, and that never chatters

**A running operation's progress bar is a focusable `role="progressbar"` named for what it measures and for its run, which draws every report but tells a screen reader its value (the step, the percentage, the amounts and the time left) at most every 30 s while the step stays the same, and at once when the step changes** (recorded 2026-11-12, §4.4, §4.5; #428). §4.5 described a focusable, throttled `<progress>` with a full value text; the component was a `div` outside the tab order whose `aria-valuetext` was only "N%" and changed at every report, so a screen reader that speaks value changes could speak four times a second.

Decided:

1. **Focusable wrapper, not native `<progress>`.** The bar is a `div role="progressbar" tabindex="0"` that holds everything it draws: the step line, the track and the percentage (or the step in its place). Its children are presentational, so a screen reader hears the value text alone, and the focus ring surrounds what a sighted reader sees, also while the bar is indeterminate (WCAG 2.4.7). A native `<progress>` was rejected: it draws from its value, which is throttled, so it couldn't move smoothly; it can't hold the step and text; and a hidden one beside a visual bar would have a focus ring around nothing.
2. **Named for what it measures and for its run**, as its row and its Cancel button are (`web::operations::progress_label`), so a check's bar is never announced as a backup's and two running backups' bars are told apart (WCAG 2.4.6): a backup by its plan, "Backup progress of home" (`ui-plan-progress`); any other run by what runs and its repository's alias, "Check progress of demo", "Forget progress in demo" (`ui-operation-progress-of`); a run the log names neither for by what runs alone, "Check progress" (`ui-operation-progress`). A kind this build doesn't know is an operation: "Operation progress on demo".
3. **What is told, and when (`web::progress::Teller`).** The first report is told at once. A report that tells the same as the exposed value changes nothing. A new step, a total learnt or lost, and the total newly reached are told at once. Any other change waits until 30 s after the value last told, and then the latest report is told; one timer waits for it, replaced by a newer one, cleared when the value is told sooner and when the bar goes away (`Wake`), so a removed row leaves no timer to fire. The timer waits in whole milliseconds, rounded up (`wait_for`), so it never fires a little before the hold is over only to be set again. A bar that goes while it holds focus, as it does when its run ends, hands focus to the element its `then_focus` prop names, so focus never falls to the page (WCAG 2.4.3): on the Operations page, its row's header, which takes focus from a script (`tabindex="-1"`) and is no tab stop. Its cleanup does this, which runs before the bar leaves the page. The fill and the visible text follow every report; the fill moves with a short transition that the reduced-motion rule removes, and it then jumps to the value.
4. **The time left (`Pace`).** Only for a bar with a total and not yet at it. It is measured from the first report of the same step and total that the page saw, and starts again on a new step, a new total or a count that goes back. It is told once that measure has been watched for 30 s and has done at least 1 % of the total since: the rest of the total at the average pace since then. Under a minute is "less than a minute"; then the nearest whole minute; from 59 min 30 s the nearest whole hour. A page that opens mid-step waits 30 s before it says any time left.
5. **The value text.** `ui-progress-value` takes `$step` (the step's own message, already translated), `$percent`, `$done` and `$total` (sizes when the bar counts bytes, plain numbers otherwise), and `$left` (`none`, `soon`, `minutes`, `hours`) with `$minutes` or `$hours`. Each step message is a complete clause, and the translator places it in the value's message; the code joins nothing. Without a total the value text is the step's message, or `ui-progress-working`, and there is no `aria-valuenow`, never 0 % (#422).
6. **The unit on the wire.** `operation-progress` carries `unit`: `bytes` for a bar of bytes, `count` for a counter or a spinner. A daemon older than the field leaves it out, read as `count`; a unit newer than the page reads as `Unknown`, shown as a plain number.

Rejected: telling the value only on focus (a screen reader in browse mode reads the bar without focusing it, and would hear a stale value); a shorter hold (§4.5 already set 30 s; whether bars over-announce is checked in each milestone's manual screen-reader pass, §4.5); the last report's pace for the time left (it jumps with every pause the engine takes).
