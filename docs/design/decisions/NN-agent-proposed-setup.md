# Decision NN: How an AI agent proposes a backup setup for a person to confirm

**An AI agent (or any API client with the `propose` scope) can propose changes to an agent's configuration, as a list of typed changes, and nothing changes until a person approves the whole proposal in the web UI: Ladderback writes the plain-words summary and the exact `config.toml` diff from the changes itself, shows separately what the proposal could delete, which maintenance it claims and every command it would add, each command needing its own tick, and approval needs step-up confirmation. The agent names secret sources, never values. A proposal is checked at submission without resolving a secret, running a command or contacting a location; it is applied in one step under the configuration write lock, and it expires after 48 hours. There is still no MCP tool that approves anything** (recorded 2026-11-14, §0, §3.1, §4.4, §4.6, §10.1, §10.5; #518, approved by the maintainer). It amends decision 20 ("nothing … edits config or adds a command") and I4 (one display of a generated password, below).

The terms are in the glossary first (§3.1): a **proposal** and a **configuration change**.

## Why

People will expect to ask an agent to help them define, build and set up a backup strategy: which folders matter, what to leave out, where to send it, how long to keep it. Decision 20 kept every config edit away from MCP because a model-driven client is not a human confirmation, and that reason stands. What changes is that the agent no longer edits: it proposes, and a person confirms in the one place an agent's host can't draw or auto-approve, the web UI. The feature guards against a confused or prompt-injected agent using its MCP or API access. It does not guard against code execution: an agent with a shell as the daemon's user can edit `config.toml` directly and bypass all of it.

## Decided

1. **A proposal is a list of typed changes** (`add-repository`, `change-repository`, `remove-repository`, `add-plan`, `change-plan`, `remove-plan`, `set-retention`, `add-hook`, `remove-hook`, `claim-maintenance`, …), parsed into domain types where the request enters (§3.1), never `config.toml` text or a patch. Each configuration change is applied by a method of `AgentConfig`, which keeps its rules, and the proposal applies them all in one config edit. The web UI's plan editor sends the same change type, so there is one way to write the configuration. `Proposal` is an aggregate of the Planning context: an ID, the agent's identity (its token's label), the configuration it was based on (a hash of `config.toml`), the changes, the agent's rationale, a status and an expiry.

2. **Lifecycle.** `pending` → `applying` → `applied` or `failed`; from `pending` also `rejected`, `withdrawn`, `expired` and `stale`. Approval starts the apply in the same atomic status change in the store, so nothing sits approved but unapplied, and of two tabs approving at once only one does. A pending proposal **expires 48 hours** after it was made, a fixed limit; ended proposals stay visible as history.

3. **`stale` is narrow.** When the page opens, the typed changes are applied again to the current file and the person approves that rebuilt diff. Only a change that no longer applies (a plan removed meanwhile, an alias taken) makes the proposal `stale`, and the agent proposes again. A comment edit, a load migration or the daemon recording a repository ID doesn't.

4. **What the agent sees and what the person sees.** The plain-words summary is generated by Ladderback from the changes, never written by the agent, so an agent or a prompt injection can't describe one thing and propose another. The agent's rationale is shown apart from it, labelled as the agent's words. Values the agent chose are rendered as code, with bidi isolation; labels, aliases, tags, paths, hosts and hook arguments holding format, bidi or confusable characters are refused at submission. A command is shown as its program as resolved on `PATH`, with its arguments as a list. A remote location the configuration has never held is marked "new destination". Notifications of a proposal carry facts only, never its rationale or labels.

5. **Checks at submission are pure:** parsing and the domain rules, nothing else. No secret is resolved, no command runs and no location is contacted: a connection check there would send a stored credential to an address the agent chose, run a `password-command` nobody ticked, and let the agent scan the network. What the checks find goes back to the agent, so it can fix its draft before a person sees it: warnings (`glob-never-matches`, two plans over the same sources) and refusals (an inline secret, a credential sent over plain HTTP, and whatever the configuration already refuses, such as a retention policy that keeps nothing on a plan with history, decision 25). Testing a new location is a button on the confirmation page, which only a person starts.

6. **Approval is in the web UI only, and for the whole proposal.** A "Pending changes" page, with a count in the navigation, shows the summary, the exact diff and, separately, the forget preview (point 8), any maintenance claim (point 9) and each command verbatim (hooks, `password-command`), each with its own tick. **Approve** needs every command ticked and step-up confirmation (§10.4): the admin password, or with sign-in off the proposal's short ID. Step-up attempts share the sign-in waits (`SignInWaits`, §10.1), so a stolen session cookie can't guess the password through approve. The approval is bound to what was shown: a hash of the base file, a hash of the diff shown and a hash of each ticked command. **Reject** takes a reason per change, which the agent can read and revise that part against. There is no partial approval: it would create combinations nobody validated, and the agent proposes the rest again instead. Proposals after a rejection are rate-limited per token, and the page shows how often an agent's proposals were rejected.

7. **With sign-in off, approval is a convenience, not a safety boundary.** Nothing then tells a browser from an agent's HTTP call, so an agent that can send HTTP requests can approve its own proposal. The design, the "Pending changes" page and the docs say so plainly. With sign-in on, approval needs a signed-in browser session plus step-up, and a token can never approve.

8. **The forget preview covers every repository the proposal touches** (I6): the snapshots the retention policies would delete before the proposal and after it, and the difference. A retention change is only one way a proposal can delete: so are a new plan whose ID matches an orphaned group's plan, a change of a plan's ID, repository, `group-by`, `keep-tags` or host, every removal, and a maintenance claim on a repository plans already write to. For a repository being connected, the page asks for the password first, then computes the preview.

9. **A maintenance claim defaults to off** on the page and shows the evidence of another owner (I1; decision 62).

10. **Secrets are references.** The agent proposes only a `new` secret, or `existing` for the location that secret was configured for. A `password-file`, a `password-command`, an environment variable, or reuse of a secret for another location is chosen by the person on the page, which labels it "the agent may know this value". A `new` secret is stored in the system keyring (#476), where the page offers **Type it** or **Generate one**. Where the keyring isn't available (headless servers, system services), and for backend option credentials, which take only `${VAR}` and `${file:}` (§10.2), the person types it and the page writes it to a mode-`0600` secret file under the data folder and references it; "Generate one" is offered only for the keyring (point 11). The approve request carries a typed secret, so the redactor of the job that initialises the repository is seeded with it. The agent only ever sees that a secret was stored, and a failed apply sends it codes only; masked details appear only in the web UI.

11. **A generated password is shown once (amends I4).** "Generate one" displays the password exactly once, in the response to the confirmation page's request that generated it: never stored outside its keyring entry, logged, sent as an event or readable again. The person must confirm "I have saved it" before approving, because a password kept only in one machine's keyring is lost with that machine, along with every backup it encrypts. A canary test proves the password appears in that one response and nowhere else.

12. **Applying.** Under the configuration write lock (decision 57), in order, stopping at the first failure:
    1. reload the file, rebuild its text from the typed changes and require it to match the diff the person approved;
    2. store the new secrets;
    3. connect to or initialise the repositories (`init` writes a repository's first files, harmless if a later step fails);
    4. write `config.toml` through decision 69's editor in one atomic save, only if the file's bytes are unchanged just before the rename, as recording a repository ID already does (`ChangedMeanwhile`);
    5. reload the scheduler.

    A hand edit made during the apply is never overwritten: the apply stops before the write, keeps what steps 2 and 3 did, and the page shows the rebuilt diff for a new approval. The proposal records each step that succeeded, the keyring items it created and the repositories it initialised, so a failure is reported exactly and a retry, started by a person under the same approval rules, reuses them (connect, not init). A proposal the daemon finds `applying` when it starts resumes, or becomes `failed` with what to clean up listed. The config history entry the save makes (decision 29) links to the proposal, recording who approved what, when and from where. Undo is reverting to that history entry; keyring items and initialised repositories aren't undone, and the page says so.

13. **The dry run** (`dry_run_plan`) walks a draft plan's sources through its source filter and returns how many files and bytes it would back up and what each exclude removed: counts and sizes only, never paths. It never runs a hook or a secret source nobody approved and opens no repository, so it gives no "new data" figure. It runs one at a time outside the backup concurrency limit, gives way to scheduled backups, has a short time limit and a per-token rate limit, and reads only within the **allowlist**: one list of folders, empty by default, on the Settings page. "Add home folder" there warns that the home folder holds `~/.ssh` and browser profiles.

14. **API and MCP.** `/api/v1/proposals` (additive): create, list, get and withdraw with the new `propose` token scope; approve and reject accept only a browser session, never a token. Pending proposals per token and a proposal's size are capped, as input-derived limits (§13.5). The events WebSocket announces status changes. MCP gains `propose_setup`, `check_proposal` (the submission checks only), `dry_run_plan`, `get_proposal` and `withdraw_proposal`, in connect mode (§4.6), with #517. There is no approve tool.

15. **Order of work.** First, plan writing as a use case with the plan editor in the web UI, valuable alone and the apply's last step; then the `Proposal` aggregate, its REST API and the "Pending changes" page, usable by REST clients before the MCP tools, and needing M3's scoped tokens and step-up confirmation; then the dry run; then the MCP tools, with the MCP server (#517) in M3 (§14). Proposals made on the hub come later, with editing plans from the hub, through `UpdatePlan` (decision 2).

16. **Proof.** Scenarios: a proposal changes nothing until approved; a token can't approve; a proposal with a command can't be approved until that command is ticked; a change that no longer applies makes a proposal `stale`, and a comment edit doesn't; the summary matches the changes even when the rationale claims otherwise; no secret is resolved and no location contacted at submission; a dry run runs no hook; the forget preview is shown for a retention change and for a new plan that reuses an orphaned plan's ID; a hand edit made during an apply is kept; approval with sign-in off works and the page says it is no safety boundary; the I4 canary scans every proposal response and MCP result, and finds a generated password in its one response and never again.

**Cut from v1:** a folder-size probe (the limited dry run covers it) and a `wait_proposal` tool (`get_proposal` and the events cover it).

## Rejected

- **A: the agent submits `config.toml` text or a patch.** The agent would write TOML, checks would come late, the plain-words summary would have to be worked out backwards from text, and it fights decision 69's keeping of the person's layout.
- **C: the agent writes directly with a scoped token, plus an undo window.** It breaks the decided web-UI confirmation, and a forget (I6) or a maintenance claim (I1) can't be undone.
- **D: the agent fills a wizard through MCP elicitation.** The agent's host draws the form and may approve it automatically, so it is no human confirmation (decision 20).
