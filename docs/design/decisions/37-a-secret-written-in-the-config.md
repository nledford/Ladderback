# Decision 37: A secret written in the config

**A typed warning when the config loads, in the log and as a quiet note on the repository's row; never a refusal** (recorded 2026-11-10, §10.2; #27). `config-inline-secret` names the setting (`password`, `options.NAME`), never the value: an inline password, and an option whose name says it is a credential (`is_secret_option`) and whose value holds no `${…}` reference. The daemon logs one line per secret when it starts and loads the config; `GET /api/v1/repositories` carries the same warning in the row's `warnings`, and the Repositories page writes it as text in the password cell, so no colour is needed to read it. Why: the secret works as written, so a refusal would break setups that run today, while a person should be told that a reference keeps it out of the file and its history copies; the form's own hint about where a typed password is kept stays. A repository saved while the daemon runs is noted on its row at once and logged at the next start.

**A password in a location is one too** (added 2026-11-11, #190). A location that holds a password as text gets the same treatment under its own code, `location-secret`, whose words fit a location: put a `${VAR}` or `${file:/path}` reference where the password is, or give it in the backend's own option. Its `kind` argument is `url` for that advice and `rclone` for an rclone location: rustic hands that location to rclone as an argument, where a reference is refused (§10.2) and other users of the machine can read it, so the warning says to set the remote up in rclone's own configuration file and name it in the location (`rclone:remote:path`) instead. It is said by the import (field `repository.repository` or `repository.repo-hot`), when the config loads and on the row (field `repository` or `repo-hot`), and names only the setting, never the location, the user name or the password (I4). `location_secret_written` decides it in the domain: the URL is what follows the first `://`, its authority ends at the first `/`, `\`, `?` or `#` (as the WHATWG URL standard reads a special scheme), the userinfo at the last `@` of the authority, and the password is what follows the userinfo's first `:`; a user name alone, an empty password, and a password that is or holds a `${…}` reference are not text. Percent-encoding is not undone: an encoded password is still in the file. A `${…}` is one opaque piece, so the `/` and `:` of `${file:/path}` end nothing. An rclone connection string counts when one of its settings, the `key=value` pieces between commas up to the `:` that starts the path, has a key `is_secret_option` names and a value that, quotes aside, is not empty and holds no reference. A value quoted with `'` or `"` may hold `,` and `:`, and a quote written twice inside it stands for itself, as rclone reads it; what follows the settings is the path, so `rclone:remote:backups/token=2024` is no credential. `is_secret_option` takes `pass`, the password option of rclone's SFTP, FTP and SMB backends, as a whole name only, so `bypass_cache` and `passive` are not credentials; the redactor and the export's refusal of an rclone credential read the same list. An option whose value is a URL with a password in it counts as a credential option (`config-inline-secret`, `options.NAME`). A `@` in a URL's path, query or fragment is not a userinfo, so a location rustic can't parse (a raw `/`, `?` or `#` in the password) gets no warning; its password is still masked wherever it shows, as before.
