# Decision 134: A run whose keyring is locked waits for it to be unlocked

**A run nobody waits on whose repository password is in a keyring the service answers is locked isn't refused at once: it waits for the keyring to be unlocked — asking only whether it is locked, never reading the entry, so waiting can raise no unlock prompt — and reads the entry again the moment it is. It gives up when the plan's next run is due, never waiting past its successor, and is then refused once as `secret-keyring-locked`. While it waits the run holds no place in the queue, so the scheduler goes on: it waits on a task of its own under the freeze of the daemon's stop, and takes a place only once the keyring is unlocked, giving way to a newer run of its plan. A retry and a run with no next run are refused at once** (recorded 2026-11-20, §5, §10.2; #1221).

## Why

- **The locked state outlasts any uptime bound.** Decision 116 waits for a Secret Service that isn't on the bus, for 2 min of the daemon's uptime: the login race. A locked keyring is the other half of the same start — the service answers, locked — and it lasts from boot to login on a machine that lingers, hours past any bound counted from the daemon's start. Before this, every run that fired in that window failed and the backup was skipped (#1221).
- **Waiting can't prompt.** The wait asks the collection's `Locked` property, a read that touches no entry; only the answer `Unlocked` reads the entry again. A dismissed unlock prompt is a no: that refusal still fails at once and is never asked again, decision 116's rule untouched.
- **The bound is the plan's next due run** (the maintainer's decision on #1221). The scheduler plans the following run before it starts one and hands it to the run, so a waiting run never outlasts its successor; when the keyring never unlocks, each run of the schedule is refused once, at its successor. A queued backup the daemon takes up again has nobody waiting on it either: it is handed the next run its plan's planner kept — the same run the scheduler plans by — and waits on a task of its own, its operation showing as queued, so the queue's other leftovers go on.
- **No place is held while waiting.** The run parks on a task and gives up the place the scheduler gave it, so other plans' backups run while it waits; once unlocked it takes a place again, and gives way to a newer run of its plan that is going, running or waiting.
- **A log line, as the service wait's** (decision 116, the maintainer's Option B): the wait happens before an operation exists, so no wire step shows it; a queued run taken up again has its operation already, and it shows as queued while its run waits.
- **The daemon asks twice before it waits.** The probe that decides whether a run parks reads the entry, and the armed resolution reads it again and finds the keyring locked; from then until the keyring is unlocked no entry is read. A locked answer comes without a prompt — the service answers locked rather than asking — so neither read prompts. An entry the service still finds locked once the keyring says it is unlocked is read again only every 10 s, within the same bound, never in a loop.
- **Built from the configuration as it stands after the wait.** A wait can last hours, so the run reads the configuration again once the keyring is unlocked: a plan deleted while it waited doesn't run, and one that now backs up to another repository than the one whose keyring it waited for doesn't run there. A queued backup recorded on a repository its plan had left already isn't parked at all; it ends at once.
- **A queued run's wait can be cancelled.** Its operation shows as queued, so a cancel of it ends the wait and the operation, cancelled, with nothing run, as a cancel of a backup waiting for its turn does (§4.2).

Cost: a backup can start hours after its schedule, at login. On a machine meant to back up while logged out, the Repositories page's note and the move to a password file or a systemd credential (#1222) say so instead. Amends decision 116, whose "a locked keyring fails the run at once" now holds only for a run with no next run to wait within.

A service that accepts connections and never answers is asked whether the keyring is locked one question at a time, never once per poll; a question that is lost, by a panic or the runtime's stop, lets the next one be asked.
