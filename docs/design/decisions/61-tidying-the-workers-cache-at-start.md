# Decision 61: Tidying the workers' cache at start

**Each time it starts, before it listens, the daemon removes from its cache folder what no worker will use again: the cache of a repository no entry records, the cache slots above the highest one in use, and rustic's unfinished files a day old; nothing a running worker holds, nothing not named as Ladderback's, and nothing a link points to** (recorded 2026-11-11, §4.1; #262). Decision 59 put rustic's cache in the agent's cache folder and left it unbounded.

What is removed, in a folder named exactly as a repository ID (64 lowercase hex digits), and in it only from the folders named as a slot's number (`0` to `63`, no leading zero):

- **A repository no entry records** (removed from the configuration, or initialised again under a new ID): every slot no worker holds, then the repository's folder once it is empty. While an entry records no ID, there is none (below).
- **Spare slots of every other repository:** the slots above the highest one in use. Slot 0 is always in use, being the one a lone job takes; a slot is in use too when another process's worker holds its lock (one that outlived a restarted daemon, or one of another daemon sharing the cache folder), or when its lock can't be looked at. A moment of many workers at once then leaves its slots behind only until the next start.
- **Unfinished files** in every slot a repository keeps: regular files named as rustic names one, `<64 hex digits>-tmp-`, last written more than a day before. rustic writes a cache file there and renames it once it is complete, so a worker killed in between leaves it behind for good. The day is the one the worker's own clean-up of a local repository's temporary files waits (§4.1).

Why:

- **A slot is only touched while the daemon holds its lock.** The lock is the one a worker holds for as long as it runs (decision 59), so a running worker's slot is never removed or written to. A daemon looking for a slot being removed finds it held and takes the next one; a worker that comes for it finds it held and runs without a cache. A lock is only taken while the slot's path still names the folder locked, not a link: a worker that opened a slot just before it was removed finds it held too, and never holds the removed folder while one made again at the path is nobody's. A repository's folder is never removed whole: slot by slot, and then the folder alone, which fails harmlessly when a slot is kept or a new one appeared meanwhile.
- **Only what is named as Ladderback's.** The cache folder can be any folder `LADDERBACK_CACHE_DIR` names, a wider one of the user's included. A folder or file whose name is not a repository ID in rustic's form, and anything in a repository's folder not named as a slot, is left alone; inside a slot, every file is rustic's.
- **A link is never followed.** Folders are told apart by the type of the entry itself, not of what it points to: a link named as a repository or a slot is left alone, a link inside a slot being removed is removed itself and what it points to is kept, and a link named as an unfinished file is not a regular file and is kept.
- **At start, and only then.** No worker of this daemon runs yet, so nothing of its own is in use; and starting is the one moment every daemon has until the scheduler (M2) can run it as a task of its own. It costs the start the time it takes to list the cache and remove what goes, in a blocking task the start waits for.
- **The log says what went and its size,** one line per repository and kind (`removed the cache of repository <id>, which no repository entry records: <n> cache slot(s), <bytes> bytes`, `removed <n> spare cache slot(s) of repository <id>: <bytes> bytes`, `removed <n> unfinished cache file(s) of repository <id>: <bytes> bytes`), at the info level, the size of the files themselves with links not followed. What can't be removed or read is a warning naming it and the OS's reason; the start goes on, and nothing else is said when nothing goes.
- **No size cap.** A slot keeps what rustic keeps: index and snapshot entries rustic prunes itself when it lists the repository, and tree packs it prunes only in a check. A cap would remove data a job is about to read again, and keeping the cache is cheaper than reading it again; with spare slots gone, a repository's cache is as many copies as the most workers it ran at once since the start.
- **Two daemons sharing one cache folder** each remove the slots no worker holds of the repositories the other records and they don't. That costs the other daemon's next job a cold cache, never a slot one of its workers holds.

A cache folder the daemon can't use (decision 59) is not tidied. **While an entry records no repository ID, no repository counts as one no entry records,** and every repository keeps its folder: the tidy can't tell which folder is that entry's repository's, and removing it would cost a repository in use a cold cache. Its spare slots and unfinished files still go. The entry's next job records the ID (decision 57), so what this keeps is disk space until then, and the next start after that removes the cache no entry records.
