# Decision 32: Worker messages that outgrow the cap

**The cap stays at 1 MiB and the sender splits what is too long; no list in a message grows with a repository** (recorded 2026-11-10, §4.1, §9; #83, #76). Two lists met the cap: a forget's snapshot IDs in the job spec (about 15,000 of them filled it) and a listing in its one result message (about 2,500 snapshots). Decided: a forget or adoption runs as jobs of at most `MAX_JOB_IDS` (5,000) IDs, one operation and one merged summary; a listing is a series of `snapshots` events of at most 512 KiB with a closing count; each snapshot is cut to 64 paths, 64 tags and 1 KiB a text, with `paths_truncated` and `tags_truncated` saying so; a listing past 200,000 snapshots fails rather than lists in part; `assess`'s reads time out after 10 minutes. Why: every other way keeps a bound the cap was meant to give. Raising the cap (or special-casing it for a forget) only moves the ceiling and lets a hostile repository or a long history size the buffers (§13.5, rule 2); refusing up front in `assess` leaves the repositories that need forget most unable to run it; a newest-N listing with a flag and pagination makes the UI and forget decide on part of a history, which for forget is wrong (a policy sees the snapshots it does not name). Splitting is safe because each job touches only snapshots the selection named (I6), so a run that stops partway leaves done what was done, says so, and the next run selects what is left. Not done: a cancel between a forget's jobs does not undo the earlier ones.
