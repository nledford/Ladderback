# Decision 49: One name per repository

**An agent's configuration names a repository once: two entries with one recorded repository ID, or at one location when either knows no ID, are refused, and connecting, initialising or importing a repository the configuration already holds under a new alias is refused with `repository-already-configured`, naming the alias it has** (recorded 2026-11-11, §6.1, §6.2, §7.3; #186). Connecting one repository as "nas" and again as "backup" was accepted, so its plans split into two histories, two maintenance requests (I1) and two lines on every page for one set of snapshots. Decided: (1) `RepositoryConfig` keeps the rustic repository ID it read when it connected or created the repository, written as `repository-id`; an entry written by hand or imported from a profile has none, since Ladderback never opened it. (2) A location is the whole of where the entry points: its `repository` string, `repo-hot`, and the three option sets (`options`, `options-hot`, `options-cold`), where an `opendal:` backend keeps its bucket or root (`RepositorySettings::same_location`). The password and the options that hold a credential are how to open it, not where it is, and are left out; an option is a credential when the `inline-secret` warning takes it for one (`is_secret_option`, by name), so the two never disagree. Moving a credential from text to `${VAR}`, as that warning advises, adding one or removing one leaves the same location; every other option still counts, so two buckets of one backend are two locations. The exception is a drive: on opendal's `dropbox`, `gdrive`, `onedrive` and `yandex-disk` services only a credential (`access_token`, `refresh_token`) names the account, so two accounts can hold one `root`, and leaving the credentials out would make them one location: a configuration with both refused, the second account's connect or init refused, and its profile imported under the first account's alias added to that entry, so its plans would back up to the wrong account. There the option sets that reach the drive keep their credentials (`options`, and `options-cold` for a `repository` on a drive, `options-hot` for a `repo-hot` on one). The domain tells a drive from the `repository` string alone (`opendal:<scheme>`, the scheme read as opendal reads it, without case and up to a `:`), from one list (`DRIVES`), and knows no opendal type. Its cost is accepted: on a drive, a token moved from text to `${VAR}` is another location, so a profile that writes it the other way is refused under the alias that holds it, as before this decision, and two entries for one account with the token written two ways are caught as one repository only when both know their ID. Nothing backs up to the wrong account. Two entries are one repository when both know their ID and the IDs are equal; when either knows none, when they are at one location (`RepositoryConfig::is`). So the ID decides alone once both are known: a location that now holds another repository is another one, and one repository reached two ways (an SFTP URL beside a mounted path) is one. A location written two ways is caught only when both entries know their ID; comparing locations by what they resolve to would need the backend, and the configuration is read without one. `AgentConfig::new` refuses two entries that are one repository (`Violation::SameRepository`, at the second entry's key, both named). (3) Connect and init refuse a taken alias first (`repository-alias-taken`), then a repository the configuration holds under another alias (`repository-already-configured`, HTTP 409); init checks before it creates anything. (4) A profile knows no ID, so an import compares its location, with the entry the alias names first: when that entry is at the profile's location the import adds its plans to it, and the entry keeps its settings, hooks, ID and maintenance; the import says which of the entry's settings the profile sets otherwise (`profile-setting-kept`, one per setting: `password`, `maintenance`, `group-by`, `options`, `options-hot`, `options-cold`, `hooks`; an option set can differ only in its credentials), without refusing or merging them; the profile's repository is not written, so no secret it holds as text is said kept as text (`inline-secret`). An alias held for another location (another bucket, or another account of a drive, included) is refused as taken; under a new alias, a location the configuration holds, whatever its credentials (on a drive, with the same ones), is refused as already configured. (5) A job given an entry with an ID compares it with what it opened before it reads or writes anything, and fails with `repository-replaced` (no argument; the two IDs are not shown, as `repository-exists` shows no detail) when the location now holds another repository. The forget preview's in-process read of the retention opens the repository without comparing; it runs only after the preview's listing job, which compared it. The schema stays at 1: the key is optional and a file without it reads as before. Two costs. A downgrade: a build older than this one refuses a file that holds `repository-id` as an unknown key, so going back means removing the key by hand. An upgrade: a 0.1.0 file with two entries at one location (two buckets of one backend are two; two entries that differ only in a credential are one, except on a drive) is now refused when it loads, naming both entries; the fix is by hand: remove one entry and point its plans at the other. Entries written by 0.1.0 have no `repository-id`, and nothing fills it in yet (#200), so they are told apart by location alone. *Extended by decision 80:* an entry with several locations counts as at each of them; the ID still decides alone when both entries know one, a drive's credentials still count, and two locations of one entry at one location are refused.
