# Decision 49: One name per repository

**An agent's configuration names a repository once: two entries at one `repository` string, or with one recorded repository ID, are refused, and connecting, initialising or importing a repository the configuration already holds under a new alias is refused with `repository-already-configured`, naming the alias it has** (recorded 2026-11-11, §6.1, §6.2, §7.3; #186). Connecting one repository as "nas" and again as "backup" was accepted, so its plans split into two histories, two maintenance requests (I1) and two lines on every page for one set of snapshots. Decided: (1) `RepositoryConfig` keeps the rustic repository ID it read when it connected or created the repository, written as `repository-id`; an entry written by hand or imported from a profile has none, since Ladderback never opened it. (2) `AgentConfig::new` refuses two entries that are one repository (`Violation::SameRepository`, at the second entry's key, both named): the same `repository` string, or the same `repository-id`. A location written two ways is caught only when both entries know their ID; comparing locations by what they resolve to would need the backend, and the configuration is read without one. (3) Connect and init refuse a taken alias first (`repository-alias-taken`), then a repository the configuration holds under another alias (`repository-already-configured`, HTTP 409); init checks before it creates anything. (4) A profile knows no ID, so an import compares its location: under the alias that already holds the location it adds its plans and hooks to that entry, which keeps its settings, ID and maintenance; under another alias it is refused as already configured; an alias held for another location is refused as taken. (5) A job given an entry with an ID compares it with what it opened before it reads or writes anything, and fails with `repository-replaced` (no argument; the two IDs are not shown, as `repository-exists` shows no detail) when the location now holds another repository. The schema stays at 1: the key is optional and a file without it reads as before. The cost is a downgrade: a build older than this one refuses a file that holds `repository-id` as an unknown key, so going back means removing the key by hand.
