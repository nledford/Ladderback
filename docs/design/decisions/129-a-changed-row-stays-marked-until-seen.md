# Decision 129: A changed live row stays marked until it is seen

**A row of a live table whose status a live update changed is marked "changed, not yet seen" until the reader sees it: its status reads in bold, an edge in its own color (`--cue`) stands at the row's start, and its status cell says "Changed, not yet seen" to a screen reader. The mark arrives once with decision 130's fade. Focus entering the row sees it, as does Mark all as seen, a button in the page's own row of actions that is always there and hidden, its room kept, while nothing is marked** (recorded 2026-11-20, §4.5; the maintainer's decision).

## Why

Decision 130's first cue lit a changed row once and let it settle in 600 ms. A run that starts, ends or fails while the reader looks at another part of the page, or at another window, is over before they look back, and a badge that flipped unwatched is easy to miss. The fade says that something changed as it happens; the mark says which rows changed since the reader last looked, for as long as that holds.

## Decided

1. **What marks a row.** A change of the value of the table's cued column (`Column::cued`; the Operations page's status) while the row shows. Never the first rows the page shows, a row that arrives, a table built again, an update that leaves the value as it was (a progress report, a re-sort), or a page whose rows a pause holds still; the resume marks each changed row once. A change while focus is in the row is seen as it comes. `table::rules::Marks` decides it on the host.
2. **How a mark shows.** The cued cell reads in bold (700) and a 3 px edge stands at the row's start, on its pinned header: weight and shape, never color alone (1.4.1). The edge is `--cue`, slate-600 `#475569` light and slate-400 `#94a3b8` dark, at least 3:1 against the page and the cue's fill (1.4.11, `just test-contrast`); under forced colors it is `CanvasText`. Its arrival is decision 130's fade, from `--cue-fill` (`#dae0e7` light, `#282f38` dark), the tokens the mark owns, rather than Ledger Gray, so it stays visible on a page that already uses that gray.
3. **What a screen reader hears.** The marked cell says "Changed, not yet seen" after its own words (`ui-table-cue-unseen`, a message that reads on its own), out of sight, until the mark is seen (1.3.1). Nothing is announced: the page's announcer already says a run's end, and a start announced on every live page would be noise.
4. **What sees a mark.** Focus entering the row; Mark all as seen; the row leaving the table; the reader leaving the page, since nothing is stored. A pointer click that doesn't focus anything leaves it, and Mark all as seen clears it. A row with no control of its own, as an ended run's is once its Cancel has gone, takes no keyboard focus: Tab never enters it, and a screen reader's browse mode, which reads it, moves no focus. A keyboard reader sees such rows with Mark all as seen. The one exception is the row whose Cancel had focus as its run ended: focus goes to its header, which sees it.
5. **Where Mark all as seen stands.** In the page's existing row of actions before the table (the Operations page's start buttons; `MarkAllSeen`, sharing the page's `ChangeMarks` with the `Table`), so a keyboard reaches it before the rows whose focus would see their marks one by one. It is always rendered, and while nothing is marked it is hidden with its room kept (`invisible` and `inert`: no Tab stop, out of the accessibility tree), so it comes and goes without moving anything at any width (1.4.10); the row stays on a page with no plans. Its press says politely how many rows it marked as seen and hands focus to the page's heading, which stays (2.4.3). When the last mark goes without a press (a refusal takes the table's place), focus on it goes there too, silently, before `inert` would drop it.

## What it costs

The button's room is a gap at the end of the row of actions while nothing is marked, and a line of its own on a narrow screen where the row wraps. A line above the table for it alone was the other way to move nothing, and the page already keeps a line there for its toast; after the table, a keyboard would cross every marked row, and so see each mark, before reaching it.

A mouse reader whose click lands on a cell's words, not a control, doesn't see the row's mark that way, and clears marks with the button. A keyboard or screen reader can't see one row of an ended run alone either, since nothing in it takes focus; they clear its mark, with the others, with the button. Making each row focusable for this alone would add a Tab stop per row, and the table already has one for its frame.
