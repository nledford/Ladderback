# Decision 78: The Rust toolchain is pinned, and the MSRV is the pin

**`rust-toolchain.toml` names an exact Rust version (`channel = "1.100.0"`), not the stable channel, and the workspace's `rust-version` (the MSRV) is that same version. A new Rust release is adopted by a pull request of its own that moves both** (recorded 2026-11-12, §8.2, §13.12; #409). Supersedes decision 47. The file keeps rustfmt, Clippy and the `wasm32-unknown-unknown` target.

Decided:

1. **One compiler everywhere.** rustup installs the pinned version on the first build in a checkout, so `cargo build`, the recipes and `just install` use it. No workflow names a version of its own: CI's Check and Dependencies jobs, the red-first check, `release-builds.yml` and `release.yml` run `rustup toolchain install`, which installs the version the file names, and CI's other Rust jobs get it from rustup when they first run `rustc` or `cargo` in the checkout. `release-builds.yml` builds and smoke-tests the release archives with `dist build` (decision 54), so a release's binaries are built with the compiler CI tested; `release.yml` compiles nothing, and installs the pin so that release-plz reads the workspace with the same cargo.
2. **The MSRV equals the pin.** `rust-version` in the workspace `Cargo.toml` is the pinned version, and the two always change together. Ladderback is an application: no crate is published (`publish = false`) and it ships binaries (§12), so the MSRV binds only those who build it from source and is not part of §12.1's contract; raising it is not a breaking change. `just msrv`, which built the workspace with the older MSRV in a container, is gone.
3. **A bump is its own pull request,** titled `chore: update the Rust toolchain to 1.x.y`, within about two weeks of a stable release, a point release included. One commit moves the pin and `rust-version` and nothing else, and each fix the new compiler needs is a commit of its own; a fix a user would notice lands first, in a `fix:` pull request of its own, so the changelog lists it (§13.12). New Clippy lints, those that wait for the MSRV included, arrive through the bump, not through a pull request about something else.

Why:

- **A Rust release must not turn every pull request red.** Rust 1.100.0 became stable on 2026-11-12, and every CI run after that picked it up: three `domain::secrets` tests failed on every open pull request at once, through no change of theirs, because masking asked the standard library's `Debug` escaping which characters Go prints, and 1.100.0's Unicode tables changed the answer (#406, fixed by #407). `main` had passed at 18:13 UTC on 1.99.1; every run on 1.100.0 after it failed. With a pin, that breakage shows on the bump's pull request, the one change that caused it, and is fixed there.
- **Builds use the compiler CI tested.** On the stable channel, a contributor's build, `just install` and a release build used whatever stable rustup had installed that day, which CI may never have run.
- **CI proves the floor on every run.** Under decision 47 the MSRV was 1.94 while CI built with stable, so no check held the floor between raises: only `just msrv`, run by hand when a raise was made, did. With the MSRV equal to the pin, every CI run builds and tests with the oldest compiler Ladderback claims to support.
- **Dependencies aren't held back.** The workspace uses `resolver = "3"`, which prefers dependency versions whose own `rust-version` the MSRV meets. At 1.94 that held updates back to releases that still built with 1.94; at the pin it holds nothing back that CI could build.
- **Decision 47's macOS caveat goes away.** macOS 27 can't load the proc-macro libraries 1.94 builds, so the MSRV could be proven only on Linux, in a container, and the README told Mac users to use a newer Rust than the MSRV. The pin builds on every platform CI runs.

Alternatives:

- **Following the stable channel** (as before): no upkeep, and a release's breakage is found on its release day, which is how #406 was caught. But it is found on every open pull request at once, by people whose change didn't cause it, and nothing builds with a compiler CI tested before.
- **A pin, plus a scheduled job that builds and tests `main` on the newest stable** and opens an issue when a release breaks it. It would find the breakage before the bump, but is one more workflow to keep, and the bump's pull request finds the same thing within the two weeks. It can be added later without changing the pin.
- **A pin with an older MSRV kept apart** (decision 47's MSRV beside the pin): it lets a distribution's older Rust build Ladderback, but needs its own check (`just msrv`, by hand and on Linux only) and holds dependencies back, for builders the binaries already serve.

Cost: a bump every six weeks, and one for each point release, by hand: a pull request that changes two lines, the pin and `rust-version`, whose CI shows what the release breaks, plus its fixes. Until it merges, everyone stays on the previous compiler, so new lints and standard-library changes arrive up to about two weeks late. A contributor who builds with a distribution's Rust rather than rustup waits for their distribution to ship the pinned version, or installs rustup.
