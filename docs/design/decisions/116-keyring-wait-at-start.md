# Decision 116: A scheduled run waits for the session's keyring service while the daemon starts

**A run nobody waits on (a scheduled run, a catch-up, a retry, or such a run resumed from the queue) whose repository password is in the keyring holds when no Secret Service is on the session bus yet and the daemon has been up for less than 2 minutes: it reads that one keyring entry again every 10 s until the service answers or those 2 minutes pass, then goes on as it would have, resolved or refused. The daemon's uptime is counted in monotonic time, as the network wait counts its own, so a clock set back can't stretch the window. The daemon logs the wait once, naming the run, the plan and the keyring entry, never a secret; no progress step shows it** (recorded 2026-11-16, §5, §10.2; #877).

## Why

- **The login race is real and short.** At login a user unit can start before the session's Secret Service owns `org.freedesktop.secrets`, and a catch-up or scheduled run fired in that gap fails for want of a password the keyring holds. The network wait (§5, [decision 63](63-the-ports-for-the-conditions-before-a-run.md)) answers the same kind of race with a bounded wait, and this one takes its bound.
- **Only a service that isn't there.** The secrets adapter tells a Secret Service that isn't on the bus (no bus, no owner of its name, `Error::Unavailable`: `KeyringCause::NoService`) apart from one that answered and refused (a locked keyring, `KeyringCause::Locked`, refused as `secret-keyring-locked` since #993; a dismissed unlock prompt, `KeyringCause::Dismissed`, refused as `secret-keyring-locked` too since #993, and `KeyringCause::Refused` before it; a service with no collection, `KeyringCause::Refused`). A dismissed prompt fails at once and nothing asks again, so no run re-prompts a person who dismissed it; a locked keyring is waited out since [decision 135](135-keyring-unlock-wait.md), and a dismissed prompt never is, though it shares the locked code. On macOS the Keychain is never `NoService`: a launchd agent starts inside the session, so there is no race to wait out there.
- **Only a run nobody waits on.** A person who starts a run or tests a repository is answered at once, as before: they are there to read the refusal and to act on it.
- **Only the entry that failed is read again.** The rest of the repository's references are read once, as always (§10.2); nothing is cached past the run.
- **A log line, not a progress step.** A backup's secrets are resolved before its operation exists, as the network wait happens before it, which has no progress step either. Showing the wait on the operation would mean recording the operation first and a new wire step with its text; a wait of at most 2 minutes, only in the daemon's first 2 minutes, doesn't justify that. If it changes, both waits move inside the operation together. A run resumed from the queue has its operation already; it shows as queued while it waits.
- **Stopping the daemon ends it.** The wait is the run's start; dropping that future, as the daemon's stop does, ends the wait, and the run never starts.

Cost: while a run waits, the scheduler waits with it, so another plan's run due in the daemon's first 2 minutes starts once the wait ends, at most 2 minutes after the daemon started. A run resumed from the queue can't be cancelled while it waits: a cancel is answered that the run isn't running, and stopping the daemon ends the wait. Amends decision 63's principle that a source the platform can't report never holds a run back.
