# Decision 111: The recent log in the web UI

**The daemon keeps the newest lines of its own log in memory, at most 1,000 lines and 1 MiB of text, each as masked as the log writes it, and serves them newest first at `GET /api/v1/log` to a session or a `read` token. The web UI shows them on a page of its own, Log at `/log`, narrows them by level in the browser, and copies the lines shown for a bug report, the running version first** (recorded 2026-11-15, §3.1, §4.2, §4.4, §10.1; #618).

## Why

- **Fed from inside the masking, never from the file.** The logger keeps each line in the recent log as it writes it, after the masking that guards the log while the daemon has a repository open itself, so the page shows no more than the log already holds (I4) and needs no masking of its own. Reading the log file instead would depend on where the platform puts it (journald, `~/Library/Logs`, a service's own file), would read lines from before this start (#618 leaves them out), and would make the route a reader of files.
- **In memory, within caps.** 1,000 lines and 1 MiB of text, the oldest let go first; a message is cut at 4 KiB and a source at 256 bytes, each ending in `…`, so one noisy line can't push out the rest, the daemon's memory stays bounded however long it runs, and the answer stays small enough to read whole. A restart starts it empty: what came before is in the log file, where the platform keeps it.
- **A page of its own, not a section of Operations.** Operations is the history of runs, each with its own reason for failing. The recent log is what Operations doesn't show: the start, the scheduler, notifications. A page of its own keeps a table with one meaning per page and gets its own link and title, so a person told "look at the log" finds it from the navigation.
- **The level filter in the browser, not in the URL.** The answer is at most 1 MiB, read once as the page opens, so narrowing it needs no second request and the route needs no parameters to check. The choice isn't kept in the address: a person opening the page wants the whole log first.
- **Copy as shown.** "Copy for a bug report" puts on the clipboard what the table shows, newest first with the filter applied, each line as the log writes it (`[<time> <LEVEL> <source>] <message>`, UTC times), so what a person pastes into an issue is what they saw and reads like the log a maintainer knows. The first line is `ladderback <build>` as `--version` prints it, from the build the daemon told the page (decision 90); a page not yet told it leaves the line out rather than guess.
- **`read` scope.** The lines are already masked and say no more than the operations and plans a `read` token sees, so the same scope opens them (§10.1); no new scope.
