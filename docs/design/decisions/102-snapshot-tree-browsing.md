# Decision 102: Browsing a snapshot's tree

**A snapshot's page shows its tree in the accessible tree of §4.5, and each folder is read live from the repository the first time it is opened: one worker reads one page of one folder, at most 1,000 entries in the snapshot's order, and the page says where the next starts. An entry is opened by its key, rustic's escaped form of its name, and shows its name as the file system wrote it, with what would hide in it made visible. A browse is a read: it takes no maintenance slot, writes nothing to the operation log, and an API token reads it with the `read` scope** (recorded 2026-11-15, §3.1, §4.1, §4.4, §4.5, §10.1; #562, #711).

## Why

- **Live, not indexed.** rustic already keeps a snapshot's trees in the repository and its cache (§4.1, the cache slot), so a folder is one tree read away. Copying every tree into SQLite would cost a backup's worth of writes per snapshot for a page a person opens now and then, and would go stale when a forget removes the snapshot.
- **One worker a page.** Each page is a `Browse` job, as a listing is an `Ls` job: the engine boundary stays the one process boundary (§4.1), a page that hangs is killed with its worker, and the worker gets the repository's cache slot, so a second folder of the same snapshot reads its trees from the cache. A configuration entry with no recorded repository ID is opened as a listing opens it.
- **Two folders at once.** A worker may hold a folder's whole tree (350 MiB for one of 300,000 entries, below), and nothing stops a page, a script or several tabs from asking for many folders together, so the daemon reads at most two at once, whichever browses ask (`app::reads::READS_AT_ONCE`). The rest wait for a turn, in no set order: a turn is held for one page, but a steady stream of others can keep one browse waiting until its timeout. The wait counts against the read timeout, so a browse that waits ends no later than one that started at once, and one dropped while it waits takes no turn. The turns span every repository, so two hung reads hold up every browse until the read timeout; one at a time would let one slow folder do that, and more would let the daemon's machine run short of memory.
- **Pages, bounded.** A folder is an input-derived size (§13.5): one with a million entries must not size an answer. A page holds at most 1,000 entries and 512 KiB, and its `next` says where the next page starts, so the daemon, the wire and the browser each hold one page at a time. The tree shows the folder's total from the first page, and a last row reads the next page; a `next` at or before the page's own start ends the folder rather than asking for the same page again.
- **Opened by rustic's form of the name.** An entry's key is rustic's escaped form of its name, which is UTF-8 whatever bytes the file system had, so a path is its keys joined by `/` and the worker reaches a folder only through the trees, one name at a time; a request can't name a path outside the snapshot. A name over 4 KiB, which no file system writes, is left out and keeps its position.
- **Shown as written.** The key is no name a person wrote: `say \"hi\"` for `say "hi"`, `caf\xe9` for a Latin-1 `café`. So each entry also carries its shown name (`DisplayName`): rustic's name with the escapes undone and a byte that isn't UTF-8 as U+FFFD, as `rustic ls` prints it. The shown name is the row's accessible name and what type-ahead searches; it names nothing, and the daemon makes a worker's shown name visible again as it reads it, so a worker can't send a hidden character to the page.
- **What hides, made visible.** What would break the row or hide in it is made visible: a C0 control as its Control Picture (`new␊line.txt`), DEL as `␡`, and a C1 control, a bidirectional control (U+061C, U+200E, U+200F, U+202A–U+202E, U+2066–U+2069) or a line or paragraph separator as its code point in brackets (`abc[U+202E]txt.exe`, which would otherwise read `abcexe.txt`). The pictures keep a name one line and its length near the original's; the brackets name the characters whose look is nothing or a reordering.
- **A read.** Browsing changes nothing, so it takes no I7 slot and leaves no operation behind; it waits at most the read timeout, as a listing does. Its refusals are typed: `snapshot-unknown` (forgotten since the list was read) and `folder-unknown`, and an engine failure that names no secret is `engine-unavailable` (503).
- **A read for a token too.** The folder route is a read route, so decision 93's `read` scope opens it as it opens the list of snapshots: a program that may list a repository's snapshots may look inside them. A token without `read` is refused `403 api-token-scope` naming it.
- **The tree pattern, decided on the host.** `rules::Tree` (`crates/web/src/components/tree/rules.rs`) holds the rows, the tab stop, the keys, the type-ahead and what each answer changes, so all of it is mutated on the host; `components/tree.rs` and `snapshot_page.rs` only draw it and send its requests. The row holding the tab stop is the selected row (`aria-selected`), so a later details pane has one row to describe.
- **Refusals where the reader is.** A refusal is an alert under the tree. A refused first page leaves its folder closed, and opening it again asks again; a refused later page keeps the entries already shown.

Known limits: Restore and Download of the selected entry, and the details pane they sit in, came as later slices (decisions 109 and 113); a folder's entries come in the order the snapshot records them, with no sorting or filtering. Two names can still look alike: a name holding a real `␊` or `[U+202E]` looks like one holding the character it pictures, names that differ by a byte that isn't UTF-8 both show U+FFFD, and a default-ignorable character (a zero-width space or joiner, a soft hyphen, a variation selector) or a look-alike letter is shown as it is. Each still opens by its own key. A refusal of a folder names its path by its keys.

Measured (2026-11-15, release build, Apple M1, local repository of one snapshot of 306,000 files and 1 GiB): one worker reading the first or the last page of a folder of 300,000 entries took 0.9 s and peaked at 350 MiB, since rustic reads a folder's whole tree before the page is cut from it; a page of a folder of 5,000 entries ten levels down took 0.3 s and 148 MiB, and the top folder 0.3 s and 142 MiB. The worker ends with its page, so the daemon holds none of it.
