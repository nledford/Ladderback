# Decision 150: The hub takes one computer under each machine ID

**Each machine's `Hello` carries its machine fingerprint: the SHA-256 digest of a fixed label, the machine ID and the machine identifier its operating system gives the computer ([decision 144](144-a-copied-data-folder-stops-maintaining.md)), never the identifier itself. The hub keeps the first fingerprint it hears under each machine ID, in the same transaction that compares it, and refuses a `Hello` whose fingerprint is another as `identity-conflict`, signed as its other refusals are: it takes none of that computer's reports, keeps when it last refused one, lists it with the machine, and says so once in its log while it runs. The same computer connecting again is taken as before, and a `Hello` with no fingerprint is taken and changes nothing** (recorded 2026-11-23, §7.1, §7.2; part of #296).

**The way back is `ladderback pairing-token --forget-computer <hostname>` at the hub's terminal, with the daemon stopped: the hub forgets the computer it took and when it last refused one, and the next computer to connect as that machine is the one it takes. It asks for no confirmation.**

## Why

- **A copy proves itself as the machine.** A data folder copied to a second computer brings the machine ID and the agent key with it, so both computers pass the handshake ([decision 120](120-agent-hub-connection-security.md)). Their reports would interleave under one ID, and both could hold its leases once #571 grants them: I1 and I6 broken at the hub, where decision 144 guards only the copy's own maintenance.
- **A fingerprint, not a counter.** Decision 120 planned a connection counter written before each proof, which tells two copies apart only after both have connected, and only with an fsync per attempt. The machine identifier decision 144 already reads tells them apart at the first `Hello`, with nothing written on the machine. The counter stays unbuilt; this decision replaces it for the case it covers.
- **The identifier stays on the machine (I4's spirit).** Decision 144 never sends it. The digest is keyed by the machine ID, so the hub can't match one machine to another by it, and nothing on the wire or in the hub's store gives the identifier back: a Linux machine ID and a Mac's `IOPlatformUUID` are 128-bit values, too many to guess.
- **First heard, first taken.** The hub can't tell which computer is the original, so it keeps the first it hears, under `BEGIN IMMEDIATE`: of two `Hello`s at once, one claims and the other is refused. Machines paired before this decision take the fingerprint of their next `Hello`, so an upgrade refuses nothing.
- **The refused computer goes on backing up.** Its reports wait in its outbox ([decision 145](145-the-agents-outbox-and-the-hubs-reports.md)) and reach the hub once it is taken, so nothing is lost while the person decides. The first computer's connection is left alone.
- **An identifier that can't be read stops nothing,** as in decision 144: a `Hello` with no fingerprint is taken, and nothing is kept for it, even when the hub holds another computer's under the ID (decided again 2026-11-23 by the maintainer's delegate). The fingerprint tells an honest copy apart, and a copy isn't an attacker ([decision 99](99-who-is-trusted.md)): a computer that leaves its fingerprint out on purpose holds the agent's key already, which no check of a `Hello` can take back, so refusing an untold `Hello` would stop only machines whose identifier can't be read.
- **Two ways back, both said to the person.** If the refused computer is the copy, it takes a new machine ID on its start page (decision 144) and pairs again. If it is the one that should keep the ID, the person stops Ladderback on the other computer, or gives that one a new ID, then forgets on the hub the computer it took. The machine's refusal, the hub's log line and the hub's Settings → Machines name the two ways. There the machine's note says how long ago, by the hub's clock, the hub last refused a second computer as it, and a warning above the tables, one for each such machine in the tables' order, names it and gives the two ways, the command on a line of its own: a table's cell is too narrow for them.
- **A refused machine may take a new ID, when the person asks** (#1462; decided 2026-11-23 by the maintainer's delegate). A machine holding its hub's `identity-conflict` refusal, verified as signed by the hub it paired with, stands `refused-by-hub`, and its start page offers the same button and review dialog as a copied data folder's; taking the new ID does what it does there. A refusal the hub didn't sign, or any other refusal, changes nothing, and the machine never takes a new ID by itself. The start page says the hub took another computer as this one and names both ways back, never that this computer is the copy, since it may be the original.
- **The refused standing lasts while the hub refuses.** It turns back to as usual once the hub takes the computer, after `--forget-computer`; a copied data folder stays stopped whatever its hub says (I1). Maintenance runs on as the standing allows, since the refused computer may be the original: under decision 151's lease gate (#1443), a refused machine gets no lease, so its maintenance stops as its lease lapses.
- **No confirmation prompt.** `--forget-computer` runs only as the user that owns the hub's data folder, with the daemon stopped, as `pairing-token --approve` does; that user is trusted with the hub's store already ([decision 99](99-who-is-trusted.md)). Forgetting changes nothing a person can't see: the next computer to connect is taken, and if that is the wrong one it is forgotten the same way. A running hub refuses the command in words of its own, and a hostname no machine paired with changes nothing.

## Known limits

- A copy that keeps the machine identifier, such as a cloned virtual machine whose `/etc/machine-id` was cloned too, has the same fingerprint and is taken as the same computer. Decision 144 can't tell it either.
- Two copies of one data folder on one computer, such as two users or two containers sharing the identifier, have one fingerprint and are taken as one machine.
- A computer whose identifier changes, by a reinstall on Linux or a new logic board on a Mac, is refused as a second computer; forgetting the computer the hub took is the way on.
- No event tells the hub's page of a refusal: Settings → Machines shows one from its next read of the list, on another of the hub's events or when its events stream opens again. That read says the new warning politely, or the resume does when the tables were paused, since the warning is no live region.
- Only forgetting the computer the hub took clears its flag: after the copy took a new ID, the warning stays until the command runs, which is safe then, and says so.
- The command runs only with the hub stopped; the running hub's Settings can't forget a computer yet.
- A `Hello` with no fingerprint, from a computer whose identifier can't be read, is taken beside the computer the hub holds: two such computers under one ID take turns, as before this decision.
- The `refused-by-hub` standing isn't kept across a restart: a refused machine stands as usual from its start until its first session with the hub is refused again, so its start page shows nothing until then.
- The hub takes a copy's proof before its `Hello` is checked, as any good proof under the agent's key: the machine's last-seen time is the copy's, and a copy that connects before the first computer since its approval is logged as connected, then refused.
