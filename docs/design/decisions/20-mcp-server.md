# Decision 20: MCP server

**`ladderback mcp`: newline-delimited JSON-RPC 2.0 over stdio (MCP `2025-06-18` or later), in one inbound adapter (`adapters/mcp`).** Connect mode drives a running agent through `/api/v1` (a hub from M5) with a scoped API token; headless and scratch modes run their own in-process session under the data-dir lock. Tools read state, run and cancel backups, and preview forget and import. Nothing restores, deletes, edits config or adds a command: a model-driven client is not a human confirmation, and token scopes enforce this in the daemon (§4.6, §10.5).

**Amended by decision 89** (2026-11-14, #518): MCP gains tools that propose configuration changes (`propose_setup`, `check_proposal`, `dry_run_plan`, `get_proposal`, `withdraw_proposal`) under a new `propose` token scope. A proposal changes nothing until a person approves it in the web UI, ticking each command it adds, with step-up confirmation; there is still no tool that approves, restores, deletes or edits config directly. With sign-in off, that approval is a convenience, not a safety boundary.

**Amended** (2026-11-17, #960): agents read each repository's last check through the read tools: when it ran, what it verified (structure only, or which data subset) and its result. Ladderback runs checks on their schedule (#974). A check an agent wants now goes through a person's confirmation in the web UI, the pattern of decision 89; `--read-data` stays with the person. A plain check an agent starts directly is not offered now. If it ever is, it comes only after the maintenance queue (#970, decision 75 point 8) and its switch in Settings' AI agents tab (#962), off by default, and only on the agent that owns maintenance (I1).
