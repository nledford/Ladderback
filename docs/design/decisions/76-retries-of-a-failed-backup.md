# Decision 76: Retries of a failed backup

**A failed backup the schedule started is retried at most `attempts` times, the first `backoff` after the failure and each after twice the wait before it, at most an hour. A series stops at the plan's next scheduled run, when its attempts are spent, or at a success or a cancel. A retry takes its turn in the persistent queue under the concurrency limit, is skipped while a run of its plan is going, and a pending one outlives a restart. A backup a person or another program asked for is never retried** (recorded 2026-11-12, §5; #275). Builds on decision 73's persistent queue and decision 75's queue and overlap policy.

Decided:

1. **The wait is `backoff` × 2^(n − 1) for retry n, at most an hour** (`RetrySchedule::wait`), counted from the moment the scheduler hears of the failure. The doubling is cut at the hour before it can overflow, so no number of failed retries makes it wrap or panic, and a retry whose time would pass the last instant there is isn't planned.
2. **A series stops at the plan's next scheduled run,** as it was planned when the run that began the series failed (`RetryScheduled::until`). A retry that would run at or after it isn't planned; a pending one is dropped when that run comes due, whether it starts, is skipped, or catches up, and when the agent finds it past that run after a restart or a sleep. A plan with no schedule has no such run: only its attempts end its series.
3. **A success or a cancel ends the plan's retries,** whatever started the run. A cancelled run isn't retried: a person stopped it. A run that ended `failed` with `daemon-stopped` (decision 40) isn't retried either: the daemon that would have heard of it was gone, and a pending retry it left is kept (point 6).
4. **Only a run the schedule started is retried:** a scheduled run, a catch-up, or a retry of one (`RetrySchedule::retried`). A run started by hand, from the hub or over MCP is the asker's: the person who pressed "Run now" sees it fail and decides, and retries running in the background afterwards would surprise them. Its failure starts no retries and leaves the plan's own as they were, pending or going. This matches decision 75, where the overlap policy applies to the runs a schedule starts only.
5. **A retry is skipped while a run of its plan is going,** running or waiting, whatever the plan's overlap policy: that run backs up the same sources and takes the retry's place. Otherwise a retry takes a place in the queue as any backup does (decision 75), so it waits its turn under the concurrency limit and a plan still runs one backup at a time.
6. **A retry planned and not started yet is kept in `retry_state`** (§9), one per plan, so it runs at its time after a restart unless its series' end came meanwhile. The row goes as the retry takes its place; a retry the queue held from before a restart runs again under its own ID (decision 73), and its failure begins a new series. A plan that no longer sets `retry` forgets its pending retry.
7. **Each run of a backup says how it ended to the scheduler,** through an unbounded channel (`app::retry`): a run never waits on the scheduler to end, and the scheduler reads the ends between its sleeps and as they come. A run that ends after the scheduler stopped says it to nobody. The scheduler sleeps until the first planned run or pending retry, at most the 30 s of the wake check.
8. **An end is handled when it is heard,** before the loop's wake check: its retry is planned from that moment, and a sleep found by the wake check after it changes only the planned runs. A retry planned across a sleep is then started late or dropped as its series' end says (point 2).
9. **A retry whose start fails before it records anything** (the configuration can't be read, or its job can't be built) leaves its plan marked as retrying until a run of the plan next ends, other than a failure of a run a person asked for, or until the plan no longer sets `retry`: that end clears the mark, and a failure of a run the schedule started then begins a new series. The mark only keeps the plan from planning a second retry beside it; nothing waits on it, so it neither strands the plan's retries past its next scheduled run nor loops. The daemon's log says why the run didn't start.
10. **Each retry planned is announced** as `backup.retrying` (`UiEvent::BackupRetrying`: the operation that failed, its plan, the attempt, the attempts and when it runs, §11), and the daemon's log says each retry planned and why a series ended.

Why:

- **Stopping at the next scheduled run** keeps a plan from backing up twice in a row for one missed moment: the scheduled run backs up the same sources, and retrying past it would only add runs.
- **Doubling, capped at an hour,** spaces the retries of a failure that lasts (a repository that is down) without leaving a short one waiting long.
- **Skipping a retry while a run is going** follows from point 5's reason for the overlap policy: the going run takes the failed run's place, and a retry behind it would back up nearly what it does.
- **Only the schedule's runs:** see point 4.

Cost: a series stops at the next scheduled run even when that run is a day away and the failure was brief; `attempts` bounds the series either way. A retry is planned from the moment the failure is heard, not when the run ended, so a scheduler busy for a moment plans it that moment later. A retry whose start failed (point 9) isn't followed by the series' next retry: the next scheduled run takes over.
