# Decision 66: The server accepts through the spawn gate

**Where the platform makes a socket and accepts a connection in two steps (macOS), the HTTP server accepts each connection, and makes its listening socket, while it holds the spawn gate of decision 58: `http_adapter::GatedListener`, which `axum::serve` takes in place of tokio's `TcpListener`. Linux, Android and FreeBSD accept as tokio does, without the gate** (recorded 2026-11-12, §4.2, §10.2; #283). An accept takes the gate on the runtime's thread when it is free at once (`spawn_gate::try_hold`), and holds it for the one non-blocking `accept` and its `fcntl`, a few microseconds. While another holds the gate, the accept waits for it on tokio's blocking pool and accepts there (`spawn_gate::hold_blocking`), never on one of the runtime's threads. A failed accept is handled as `axum::serve` handles its own listener's: a connection its client gave up on is passed over, and any other failure is logged and tried again a second later.

Why:

- **A held connection.** Where the platform has no `accept4` (macOS), mio and the standard library accept a connection in two steps, `accept` and then `fcntl` for close-on-exec, and the listening socket in two as well, `socket` and then `fcntl`. A worker, a hook or a password command that another thread starts in between inherits the descriptor and holds it for as long as it runs: the browser's connection stays open until a long backup's worker exits, and a listening socket held by a child keeps the address taken after the daemon stopped. Linux makes both close-on-exec in one step and never had the moment.
- **The gate, not a start of our own.** An accept that holds the gate cannot overlap a start, which is all decision 58's gate is for, and it needs no `unsafe` and no new crate. The other route, starting every child with `posix_spawn` and `POSIX_SPAWN_CLOEXEC_DEFAULT` so a child inherits only the descriptors it is given, covers more (an outbound socket too), but it is a start of our own in place of the standard library's and tokio's `Command` for every worker, hook and password command: their pipes, environment, working folder, process group and reaping, each rebuilt. nix 0.31's `spawn` module, which the workspace's `signal` feature already turns on, has no name for that flag; passing its bits unnamed would be the first start that steps outside `Command`. Decision 58 rejected the route for the same reasons.
- **The gate is a plain mutex, so an accept and a start wait for each other.** A start waits for at most one accept's few microseconds. An accept waits for whatever holds the gate: a start until its child has run `exec`, and the start of an `rclone` backend until `rclone` says it serves, with no deadline (#319). Meanwhile the server accepts no new connection, so a page that opens one waits; connections already open go on. #319 is where that hold gets shorter (the gate held only for the start, or a deadline). Measured on macOS for this decision, 1500 connections a run, each connected and accepted in turn on loopback, in two runs on a machine busy with other builds (the second the quieter): with no starts, the gated and the plain accept are the same (median 34–37 µs gated, 38 µs plain in the quieter run). Beside one thread starting children back to back (about 600 a second), the median is unchanged and the 99th percentile rises from 0.09 ms to 0.28 ms (0.19 ms to 2.8 ms in the busier run). Beside four such threads (about 1 900 starts a second, the gate held most of the time), the median rises from 49 µs to 65 µs (36 µs to 297 µs), the 99th percentile from 0.14 ms to 3.1 ms (0.32 ms to 14 ms) and the slowest from 1.4 ms to 11 ms (1.3 ms to 29 ms). A daemon starts a few children a job, not hundreds a second, so the wait is rare and short; the four threads are the worst case.
- **Free at once on the runtime's thread, otherwise on the blocking pool.** A start whose `exec` stalls (a script on a hung mount) holds the gate for as long, and an accept that waited for it on one of the runtime's threads would stop every other task of that thread, the other requests among them (decision 58). A trip to the blocking pool for every accept would add a thread hand-off to every connection the browser opens; taking the gate where it is free costs one uncontended lock. The accept on the blocking pool waits for the lock as a start does, and accepts the connection there once it has it, rather than letting go and trying again on the runtime's thread, where a stream of starts could take the gate each time first. Only when no connection is there yet does it go back and wait for one as before.
- **Not on Linux.** Linux makes the connection and the listening socket close-on-exec in the one step (`accept4`, `SOCK_CLOEXEC`), so the gate would cost it a lock per accept and every wait above, the one behind an `rclone` start among them, and prevent nothing. Gating Linux too, for one code path that CI's Linux job tests, was the alternative. The gated path is tested where it runs: CI's macOS job runs the listener's tests, which skip, saying why, on a platform that accepts in one step.

Not covered:

- A socket a client of the daemon opens (an outbound connection to a backend, or to an `rclone` server rustic started) is still made in two steps outside the gate on macOS, in code that isn't ours. Covering it needs every start to inherit only what it is given, `posix_spawn` with `POSIX_SPAWN_CLOEXEC_DEFAULT`, the route this decision leaves for later.
