# Decision 75: The overlap policy and the concurrency limit

**Every backup takes its turn in one queue: the agent runs at most `concurrency` of them at once, across its plans, and a plan one at a time. A run its schedule starts while the plan's last run is still going, running or waiting, is skipped under `skip`; under `queue` it waits for the last one to end, and a plan never has two runs waiting. A skipped run is said in the daemon's log and records no operation** (recorded 2026-11-12, §5; #276). Builds on decision 73's persistent queue.

Decided:

1. **The rules are one aggregate's.** `domain::execution::queue::BackupQueue` holds the running and the waiting runs, each by a ticket it issues in order, and decides which may start: while fewer than the limit run, the oldest waiting run whose plan has none running. `app::queue::RunQueue` holds it behind a lock, gives each run a `Place` that waits for its turn and gives its slot up when it is dropped, however the run ended, and starts what may start then. One `RunQueue` serves the scheduler, the route that starts a backup by hand and the runs the queue held from before the start, so the limit holds across all of them.
2. **The limit counts backups, hooks included.** A slot is held from the run's before-hooks to its last write and its announcement. Forget, prune, check and adopt are serialized per repository by I7 instead, and a read (`ls`, an identify) takes no slot. The queue takes the limit from the configuration each time the scheduler reads it, at least every 30 s, and each time a run started by hand or held from before the start asks for a place: a raised limit starts the waiting runs it makes room for then, and a lowered one stops nothing, only starts nothing, the runs already waiting included, until fewer run.
3. **A plan runs one backup at a time,** whatever the limit: a run of a plan whose last run is running waits, and a run of another plan behind it doesn't wait for it.
4. **The overlap policy applies to a run its schedule starts** (a scheduled run or a catch-up). Its last run is still going when the plan has a run running or waiting: under `skip` the due run is skipped; under `queue` it waits for the last one, unless a run of the plan is already waiting, and then it is skipped too (`Overlapping::Waiting`). A run started by hand and a run the queue held from before the start always take a place: a person asked for the one, and the other is in the log as queued already. Whether a retry is skipped is #275's to decide.
5. **A skipped run records no operation.** The scheduler says it in the daemon's log, with why (`ScheduleReport::Overlapped`), as for a run skipped for its conditions, and plans the plan's following run from the time it was skipped.
6. **A waiting run is in the log as queued** once its job is built, before its turn comes, so the history shows it and a restart runs it again (decision 73). Its job is built from the configuration of that moment; the resolved password stays in memory only (I4). A scheduled run takes its place before its job is built, so that the skip and the place are one decision; a run started by hand takes it after.
7. **A cancel ends a waiting run at once,** as cancelled, without its hooks and without asking the engine: nothing of it ran. Its place leaves the queue.

Why:

- **One run waiting is enough.** A plan whose runs take longer than its schedule's interval would otherwise grow its queue without end under `queue`, each run backing up nearly what the one before it did. The waiting run starts as soon as the last one ends, and backs up the sources as they are then.
- **A waiting run counts as going.** Under `skip`, a run waiting for the limit has not started; a second one due meanwhile would back up the same sources right after it.
- **One plan at a time** keeps two backups of the same sources from racing each other to the same repository for nothing, and makes "once the last one ends" mean what it says when the limit is above 1.
- **The oldest that can start starts,** not the oldest: a run waiting behind its own plan's run would otherwise hold every other plan back.
- **Skipping records nothing** because no operation ran or was queued; a row that was never queued would show in the history as a backup that ended without running.

Cost: a waiting run's job is the one built when it was queued, so a change to its plan while it waits doesn't reach it (a restart builds it again, decision 73). The slots are the daemon's: two daemons on two data folders would each run their own limit, which the data folder's lock already rules out for one configuration. After a restart, the runs held from before take their places one by one as their jobs are built again, after the daemon listens: a run started by hand in those moments may take its place ahead of the ones still being built.
