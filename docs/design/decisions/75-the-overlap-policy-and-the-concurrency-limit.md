# Decision 75: The overlap policy and the concurrency limit

**Every backup takes its turn in one queue: the agent runs at most `concurrency` of them at once, across its plans, and a plan one at a time. A run its schedule starts while the plan's last run is still going, running or waiting, is skipped under `skip`; under `queue` it waits for the last one to end, and a plan never has two runs waiting, however they were started. A skipped run is said in the daemon's log and records no operation** (recorded 2026-11-12, §5; #276). Builds on decision 73's persistent queue.

**Amended by point 8** (2026-11-17, #970): maintenance has its own queue and its own limit, `maintenance-concurrency`. Decided; not built yet (#970).

**Amended by points 4 and 6** (2026-11-19, #1140): a run started by hand is refused while a run of its plan waits, and takes its place before its job is built.

Decided:

1. **The rules are one aggregate's.** `domain::execution::queue::BackupQueue` holds the running and the waiting runs, each by a ticket it issues in order, and decides which may start: while fewer than the limit run, the oldest waiting run whose plan has none running. `app::queue::RunQueue` holds it behind a lock, gives each run a `Place` that waits for its turn and gives its slot up when it is dropped, however the run ended, and starts what may start then. One `RunQueue` serves the scheduler, the route that starts a backup by hand and the runs the queue held from before the start, so the limit holds across all of them.
2. **The limit counts backups, hooks included.** A slot is held from the moment the run takes its place, before its job is built (point 6), to its last write and its announcement. Forget, prune, check and adopt take no backup slot, and I7 serializes them per repository; point 8 gives them a queue of their own. A read (`ls`, an identify) takes no slot. The queue takes the limit from the configuration each time the scheduler reads it, at least every 30 s, and each time a run started by hand or held from before the start asks for a place: a raised limit starts the waiting runs it makes room for then, and a lowered one stops nothing, only starts nothing, the runs already waiting included, until fewer run.
3. **A plan runs one backup at a time,** whatever the limit: a run of a plan whose last run is running waits, and a run of another plan behind it doesn't wait for it.
4. **The overlap policy applies to a run its schedule starts** (a scheduled run or a catch-up). Its last run is still going when the plan has a run running or waiting: under `skip` the due run is skipped; under `queue` it waits for the last one, unless a run of the plan is already waiting, and then it is skipped too (`Overlapping::Waiting`). A retry is skipped while a run of its plan is going, whatever the policy (decision 76).
   - **A run started by hand,** by a person, an API token, an AI tool or the hub, waits behind a running run of its plan, and is refused while a run of the plan waits, however that one came (`RunWaiting`, answered `409 plan-run-waiting`): nothing is queued or recorded (amended 2026-11-19, #1140). The answer says why and the daemon's log doesn't, so a client that retries in a loop can't fill it, as a cancel of an operation that isn't running leaves no line.
   - **A run the queue held from before the start** always takes a place, as it is in the log as queued already; a restart runs one per plan (decision 73, point 2). The daemon listens before they take their places again, so until a plan's has, or every one has been handed back or ended, a run of the plan started by hand is refused as if that run waited already (`BackupQueue::resuming`, set before the listener opens). A headless or scratch MCP session leaves them in the log for the next `serve` and refuses no run for them.
5. **A skipped run records no operation.** The scheduler says it in the daemon's log, with why (`ScheduleReport::Overlapped`), as for a run skipped for its conditions, and plans the plan's following run from the time it was skipped.
6. **A waiting run is in the log as queued** once its job is built, before its turn comes, so the history shows it and a restart runs it again (decision 73). Its job is built from the configuration of that moment; the resolved password stays in memory only (I4). A run takes its place before its job is built, scheduled or by hand, so that the refusal and the place are one decision and a refused start reads no secret and runs no password command.
7. **A cancel ends a waiting run at once,** as canceled, without its hooks and without asking the engine: nothing of it ran. Its place leaves the queue.
8. **Maintenance has its own queue and its own limit** (amended 2026-11-17 and 2026-11-27, #970). Forget, prune, check and adopt take their turn in a queue of their own, sharing no slot with backups, limited by `[agent] maintenance-concurrency`: default 1, 1 to 64 like `concurrency`. One queue rule in `domain`, `Queue`, serves both, keyed by the plan for a backup (`BackupQueue`) and by the repository for maintenance (`MaintenanceQueue`). The queue limits load only; I7's store slot (`OperationStore::try_start`) stays the authority, taken when the run's turn comes. A run started by hand waits as queued, with its reason, and a cancel ends it at once (point 7), rather than being refused while another repository's maintenance runs. At a restart, a queued maintenance run ends `daemon-stopped`, unlike a queued backup (decision 73); a running one holds a restart that waits, and is counted, as a running backup is.

Why:

- **A queued maintenance run isn't taken up after a restart (point 8, amended 2026-11-27).** A backup only adds, so running it late is safe. A forget or an adoption acts on the review a person confirmed; taken up after a restart, it would act on a history that may have changed since, and I6 lets a forget delete only what a plan owns or the person selected. A prune or a check taken up has nobody waiting on it, so a locked keyring would hold it as decision 135's runs are held, with no next run to bound the wait. And a scheduled prune or check is run again by #974's catch-up anyway. Ending it `daemon-stopped` says plainly that it didn't run, and a person can start it again.
- **Maintenance doesn't share the backups' slots (point 8).** A prune can take hours, and every backup's deadline already counts prune's duration (§7.3). Making one wait on the other would mix two timing rules.
- **Maintenance needs a limit of its own (point 8).** A cron such as `0 3 * * 0` on every repository starts them all at once, and a hub (M5) owns maintenance for many repositories. I7 alone leaves runs on different repositories unlimited.
- **One run waiting is enough.** A plan whose runs take longer than its schedule's interval would otherwise grow its queue without end under `queue`, each run backing up nearly what the one before it did. The waiting run starts as soon as the last one ends, and backs up the sources as they are then. The same holds for runs started by hand: a page reloaded, an API token or an AI tool looping on `run_plan` would otherwise queue rows without bound, each holding a resolved password in memory (#1140).
- **A waiting run counts as going.** Under `skip`, a run waiting for the limit has not started; a second one due meanwhile would back up the same sources right after it.
- **One plan at a time** keeps two backups of the same sources from racing each other to the same repository for nothing, and makes "once the last one ends" mean what it says when the limit is above 1.
- **The oldest that can start starts,** not the oldest: a run waiting behind its own plan's run would otherwise hold every other plan back.
- **Skipping records nothing** because no operation ran or was queued; a row that was never queued would show in the history as a backup that ended without running.

Cost: a waiting run's job is the one built when it was queued, so a change to its plan while it waits doesn't reach it (a restart builds it again, decision 73). The slots are the daemon's: two daemons on two data folders would each run their own limit, which the data folder's lock already rules out for one configuration. While a run's job is built, which can wait on a password command, the run holds its place: a second start by hand is refused, the plan's due run is skipped, and a failed scheduled run of the plan isn't retried; if the build is then refused, none of them ran.

After a restart, a start by hand of a plan whose run from before the start ends rather than runs is refused until the daemon has handed back every such run, which can take as long as building their jobs. A start refused for a waiting run answers its code, not the waiting run's ID: a scheduled run takes its place before its operation exists.
