# Decision 132: How an agent finds a file across a repository's snapshots

**A snapshot search looks a name up across a repository's newest snapshots, or one plan's, and answers each path whose last name matches, with the snapshots that hold it, newest first, and each one's size and modification time. The pattern matches a whole name, never a path, ignoring case, with `*` for any run of characters and `?` for any one. One worker walks the chosen snapshots' trees, reading an unchanged tree once, and stops at the first cap it meets: 20 snapshots (at most 100), 100 matches (at most 500; a match is a path and kind, however many snapshots hold it), 384 KiB of matches, 15 s from the repository's open. The answer says which cap cut it short. It is a read, like a folder page (decision 102): the permission Snapshot contents opens it, and it takes no maintenance slot and leaves no operation behind.**

MCP offers it as `find_in_snapshots`, beside `list_snapshot_folder`, the folder page of decision 102 (§4.6); the API as `GET /api/v1/repositories/{alias}/find` (#953).

## Why

- **An agent has to find a file before the person can get it back.** "Did my backup get the tax folder?" and "which snapshot still has last week's version of this file?" are the questions people bring. A folder page answers the first only for someone who knows where to look; a search answers both in one call, and the folder page then shows what sits beside the match. Restoring and downloading stay the person's, in the web UI (decision 20).
- **Names, not paths.** A pattern is a file's or a folder's name, so `tax-*.pdf` finds the file at any depth, which is what someone who has lost a file knows. A pattern with `/` is refused rather than read as a path. rustic's `find` takes a full-path glob, and its globset crate is no workspace dependency; a name is the part people remember, and a full-path pattern can come later as a second argument without changing this one.
- **Case ignored.** A person types `tax*` for `Tax-2026.PDF`. The pattern and each name are compared one character against one, each character lowercased by Unicode's lowercase mapping and a final `ς` taken as `σ`, so a match never depends on the file system the snapshot came from, and a `?` stands for one character of the name as written, even `İ`, whose lowercase is two.
- **Bounded against hostile input (§13.5).** The pattern and the caps come from an agent. A pattern holds at most 255 characters, the longest name a file system writes, and is counted before it is copied; matching it is never worse than the name's length times the pattern's, with no backtracking that grows with the number of `*`. A cap past its most is lowered to it and 0 is raised to 1, never refused, as a page's length is (§4.6).
- **The newest snapshots first.** The snapshots are chosen newest first, ties by ID, so the same search reads the same ones each time, and a plan narrows them by its first `ladderback-plan:` tag, as the snapshot list reads it. Grouping matches by path answers the second question at a glance: one match, with the snapshots it is in and how it looked in each. A file and a folder at one path stay two matches, since a browse opens each differently.
- **Each tree read once.** A tree's ID is the hash of all it holds, so a folder that didn't change between snapshots is walked once and what matched in it is reused. Twenty snapshots of a home folder cost little more than one.
- **Time, bytes and count all capped.** One worker stops 15 s after it opens the repository, with what it found. The whole search, the resolution of the repository's secrets, its wait for a read turn and the repository's open included, has 25 s, after which it is refused as `repository-read-timed-out`, so a running daemon answers within the 30 s an MCP client in connect mode waits (§4.6). The matches fit 384 KiB of the 512 KiB one worker message carries, the rest kept for the snapshots read. A single match whose path alone passes that is not returned: the search stops there, as `matches`. Each cut says which cap made it, and `left-out` counts the chosen snapshots not read to the end, so an agent can ask again with a narrower pattern or one plan.
- **One worker, one read turn.** A search is a job like a folder page: the engine boundary stays the one process boundary (§4.1), a search that hangs dies with its worker, and the worker gets the repository's cache slot. It waits for one of the two read turns every browse shares (decision 102), so searches and folder pages together hold at most two workers at once.
- **Snapshot contents.** A search shows the names inside snapshots, as a folder page does, so it needs what the folder route needs: the permission Snapshot contents (decision 127). Backups, which lists the snapshots, isn't enough: with it alone a token would learn through a search the names the folder route refuses it. The refusal comes from the permission table, before the repository is looked up, so it tells nothing of the repository or its snapshots. One function in the MCP server runs both tools, the one place to leave them out when the server lists only the tools its permissions open (#962; §10.5).

## Rejected

- **An index in SQLite.** It would answer fast but cost a backup's worth of writes per snapshot and go stale at each forget, for the reason decision 102 reads folders live.
- **A full-path glob now.** It needs a glob crate outside the workspace's dependencies and a second meaning for `/`; a name answers the questions #953 brings.
- **Refusing a cap past its most.** An agent would only retry with a guess; the lowered cap costs it nothing, and `stopped` says when that cap cut the search short.

Known limits: a search through a repository much larger than its snapshots' cached trees may stop on time before it reads the 20 snapshots it chose; `left-out` and `stopped` say so. Lowercasing isn't full case folding, so `ß` doesn't match `SS`. The answers carry no web UI address until #952 lands.
