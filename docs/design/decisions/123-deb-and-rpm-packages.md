# Decision 123: .deb and .rpm packages with each release, built by nfpm

**From 0.5.0, each release also publishes a `.deb` and an `.rpm` for each Linux target, built by nfpm from the binary the release's archive holds, so that `apt install ./ladderback_<version>_arm64.deb` on a Raspberry Pi (Debian 13) and `dnf install ./ladderback-<version>-1.x86_64.rpm` on Fedora install Ladderback. They are unsigned, and there is no apt or dnf repository yet, so an update means installing the next package** (recorded 2026-11-18, §12, §12.1; #362, #363).

## Why

The archive and the install script need a person to know where a binary goes and which folder is on the `PATH`. A package puts the program at `/usr/bin/ladderback`, where every shell finds it, lets the system's own tool list what it installed and remove it, and checks the glibc the binary needs. Debian and Fedora are the two systems the maintainer's servers and Raspberry Pis run.

## Decided

1. **nfpm builds both formats from one file.**
   - **The tool.** nfpm 2.49.0 (MIT) reads `packaging/nfpm.yaml` and writes the `.deb` and the `.rpm` from it, so the two never differ in what they hold. `scripts/install-nfpm.sh` installs it from the official release, checked against a SHA-256 pinned per host, as `scripts/install-dist.sh` does for dist; `just setup` runs it.
   - **The binary.** The packages hold the binary the archive holds, unpacked from the archive the same job built, and the smoke test checks that `/usr/bin/ladderback` in an installed package has the same SHA-256. Nothing rebuilds it, and nothing strips it, so `cargo audit bin /usr/bin/ladderback` reads the same dependency list as the archive's.
2. **What is in a package, and what isn't.**
   - **In it.** `/usr/bin/ladderback` (root's, mode 0755) and the two license texts, under `/usr/share/doc/ladderback/` in the `.deb` and `/usr/share/licenses/ladderback/` in the `.rpm`. The `.deb` depends on `libc6 (>= 2.35)` and the `.rpm` on `glibc >= 2.35`: the floor the release builds are built and smoke-tested for (decision 54), and no other dependency declared: the binary needs nothing outside glibc and `libgcc_s`, which every system's base has, and the smoke test installs and runs it in a clean container of each.
   - **Not in it.** No maintainer scripts, no service unit, no file under `/etc`, no man page. Ladderback runs as the person's own user service (decision 64): `ladderback install-service` writes and starts it, and a package that enabled a system service would run Ladderback as another user, with another home and another configuration. Installing the package changes nothing but its own files (the smoke test checks that no file or folder of it is left after the removal), and removing it leaves the person's configuration, data and cache folders, and their service unit, as they were.
3. **Names and versions.** The files are `ladderback_<version>_<amd64|arm64>.deb` and `ladderback-<version>-1.<x86_64|aarch64>.rpm`, with the version as the tag says it. The `.rpm`'s release is 1 and the `.deb` has no revision, because every package is built from one tag. nfpm reads the version as a semantic version, so a release candidate `0.5.0-rc.1` is `0.5.0~rc.1` inside the package, which sorts before `0.5.0` in both systems. Builds between releases, which are run artifacts only, carry the version their binary names (`0.5.0+3f937cf`, decision 90).
4. **Built and tested on every build, published with a release.**
   - **The builds.** `release-builds.yml` builds both packages after each Linux archive and uploads them with it. `scripts/smoke-release.ts` installs the `.deb` in clean containers (Debian 12 and 13, Ubuntu 22.04 and 24.04) and the `.rpm` in Fedora's, with no network and with the person's folders seeded first. It checks the version, the binary, the files and the absence of maintainer scripts, removes the package, and checks that the folders are as they were. Debian 13 is new to the containers: it is the Raspberry Pi's system.
   - **The release.** The publishing job of `release.yml` downloads the four packages with the two archives, checks each against the checksum its build wrote, lists all six files in the one `SHA256SUMS`, checks it, checks that nothing else is in the folder, and attaches them. Its permissions are unchanged.
5. **No repository yet, so an update is the next package.** `apt install ./new.deb` and `dnf install ./new.rpm` upgrade an installed package in place; the running service keeps its old process until `ladderback install-service` runs again, as after any update (decision 64). The update banner (#1080) will name that command. An apt repository and a COPR need a signing key, hosting and a rotation plan, so they wait for a decision of their own.
6. **Unsigned for now.** `apt` and `dnf` install a local file without checking a signature: a repository's key signs the repository's metadata, not a file a person downloads, and `dnf` only warns that it skipped the OpenPGP checks for a package from `@commandline`. A signature on the file would check nothing until a person has the key from somewhere other than the release page. What a person can check today is the `SHA256SUMS` beside the packages, as for the archives. Signing comes with a repository, which gives the key a place to be published.
7. **Moving an existing install.** A binary installed with `cargo install`, `just install` or the install script sits in `~/.cargo/bin`, and its service unit names that path. To move to the package: remove `~/.cargo/bin/ladderback`, install the package, and run `ladderback install-service` again, so the unit names `/usr/bin/ladderback` (decision 64: the unit names the path the person ran, so run it as `/usr/bin/ladderback install-service` or with `~/.cargo/bin` out of the way). The install guide says so.

## Alternatives

- **cargo-deb and cargo-generate-rpm**: two tools and two sets of metadata in `Cargo.toml`, each of which would package a binary built by `cargo`, not the one dist built and the smoke test checked.
- **fpm**: Ruby and a gem to install, with no release binary to pin by SHA-256.
- **Packages built from source in each distribution's own toolchain** (debhelper, rpmbuild): the natural form for the distributions' repositories and a build per target and distribution release, where this packages the binary already built and tested.
- **A system service in the package**: it would run as a service user, and `install-service` and the web UI's restart (decisions 64 and 94) manage a user unit.
- **An apt repository and a COPR now**: they need the signing key and hosting above. The packages are useful without them.

Cost: nfpm is a third pinned tool whose hashes move by hand. The container smoke test grows by Debian 13 and by a package install in each container. Each update is a download and an install by the person until a repository exists.
