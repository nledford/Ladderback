# Decision 140: A reader chooses which of a table's columns show, and in what order

**A table may offer a Columns button before it, a disclosure whose panel lists the columns after the row header's, in the table's order, each with a checkbox that shows or hides it, Move up and Move down buttons named for it, and a drag handle for a pointer, then Reset columns. This browser keeps the choice per table. Hiding the column a table is sorted by ends the sort, and a hidden cued column marks nothing. Operations, Repositories, the plans, the Log and API tokens offer it; a repository's snapshots don't** (recorded 2026-11-21, §4.5; the maintainer's decision).

**Amended 2026-11-27 (#1625, the maintainer's suggestion in the issue):** a table may also give columns the reader can't hide (`Table`'s `always_shown`), for the one fact the page exists to let a reader check. They stand right after the row header, in the order given, and the panel doesn't list them. The Repositories table's Maintenance column is the one: who maintains a repository is what I1 asks a reader to check there, and with the note in the Password cell (#1615), hiding Password hid it too.

## Why

The app's tables are wide: at 320 px, or with 200 % text, their frames scroll sideways, and a reader who never reads a column still scrolls past it. Which columns matter differs by reader and by task, so the reader chooses, rather than the page guessing one narrow layout for everyone.

## Decided

1. **The control.** A `Table` given `columns_choice` (a `ColumnsChoice` holding the table's stable id) puts a **Columns** button (a Ghost Small `Button`) before it. It is a disclosure, not a dialog: `aria-expanded` says whether its panel shows and `aria-controls` names the panel, which stays in the page's flow. Escape in the panel closes it and hands focus to the button; an Escape a tooltip took first closes only the tooltip. The panel's list is named by the button.
2. **What the panel holds.** Every column after the row header's, in the table's order, each with a `Checkbox` labeled with the column's header words; **Move ⟨column⟩ up** and **Move ⟨column⟩ down**, icon-only, unavailable (`aria-disabled`, still a Tab stop) at the list's ends, focus staying on the button pressed, or going to the other one once its column can't move that way; and a drag handle, decoration a screen reader skips. **Reset columns** ends it, restoring the order given with every column shown. Each change is said politely in a whole sentence ("Size hidden.", "Files moved to position 2 of 4.").
3. **The row header** always stays first and shown, and isn't listed. **A column the table always shows** (`always_shown`, amended above) stands right after it, isn't listed and can't be moved. Every other column may be hidden: the table still shows its row headers and those columns.
4. **Dragging** happens only in the panel's list, by pointer events with the pointer captured by what it pressed in the handle, so a mouse, a pen and a finger drag alike; only the handle has `touch-action: none`, so a finger elsewhere still scrolls. A line at the gap shows where the column would land. Nothing animates, under reduced motion or not (decision 130). Dragging is never the only way: the Move buttons do all of it by keyboard (2.5.7), and every target is at least 24 × 24 CSS px (2.5.8).
5. **Where.** Operations, Repositories, the plans, the Log and API tokens, the tables a reader comes back to, and the gallery's Table demo. A repository's snapshots table has one column besides its row header, so a panel there would be noise. The stats table, the forget review's lists, a proposal's forget preview, the dry-run allowlist and the start page's plans are left as they are.
6. **Kept in this browser** (`localStorage`, `ladderback-columns-<id>`), as the page width is: a viewing preference of one browser and its screen, never the daemon's. The value is the column ids in order, comma-separated, a hidden one marked `!`; the order given keeps nothing. What a browser kept is outside input, read once on the host (`table::rules::Layout::from_kept`): ids unknown to the table drop, columns it doesn't name append in the order given, shown; a column named twice, junk, more than 64 entries or an id over 64 bytes falls back to the order given. A browser that refuses to keep it keeps the choice for the visit. Each column has a stable id (`Column::new(id, …)`), so a header reworded or translated keeps the choice.
7. **Hiding the sorted column ends the sort,** and the rows return to the order given; showing it again doesn't sort by it. A sort by a column the reader can't see would order the rows for no reason the page shows: its header's `aria-sort` and its sort button, the only things that say the sort and undo it, go with the column. Nothing is announced for the ended sort beyond the column's "hidden".
8. **A hidden cued column marks nothing** (decision 129). The mark is the cued cell's bold and its "Changed, not yet seen" word, so with the cell gone a mark would be an edge alone, which no screen reader hears (1.3.1). Hiding the cued column sees every mark it had, and a change while it is hidden is seen as it comes, so showing it again brings back no marks for changes the reader couldn't have seen as they happened.

## What it costs

Each table that offers it has one more Tab stop before its frame, after the page's own actions. The choice is one browser's: another browser, or this one after its storage is cleared, shows the order given. A reader who sorted by a column and hides it loses that sort and sorts again after showing it.

A column the table always shows takes room no reader can give back, so only the one fact a page exists for gets one. On Repositories its 9rem came from Location, since the columns still add up to the page's 58rem at 1280 px: a 43-character address there now takes two lines, broken only between its parts (#1625).
