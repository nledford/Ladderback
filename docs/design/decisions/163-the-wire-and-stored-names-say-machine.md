# Decision 163: The names on the wire, in the data folder, in snapshot tags and in the database say machine, in one breaking change

**Every name that leaves the program or outlives it and says "agent" for a machine says "machine" instead: the sync protocol's fields, the signed labels, the refusal and error codes, the hub's API paths and fields, the hub's events, the adoption field, the data folder's two files, the snapshot tag, the hook level's code, the Settings tab's address and the database's tables, columns and index. The hub's registry moves to `/api/v1/hub/machines`, and the dashboard, which held that path, moves to `GET /api/v1/hub/dashboard`. Nothing accepts the old names: no alias, no fallback, no window of two releases. The person moves two files and retags their snapshots, and the database migrates itself** (recorded 2026-11-25, §7.1, §7.2, §7.3, §9; #1220).

## Why

[Decision 133](133-a-machine-not-an-agent.md) made "machine" the word a person reads, and left code, design prose and scenarios for one mechanical change. That change is mostly internal and can come any time. The names below can't: each is frozen somewhere outside the code, in a peer running another build, in a file on disk, in a tag in a repository or in a row of the database, so each later release that keeps "agent" there makes the move cost more. No hub has shipped in a full release yet, so few people hold the old names, and the move is cheapest now.

The move is a clean cutover. [Decision 88](88-hub-and-agent-version-compatibility.md), as PR #1619 amended it, lets the sync protocol, the handshake and the hub's API change in place until 1.0.0, with no window in which a hub speaks to a machine a release behind; each such change gets a Breaking entry in the changelog with its upgrade step. Aliases would keep both spellings in the code and the tests for as long as anyone holds the old one, which is the cost the amendment exists to avoid.

## Decided

1. **The sync protocol.** The fields of the frames and payloads that name the machine say `machine_` where they said `agent_`: `machine_id`, `machine_nonce`, `machine_protocols`, `machine_version` and the rest (multi-machine §7.1). The types keep their names until the mechanical change.
2. **Signed labels.** A machine's proof is signed under `machine-proof`, its messages under `machine-signed` ([decision 120](120-agent-hub-connection-security.md)). A hub and a machine that disagree on a label refuse each other's signatures, so both move together.
3. **Refusal and error codes.** `agent-key-mismatch`, `agent-removed`, `agent-key-removed`, `agent-unknown` and `agent-approved-already` become `machine-key-mismatch`, `machine-removed`, `machine-key-removed`, `machine-unknown` and `machine-approved-already`, and their messages' Fluent IDs `error-machine-…` (§13.7.1).
4. **The hub's API.** The registry is `/api/v1/hub/machines`, with `/{id}/approval` and `/{id}/removal` below it, where it was `/api/v1/hub/agents`. The dashboard, which [decision 149](149-the-hubs-dashboard.md) put at `GET /api/v1/hub/machines`, is `GET /api/v1/hub/dashboard`, so the registry can take the name that says what it lists. The fields say `machine-id` where they said `agent-id`, and the registry's list is `machines` where it was `agents`.
5. **The hub's events.** The eight events a hub tells its browsers are `machine-online`, `machine-offline`, `machine-pending`, `machine-approved`, `machine-removed`, `machine-reported`, `machine-plans` and `machine-progress`, each with its machine in `machine`.
6. **Maintenance.** An orphaned group and an adoption's source name their machine in `machine`, where they said `agent`.
7. **The data folder.** The machine ID is kept in `machine-id` and the machine's key in `machine-key`, where they were `agent-id` and `agent-key`. A backup of the data folder leaves `machine-key*` out as it left `agent-key*` (decision 120), and it leaves `agent-key*` out too. That is no alias: nothing reads `agent-key`, but a person who skips the upgrade's rename, or a write an earlier build staged beside the key (`agent-key.<id>.tmp`), leaves a secret key behind, and I4 keeps it out of the repository as before.
8. **The snapshot tag** is `ladderback-machine:<id>`, where it was `ladderback-agent:<id>` (decision 8, §7.3). Grouping, parents and an exported profile's filter read the new tag only. The old tag is read in one way only, to fail closed: a snapshot that still carries `ladderback-agent:` counts as another machine's, whichever machine it names, in what a machine tells its hub of each repository ([decision 156](156-an-agent-knows-others-snapshots-from-its-last-listing.md)) and in the other-hosts warning ([decision 62](62-another-agents-recent-snapshots-come-from-another-machine.md)). It never makes a snapshot a plan's or this machine's, so it is no alias; without it, a machine whose snapshots kept the old tag would tell its hub that no other machine backs up there, and the hub could grant a lease for a repository another machine maintains (I1).
9. **The hook level** the first `[hooks]` table runs at is coded `machine`, in a failed hook's arguments and its message, where it was `agent`. The `[agent]` table of `config.toml` keeps its name (decision 133).
10. **The Settings tab's address** is `settings#machines`, where it was `settings#agents`.
11. **The database.** Migration `0029_machine_names.sql` renames the tables `agents`, `agent_leases`, `agent_epoch_floors`, `agent_tombstones` and `agent_maintenance_paused` to `machines`, `machine_leases`, `machine_epoch_floors`, `machine_tombstones` and `machine_maintenance_paused`; the column `agent_id` to `machine_id` in `operations`, `sync_watermarks`, `sync_reports`, `sync_report_tallies`, `ownership_reports`, `sync_plans`, `sync_plan_snapshots` and `sync_progress`; `pairing_tokens`' `used_agent_id` and `used_agent_key` to `used_machine_id` and `used_machine_key`; and the index `sync_reports_by_agent` to `sync_reports_by_machine`. It rewrites a failed hook's stored level from `agent` to `machine`, so an old row reads back as a new one. No name in the schema says `agent` afterwards (§9).

Left alone: the `[agent]` table of `config.toml`, "launchd agent", the AI agent and its names (the `ui-agents-*` messages, the AI agents tab), and every Rust identifier that names no wire or stored value. Those move, if at all, in the mechanical change decision 133 left for later.

## What it costs

Upgrading takes four steps, and the hub and every machine paired with it are upgraded together, since an old build and a new one refuse each other's signatures and codes:

1. Stop the service.
2. In the data folder (on macOS `~/Library/Application Support/ladderback`), rename `agent-id` to `machine-id` and `agent-key` to `machine-key`. A machine that starts without them takes a new machine ID and key, as a new machine does, and must pair again.
3. Retag the snapshots this machine made with rustic, replacing `ladderback-agent:<id>` with `ladderback-machine:<id>`: `rustic tag --filter-tags ladderback-agent:<id> --add ladderback-machine:<id> --remove ladderback-agent:<id> --dry-run`, then again without `--dry-run`. Retag every machine that backs up to a shared repository, not just one.
4. Start the service. The database migrates itself.

Known limits:

- **A snapshot that keeps the old tag is orphaned.** It names no machine Ladderback knows, so it lists as orphaned with no machine and can't be adopted from the UI until it is retagged, and a plan's next backup finds no parent among such snapshots and reads its sources in full.
- **A repository with recent snapshots under the old tag counts as shared.** Until every machine's old snapshots are retagged, or are older than the 30 days of decision 62, a machine tells its hub that another machine backs up there, so the hub withholds the maintenance lease, and a standalone machine with `local` maintenance warns of another host.
- **An exported rustic profile** that filters on `ladderback-agent:` is refused on import as a narrowing filter; export it again from the new build.
- A clean cutover means a mixed fleet doesn't sync: a machine a release behind its hub is refused until it is upgraded.
