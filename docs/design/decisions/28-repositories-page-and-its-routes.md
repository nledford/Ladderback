# Decision 28: Repositories page and its routes

**A form that tests, connects or creates a repository over three underscore-prefixed routes, saving a typed password inline** (recorded 2026-11-10, §4.2, §4.4). `POST /api/v1/repositories/_test`, `POST /api/v1/repositories` and `POST /api/v1/repositories/_init` take the configuration's own `settings`; the underscore keeps an alias, which is a slug, from ever colliding with `/repositories/{alias}`. `GET /api/v1/repositories` now answers rows, not bare aliases (a clean cutover; the Snapshots page reads the alias from a row), with the location masked and the password as its source, never its value (I4). Three choices carry the weight. (1) **A `command` password source is refused over HTTP.** It would make this the first route that runs a program, and that belongs behind authentication and scopes (§10.1); a file written by hand still takes one. (2) **A typed password is saved inline in `config.toml`** (written 0600, as are the copies of earlier versions the history keeps), with no keyring write yet: the keyring needs a design of its own, and the file already holds a password the same way for a repository written by hand; the form says where the password goes. (3) **Connecting is test, then save, under one lock in the composition root**, so two connections at the same moment both survive; the configuration store has no transactional update, and a later writer must take the same lock, or the store grows one. A refusal carries the engine's own words as `detail`, shown in `lang="en"`, and nothing else of rustic's is parsed: a wrong password and a missing repository are not yet typed. With auth off these routes are as open as every other mutating route, which §10.1's request checks alone guard: a caller can have the daemon open or create a repository at any location it can reach, and name a file, an environment variable or a keyring entry as the password's source. No value read that way is ever returned.
