# Decision 98: No core dumps or debugger attach for the daemon, its workers and the MCP server

**As the daemon starts, before it resolves any secret, and as each worker starts, before it reads its job, the process sets its core-dump limit to 0, soft and hard (Linux and macOS), and on Linux clears its dumpable flag (`PR_SET_DUMPABLE` 0). A process that can't logs a warning by its code, `core-dumps-on` or `debugger-attach-allowed`, and goes on** (recorded 2026-11-15, §10.2; #351). Wiping a secret's bytes when it is dropped is a separate change (#600).

**Amended 2026-11-15 (#719):** the MCP server, `ladderback mcp` in every mode, and its one-shot command, `ladderback mcp call`, do the same as they start, before they resolve any secret or read an API token file or a script of calls, and log the same warning when they can't. A session of its own, headless or in a scratch folder, resolves repository secrets as the daemon does, and connect mode keeps the token it read, for as long as its client keeps it running or, for a one-shot command, until its last call; a script read from standard input can keep one running for as long as its writer likes.

## Why

- **A dump is a copy of the secrets on disk.** The daemon holds resolved repository passwords, notification credentials and its sign-in secrets, and a worker the secrets of its job. Many Linux systems keep a dump of any process that crashes (`systemd-coredump` is on by default on several distributions), so a crash in the daemon, in a worker or in a C library either links would write them where no rule of I4 reaches.
- **Both the soft and the hard limit.** A hard limit of 0 can't be raised again by the process or by anything it starts. Hooks and secret commands inherit it, so they leave no dump either, and a hook that wants one has to be run by something other than Ladderback.
- **The dumpable flag on Linux.** A dump through a pipe that the kernel's `core_pattern` names is not held to the limit by the kernel; a process that isn't dumpable leaves no dump at all. The flag also refuses `ptrace` and reads of `/proc/<pid>/mem` and `/proc/<pid>/environ` by other processes of the same user, so a debugger can't read the secrets of a running daemon. Root still can.
- **Each worker does it itself.** The kernel sets the dumpable flag again when a process starts a program, so a worker, which the daemon starts as `ladderback worker`, clears it first thing, before it reads the job its secrets come in. The limit is inherited, and set again all the same.
- **A failure warns and starts anyway.** Neither call fails on a normal system; a security policy might refuse one. A daemon that stopped there would stop every backup for a protection it can do without, so it logs `core-dumps-on` or `debugger-attach-allowed` with the system's words, by its code (§13.7.1), and starts. A worker writes the same code to stderr, which the daemon logs as a warning; a worker reads no catalog.
- **Not behind a port.** The core decides nothing here: the composition root calls the platform adapter (`platform::dumps::refuse`) as each process starts.

Left out: macOS's `PT_DENY_ATTACH`, which refuses a debugger only, can be undone by anything that runs before it, and stops the crash reporter; `ladderback set-password`, `import-profile` and the other commands, which run briefly in a terminal; and swap. Programs the daemon, its workers and the MCP server or its one-shot command start (rclone, secret commands, `secret-tool`, hooks) keep the limit of 0, but the kernel makes them dumpable again, so a process of the same user can read their memory and environment. A debugger of the same user that attaches to a worker in the instant between its start and its first call keeps what it has; the flag refuses only what comes after.
