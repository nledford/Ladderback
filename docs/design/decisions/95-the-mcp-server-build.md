# Decision 95: The MCP server as built

**`ladderback mcp` is built on the official Rust SDK, `rmcp` 3.10, pinned, inside `adapters/mcp` alone; its tools' output schemas come from the `api` types through `schemars`; there is no `operation_log` tool for now; connect mode gets two new HTTP routes so it offers every tool, reads an API token from a file only its owner can read and sends it only to `https` or loopback; a `read`-scope token may read the daemon's build; headless mode takes `serve`'s folders and their variables, with no folder flags; a scratch folder is locked before it is named; `wait_operation` polls every 500 ms; a change whose answer is lost is `daemon-answer-lost`, never resent; and a headless session stops at EOF as `serve` does, leaving its queue to the next `serve`** (recorded 2026-11-14, §4.6, §10.5; decided by the maintainer on #517).

It amends decision 20, which planned the protocol and the tool list before revision `2026-07-28` existed, decision 93, whose `GET /api/v1/session` was for a session only, and §4.6's earlier text, under which a headless session canceled its queue at its end.

**Amended 2026-11-15 (#724, #725, #726):** a tool's arguments change in three ways; §4.6 has the details.

- **A refusal, not a protocol error.** A call that leaves out an argument the tool needs, gives one it doesn't take, or gives a value it doesn't take is the tool's refusal `invalid-arguments`, a result with `isError` as point 4 says. Its `field` names the argument and its `problem` says what is wrong (`missing`, `unknown-key` or `invalid`), never the value given, and the tool doesn't run. The agent reads a refusal and can call the tool again, while some clients show a protocol error only to the person, or retry the call as it was. A tool that doesn't exist, and a call whose arguments aren't an object, stay JSON-RPC invalid params (-32602); for the latter the server overrides `rmcp` 3.10, which answered method not found (-32601).
- **`operation`.** `get_operation`, `wait_operation` and `cancel_operation` take the operation's ID as `operation`, the name `run_plan` returns it under, no longer `id`.
- **Narrow input schemas.** Some clients turn an input schema into a function declaration of a narrower schema language. An optional argument has its one type, never a type list with null, as [Gemini's function declarations](https://ai.google.dev/api/generate-content#schema) take; no argument has a `format`, which [OpenAI's strict mode takes on strings only](https://developers.openai.com/api/docs/guides/structured-outputs#supported-schemas), or a `minimum`, which [Claude's strict tool use refuses](https://platform.claude.com/docs/en/build-with-claude/structured-outputs#json-schema-limitations). The argument's description says its bounds.

**Amended 2026-11-15 (#752):** `ladderback mcp call` runs tools once, without a client; §4.6 has the details.

- **One dispatch.** A one-shot call goes through the dispatch `tools/call` uses, so its tools, checks and results can't drift from MCP's. The dispatch answers a result, a refusal, or a result that couldn't be written as JSON; `tools/call` turns that into its result, and `mcp call` into one JSON line. It takes the request's context as an option rather than a cancellation token of its own: a token type would need `tokio-util` as a new dependency, and a call with no client has nothing to cancel it, so its wait runs its length.
- **Exit statuses.** 0 when every call worked, 1 when one failed or the session couldn't start, 2 for a command line that can't be read, the parser's own status, or an address that isn't one, before any session starts.
- **No `--json`.** Its output is JSON lines whatever is asked, and `--json`'s contract is one document with every failure a document, which a stream of lines with refusals said on stderr isn't; only a command that reports state takes `--json` (`features/cli/output.feature`). The flag is refused as any unknown one is.
- **A script read a line at a time.** `--script -` reads standard input lazily, each call answered before the next line is read, so a run and a wait for it share one session: a file written before can't know the run's operation ID. A line that isn't a call is said on stderr by its number, never its text nor a tool it names, which may hold a profile's password (I4).
- **One address.** `--connect` under `call` takes exactly one URL, connect being the default: in the bare form `mcp --connect` has, it would take the tool's name as the address.
- **No lone run in a session of its own.** `run_plan` alone on the command line with `--headless` or `--scratch` is refused before the session starts (exit status 2): the session ends after the call, and its end stops the backup, so exit status 0 would report a backup that never finishes. The maintainer chose the refusal over waiting for the backup (2026-11-15), so a one-shot run never blocks unasked; a script runs it and then `wait_operation`.

**Amended 2026-11-15 (#723):** a refusal says what to do next; §4.6 has the details.

- **A sentence after the code.** A refusal's result keeps its one `{code, args}` text content, unchanged, so a client still branches on the code, and adds a second: the catalog's sentence for the code (`error-<code>`, the same arguments and detail), as the web UI and the CLI say it. An AI agent reading `api-token-scope` alone doesn't learn what to do, and neither does a person it relays the refusal to. The code stays first, so a client that reads the first content as JSON goes on working; the sentence holds nothing the code, its arguments and its detail don't (I4). `ladderback mcp call` says the sentence of a refused call on stderr and leaves its JSON line on stdout as it was, since scripts read that line.
- **The environment's locale.** An MCP client sends no language, so the sentence follows the locale of the environment `ladderback mcp` runs in, found as for the CLI's own messages (§8.4), not a fixed `en-US`: the maintainer's choice (2026-11-15). An AI agent launched by a person runs in their environment, and the sentence is for them as much as for it.
- **The catalog's words, unchanged.** No message is written for MCP alone: one message per code keeps one convention. Where today's sentence speaks to someone at a browser, an MCP client gets that sentence too, a known limit left to the messages themselves.

## Why

- **`rmcp`, not a protocol layer of our own.** MCP revision `2026-07-28` removed `initialize` and `ping`, added `server/discover`, a revision named in each request's `_meta`, a required `resultType` and new cache hints. Clients in use speak both eras, and `rmcp` 3.10 serves both: it negotiates `initialize` for `2025-06-18` and `2025-11-25`, answers `server/discover`, checks each request's revision against the ones we serve, and strips `resultType` for older peers. A layer of our own would be about a thousand lines that follow every revision by hand. It is the official SDK (Apache-2.0, MSRV 1.88) and adds four crates to the lockfile. The cost is churn: three majors in five months, so it is pinned exactly (`=3.10.0`) and upgraded in a change of its own.
- **The SDK's log capped at `warn`.** `rmcp` logs through `tracing`, whose records reach the daemon's log, as nothing subscribes to `tracing`. At `debug` it logs every request and result whole, a profile's password with them, so the daemon's logger refuses any record of `rmcp` or a module of it below `warn`, whatever `RUST_LOG` says (I4). It checks each record's target rather than adding a directive for `rmcp`: env_logger lets the directive for the longest matching name decide, so `rmcp::service=debug` would outrank it.
- **Revisions `2025-06-18` to `2026-07-28`.** The oldest is the first with `structuredContent` and `outputSchema`, which every result relies on. A handshake asking for an older one is answered with the newest revision that has a handshake, as the protocol says, and the client then leaves; a request naming an older revision in its `_meta` is refused.
- **Output schemas from the `api` types.** `schemars` derives them, behind a feature of `api` that only `adapters/mcp` turns on, and a golden `tools/list` file makes every schema change visible in review. A schema written by hand would drift from the type it describes; no JSON-schema validator is needed, because the schema and the value come from the same type. The output schemas drop the fields' descriptions, and error and warning codes are plain strings rather than every code listed: with the `api` doc comments in, `tools/list` was 83 KB, which a client reads at the start of every session; without them it is 57 KB. The field names say enough, the doc comments stay in the code, and each tool and input field keeps its description, which is what a model reads to call a tool well.
- **No `operation_log`.** No per-operation log exists: the "operation log" is the history database. `get_operation` carries the operation's failure `{code, args, detail}` and its warnings, which is what a log would mostly have been read for. A known limit, until such a log exists.
- **Two new routes, so both modes offer every tool.** `preview_import` and `export_profile` had no route: `POST /api/v1/profiles/preview` (scope `preview`) previews a profile's text without writing, and `GET /api/v1/plans/{id}/profile` (scope `read`) exports a plan. Without them connect mode would offer fewer tools than headless mode, and the parity suite would have to know which.
- **A `read` token reads the build.** `status` names the daemon's `version`, `commit`, `dirty` and `release` as fields of their own (decision 90), so an agent never parses `0.3.0+3f937cf`. Over `--connect` with sign-in on, that needs `GET /api/v1/session` open to a `read` token; the build says which fixes a daemon lacks, which a token holder may know, as a signed-in page may. The route answers a token `signed-out`, with no CSRF token: a token has no session, and a new state would change the wire contract and the web UI for nothing a page needs.
- **A `read` token exports a profile.** `export_profile` needs only `read`, as `GET /api/v1/plans/{id}/profile` does, so a token that may only read is shown the plan's hook command lines and the repository's password-command line. It is never shown a password: one stored in the configuration is refused as `inline-secret` (I4). A token holder can read how a password is fetched, not the password. **Amended** (2026-11-16, #856): a token is no longer shown those command lines. An export over MCP, and the route answering any request that carries an API token, leave out the `password-command`, every option rustic runs as a command (`rclone-command`, `post-create-command`, `post-delete-command`) and every hook, naming each in a `profile-command-left-out` notice, since a person typed them and one may carry a token of its own. Only a request without a token that doesn't ask `?commands=left-out` gets them: a signed-in session's, or with sign-in off any caller's (security §10.5).
- **`access`, told by how the server connected.** `status` would otherwise tell an agent holding a good token that it is signed out. It says instead `api-token`, `sign-in-off` (a daemon with sign-in off ignores a token) or `in-process`, which the adapter knows without asking, and leaves the daemon's sign-in state out.
- **A token from a file, never over plain HTTP.** A token on the command line or in the environment is readable by other users and lands in logs (I4), so it is read from a file only its owner may read or change, and a file with any group or world permission is refused. A `password-file` others can read or change only gets a warning (security.md §10.2), as it is shared with rustic and container setups; the token file is Ladderback's own, with nothing to stay compatible with. Sent over plain HTTP to another machine anyone on the way could read it, so that is refused at start, whatever the daemon's sign-in.
- **Snapshot filters in the server.** `list_snapshots` filters by plan and host before paging, over the list either backend returns, so the two modes filter alike with one implementation; tag, path and time filters wait for a client that needs them.
- **`wait_operation` polls, over no WebSocket.** It reads the operation every 500 ms until it finishes or the timeout passes. The events WebSocket would tell it sooner, but it would need a second client, with its reconnects and missed events, in connect mode, and an in-process equivalent in headless mode, for a wait of seconds to minutes; a read every 500 ms is a light `GET` on loopback, and both modes wait through the same loop. Progress counts the seconds waited of the timeout: what the wait itself knows, alike in both modes.
- **`daemon-answer-lost`, never resent.** A `run_plan` or `cancel_operation` whose request was sent but whose answer never came may have taken effect. Sent again, it could queue a second backup; called `daemon-unreachable`, it would read as "nothing happened". So it has a code of its own that says the outcome is unknown and how to find out, and the request is sent once.
- **Maintenance refused in both modes.** The daemon refuses a token's cancel of anything but a backup as `api-token-scope` naming `session` (decision 93). Headless mode has no token, but a loop that could cancel every check or prune would keep a repository from ever being pruned, so the in-process backend refuses it with the same code, and the parity suite holds the two alike.
- **Queued operations stay queued at a session's end.** §4.6 first said a headless session cancels its queued operations at EOF or SIGTERM, so a later `serve` finds no stale queue. Since decision 73 a restart runs a queued backup again, so canceling would drop a backup the owner asked for. At EOF the session stops as `serve` does (decision 92): its workers stop, what runs ends `daemon-shut-down`, and what is queued stays for the next `serve`. This amends that earlier text. The session doesn't catch SIGTERM: one ended that way leaves its operations to the next start's recovery, as after a crash, a known limit.
- **`preview_forget` without its selection.** The daemon's forget preview names a selection, the token a forget's start is held to, so the forget acts on exactly what a person reviewed (I6). MCP starts no forget (§4.6), so the selection would be a token nothing in MCP takes, and an agent handed one might pass it on to something that does: the result leaves it out.
- **`test_repository` isn't offered as a read.** It records nothing, but it opens the repository at each location and resolves its secrets, as a backup does, and the daemon grants its route to the scope `run` (decision 93). A client that runs read-only tools without asking would run it unasked under a token that has no `run`, so its annotation says it isn't read-only.
- **A profile previewed from its text.** `preview_import` takes the TOML, never a path, so an agent can't make the server read a file of its choosing. For the same reason it reads no profile the text uses and no rustic variable from the environment: each profile named in `use-profiles` is the warning `profile-used-not-read`. The preview's route has a body class of its own, as a profile may hold 1 MiB and JSON may write each character as two.
- **The MCP message cap stays 1 MiB.** A profile near its own 1 MiB cap, written as JSON in a call, passes the 1 MiB an incoming MCP message may hold, so it can't be previewed over MCP. Raising the cap for one tool would let every message on stdio hold that much; a profile that large is imported from its file instead. A known limit.
- **A repository read gets 30 s in connect mode.** Listing snapshots, testing and previewing a forget read the repository, which can be slow. Every request keeps the one 30 s limit, and a slower answer is `daemon-unreachable`, as any read that goes unanswered is: a read is safe to ask again. A known limit.

## Decided

1. **Placement:** one crate, `adapters/mcp`, an inbound adapter beside `http`. Its tools call the `Backend` trait the crate defines; connect mode's implementation is an HTTP client that depends on `api` alone (§3.2). The in-process implementation, for headless and scratch modes, lives in the composition root and calls the handles `serve`'s router reads, so the two modes can differ only in transport, which the parity suite checks.
2. **Stdio:** an incoming message over 1 MiB is dropped unread and the session goes on; standard output carries protocol messages only; the session ends when standard input closes.
3. **`status`:** this program's build and `access`, then in connect mode the daemon's build and exposure, each plan with its next run and last operation, and the operations queued or running among the newest 200. With sign-in on and no token it is `sign-in-required`.
4. **No answer from the daemon,** or an answer that isn't the API's, is the tool error `daemon-unreachable`; an answer over 8 MiB is `daemon-answer-too-large`, naming the cap; a refusal from the daemon is handed on as its own `{code, args}`. Every refusal is a result with `isError` whose first text content is that `{code, args}` as JSON, and whose second is the catalog's sentence for it (amended by #723), with no `structuredContent`: clients such as the official TypeScript SDK check `structuredContent` against the tool's output schema even on an error, and throw when it doesn't conform, which would hide the code.
5. **`--connect`** takes an `http` or `https` address of a host, with no user name, password, query or fragment: a password there would be on the command line.
6. **`--headless`** opens the folders `serve` opens, `LADDERBACK_CONFIG_DIR`, `LADDERBACK_DATA_DIR` and `LADDERBACK_CACHE_DIR` included, and takes no `--config` or `--data` flag: one way to name the folders for both commands, and the data-dir lock (§9) keeps a session off a data dir `serve` or another session holds.
7. **`--scratch`** makes its folder under a hidden staging name, mode 0700, takes that folder's data-dir lock, then renames it to `ladderback-scratch-<random>`, so no sweep ever sees it unlocked. A sweep deletes only folders with that prefix, not links, whose lock it can take: a crashed session's, never a live one's, nor another user's in a shared temporary folder.
8. **Paging:** the server cuts every list into pages, over the whole list either backend returns, so the two modes page alike by construction; operations page through the history's own cursor. `limit` defaults to 50 and is clamped to 1..200, never an error: a client that asks for too much gets a page and a `next`. Every other cursor is the key of the page's last item. `get_operation` lists an operation's first 100 warnings and counts the rest in `unlisted-warnings`, since an operation keeps up to ten thousand.
9. **Tokens:** `--token-file PATH`, or else `mcp-token` in the configuration folder when it is there. A named file that isn't there, a file with any group or world permission or over 4 KiB, and a token with a plain `http` address beyond loopback (127.0.0.0/8, `::1`, `localhost`) each stop the server at start with exit 1. The token is sent as `Authorization: Bearer` on every request, redirects are never followed, no proxy the environment names (`HTTP_PROXY`, `ALL_PROXY`) is used, as it would be sent a loopback request's token in clear, and it is never shown.
10. **Snapshot filters:** `plan` keeps the snapshots whose first `ladderback-plan:` tag names it, as maintenance reads a snapshot's plan; `host` keeps those of that exact host. A cursor must be one the same filters keep.
11. **`wait_operation`:** `timeout` in seconds, 60 by default, clamped to at most 600, and 0 reads the operation once. It reads the operation's summary every 500 ms, then its detail once, and returns `finished` and the operation as `get_operation` does; a canceled call never reads the detail. Progress notifications, only with a progress token, give the seconds waited of the timeout. Canceling the call ends the wait unanswered, and the operation goes on.
12. **A lost answer:** in connect mode a request that changes something, sent but unanswered or answered with something that isn't the API's, is the tool error `daemon-answer-lost` and is never sent again.
13. **`cancel_operation`:** a backup, queued or running, however it started; anything else is `api-token-scope` naming `session`, in every mode. Connect mode reads the operation's summary first, as the history page of one just past its ID (newest first by ID, a cursor that need not exist), never its detail, which can pass the 8 MiB cap, and sends no cancel for anything but a backup.
14. **A headless or scratch session's end:** at stdin EOF its workers stop within `serve`'s bound, what runs ends `daemon-shut-down`, queued operations stay queued, and the operation log closes, before the process exits 0. SIGTERM isn't caught.
15. **`test_repository` and `preview_forget`** take `repository`, an alias; one that can't be a path segment is `repository-unknown` without asking the daemon. `test_repository` is annotated idempotent and not read-only; `preview_forget`, `preview_import` and `export_profile` read only.
16. **`preview_forget`** returns `plans`, `left-alone` and `warnings`, never `selection`. A repository not maintained here is `maintenance-not-owner`, and a daemon's preview of another kind is `daemon-unreachable`.
17. **`preview_import`** takes `content` and `repository`, the alias the profile's repository would be saved under, both required, and returns the import's proposal. It reads no file and no rustic variable; a profile named in `use-profiles` is `profile-used-not-read`, naming it. A refusal of the text names `content`, and a parse error carries none of it (I4).
18. **`export_profile`** takes `plan`; one that can't be a path segment is `plan-unknown` without asking the daemon. A password stored in the configuration is `inline-secret`. The `password-command`, every option rustic runs as a command and every hook are left out, each named by a `profile-command-left-out` notice (#856).
19. **Routes:** `POST /api/v1/profiles/preview` (scope `preview`, a body of at most 2 MiB and 128 KiB) and `GET /api/v1/plans/{id}/profile` (scope `read`). A preview whose merged configuration breaks a rule is `422`; a configuration that can't be loaded is `503`. The export takes `?commands=left-out`, which connect mode always sends; a request with an API token gets the commands left out whatever it asks (#856).

Left out: proposal tools (#518), the hub's `agent` argument (M5), and a per-operation log.

**Amended by decision 127** (2026-11-20, #962): the refusals above named `api-token-scope` are `api-token-permission`, naming `session` or the permission a route needs; the scopes named for the routes are the permissions their tokens were migrated to (`read` Backups, `run` Backup runs, `preview` Previews, `propose` Configuration).
