# Decision 144: What a machine does when its data folder was copied from another computer

**A machine records the machine identifier its operating system gives the computer (`/etc/machine-id`, else `/var/lib/dbus/machine-id`, on Linux; `IOPlatformUUID` on macOS) in the file `machine-identifier` beside its machine ID in the data folder, and compares it at each start (#296, the maintainer's call of 2026-11-14: detect and stop). When the recorded identifier is another computer's, the data folder is a copy: the machine keeps backing up, and refuses every forget, prune and adoption, the preview of each and a proposal's forget preview, with `maintenance-data-folder-copied` (HTTP 409), before the repository is opened; a check only reads, and still runs.**

**The log says so at start, and the start page says so with the button "This is a new computer: take a new ID", which a review dialog confirms. Taking a new ID turns maintenance off (`maintenance = "none"`) on every repository the configuration had this machine maintain, then writes a new machine ID and records this computer's identifier beside it; while a maintenance operation (a check) runs on one of them, it is refused with `maintenance-busy` and nothing changes. The new ID is used from the next start; until then maintenance stays refused. A data folder with no recorded identifier records this computer's silently, and an identifier that can't be read, or a record that can't be read or written, refuses nothing and is said in the log.**

## Why

- **A copy runs under the first computer's machine ID.** The ID lives in the data folder (§7.1), so a home folder restored onto a new computer, or a cloned disk or virtual machine, brings it along. Backups are tagged with the ID (§7.3), so the copy's forget would take the first computer's snapshots for its own, and both would maintain the same repositories: I1 and I6 broken at once, with no warning, since decision 62's check of other hosts sees one host.
- **Backups go on.** A copy's backups add snapshots and lose nothing; stopping them would leave a person without backups for a question they may not see for days. Only what can remove snapshots, or change who owns them, stops. A check reads, so it runs.
- **Refused before anything is read.** The gate is on `RunMaintenance` itself, before it reads the configuration or opens the repository, so a preview that would list the other computer's snapshots as this one's is never shown, and no path into maintenance (the page, the API, a schedule) goes around it.
- **Taking a new ID gives up maintenance first** (decided 2026-11-22 by the maintainer's delegate). After a new ID the copy no longer owns the old ID's snapshots, and the computer it was copied from still maintains the repositories it maintained: if the copy kept `maintenance = "local"`, the two would both maintain them (I1). Turning maintenance off on every repository it maintained, in one configuration write under the configuration's lock, and before the new ID is written, means a failure halfway leaves the copy maintaining nothing, the safe direction. The person turns maintenance back on per repository once they know which computer should maintain it; the dialog says so plainly.
- **From the next start** (decided 2026-11-22). The running daemon has tagged and selected snapshots under the old ID since it started, in its scheduler, its queued runs and its caches. Swapping the ID under them invites a run that mixes the two, so the new ID waits for a restart, and maintenance stays refused until then (`new-id-taken`).
- **An identifier that can't be read refuses nothing** (decided 2026-11-22). A container without `/etc/machine-id`, or an `ioreg` that fails, would otherwise stop maintenance on machines that were never copied. The log names the reason, and the check runs again at each start.
- **On Linux, only 32 lowercase hexadecimal digits are an identifier** (decided 2026-11-22). machine-id(5) gives the machine ID that form; anything else, such as the `uninitialized` systemd writes on a first boot or an empty file, isn't the computer's lasting identifier, and recorded or compared it would make the computer look like a copy of itself at a later start. It counts as unreadable: it refuses nothing, and the log says so.
- **A running maintenance operation keeps the ID.** A copy still runs checks, and while one runs this machine maintains its repository. Giving that up at once would let the computer it was copied from start a prune beside it (I1), so taking a new ID asks `Ownership::give_up` of each repository it maintained, as turning its maintenance off does, and a running one refuses the whole take with `maintenance-busy`.
- **No identifier recorded is an upgrade, not a copy.** Data folders from before this decision have none; recording this computer's at the first start keeps every existing machine as it was.
- **The identifier stays in the data folder, never the database**, as the machine ID and key do (§7.1), so `db rebuild` can't change it. It is read only to compare, and never shown or sent: what reaches the hub is a digest of it keyed by the machine ID, which doesn't give it back ([decision 150](150-the-hub-takes-one-computer-per-machine-id.md)).

## Known limits

- A copy that keeps the identifier, such as a cloned virtual machine whose `/etc/machine-id` was cloned too, or a data folder restored onto the computer it came from, isn't told. The hub doesn't tell it either: its machine fingerprint is the original's ([decision 150](150-the-hub-takes-one-computer-per-machine-id.md)).
- Reinstalling the operating system changes `/etc/machine-id` on Linux, so the same computer is told it is a copy. Taking a new ID is then the way on, and its old snapshots stay under the old ID until the person adopts them.
- A recorded file that can't be read runs as usual with a warning in the log, so a damaged record hides a copy until it is fixed.
- The snapshots the copy backed up before the restart carry the old ID.
- A paired machine that takes a new ID has to pair again: the hub knows it by the old one.
- A Linux computer that boots two systems sharing one home folder, and so one data folder, has two machine identifiers: each start finds the other system's and is told it is a copy. Taking a new ID on one makes the other a copy in turn. A "this is the same computer" choice that records the identifier without a new ID isn't built.
- A `/etc/machine-id` that systemd fills with a new random identifier at each boot, on a system whose `/etc` is read-only, looks like a different computer at each start.
- A data folder restored onto the computer it came from after its system was reinstalled, or a Mac whose logic board was replaced, is told it is a copy, as a reinstall is.
