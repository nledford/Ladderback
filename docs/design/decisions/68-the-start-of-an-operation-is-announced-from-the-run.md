# Decision 68: The start of an operation is announced from the run

**The run that records an operation announces its start, once, after the write that says it is running; the engine's own start is no news to a page; and a page reads the history again each time its events stream opens** (recorded 2026-11-12, §4.2, §4.4, §9; #305, #308). The daemon turned the engine's `Started` into `operation-started` as the event went by, before the run wrote the operation to the log as running, and the page read the history before it opened its events stream. A page that opened while a run was starting could read the run as queued and hear its start before it listened, or hear it and read a history that still had it queued, and then showed the run as Queued until it ended (#305). The reads a maintenance run makes first (the repository's ID, a forget's listing) published a start under the run's operation before the log held it, one per job of a forget that needs several, and the reads that are no operation (a snapshot list, the groups, a preview) published starts that never ended, which a client counting running operations from the stream would count for ever (#308).

Decided:

1. **The run announces the start** once its write that says the operation is running is done, from the operation as written. A write the log refuses, or leaves unanswered past `SAVE_BOUND`, is given up on and the start is announced anyway, as decision 41 does for the end: the history then shows the operation as queued, and `Finished::recording_errors` holds the write. A run cancelled while that write is out announces nothing.
2. **The start's time is the run's**, its clock when it went running, not the engine's time of reading the index. The event carries it at the run's full precision; the log keeps it to the millisecond, so a history read may show it up to a millisecond earlier.
3. **A maintenance run announces its start once**, as it begins its jobs: its `start` already wrote it running. A forget that runs as several jobs announces one start, as it announces one end.
4. **The engine's start is no news, and a job that is no operation is none at all.** No read that is no operation (identify, list, groups, the previews, a repository test, init, connect) announces a start or an end, and the daemon publishes none of its progress or warnings either (#308), which decision 41 left publishing: the history has no row for it, so a client that counts running operations from the stream would count it for ever, and a run that reads first (a maintenance run's identify and listing) keeps none of what the read said, so a page would show news the history never has. Which jobs are operations is the daemon's engine wrapper's to say, by the job's kind. A first job's start still names the repository the engine says it opened (decision 57).
5. **The page reads the history at once and again once each stream opens**, the first and every reconnect's, so news told before it listened is in what it reads. The first read doesn't wait for the stream, so a slow or refused stream never holds the page on Loading. The read an opening asks for goes through the same pacer as an end's re-read (§4.4): one out at a time and one owed after it, so no run of reconnects piles reads up, and the rounds are paced by the reconnect backoff. Events heard while it is out are applied as they come, and no order takes a row back: a start moves only a queued row, progress and warnings reach only a row that has not ended, and a merge never hands a row back to an older status. A read at the stage the row already has still brings what the page missed: a run still going gains the warnings the store has and the row lacks (mid-run, a before-hook's, which no event tells), and an ended run takes the store's end. A read that moves a row on keeps the warnings the page heard (#328, §4.4).

Why: a client told an operation started, then reading the history, must find it running there; a page that missed the news must find it in the next read.

Rejected: holding the page's first read until the stream opens (one read fewer, but a stream that never opens leaves the page on Loading, and it needs a timeout of its own); holding the stream's events until the read returns (more state for an order the rules above already make harmless); announcing at the engine's start and having the page read the history on every start (the page would still race the write, as decision 41 found for ends).

Not covered:

- A run queued after the page's first read and started before its stream opened is in the history the opening's read finds; one queued and started after that read, by a schedule or another page, comes in with the next end's re-read or reconnect, as before: a start for an operation the page doesn't hold is still ignored.
