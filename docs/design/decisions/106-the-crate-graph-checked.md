# Decision 106: Which workspace crates and foreign models each crate may depend on

**`app` depends on `api` as well as `domain`, as it has since #79, and the dependency rule of §3.2 is a table that `just architecture` checks: every edge between workspace crates, of any kind, must be in it; only the owner of a foreign model (`rustic_core`, `sqlx`, `toml`, `keyring`, `rmcp`, `axum` and the rest) depends on it outside tests; and `domain` holds no `async`** (recorded 2026-11-15, §3.2; decided by the maintainer on #731).

## Why

- **`api` in the core.** The use cases return `UiEvent`, `ErrorCode`, `ErrorDto` and `OperationStep`, which `api` defines for the wire. `api` is a pure, wasm-safe crate of types with no I/O, so it can't bring I/O, a runtime or a foreign model into the core, and the banned-crate check on `app` still holds that. The cost: a change to the wire format reaches the use cases. Moving the types into `app` or `domain` and mapping them at the edge would cost a second copy of each and its mapping, for a crate that has none of what the rings keep out.
- **A rule that had drifted.** §3.2 said `app` depended only on `domain`, `async-trait` and `futures`, and nothing checked it: `just architecture` checked what `domain` and `app` pull in, not which workspace crates any crate depends on. An adapter depending on another, or `sqlx` in an adapter other than `store`, passed CI.
- **Read from `cargo metadata --no-deps`.** It lists every crate's declared dependencies, of every kind and target and optional or not, under their packages' names, with no build and no network, so the check takes seconds. A feature can only turn an optional dependency on, never add one, so the list holds every dependency any feature set can have.
- **Every kind of workspace edge.** Adapters stay apart in their tests too; a dev-dependency may additionally be the crate itself (its tests turning on its own features) or what its row allows in tests alone (`testkit`, and `spawn-gate` for `l10n`).
- **Foreign models outside tests.** A test may use a foreign crate as an oracle (`config-adapter`'s parity test checks the file's keys against `rustic_core`'s structs), and nothing of it ships, so dev-dependencies are exempt, as they are from the banned-crate check. A model counts with its family (`sqlx-core`, `axum-core`, `toml_datetime`), so a crate can't reach it through a part. The check covers direct dependencies only: a third-party crate that re-exports a foreign model's types would reach past it, and a review catches that.
- **Today's graph, not new permission.** The crates outside the rings (`api`, `spawn-gate`, `l10n`, `web`, `testkit`) keep the edges they had when the check was added.
