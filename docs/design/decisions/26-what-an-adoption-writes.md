# Decision 26: What an adoption writes

**A rewrite with the plan's tags, nothing else** (recorded 2026-11-09, §7.3 step 3). The daemon picks the group (an orphaned group by its `(agent, plan)` tags, or the unmanaged group whose `(host, label, paths)` equals the destination plan's host, label and sources — the agent's hostname standing in when the plan names none, and the sources normalized the way rustic records them, through a `NormalizeSources` port because that reads the disk), and hands the worker the exact IDs with `PlanTags`. The worker rewrites each snapshot file with the two `ladderback-*` tags, keeping the user's own tags, saves it (a new ID over the same tree) and removes the original. Saving and removing are two writes, so a worker stopped between them leaves both; a copy is known by its original's tree and time and the plan's tags, a run that finds one keeps it rather than saving another, and the summary counts exactly one copy per original, never a snapshot the plan already held or a backup's that ran meanwhile. More than one plan matching one group is refused (`AdoptionAmbiguous`, HTTP 422, naming them) — which plan history belongs to is the owner's decision; no match is `AdoptionNoMatch` (422); a destination plan that isn't configured for that repository is `PlanUnknown` (404), checked before the repository is listed. A body that names `into` or `from` for another kind is `InvalidBody` (400); an unknown kind stays `MaintenanceKindUnknown` (404). Adoption takes the I7 slot (`OperationKind::Adopt`, migration `0003`), runs through the one maintenance route with `{"kind":"adopt","into":…,"from":…}`, and its summary counts what it created. Why: matching is policy, so it lives in the domain where I6's partition already is; the rewrite is mechanical, so the worker does it; and refusing ambiguity stops one keystroke giving a plan another's whole history.
